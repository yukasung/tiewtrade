# F-02 ชนิดข้อมูลเงินและการคำนวณพื้นฐาน — Requirements

สถานะ: **Proposed** — รอเจ้าของอนุมัติ
วันที่: 2026-09-27
งานใน roadmap: F-02

---

## ทำไมต้องมี

ทุกงานที่เหลือในโปรเจกต์นี้คิดเงิน — margin, PnL, ขนาดไม้, เพดานขาดทุน, ยอดคงเหลือ

ถ้าแต่ละงานคิดเงินด้วยวิธีของตัวเอง ตัวเลขจะไม่ตรงกันระหว่างหน้าจอ ฐานข้อมูล และสิ่งที่
ส่งไป Binance และเราจะไม่รู้ว่าอันไหนถูก

`specs/standards/backend.md` หัวข้อ 1 สั่งไว้แล้วว่า **ตั้งค่าความละเอียดไว้ที่เดียว
ใช้ร่วมกันทั้งระบบ** งานนี้คือการสร้าง "ที่เดียว" นั้น

**คนที่เดือดร้อนถ้าไม่มี** — ผู้ใช้ เพราะยอดเงินที่เห็นจะไม่ตรงกับความจริง
และเจ้าของ เพราะจะหาสาเหตุไม่ได้ว่าตัวเลขเพี้ยนตรงไหน

งานนี้ยังเป็นงานแรกที่ **ด่านความบริสุทธิ์ของ `core` จะได้ทำงานจริง** — F-01 สร้างด่านไว้
แต่ `core` ยังว่าง ยังไม่เคยมีโค้ดให้ตรวจ

## ขอบเขต

### ทำ

- ชนิดข้อมูลสำหรับจำนวนเงินและปริมาณ ที่สร้างแล้วแก้ไม่ได้ และตรวจความถูกต้องตั้งแต่ตอนสร้าง
- กฎความละเอียดและการปัดเศษ ที่ประกาศไว้ที่เดียวและใช้ร่วมกันทั้งระบบ
- การคำนวณพื้นฐาน: บวก ลบ คูณด้วยจำนวน เทียบค่า
- การแปลงเข้าออกเป็นข้อความสำหรับ API — ฐานข้อมูลเก็บเป็น `NUMERIC` เส้นทางภายในไม่ต้องผ่านข้อความ (ดู Q-5)
- เทสต์สองชนิดตาม `specs/standards/testing.md` หัวข้อ 2

### ไม่ทำ

- **ไม่คิด PnL, margin หรือ position** — เป็นงาน F-14
- **ไม่จำลองการจับคู่ออเดอร์** — เป็นงาน F-15
- **ไม่ทำการหาร** (เจ้าของตัดสิน 2026-09-27) กฎเรื่องผลหารไม่ลงตัวใน Q-1.3
  เขียนไว้ล่วงหน้าและ **มีผลเมื่อมีงานที่ต้องหารในภายหลัง** ไม่ต้องเพิ่มฟังก์ชัน
  เพื่อให้ทุกกฎมีผู้ใช้ทันที ส่วนกฎเรื่องค่าเกินช่วงยังมีผลกับ F-02 ตามเดิม
- ไม่แตะข้อจำกัดของเหรียญที่ Binance กำหนด (ขนาดขั้นต่ำ, ทศนิยม, มูลค่าขั้นต่ำ)
  เพราะเป็นของรายตลาด อยู่ในชั้น `venues` (F-33, F-35)
- ไม่คิดค่าธรรมเนียม — ยังไม่มีงานไหนรองรับ และยังไม่มีข้อกำหนด
- ไม่สร้างตารางฐานข้อมูล — เป็นงาน F-03 งานนี้กำหนดแค่ว่าเก็บด้วยความละเอียดเท่าไหร่
- ไม่แปลงสกุลเงิน (เช่น USDT เป็น THB) — ยังไม่มีข้อกำหนดและยังไม่มีงานไหนต้องใช้

### Q-1 ความละเอียด — ✅ ตัดสินครบแล้ว 2026-09-27

| | ค่าที่ตัดสิน |
|---|---|
| ความละเอียดตอนคำนวณ | **80 หลัก** |
| ความละเอียดตอนเก็บ | **`NUMERIC(38,18)`** — หน้าจุด 20 หลังจุด 18 |
| ค่าที่เก็บไม่ได้ | **ปฏิเสธ หรือปัดตามกฎที่อนุญาตอย่างชัดเจนก่อนบันทึก ห้ามให้ฐานข้อมูลปัดเอง** |

**Q-1.1 ความละเอียดตอนคำนวณ = 80 หลัก และต้องบังคับด้วยตัวเอง**

`Decimal` ของ Python ปัดตาม context ของผู้เรียก **โดยไม่ต้องมีใครสั่งปัด**
ทดลองใน venv ของ repo นี้:

| context precision | `12345.67 + 0.01` |
|---|---|
| 6 | **`12345.7`** — หายไปหนึ่งสตางค์ |
| 12 | `12345.68` |
| 28 (ค่าเริ่มต้นของ Python) | `12345.68` |

context เป็นค่ากลางของทั้งโปรแกรม ไลบรารีที่ติดตั้งมาก็เปลี่ยนได้
**การคำนวณของเราจึงต้องบังคับค่าของตัวเองทุกครั้ง และผลต้องไม่เปลี่ยน
ไม่ว่าใครจะตั้ง context ภายนอกไว้เท่าไหร่**

ทำไม 80: ค่าที่เก็บได้ยาวสุด 38 หลัก การคูณสองค่าจึงยาวได้ถึง **76 หลัก**
(บวกลบยาวสุด 39) 80 จึงครอบ **บวก ลบ คูณ ของค่าใด ๆ ที่เก็บได้ โดยไม่ถูกปัดเลย**
ต้นทุนแทบไม่มี เพราะ `Decimal` ใช้หน่วยความจำเท่าที่ตัวเลขจริงต้องการ ไม่ใช่ตามค่า context

**Q-1.2 ความละเอียดตอนเก็บ = `NUMERIC(38,18)`**

ข้อมูลจริงจาก `exchangeInfo` ของ Binance TH ทั้ง 519 คู่ (ตรวจ 2026-09-27):

| | ละเอียดสุดที่พบ |
|---|---|
| ขั้นราคา `tickSize` | 8 ตำแหน่ง (`1000SATSUSDT` = `0.00000001`) |
| ขั้นปริมาณ `stepSize` | 5 ตำแหน่ง (`BTCFDUSD`) |
| `quoteAssetPrecision` | **8 ทุกคู่ ครบ 519** |
| `baseAssetPrecision` | 8 ใน 499 คู่ ที่เหลือน้อยกว่า |

8 เป็นเพดานของวันนี้ แต่เปลี่ยนได้ถ้า Binance เพิ่มเหรียญใหม่
**เลือก 18 เพื่อไม่ต้องกลับมาแก้ migration ตอนนั้น** และการประกาศ scale สูง
ไม่ได้ทำให้เปลืองพื้นที่ เพราะ PostgreSQL `NUMERIC` เก็บตามค่าจริง ไม่ได้จองตามที่ประกาศ

**ที่คำนวณกว้างกว่าที่เก็บโดยตั้งใจ** ถ้าให้เท่ากันพอดี การคูณสองค่าที่ยาวเต็มช่วง
จะเกินทันที ความเท่ากันเป๊ะจึงไม่ได้แก้ปัญหาจริง

### Q-1.3 ผลลัพธ์ที่ไม่ลงตัว หรือเกินขอบเขต — ✅ ตัดสินแล้ว 2026-09-27

**สองสถานการณ์นี้มีธรรมชาติต่างกัน จึงใช้กฎต่างกัน**

| สถานการณ์ | ทำอย่างไร | เพราะ |
|---|---|---|
| **หารไม่ลงตัว** เช่น 1 ÷ 3 | **ปัดตามกฎใน Q-2** | เป็นธรรมชาติของเลข ไม่ใช่ความผิดปกติ ถ้าพังทุกครั้งระบบใช้งานไม่ได้ |
| **ผลลัพธ์เกินช่วงที่เก็บได้** | **ผิดพลาดชัดเจน หยุดทันที** | แทบทุกครั้งแปลว่ามีบั๊ก ควรดังให้เร็วที่สุด |

ถ้าปัดกรณีที่สองด้วย ตัวเลขที่ล้นขอบเขตจะกลายเป็นตัวเลขที่ดูปกติทั้งที่ผิด
**บั๊กจะถูกกลบ** ตรงกับกฎใน `standards/trading-safety.md` หัวข้อ 10
ว่าเมื่อไม่แน่ใจให้หยุด ไม่ใช่เดาแล้วทำต่อ

80 หลักครอบบวก ลบ คูณ ของค่าที่เก็บได้ทั้งหมด **การหารเป็นการคำนวณเดียว
ที่ยังให้ผลไม่ลงตัวได้เสมอ** ไม่ว่าตั้งกี่หลัก

**ขอบเขตการใช้กฎ** F-02 ไม่มีการหาร (ดูหัวข้อขอบเขต) กฎแถวแรกจึง
**มีผลเมื่อมีงานที่ต้องหารในภายหลัง** ส่วนกฎแถวที่สองเรื่องค่าเกินช่วง
มีผลกับ F-02 ทันที เพราะบวก ลบ คูณ ก็ทำให้เกินช่วงได้

### Q-2 ทิศทางการปัดเศษ — ✅ ตัดสินแล้ว 2026-09-27

**แต่ละการคำนวณต้องระบุทิศทางการปัดเอง ไม่มีค่าเริ่มต้น**

เรียกฟังก์ชันปัดโดยไม่บอกทิศทาง ต้องเป็นข้อผิดพลาด ไม่ใช่ใช้ค่าปริยาย

**เหตุผล: "ไม่เข้าข้างผู้ใช้" กลับด้านตามสิ่งที่กำลังคิด**

| กำลังคิดอะไร | ไม่เข้าข้างผู้ใช้คือ |
|---|---|
| ยอดเงินคงเหลือ | ปัดให้น้อยลง |
| ค่าธรรมเนียมที่ต้องจ่าย | ปัดให้มากขึ้น |
| กำไร | ปัดให้น้อยลง |
| ขาดทุน | ปัดให้มากขึ้น |

กฎเดียวทั้งระบบจะผิดครึ่งหนึ่งเสมอ และความผิดจะเงียบ — ตัวเลขดูปกติ ไม่มีอะไรพัง
แค่เข้าข้างผู้ใช้ทีละนิดสะสมไปเรื่อย ๆ จนยอดไม่ตรง

**ค่าลบต้องระวังเป็นพิเศษ** คำว่า "ขึ้น" กับ "ลง" ใช้กับค่าลบไม่ได้ตรง ๆ
ขาดทุน `-10.555` ปัดที่ทศนิยมสองตำแหน่ง:

| วิธี | ผล | ความหมาย |
|---|---|---|
| ขึ้นตามเส้นจำนวน | `-10.55` | ขาดทุนน้อยลง — **เข้าข้างผู้ใช้** |
| ออกห่างจากศูนย์ | `-10.56` | ขาดทุนมากขึ้น — ไม่เข้าข้าง |

**ทิศทางจึงต้องระบุด้วยคำที่ไม่กำกวมกับค่าลบ** ไม่ใช่คำว่าขึ้นหรือลง
และต้องมีเทสต์ด้วยตัวเลขจริงทั้งค่าบวกและค่าลบทุกทิศทาง

**แยกทิศทางการปัด ออกจากจังหวะที่อนุญาตให้ปัด** — จังหวะที่ปัดคือ
ตอนจะเก็บลงฐานข้อมูลและตอนหารไม่ลงตัว (Q-1.3) ระหว่างคำนวณห้ามปัด
เพราะความละเอียด 80 หลักครอบบวกลบคูณได้อยู่แล้ว

### Q-3 หน่วย — ✅ ตัดสินแล้ว 2026-09-27

**ผูกหน่วยทั้งเงินและปริมาณ** F-02 ส่งมอบสองชนิด

| ชนิด | คืออะไร | ตัวอย่าง |
|---|---|---|
| **เงิน** | จำนวน + สกุลเงิน | `100.00 USDT`, `3500.00 THB` |
| **ปริมาณ** | จำนวน + เหรียญ | `0.5 BTC`, `3 ETH` |

**ตารางว่าอะไรคำนวณกับอะไรได้**

| การคำนวณ | ผลลัพธ์ | หมายเหตุ |
|---|---|---|
| เงิน + เงิน สกุลเดียวกัน | เงิน สกุลเดิม | |
| เงิน − เงิน สกุลเดียวกัน | เงิน สกุลเดิม | ผลลบได้ ดู Q-4 |
| **เงิน ± เงิน คนละสกุล** | **ไม่อนุญาต** | ต้องผิดตั้งแต่ตอนเขียนโค้ด |
| ปริมาณ ± ปริมาณ เหรียญเดียวกัน | ปริมาณ เหรียญเดิม | |
| **ปริมาณ ± ปริมาณ คนละเหรียญ** | **ไม่อนุญาต** | |
| **เงิน ± ปริมาณ** | **ไม่อนุญาต** | คนละชนิดกัน |
| เงิน × ตัวเลขเปล่า | เงิน สกุลเดิม | |
| ปริมาณ × ตัวเลขเปล่า | ปริมาณ เหรียญเดิม | |
| เทียบค่า หน่วยเดียวกัน | จริง/เท็จ | |
| **เทียบค่า คนละหน่วย** | **ไม่อนุญาต** | |

**ราคา ปริมาณ × ราคา → มูลค่า ยังไม่อยู่ในขอบเขต F-02** เพราะราคาเป็นอัตราส่วน
ระหว่างสองหน่วย (เช่น USDT ต่อ BTC) ซึ่งต้องออกแบบเพิ่ม และ F-14 เป็นงานที่ต้องใช้จริง
ถ้าเพิ่มใน F-02 จะกลายเป็นการออกแบบล่วงหน้าโดยไม่มีคนใช้

**เหตุผลที่ผูกหน่วย** ความผิดพลาดเรื่องหน่วยเป็นแบบที่**ไม่มีอะไรพัง** —
ตัวเลขออกมาดูปกติ แต่ความหมายผิด เช่นบวกยอด USDT กับ THB เข้าด้วยกัน
เป็นความผิดพลาดที่หายากที่สุด เพราะไม่มีสัญญาณอะไรเลย

ต้นทุนของการผูกหน่วยจ่ายครั้งเดียวตอนนี้ ส่วนต้นทุนของการไม่ผูก
จ่ายทุกครั้งที่มีคนเขียนโค้ดใหม่ ตลอดอายุโปรเจกต์

**ต้องบังคับตั้งแต่ตอนตรวจชนิดข้อมูล ไม่ใช่แค่ตอนรัน** เท่าที่ทำได้

### Q-4 ค่าที่ถือว่าถูกต้อง — ✅ ตัดสินแล้ว 2026-09-27

**4.1 รับค่าลบทั้งเงินและปริมาณ**

ชนิดพื้นฐานแทน **ยอดที่เปลี่ยนแปลงได้** จึงติดลบได้

ข้อจำกัดอย่าง "ยอดถือครอง Spot ห้ามติดลบ" หรือ "ปริมาณออเดอร์ต้องเป็นบวก"
**ให้ตรวจในโดเมนที่ใช้ ไม่ใช่ในชนิดพื้นฐาน**

**การขายไม่ได้หมายถึงส่ง quantity ติดลบ** ต้องแยกออกจากรายการที่ลดสินทรัพย์
(แก้ความเข้าใจผิดในการเสนอครั้งแรก)

**4.2 ปฏิเสธค่าที่ไม่ finite ตั้งแต่ตอนสร้าง**

ครอบ `NaN`, `sNaN` และ `±Infinity` ทั้งหมด

| ทดลองใน venv ของ repo | ผล |
|---|---|
| `Decimal("NaN")`, `Decimal("Infinity")` | สร้างได้ตามปกติ |
| `NaN == NaN` | `False` |
| `NaN < 1` | **โปรแกรมพังทันที** (`InvalidOperation`) |

**4.3 ปฏิเสธเมื่อ *ค่าจริง* มีทศนิยมเกิน 18 ตำแหน่ง**

ตัดสินจากค่าจริงหลังตัดศูนย์ท้าย ไม่ใช่จากรูปแบบที่เขียนมา

| ค่าที่รับเข้ามา | เขียนมากี่ตำแหน่ง | ค่าจริง | ผล |
|---|---|---|---|
| `1.0000000000000000000` | 19 | 0 | **รับได้** — ศูนย์ท้ายไม่ได้เปลี่ยนค่า |
| `1.5` | 1 | 1 | รับได้ |
| `1.2345678901234567890123` | 22 | 22 | **ปฏิเสธ** |

ปฏิเสธแทนการปัดให้เอง เพราะ Q-2 ตัดสินว่าการปัดต้องระบุทิศทางทุกครั้ง
ถ้าปัดให้เองตรงนี้จะขัดกันเอง คนเรียกต้องปัดมาเองด้วยทิศทางที่ตั้งใจ

**4.4 รับ `str`, `int`, `Decimal` — ปฏิเสธ `float` และ `bool` ที่ runtime**

- รับ `Decimal` ด้วย เพื่อให้ใช้ผลคำนวณภายในได้โดยไม่ต้องแปลงผ่านข้อความ
- ทุกชนิดที่รับต้องผ่านกฎเดียวกันทั้งหมด
- **ต้องปฏิเสธ `bool` แยกต่างหาก** เพราะ `bool` เป็น subclass ของ `int`
  ทดลองแล้ว `Decimal(True)` ได้ `1` — `True` จะกลายเป็นเงินหนึ่งหน่วยเงียบ ๆ
- `float("0.1")` ไม่ใช่ 0.1 แต่เป็น 0.1000000000000000055511151231257827
  รับเข้ามาเมื่อไหร่ก็พาความคลาดเคลื่อนเข้ามาด้วย
- **ปฏิเสธที่ runtime ไม่ใช่พึ่ง type hint** เพราะ Python ไม่บังคับ type hint ตอนรัน
  และต้องมีเทสต์พิสูจน์

**4.5 ลบศูนย์ต้องกลายเป็นศูนย์รูปแบบเดียว**

`Decimal("-0")` เท่ากับ `0` แต่แสดงผลเป็น `'-0'` ถ้าไม่จัดการ
**ผู้ใช้จะเห็นยอดศูนย์ติดลบบนหน้าจอ**

### Q-5 การแปลงเป็นข้อความและกลับ — ✅ ตัดสินแล้ว 2026-09-27

**ขอบเขตของข้อนี้:** API ส่งตัวเลขเป็นข้อความ (RQ-5) ส่วนฐานข้อมูลเก็บเป็น `NUMERIC`
**เส้นทางภายในระหว่าง `core` กับ database adapter ไม่จำเป็นต้องผ่านข้อความ**

**5.1 แปลงออกแล้วกลับ ต้องได้ค่าเดิมโดยไม่สูญเสียความแม่นยำ**

ต้องได้ **ค่าตัวเลข ชนิด และหน่วยเดิม** — **ไม่จำเป็นต้องได้ข้อความเดิม**
เช่น `"1.2300"` แปลงกลับออกมาเป็น `"1.23"` ได้ ถือว่าถูกต้อง

สำคัญเพราะยอดคงเหลือคือผลรวมของรายการ (`standards/database.md` หัวข้อ 4)
ถ้าค่าเปลี่ยนทีละนิดทุกครั้งที่เข้าออก ผลรวมของรายการยาว ๆ จะเพี้ยน

**5.2 `1.2300` เท่ากับ `1.23` และใช้ข้อความมาตรฐานเดียว**

- ตัดศูนย์ท้าย **เฉพาะส่วนทศนิยม**
- ศูนย์แสดงเป็น `"0"`
- **จำนวนตำแหน่งที่แสดงบนหน้าจอเป็นคนละเรื่อง** จัดรูปแบบแยกที่ชั้นแสดงผล

**5.3 รับรูปแบบวิทยาศาสตร์ ขาออกเป็นเลขธรรมดาเสมอ**

รับ `1e-8` ได้ แล้วตรวจช่วงค่าและความละเอียดตามกฎใน Q-4 เหมือนรูปแบบอื่นทุกประการ

ขาออกเขียนเป็นเลขธรรมดา เช่น `0.00000001` ไม่ใช่ `1E-8`

เหตุผลคือรองรับรูปแบบตัวเลขที่พบได้ทั่วไป **ไม่ได้อ้างว่า Binance ส่งรูปแบบนี้มา**
เพราะยังไม่มีหลักฐาน

**5.4 แยกค่ากับหน่วยออกจากกัน**

```json
{"amount": "100", "currency": "USDT"}
{"quantity": "0.5", "asset": "BTC"}
```

**ตอนอ่านกลับต้องตรวจหน่วยด้วย** ไม่ใช่รับแต่ตัวเลข

หน้าบ้านจึงจัดรูปแบบตามภาษาได้ โดยไม่ต้องแยกข้อความเอง ซึ่งเป็นจุดที่พลาดได้
