## แนวทาง

ทำ 5 ชั้น แต่ละชั้นมีเทสต์ของตัวเองก่อนขึ้นชั้นถัดไป

| ลำดับ | ทำอะไร | ปิดข้อกำหนด |
|---|---|---|
| 1 | บังคับ context การคำนวณ 80 หลัก | RQ-2, RQ-7 |
| 2 | กฎตรวจค่าที่ใช้ร่วมกันทุกชนิด | RQ-8, RQ-16, RQ-22, RQ-24 |
| 3 | ทิศทางและกลไกการปัด | RQ-3, RQ-4, RQ-21 |
| 4 | ชนิดข้อมูลที่ผูกหน่วย และการคำนวณ | RQ-1, RQ-5, RQ-9, RQ-13, RQ-15, RQ-17, RQ-23 |
| 5 | การแปลงเป็นข้อความ | RQ-18, RQ-19, RQ-20 |

**เหตุผลที่เริ่มจาก context** เพราะทุกชั้นหลังจากนี้คำนวณภายใต้มัน
ถ้าทำทีหลังจะต้องกลับไปแก้ทุกจุดที่เขียนไปแล้ว

**เหตุผลที่การปัดมาก่อนชนิดข้อมูล** เพราะการคูณ (RQ-23) ต้องปัดผลเมื่อผู้เรียกระบุทิศทาง
ถ้าทำชนิดข้อมูลก่อน ชั้นนั้นจะเทสต์ให้เขียวไม่ได้เพราะยังไม่มีกลไกปัด
(แก้ตามรีวิว 2026-09-27 ข้อ 2)

## จุดตัดสินทางเทคนิค

| # | เลือก | เหตุผล |
|---|---|---|
| P-1 | ทุกการคำนวณห่อด้วย context ของเราเอง ไม่ใช่ตั้งค่า global ตอนโปรแกรมเริ่ม | context แยกตาม thread และ coroutine (ยืนยันแล้วใน requirements) ตั้ง global จึงไม่ครอบ `engine` กับ `api` ที่เป็นคนละโปรเซส และไม่ครอบ thread ที่เกิดใหม่ |
| P-2 | context ที่บังคับต้องครอบ **precision, rounding, traps และ exponent limit** ไม่ใช่แค่ precision | ค่าที่เหลือก็เปลี่ยนผลได้ เช่น traps ทำให้บางการคำนวณโยนข้อผิดพลาดแทนคืนค่า |
| P-3 | คืน context เดิมของผู้เรียกเสมอ **รวมตอนเกิดข้อผิดพลาด** และคืนทั้งค่าตั้งและ flags | ถ้าไม่คืน โค้ดของผู้เรียกจะคำนวณผิดหลังเรียกเรา ซึ่งหายากมาก |
| P-3.1 | **สร้าง context ใหม่จากศูนย์ ไม่คัดลอกของผู้เรียกแล้วแก้เฉพาะ precision** | ถ้าคัดลอก ค่าที่ไม่ได้แก้ เช่น rounding, traps, Emin/Emax จะติดมาจากภายนอกและเปลี่ยนผลหรือชนิดข้อผิดพลาด |
| P-3.2 | **แปลงข้อผิดพลาดของ `Decimal` เป็นชนิดข้อผิดพลาดของโมดูลนี้** ไม่ปล่อยให้รั่วออกไป และอนุญาต `Inexact` เฉพาะจุดที่ข้อกำหนดให้ปัดได้ | ผู้เรียกดักด้วยชนิดของเราได้ และการปัดที่ไม่ได้รับอนุญาตจะดังทันที |
| P-4 | ตรวจค่าด้วยฟังก์ชันเดียวที่ทุกชนิดเรียกใช้ ไม่ก๊อปกฎไปไว้แต่ละชนิด | RQ-24 บอกว่าตัวเลขเปล่าใช้กฎชุดเดียวกัน ถ้าแยกจะหลุดกันภายหลัง |
| P-5 | นับทศนิยมจริงจาก **coefficient และ exponent ตรง ๆ ตัดศูนย์ท้ายแบบ exact** ห้ามใช้ `normalize()` หรือ `quantize()` ในขั้นตรวจ input | RQ-16 นับจากค่าจริง แต่ `normalize()` **ปัดตาม context ก่อนตัดศูนย์** ทดลองแล้วทั้ง `1.` + ศูนย์ 80 ตัว + `1` (ทศนิยมจริง 81 ตำแหน่ง ต้องปฏิเสธ) และ `1.` + ศูนย์ 80 ตัว (ค่าจริง 1 ต้องรับได้) ให้ผล `1` เหมือนกันที่ precision 80 — ตรวจหลังขั้นนี้จะรับค่าที่ควรปฏิเสธ |
| P-6 | เทียบช่วงค่าโดย **ไม่ใช้ `abs()`** | `abs()` ปัดตาม context (หลักฐานใน requirements Q-1.1) ใช้เทียบสองด้านแทน |
| P-7 | ปฏิเสธ `bool` ก่อนตรวจ `int` | `bool` เป็น subclass ของ `int` ถ้าตรวจตามลำดับปกติจะหลุด |
| P-8 | ข้อผิดพลาดทุกชนิดสืบทอดจากฐานเดียวของโมดูลนี้ | RQ-14 ต้องระบุชนิดได้ และผู้เรียกดักรวมได้ด้วยชนิดฐาน |
| P-9 | หน่วยเก็บเป็นค่าที่เทียบเท่ากันได้ ไม่ใช่ข้อความอิสระ | RQ-15 ต้องปฏิเสธหน่วยผิดที่ runtime การเทียบข้อความเสี่ยงพลาดเรื่องตัวพิมพ์ |
| P-10 | ทิศทางการปัดเป็นค่าที่ระบุชื่อได้ **ไม่ใช้คำว่าขึ้นหรือลง** | Q-2 ระบุว่าคำเหล่านั้นกำกวมกับค่าลบ ใช้คำที่อิงศูนย์หรืออิงความหมายแทน |
| P-11 | **ตัวเลขเปล่าเป็น input ที่ผ่านการตรวจ ไม่ใช่ชนิดสาธารณะตัวที่สาม** | requirements ส่งมอบสองชนิดที่ผูกหน่วย การเพิ่มชนิดสาธารณะตัวที่สามคือการขยายขอบเขตโดยไม่มีคนใช้ |
| P-12 | **ห้ามลดความเข้มของด่านความบริสุทธิ์เพื่อให้โค้ดผ่าน** การปฏิเสธ `float` ที่ runtime ต้องเขียนโดยไม่อ้างชื่อ `float` ในโค้ด `core` | ด่านใน F-01 ปฏิเสธการอ้าง `float` แบบ AST ถ้าแก้ด่านเพื่อให้โค้ดผ่าน เท่ากับทิ้งสิ่งที่ F-01 สร้างไว้ |

## สัญญาของโมดูล

รายละเอียดเหล่านี้เป็นการออกแบบทางเทคนิคภายใต้ requirements ที่อนุมัติแล้ว
กำหนดไว้ที่นี่เพื่อให้ validation ตรวจได้จริง และให้คนเขียนโค้ดกับคนเขียนเทสต์
อ้างถึงสิ่งเดียวกัน

### ทิศทางการปัดที่รองรับ — มี 4 ทิศทาง

ไม่ใช้คำว่าขึ้นหรือลง เพราะกำกวมกับค่าลบ (Q-2)

| ทิศทาง | ความหมาย | `2.5` → | `-2.5` → |
|---|---|---|---|
| `TOWARD_ZERO` | เข้าหาศูนย์ | `2` | `-2` |
| `AWAY_FROM_ZERO` | ออกห่างจากศูนย์ | `3` | `-3` |
| `TOWARD_POSITIVE` | ไปทางค่าบวก | `3` | `-2` |
| `TOWARD_NEGATIVE` | ไปทางค่าลบ | `2` | `-3` |

**ไม่มีทิศทางแบบ half-even หรือ half-up** เพราะ RQ-4 ต้องการทิศทางที่ผู้เรียก
ตั้งใจเลือกตามความหมายของตัวเลข ไม่ใช่กฎที่ตัดสินจากตัวเลขเอง

ตัวอย่างการใช้ตามเจตนาของ RQ-4: ยอดคงเหลือใช้ `TOWARD_NEGATIVE`
ส่วนหนี้หรือค่าธรรมเนียมใช้ `TOWARD_POSITIVE`

### หน่วย

| | ตัดสิน |
|---|---|
| เก็บเป็นอะไร | ข้อความสั้น ปรับเป็นตัวพิมพ์ใหญ่ตอนสร้าง เช่น `"usdt"` → `USDT` |
| เทียบเท่ากันเมื่อไหร่ | หลังปรับตัวพิมพ์แล้วตรงกันทุกตัวอักษร |
| ค่าที่ปฏิเสธ | ข้อความว่าง, มีช่องว่าง, ไม่ใช่ตัวอักษรหรือตัวเลข |
| **ไม่จำกัดรายชื่อ** | โมดูลนี้ไม่รู้จักรายการเหรียญที่ระบบรองรับ การจำกัดรายชื่อเป็นงานของ F-37 ถ้าเอามาไว้ที่นี่จะกลายเป็นกฎธุรกิจใน `core` |

### ชนิดข้อผิดพลาด

ทุกชนิดสืบทอดจากฐานเดียวของโมดูล (P-8)

| ชนิด | เกิดเมื่อ | เกณฑ์ที่ตรวจ |
|---|---|---|
| ค่าไม่ finite | `NaN`, `sNaN`, `±Infinity` | V-3 |
| ชนิด input ไม่รองรับ | `float`, `bool`, ชนิดอื่น | V-4 |
| ทศนิยมเกินที่รับได้ | ทศนิยมจริงเกิน 18 ตำแหน่ง | V-5, V-5.1 |
| ค่านอกช่วง | `\|x\| ≥ 10^20` ทั้งตอนสร้าง ตอนคำนวณ และ **หลังปัด** | V-6, V-13, V-13.1, V-13.2 |
| หน่วยไม่ตรงกัน | คำนวณหรือเทียบข้ามหน่วย | V-9 |
| หน่วยไม่ถูกต้อง | รูปแบบหน่วยผิดหรือหายไปตอนอ่านกลับ | V-20 |
| ต้องปัดแต่ไม่ได้ระบุทิศทาง | ผลคูณเกิน 18 ตำแหน่งโดยไม่ส่งทิศทางมา | V-12, V-15 |

### Public interface

| กลุ่ม | มีอะไร |
|---|---|
| ชนิดข้อมูล | เงิน (จำนวน + สกุล), ปริมาณ (จำนวน + เหรียญ) — **สองชนิดเท่านั้น** |
| สร้าง | จาก `str`, `int`, `Decimal` พร้อมหน่วย |
| คำนวณ | บวก, ลบ, คูณด้วยตัวเลขเปล่า, เทียบค่า — ตามตารางใน requirements Q-3 |
| ปัด | **เรียกผ่านการคูณเท่านั้นใน F-02** โดยส่งทิศทางเป็นพารามิเตอร์ ไม่มีฟังก์ชันปัดสาธารณะแยก เพราะยังไม่มีจุดอื่นที่อนุญาตให้ปัด |
| แปลงเป็นข้อความ | คืนค่ากับหน่วยแยกกัน (RQ-20) |
| อ่านกลับ | รับค่ากับหน่วยแยกกัน และ**ตรวจหน่วยด้วย** |

ตัวอย่างพฤติกรรมที่ validation อ้างถึง

| เรียก | ได้ |
|---|---|
| สร้างเงินจาก `"100"` กับ `"usdt"` | เงิน `100 USDT` |
| `100 USDT + 50 USDT` | `150 USDT` |
| `100 USDT + 50 THB` | ข้อผิดพลาดหน่วยไม่ตรงกัน |
| `1E-18 USDT × 0.1` ไม่ส่งทิศทาง | ข้อผิดพลาดต้องปัดแต่ไม่ได้ระบุทิศทาง |
| `1E-18 USDT × 0.1` ส่ง `TOWARD_ZERO` | `0 USDT` |
| `1E-18 USDT × 0.1` ส่ง `AWAY_FROM_ZERO` | `1E-18 USDT` |
| แปลง `100 USDT` เป็นข้อความ | `{"amount": "100", "currency": "USDT"}` |

**ถ้าระหว่างลงมือพบว่าสัญญานี้ทำให้ต้องจำกัดรายชื่อหน่วยที่ธุรกิจยอมรับ
ให้หยุดถามเจ้าของ** ไม่ใช่ตั้งรายชื่อเอง

## ความเสี่ยง

| ความเสี่ยง | จะรู้ได้อย่างไร | ถ้าเกิดแล้วทำอะไร |
|---|---|---|
| **มีเส้นทางที่หลุดจาก context ของเรา** — ความเสี่ยงหลักของงานนี้ | เทสต์ที่ตั้ง context ภายนอกไว้ต่ำแล้วเรียกทุกฟังก์ชันสาธารณะ ต้องได้ผลเดิม | แก้ให้ครอบ ไม่ใช่ลดความคาดหวังของเทสต์ |
| ลืมปฏิเสธ `bool` ในบางเส้นทาง | เทสต์ที่ส่ง `True` เข้าทุกทางเข้า | เพิ่มการตรวจที่ฟังก์ชันกลาง ไม่ใช่แก้ทีละที่ |
| นับทศนิยมจากรูปแบบแทนค่าจริง | เทสต์ `1.0000000000000000000` ต้องรับได้ | ใช้ค่าหลังตัดศูนย์ท้าย |
| เทียบช่วงค่าแล้วโดน `abs()` ปัด | เทสต์ค่าขอบ `99999999999999999999.999999999999999999` ต้องรับได้ | เลี่ยง `abs()` ตาม P-6 |
| การปัดเผลอเกิดในจุดที่ไม่อนุญาต | เทสต์ที่พิสูจน์ว่าการคูณซึ่งผลพอดี ไม่มีการปัดเกิดขึ้น | ตรวจว่าจุดที่ปัดมีเท่าที่ระบุไว้ท้าย Q-2 |
| **ตรวจ input หลังผ่านการปัด** ทำให้ค่าที่ควรปฏิเสธผ่านได้ | เทสต์คู่ input ยาวเกิน 80 หลัก ทั้งศูนย์ท้ายล้วนและ nonzero ที่ตำแหน่ง 81 | ตรวจ coefficient/exponent ตรง ๆ ตาม P-5 |
| ชนิดข้อมูลกลายเป็นที่รวมกฎธุรกิจ | รีวิวตอนจบงาน — ถ้าเริ่มมีคำว่า order, position, fee ในโมดูลนี้ แปลว่าหลุดขอบเขต | ย้ายออกไปงานที่เป็นเจ้าของกฎนั้น |

### ความเสี่ยงที่อยากให้เจ้าของรู้ก่อนอนุมัติ

**งานนี้ไม่มีอะไรให้ดูบนหน้าจอเลย และไม่มี endpoint ใหม่**

สิ่งที่ได้คือชนิดข้อมูลที่โค้ดอื่นเรียกใช้ ซึ่งมองจากข้างนอกเหมือนไม่มีอะไรเกิดขึ้น
เหมือน F-01 แต่รอบนี้ไม่มีแม้แต่หน้าเปล่าให้เปิดดู

สิ่งที่วัดความคืบหน้าได้คือจำนวนเทสต์ที่ผ่าน และการที่ `core` มีโค้ดจริง
ให้ด่านความบริสุทธิ์ตรวจเป็นครั้งแรก
