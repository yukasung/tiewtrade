### คุณสมบัติด้วย hypothesis (RQ-11)

กฎที่ต้องจริงเสมอ ไม่ว่าใส่ค่าอะไร

**เงื่อนไขนี้ใช้กับกฎที่บวกหรือลบค่าหลายตัว** — operand ต้องชนิดและหน่วยตรงกัน และ
**ผลระหว่างทางของเส้นทางนั้นต้องอยู่ในช่วงที่เก็บได้**

กฎที่คูณด้วยตัวเลขเปล่า และกฎที่ตั้งใจพิสูจน์การล้นช่วง ใช้เงื่อนไขของตัวเอง
ไม่ใช่เงื่อนไขนี้

ถ้าไม่ระบุ กฎจะไม่จริง ตัวอย่าง: `M = 99999999999999999999.999999999999999999`
และ `u = 1E-18` รับได้ทั้งคู่ แต่ `M + u` เท่ากับ `10^20` พอดี ซึ่งต้องเป็นข้อผิดพลาด
`(M+u)−u` จึงไม่มีผลลัพธ์ให้เทียบ และการรวม `[M, u, −u]` ล้น ขณะที่ `[u, −u, M]` ไม่ล้น

**ห้ามแก้โค้ดให้ยอมรับค่าระหว่างทางที่เกินช่วง เพื่อให้เทสต์คุณสมบัติผ่าน**
ถ้าเทสต์แดงเพราะเรื่องนี้ ให้แก้เงื่อนไขของเทสต์ ไม่ใช่แก้ข้อกำหนด

| กฎ | ทำไมสำคัญ |
|---|---|
| บวกแล้วลบค่าเดิมกลับ ต้องได้ค่าตั้งต้น **เมื่อผลระหว่างทางอยู่ในช่วง** | รากฐานของรายการเดินบัญชี |
| ลำดับการบวกไม่เปลี่ยนผลรวม **เมื่อทุกลำดับมีผลระหว่างทางอยู่ในช่วง** | ยอดคงเหลือคือผลรวมของรายการ ลำดับต้องไม่สำคัญ |
| **เส้นทางที่ผลระหว่างทางเกินช่วง ต้องได้ข้อผิดพลาดที่ระบุชนิดได้เสมอ** | แยกออกมาเป็นกฎของตัวเอง ไม่ใช่ข้อยกเว้นที่ซ่อนอยู่ |
| แปลงเป็นข้อความแล้วอ่านกลับ ได้ค่าเดิมเสมอ | RQ-18 ต้องจริงกับทุกค่า ไม่ใช่แค่ตัวอย่างที่เลือกมา |
| คูณด้วย 1 ได้ค่าเดิม คูณด้วย 0 ได้ศูนย์ | จับการปัดที่เผลอเกิด |
| ค่าที่สร้างได้ต้องอยู่ในช่วงที่เก็บได้เสมอ | RQ-22 ต้องไม่มีทางสร้างค่าที่เก็บไม่ได้ |
| **ผลการคำนวณไม่ขึ้นกับ context ภายนอก** | รันคุณสมบัติข้างบนซ้ำภายใต้ context หลายแบบ |

## ตรวจด้วยมือ

1. รันด่านทั้งห้าของ backend ต้องเขียวทั้งหมด
2. **ตั้ง context ภายนอกเป็น precision 6 แล้วรันชุดเทสต์ทั้งหมดอีกครั้ง** ต้องเขียวเหมือนเดิม
   — ถ้าแดง แปลว่ามีเส้นทางที่หลุดจาก context ของเรา
3. **แก้โค้ดใน `core` ให้ใช้ `float` หนึ่งจุด** แล้วรันเทสต์ ต้องแดงที่ด่านความบริสุทธิ์
   แล้วย้อนคืน — พิสูจน์ว่าด่านที่สร้างไว้ใน F-01 ทำงานกับโค้ดจริง
4. อ่าน public interface ทั้งหมด แล้วตอบให้ได้ว่า**แต่ละอย่างมีข้อกำหนดข้อไหนรองรับ**
   ถ้ามีอะไรที่ตอบไม่ได้ แปลว่าทำเกินขอบเขต

ข้อ 2 กับ 3 สำคัญที่สุด — ข้อ 2 พิสูจน์ข้อกำหนดที่ยากที่สุดของงานนี้
ข้อ 3 พิสูจน์ว่าการลงทุนใน F-01 ได้ผลจริง

## สิ่งที่ validation นี้ **ไม่** ครอบ

- ไม่พิสูจน์ว่า PnL, margin หรือ position ถูก — ยังไม่มี (F-14)
- ไม่พิสูจน์ว่าเก็บลงฐานข้อมูลได้จริง — ยังไม่มีตาราง (F-03)
  งานนี้พิสูจน์แค่ว่าค่าที่สร้างได้อยู่ในช่วงที่ `NUMERIC(38,18)` รับได้
- ไม่พิสูจน์เรื่องการหาร — อยู่นอกขอบเขต
- ไม่พิสูจน์ว่าข้อจำกัดของเหรียญที่ตลาดกำหนดถูกนำมาใช้ — เป็นงาน `venues` (F-33, F-35)
- ไม่พิสูจน์ว่าตัวเลขที่ผู้ใช้เห็นบนหน้าจอถูกจัดรูปแบบถูก — ยังไม่มีหน้าจอ
