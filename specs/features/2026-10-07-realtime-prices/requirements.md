สถานะ: **Approved** — เจ้าของอนุมัติขอบเขต A/NC-25, snapshot semantics NC-26 และ alert semantics NC-27 วันที่ 2026-10-07
วันที่: 2026-10-07
Branch: feature/f-10-realtime-prices

## ทำไมต้องมี

F-09 เก็บประวัติแท่งเทียนแล้ว แต่ยังไม่มีทางรับราคาต่อเนื่องและเผยแพร่
ความพร้อมของราคาให้ผู้ใช้หรือผู้ใช้ข้อมูลใน backend ทราบ
การต่อสำเร็จไม่ได้แปลว่าราคาปัจจุบันเชื่อถือได้ และราคาที่ค้างอยู่หลังหลุด
ต้องไม่ถูกแสดงหรือส่งต่อเหมือนเป็นราคาใหม่

## ขอบเขต

เจ้าของเลือก A วันที่ 2026-10-07: ราคาซื้อขายล่าสุด ส่งถึงเว็บพร้อมสถานะขั้นต่ำ
และการต่อกลับ ไม่รวม bid/ask หรือแท่งเทียนสด

รับราคาซื้อขายล่าสุดของ Spot ผ่าน venue สาธารณะของ Binance TH สำหรับรายการตั้งต้น
BTCUSDT, ETHUSDT, SOLUSDT, XRPUSDT, DOGEUSDT; รวมข้อมูลร่วมกันใน
market-data process และส่งต่อผ่าน API ให้หน้าบ้าน พร้อมสถานะและการต่อกลับ
ทั้งทางตลาดและทางเบราว์เซอร์ มีการแสดงราคา/สถานะแบบขั้นต่ำเพื่อทดสอบครบทาง
โดยยังไม่สร้างกราฟ F-12

ไม่รับข้อมูลบัญชี ยอดเงิน ออเดอร์หรือ position; ไม่ใช้ API key ผู้ใช้
ไม่ส่งออเดอร์ ไม่คำนวณ PnL/indicator ไม่สร้างบอทหรือเปิด Live
ไม่เพิ่ม Futures หรือตลาดใหม่ และไม่ทำหน้าจอจัดรายการเหรียญ F-37
ไม่รวมแท่งเทียนสดใน F-10 โดยคงประวัติและการซ่อมช่วงที่ขาดของ F-09 ไว้เดิม

## ความหมายของราคาเก่า

การไม่มี trade ใหม่ไม่ได้พิสูจน์ว่าท่อหลุด แต่ราคาซื้อขายล่าสุดยังต้องผ่าน
เกณฑ์อายุเดียวกัน: ราคาอายุเท่ากับ 10 วินาทียังผ่านเกณฑ์อายุ
เมื่อเกิน 10 วินาทีจึงเป็นราคาเก่า ทั้งนี้เงื่อนไขความพร้อมอื่นต้องผ่านด้วย
แยกสถานะราคาเก่าจาก connection status และไม่ใช้ heartbeat รีเซ็ตอายุราคา
ราคาเก่าแสดงได้พร้อมเวลาและป้ายสถานะ แต่ห้ามใช้เป็นราคาที่เชื่อถือได้
สำหรับเปิดไม้ใหม่ การกลับมาพร้อมต้องกู้ข้อมูลสำเร็จและผ่านเกณฑ์ราคา

เอกสาร [Trade Streams ของ Binance TH](https://www.binance.th/api-docs/en/#trade-streams)
แยก event time (`E`) กับ trade time (`T`); ข้อกำหนดนี้ใช้เวลา trade
เป็นอายุราคาซื้อขายล่าสุด ตัวเลข 10/60 วินาทีเป็นคำตัดสินของเจ้าของ
ไม่ใช่ค่าที่ตลาดรับรองหรือผลการวัด stream จริง

## ความหมายของสถานะในเว็บ — การเปลี่ยนแปลงที่อนุมัติ NC-26

เจ้าของตอบ approve วันที่2026-10-07 ให้เว็บแสดงสถานะที่ server ตรวจ ณ เวลา
snapshot พร้อมเวลาและสถานะการเชื่อมต่อ; backend ตรวจ freshness ใหม่ก่อนใช้งานจริง
ป้ายเว็บต้องสื่อว่า “พร้อม ณ เวลาที่ตรวจ” และแสดง server reference time กับ trade time
เสมอ แม้ข้อความเดินทางล่าช้าหรือเครื่องพักก็ไม่เปลี่ยนป้ายเป็นคำรับรองราคาปัจจุบัน
เวลา receive/heartbeat ไม่แทนเวลา snapshot และไม่รีเซ็ต trade time
known delivery failure/reconnect/resume ต้องแสดงว่ารอสถานะใหม่พร้อมข้อมูลค้าง
โดยไม่ลบข้อเท็จจริงของ snapshot เก่า; snapshotใหม่ยังต้องผ่าน ordering guards

ยกเลิกข้อเสนอ clock_eligible/READY proof และการรับรอง browser clock1ms
browser timers ใช้ scheduling/detection ที่สังเกตได้ ไม่ใช้พิสูจน์เวลาตลาด
เจ้าของอนุมัติ NC-27 แยกแล้ว: server นับmarket outage60s; เว็บเตือนdelivery
failureทันทีที่ตรวจพบ ไม่ใช้browserclockรับรอง60s ตามRQ-15ฉบับแก้

## กฎความปลอดภัยที่เกี่ยวข้อง

- trading-safety §1/2: แยก Paper/Live และไม่ถือคำรับรองหรือความสามารถย้ายเงิน
- §6/7: ราคาที่เชื่อถือไม่ได้ห้ามใช้เปิดไม้ใหม่; backoff และกู้คืนก่อนพร้อม
- §12: ความพร้อมราคากับความพร้อมบัญชีเป็นคนละเรื่อง; F-10 ไม่อ้างว่ากระทบยอดบัญชีแล้ว
- §13: การพักเพราะไม่มีราคาไม่ใช่การหยุดบอทถาวร; การทำงานของบอทเป็นงานภายหลัง
- architecture §2: เวลาและค่าที่ใช้ตัดสินต้องส่งเข้า core; jitter อยู่ภายนอก core
