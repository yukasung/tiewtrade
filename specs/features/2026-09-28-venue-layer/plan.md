## แนวทาง

งานนี้ไม่มีฐานข้อมูลและไม่มีเครือข่าย จึงแบ่งตามของที่ส่งมอบ ไม่ใช่ตามชั้นระบบ

```
1. ชนิดข้อมูลกลาง        ← ไม่มีคำศัพท์ของตลาดไหนอยู่ในนั้น
2. ชนิดข้อผิดพลาด 5 ชนิด   ← "ไม่รู้ผล" เป็นชนิดของตัวเอง
3. สามสัญญา              ← ราคา, กระเป๋า, ข้อจำกัดของเหรียญ
4. ตัวแทนปลอม            ← ทำตามสัญญาครบ รวมกรณีผิดพลาด
5. ด่านกันคำศัพท์รั่ว      ← บังคับด้วยเครื่องมือ ไม่ใช่การรีวิว
```

### 1. ชนิดข้อมูลกลาง

| ชนิด | เก็บอะไร | เหตุผลของรูปแบบ |
|---|---|---|
| `Symbol` | สินทรัพย์ฐาน + สินทรัพย์ที่ใช้อ้างราคา เช่น `BTC`/`USDT` | **ไม่เก็บเป็นข้อความเดียวอย่าง `BTCUSDT`** เพราะรูปแบบนั้นเป็นของตลาด การแยกเป็นสองส่วนทำให้ตัวเชื่อมแต่ละตลาดประกอบชื่อของตัวเองได้ และโค้ดข้างนอกไม่ต้องรู้ว่าตลาดเขียนชื่อคู่เทรดแบบไหน (RQ-2) |
| `Price` | `Symbol`, ราคาเป็น `Money`, **เวลาของตลาด**, **เวลาที่ระบบรับ** | สองเวลาตาม Q-10 และราคาเป็น `Money` เพราะราคาคือจำนวนเงินต่อหนึ่งหน่วยของสินทรัพย์ฐาน |
| `SymbolConstraints` | ปริมาณขั้นต่ำ, ขั้นของปริมาณ, มูลค่าขั้นต่ำ | สามข้อที่ `trading-safety.md` หัวข้อ 3 ระบุไว้ ไม่มากไม่น้อยกว่านั้น (RQ-13) |
| `WalletHoldings` | ยอดของแต่ละสินทรัพย์ แยกส่วนที่ใช้ได้กับส่วนที่ถูกจองไว้ | ทุกยอดเป็น `Quantity` ไม่ใช่ `Money` — ดูเหตุผลข้างล่าง |
| `CallCost` | ต้นทุนของการเรียกหนึ่งครั้ง | ให้ผู้เรียกเอาไปนับรวมทั้งระบบได้ (Q-8) |

**ทำไม `SymbolConstraints` ใช้ "ขั้นของปริมาณ" แทน "จำนวนทศนิยม"**
กฎเขียนว่า "ทศนิยม" แต่สิ่งที่ต้องตรวจจริงคือปริมาณที่สั่งต้องเป็นจำนวนเท่าของขั้นที่ตลาดยอม
ซึ่งครอบกรณีที่ขั้นไม่ใช่กำลังสิบ (เช่น 0.5) ด้วย และตรวจได้ด้วยเลขคณิตบน `Quantity`
ของ F-02 โดยไม่ต้องนับหลักเอง — จำนวนทศนิยมเป็นผลของขั้น ไม่ใช่ข้อมูลอีกชิ้น

**ทำไมยอดในกระเป๋าเป็น `Quantity` ทั้งหมด**
กระเป๋าถือสินทรัพย์ ไม่ได้ถือ "เงิน" — `0.5 BTC` กับ `100 USDT` เป็นของชนิดเดียวกัน
ในมุมของกระเป๋า การตีมูลค่าเป็นสกุลเงินเป็นเรื่องของ F-14 ซึ่งต้องใช้ราคาประกอบ
ถ้าเก็บ `USDT` เป็น `Money` แต่ `BTC` เป็น `Quantity` ผู้เรียกจะต้องเขียนสองทางสำหรับ
เรื่องเดียวกัน และจะมีจุดที่ต้องเดาว่าสินทรัพย์ไหนนับเป็นสกุลเงิน

### 1.1 การตรวจข้อจำกัดอยู่ใน `core` ไม่ใช่ใน `venues` (แก้หลังรีวิว 2026-09-28)

ร่างก่อนหน้าให้ `SymbolConstraints` ใน `venues` ตรวจเอง ซึ่ง **ผิดชั้น**
`standards/backend.md` หัวข้อ 3 สั่งว่า **โค้ดที่คำนวณอยู่ใน `core` เท่านั้น**
service และชั้นอื่นเป็นแค่ตัวประกอบ การเทียบขั้นของปริมาณและมูลค่าขั้นต่ำเป็นการคำนวณ

การแบ่งที่ถูกต้อง:

| ของ | อยู่ที่ | เพราะ |
|---|---|---|
| `SymbolConstraints` — **ข้อมูลที่ตลาดบอก** | `venues` | เป็นสิ่งที่ตลาดรายงาน ไม่ใช่กฎของเรา |
| **การตรวจว่าคำสั่งผ่านข้อจำกัดหรือไม่** | `core` (โมดูลใหม่) | เป็นการคำนวณ และจุดตรวจของ F-16/F-22 ต้องใช้ตัวเดียวกัน |

**`SymbolConstraints` จึงไม่มีเมธอดตรวจ** ผู้เรียกเรียกฟังก์ชันใน `core` แทน
เพื่อไม่ให้มีสองที่ที่ดูเหมือนตรวจได้ทั้งคู่

**ต้องเพิ่มหนึ่งการดำเนินการใน `core.money` ด้วย**
ตอนนี้ `Quantity` มีบวก ลบ คูณ และเทียบค่า **แต่ไม่มีการหารและไม่มีเศษ**
(F-02 ตัดสินว่ายังไม่ทำการหาร) การตรวจ "เป็นจำนวนเท่าของขั้น" จึงทำไม่ได้เลย
ด้วยของที่มีอยู่ และการไปคำนวณด้วย `Decimal` เปล่าที่อื่นขัดกับ `AGENTS.md` กฎข้อ 6

ทางที่เสนอ: เพิ่ม **การตรวจว่าเป็นจำนวนเท่าของอีกค่าหนึ่งแบบลงตัว** ไว้ใน `core.money`
ซึ่งเป็นที่เดียวที่การคำนวณบน `Decimal` ถูกต้องตามกฎ และเป็นการทำตามนโยบายการหาร
ที่ F-02 อนุมัติไว้ล่วงหน้าแล้ว (F-02 Q-1.3 — "กฎเรื่องผลหารไม่ลงตัวมีผลเมื่อมีงาน
ที่ต้องหารในภายหลัง") **งานนี้คืองานนั้น**

> **นี่คือการแตะ `core` ซึ่งร่างก่อนหน้าบอกว่าจะไม่แตะ** จึงขออนุมัติเป็นส่วนหนึ่ง
> ของแผนฉบับนี้ ขอบเขตการแตะคือ: เพิ่มการตรวจการลงตัวใน `core.money`
> และเพิ่มโมดูลใหม่ใน `core` สำหรับการตรวจข้อจำกัด **ไม่แก้กฎการปัด ไม่แก้ช่วงค่า
> และไม่แก้พฤติกรรมเดิมของ `Money`/`Quantity`** เทสต์ของ F-02 ทั้ง 197 ข้อต้องยังเขียว

ฟังก์ชันตรวจคืน **รายการข้อที่ไม่ผ่าน** (ไม่ใช่แค่จริง/เท็จ) เพราะจุดตรวจของ F-16
ต้องบอกผู้ใช้ได้ว่าไม่ผ่านเพราะอะไร และ **ไม่ปัดค่าให้** ตาม Q-7

### 2. ชนิดข้อผิดพลาด

ห้าชนิดตามตารางใน `requirements.md` Q-5 สืบจากฐานร่วม `VenueError`

- `VenueRejectedError` พา **รหัสเหตุผลกลาง** มาด้วย ไม่ใช่ข้อความของตลาด
  รายการรหัสเริ่มต้นมีเท่าที่กฎที่อนุมัติแล้วบังคับ: ไม่รู้จักคู่เทรด, ผิดข้อจำกัดของเหรียญ,
  เงินไม่พอ **การเพิ่มรหัสใหม่ต้องเพิ่มพร้อมงานที่มีผู้ใช้จริง**
- `VenueRateLimitedError` พาเวลาที่ต้องรอมาด้วยถ้าตลาดบอก และเป็น `None` ถ้าตลาดไม่บอก
  **ห้ามเดาเวลาแทนตลาด** (`trading-safety.md` หัวข้อ 7)
- `VenueOutcomeUnknownError` **ไม่มีทางถูกสร้างจากการที่ตลาดตอบว่าไม่รับ** เพราะสองอย่างนี้
  ต่างกันคนละทาง เทสต์ต้องยืนยันว่าผู้เรียกแยกได้ด้วยชนิด ไม่ต้องอ่านข้อความ
- **ห้ามมี API key, secret หรือ URL ในข้อความของทุกชนิด** (RQ-8) และมีเทสต์ด้วยค่าจำลอง

### 3. สามสัญญา

เขียนเป็น `Protocol` แยกกันสามตัว ไม่สืบทอดกัน เพื่อให้ผู้เรียกพึ่งเฉพาะส่วนที่ใช้ (Q-2)
เมธอดทุกตัวเป็น `async` ส่วนการสร้างและตรวจชนิดข้อมูลเป็น `sync` (RQ-17)

| สัญญา | เมธอด | ใครใช้ก่อน |
|---|---|---|
| `PriceSource` | ราคาล่าสุดของคู่เทรดหนึ่ง | F-10, F-12 และจุดตรวจของ F-16 |
| `WalletSource` | ยอดในกระเป๋า | F-08, F-23 |
| `SymbolConstraintSource` | ข้อจำกัดของคู่เทรดหนึ่ง | จุดตรวจของ F-16 และ F-22 |

**`WalletSource` ไม่รับตัวชี้กระเป๋าเป็นพารามิเตอร์** — ตัวที่ทำตามสัญญาหนึ่งตัวผูกกับ
กระเป๋าหนึ่งใบตอนสร้าง เหตุผล: การส่งตัวชี้กระเป๋าเข้ามาทุกครั้งจะบังคับให้ออกแบบว่า
กุญแจของผู้ใช้เดินทางอย่างไร ซึ่งเป็นงาน F-07 และ F-35 ที่ยังไม่ได้ตัดสิน (T-03)
วิธีนี้เลื่อนการตัดสินนั้นออกไปโดยไม่ปิดทางเลือกไหน และตรงกับกฎ
"หนึ่งกระเป๋า หนึ่งผู้เขียน" (`architecture.md` หัวข้อ 4)

**ตัวจำกัดอัตราการเรียก** ทุกสัญญารับ `RateLimitGuard` ตอนสร้าง (Q-8)
งานนี้ให้แค่ `Protocol` ของตัวกั้นกับตัวที่ไม่ทำอะไร ตัวจริงที่ใช้สภาพร่วมกันทั้งระบบ
อยู่ใน service (F-35 หรือ F-10) เพราะ `venues` พึ่ง `infra` ไม่ได้ (RQ-3)

**สัญญาของต้นทุนและตัวกั้น (แก้หลังรีวิว 2026-09-28)** — ร่างก่อนหน้าไม่ได้บอกหน่วย
จึงพิสูจน์ Q-8 ไม่ได้

| ส่วน | กำหนดว่า |
|---|---|
| `CallCost` | สองช่อง: **น้ำหนักของการเรียก** (จำนวนเต็มไม่น้อยกว่า 1) และ **จำนวนออเดอร์ที่คำสั่งนั้นสร้าง** (ศูนย์สำหรับการอ่าน) สองช่องเพราะ `mission.md` หัวข้อ 6 บันทึกเพดานของ Binance TH ไว้สองแบบ: 6,000 weight/นาที และ 6,000 ออเดอร์/นาที — เพดานสองแบบนับสองอย่าง |
| หน่วยของน้ำหนัก | **หน่วยที่ตลาดประกาศ** ไม่ใช่หน่วยที่เราคิดขึ้น ชั้นกลางไม่รู้ว่า 1 น้ำหนักเท่ากับอะไร รู้แค่ว่าต้องนับรวมก่อนเรียก |
| ตัวกั้น | เมธอดเดียว **จองก่อนเรียกจริง** และถ้าจองไม่ได้ต้องโยน `VenueRateLimitedError` ไม่ใช่รอเงียบ ๆ ข้างใน เพราะผู้เรียกต้องเป็นคนตัดสินว่าจะรอหรือทิ้งงาน |
| ใครประกาศต้นทุน | **แต่ละเมธอดของสัญญาประกาศต้นทุนของตัวเอง** และตัวที่ทำตามสัญญาต้องส่งต้นทุนนั้นให้ตัวกั้นก่อนทำงานทุกครั้ง |

### 4. ตัวแทนปลอม

- อยู่ใน `venues` เป็นของสาธารณะ (Q-9) ชื่อบอกตรง ๆ ว่าเป็นของปลอม
- ทำตามทั้งสามสัญญา และ **บังคับให้เกิดข้อผิดพลาดได้ทุกชนิดในห้าชนิด** (RQ-16)
  ด้วยคิวคำตอบที่ผู้เรียกเตรียมไว้ล่วงหน้า — ไม่ใช่ตั้งค่าแบบ "ให้พังตลอด"
  เพราะเทสต์ส่วนใหญ่ต้องการลำดับ เช่น พลาดครั้งแรกแล้วสำเร็จครั้งที่สอง
- **ไม่จับคู่ออเดอร์ ไม่มีบัญชี ไม่มีการเปลี่ยนยอดตามคำสั่ง** และเขียนกำกับไว้ใน docstring
  ว่าตัวจำลองของ Paper เป็นงาน F-15 (RQ-16)
- ไม่อ่านนาฬิกาเอง — เวลาที่ติดมากับราคาเป็นค่าที่ผู้เรียกกำหนด เพื่อให้เทสต์ความเก่า
  ของราคาทำได้โดยไม่ต้องรอเวลาจริง

### 4.1 ข้อมูลที่ผู้เรียกต้องใช้ลง audit log (RQ-15, แก้หลังรีวิว 2026-09-28)

ร่างก่อนหน้าอ้าง RQ-15 ไว้แต่ไม่ได้บอกว่าข้อมูลไหนมาจากไหน จึงผ่านเกณฑ์ได้
โดยที่ข้อกำหนดยังไม่ครบ ตารางนี้ปิดช่องนั้น

| ห้าอย่างที่ F-04 บังคับ | ใครมี | ชั้นนี้ต้องทำอะไร |
|---|---|---|
| **ใครทำ** | ผู้เรียก | ไม่ต้องทำอะไร — ชั้นนี้ไม่รู้จักผู้ใช้และไม่ควรรู้ |
| **ทำอะไร** | ผู้เรียก | ไม่ต้องทำอะไร — ชนิดเหตุการณ์เป็นของ F-04 |
| **กับอะไร** | ทั้งสองฝ่าย | คืน **`Symbol` ของผลที่ได้** ติดมากับค่าที่คืน เพื่อให้ผู้เรียกไม่ต้องจำว่าถามอะไรไป และไม่ต้องอ่านข้อความเพื่อรู้ |
| **เมื่อไหร่** | ทั้งสองฝ่าย | ราคาคืน **เวลาของตลาด** และ **เวลาที่ระบบรับ** (Q-10) ส่วนเวลาที่บันทึกลงตารางมาจากฐานข้อมูลตาม F-04 RQ-6 |
| **ผลเป็นอย่างไร** | ชั้นนี้ | สำเร็จ = คืนค่า, ไม่สำเร็จ = โยนชนิดที่ระบุได้ และ **ทุกชนิดต้องมีรหัสคงที่ที่เอาไปใส่ `failure_code` ได้ตรง ๆ** ห้ามให้ผู้เรียกต้องแปลข้อความ |

**ผลที่ตามมาซึ่งต้องบันทึกไว้:** `failure_code` ของ F-04 รับเฉพาะรหัสที่ประกาศไว้
ในทั้งโค้ดและ migration (F-04 RQ-4, V-18.5) ตอนนี้ยังไม่มีรหัสใดถูกประกาศ
เพราะยังไม่มีเหตุการณ์ที่แตะเงิน **งานแรกที่ลงบันทึกความล้มเหลวของ venue
ต้องประกาศรหัสของห้าชนิดนี้ลง migration ของ F-04 ในงานเดียวกัน** —
งานนี้เตรียมรหัสฝั่ง `venues` ให้พร้อม แต่ไม่แตะ migration ของ F-04

### 5. ด่านกันคำศัพท์ของตลาดรั่ว (RQ-12)

ไม่ใช่การ import — เป็นข้อความที่เขียนไว้ในโค้ด

- ตัวตรวจอ่านโครงสร้างโค้ด (AST) ของทุกไฟล์ **นอก** `tiewtrade.venues`
  แล้วปฏิเสธเมื่อพบคำศัพท์เฉพาะตลาดในค่าคงที่ข้อความหรือชื่อ: `binance`, `fapi`,
  `BTCUSDT` และรูปแบบชื่อคู่เทรดที่ติดกันเป็นคำเดียว
- ตรวจ **โครงสร้าง ไม่ใช่ค้นข้อความทั้งไฟล์** เพื่อไม่ให้คอมเมนต์หรือ docstring
  ที่อ้างถึงเอกสารสเปกกลายเป็นความผิด (บทเรียนเดียวกับตัวตรวจความบริสุทธิ์ของ F-01)
- เพิ่มกรณีที่ต้องแดงและกรณีที่ต้องผ่านใน `tests/gates/` ตามแบบ F-01 (RQ-12)
- **ด่านที่สอง: ส่วนกลางของ `venues` ต้องไม่ import ไลบรารีเครือข่าย** (RQ-14)
  ใช้รายการที่อนุญาตแบบเดียวกับตัวตรวจความบริสุทธิ์ของ `core` ไม่ใช่รายการที่ห้าม

  **ขอบเขตของด่านนี้ (แก้หลังรีวิว 2026-09-28):** ครอบ **สัญญากลาง ชนิดข้อมูล
  ข้อผิดพลาด ตัวกั้นอัตรา และตัวแทนปลอม** เท่านั้น — ไม่ครอบ package ของตัวเชื่อมจริง
  `architecture.md` หัวข้อ 1 วางตัวเชื่อมของแต่ละตลาดไว้ **ข้างใน** `venues`
  (เช่น `venues.binance_th`) และตัวเชื่อมจริงต้องต่อเครือข่ายเป็นงานหลัก
  ถ้าด่านครอบทั้ง package จะบล็อก F-35 ตั้งแต่บรรทัดแรก

  กฎที่ด่านนี้บังคับจึงเป็น: **ส่วนกลางต้องไม่รู้จักเครือข่าย** และ
  **โค้ดที่ต่อเครือข่ายต้องอยู่ใน package ของตัวเชื่อมเท่านั้น**

  **เก็บ contract ของ import-linter ไว้คู่กัน** (เจ้าของตัดสิน 2026-09-28)
  สองด่านนี้ตรวจคนละมิติ ไม่ใช่ของซ้ำ: ด่าน AST ดู **บรรทัด import ของแต่ละไฟล์**
  ส่วน import-linter ไล่ **เส้นทางการพึ่งพา** จึงจับกรณีทางอ้อมได้ เช่น
  ส่วนกลาง → ตัวเชื่อม → ไลบรารีเครือข่าย ซึ่งด่าน AST มองไม่เห็นเพราะบรรทัด import
  ที่ไฟล์นั้นเป็นของในโปรเจกต์เอง — มีเทสต์ที่พิสูจน์ความต่างนี้โดยตรง
  และเทสต์นั้นจะแดงถ้าวันหนึ่งข้อสรุปนี้เปลี่ยนไป
  ส่วน RQ-14 ("ไม่มีการเรียกเครือข่ายในงานนี้เลย") เป็นข้อกำหนดของ **งานนี้**
  ซึ่งยังไม่มีตัวเชื่อม จึงจริงทั้งสองข้อพร้อมกัน

## ความเสี่ยง

| อะไรอาจพัง | จะรู้ได้อย่างไร |
|---|---|
| คำศัพท์ของตลาดรั่วออกนอกชั้นโดยไม่มีใครเห็น | ด่านที่อ่าน AST ทุกไฟล์นอก `venues` + กรณีที่ต้องแดงใน `tests/gates/` |
| มีคนเรียกเครือข่ายจากใน `venues` ตอน F-35 | ด่านห้าม import ไลบรารีเครือข่ายด้วยรายการที่อนุญาต + contract ของ import-linter |
| ผู้เรียกแยก "ถูกปฏิเสธ" กับ "ไม่รู้ผล" ไม่ออก | เทสต์ที่ดักด้วยชนิดอย่างเดียว ไม่อ่านข้อความ และเทสต์ว่าไม่มีชนิดไหนสืบทอดกันจนดักปนกันได้ |
| สัญญาออกแบบผิดเพราะไม่มีใครใช้จริง | ตัวแทนปลอมทำตามสัญญาครบทุกทาง รวมทางที่พลาด และเทสต์เขียนจากมุมผู้เรียก ไม่ใช่มุมผู้ให้บริการ |
| ตัวแทนปลอมถูกเข้าใจผิดว่าเป็นตัวจำลอง Paper | ชื่อบอกว่าปลอม + docstring ระบุว่า F-15 เป็นเจ้าของการจำลอง + เทสต์ว่าไม่มีเมธอดที่เปลี่ยนยอดในกระเป๋า |
| `Symbol` แบบสองส่วนใช้กับตลาดที่ตั้งชื่อแปลกไม่ได้ | F-35 เป็นตัวพิสูจน์ — ถ้าประกอบชื่อของ Binance TH ไม่ได้ ให้หยุดและขออนุมัติเปลี่ยน ไม่ใช่แอบใส่ชื่อดิบเข้ามาในชนิดกลาง |
| ข้อจำกัดของเหรียญยังไม่ครบสำหรับออเดอร์แบบ Limit (เช่น ขั้นของราคา) | ยังไม่เพิ่มจนกว่าจะมีผู้ใช้จริง (RQ-13) ซึ่งจะเกิดพร้อมสัญญาออเดอร์หลัง NC-08 ปิด |
| การเพิ่มการดำเนินการใน `core.money` ทำให้พฤติกรรมเดิมของ F-02 เปลี่ยน | เทสต์ของ F-02 ทั้งชุดต้องยังเขียว และเทสต์ใหม่ต้องครอบกรณีหารไม่ลงตัวตามนโยบายที่ F-02 อนุมัติไว้ |
| ด่านห้ามเครือข่ายครอบกว้างเกินจนบล็อก F-35 | ด่านครอบเฉพาะส่วนกลาง และมีเทสต์ที่ยืนยันว่า package ของตัวเชื่อมสมมติ import ไลบรารีเครือข่ายได้ |
| รหัสความล้มเหลวของ venue ลงบันทึกไม่ได้เพราะยังไม่ประกาศใน F-04 | เขียนไว้ในข้อ 4.1 ว่างานแรกที่ลงบันทึกต้องประกาศรหัสลง migration ของ F-04 ในงานเดียวกัน |
