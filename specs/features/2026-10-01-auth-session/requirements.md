## ทำไมต้องมี

ทุกอย่างที่เหลือในระบบต้องรู้ว่า "ผู้ใช้คนไหน" ก่อนจึงทำงานได้ และตอนนี้ยังไม่มีใครเลย

- ตาราง `users` ของ F-03 มีแค่ `id` กับ `created_at` — **ยังไม่มีทางสร้างผู้ใช้จริง**
  กลไกแยกข้อมูลผู้ใช้ (RLS) ที่สร้างไว้จึงไม่มีผู้ใช้จริงมาใช้
- API key ของผู้ใช้ (F-07), กระเป๋า (F-08), บอท (F-20) ล้วนต้องมีเจ้าของ
- audit log (F-04) บันทึก `actor_user_id` ได้ แต่ยังไม่มีผู้กระทำที่เป็นคนจริง

**คนที่เดือดร้อนถ้าทำผิด:** ผู้ใช้ที่เสียบัญชีให้คนอื่น — ซึ่งในระบบนี้แปลว่า
**เสียสิทธิ์สั่งซื้อขายด้วยเงินจริงของตัวเอง** ไม่ใช่แค่ข้อมูลรั่ว

## คำตอบที่เจ้าของตัดสิน — 2026-10-02

### Q-8 สิทธิ์ของสิ่งที่ทำงานก่อนรู้ว่าเป็นใคร

**ทำใต้ RLS ทั้งหมด ไม่มีทางข้าม RLS ตัวที่สอง** และ **ไม่ใช้ค่าผู้ใช้ปัจจุบันกับตาราง
`sessions` เลย** ทุกสิทธิ์ผูกกับการถือโทเคนที่ยังไม่ถูกเพิกถอนของผู้ใช้นั้นจริง

ตัวแปรประจำ transaction สองตัว (กลไกเดียวกับ `tiewtrade.current_user_id` ของ F-03):

| ตัวแปร | ตั้งเมื่อไร | ค่า |
|---|---|---|
| `tiewtrade.presented_token_hash` | ทุกคำขอที่พาโทเคนมา | **แฮชของโทเคน** — ฐานข้อมูลไม่เคยเห็นโทเคนจริง |
| `tiewtrade.presented_email` | เฉพาะตอน login | อีเมลที่ผู้ใช้กรอก |

**สิทธิ์ของ `api` ต่อ `sessions`**

| ทำอะไร | กลไก |
|---|---|
| อ่าน | policy `token_hash = presented_token_hash` — **ห้ามอ้างตารางตัวเอง** (RQ-20) |
| ต่ออายุ | `GRANT UPDATE (คอลัมน์ต่ออายุ)` คอลัมน์เดียว + `USING` ที่กันแถวหมดอายุและแถวที่ถูกเพิกถอน (RQ-21) |
| ออกเครื่องเดียว | policy `token_hash = presented_token_hash` |
| ออกทุกเครื่อง | policy DELETE `user_id = (SELECT user_id FROM sessions WHERE token_hash = presented_token_hash AND ยังไม่ถูกเพิกถอน)` |
| ออก session ใหม่ | **ไม่มีสิทธิ์** — `auth` เท่านั้น |
| เปลี่ยนเจ้าของ/แฮช/เวลาเริ่ม/เพดาน | **ไม่มีสิทธิ์** (RQ-17) |

**สิทธิ์ของ `auth` ต่อ `user_credentials`** — `api` ไม่มีสิทธิ์ใด ๆ ตลอดชีวิต

| ทำอะไร | กลไก |
|---|---|
| อ่านตอน login | policy `email = presented_email` |
| อ่าน/แก้หลัง login | policy `user_id = ผู้ใช้ปัจจุบัน` |

**สมัคร / login / เปลี่ยนรหัสผ่าน จบใน transaction เดียวบน connection ของ `auth`**
การสร้างแถวผู้ใช้ใช้กลไกเดิมของ F-03 (สร้าง `uuid` เอง → `SET LOCAL` → `INSERT`)
จึงไม่ต้องมีข้อยกเว้นใหม่

**หลักฐาน:** ข้อสรุปข้างบนมาจากการทดลองกับ PostgreSQL 16 จริง (2026-10-02) ไม่ใช่การอ่านเอกสาร
อย่างเดียว — `DELETE` ที่อ้างคอลัมน์ลบได้แถวเดียว · แบบไม่อ้างคอลัมน์ลบได้สองแถว ·
สิทธิ์ระดับคอลัมน์กันการเปลี่ยนเจ้าของได้ · policy ที่อ้างตารางตัวเองใน `DELETE` ใช้ได้
แต่ใน `SELECT` เกิด `infinite recursion` · ไม่ตั้งตัวแปรแล้วลบได้ศูนย์แถว

| **Q-7** | **คง `USER_CREATED`** ที่มีอยู่แล้ว · เพิ่ม `SESSION_STARTED`, `SESSION_ENDED` (เครื่องเดียว), `ALL_SESSIONS_ENDED` (ทุกเครื่อง), `PASSWORD_CHANGED` · **login ที่ล้มเหลวไม่ลง audit** เพราะ `owner_user_id` เป็น `NOT NULL` จึงไม่มีเจ้าของให้ใส่ และถ้าคนที่ยังไม่ login เขียน audit ได้จะเป็นช่องถล่มให้พาร์ทิชันโต — เก็บในตัวนับอัตราการเรียกแทน |
| **Q-9** | อีเมล **ไม่ซ้ำ** · **ไม่แยกตัวพิมพ์ใหญ่เล็ก โดยบันทึกว่าเป็นนโยบายที่เราเลือก ไม่ใช่สิ่งที่มาตรฐานกำหนด** (RFC 5321 §2.4 ยอมให้ส่วนก่อน `@` แยกตัวพิมพ์ได้) · รหัสผ่าน **ขั้นต่ำ 15 code points** (NIST SP 800-63B-4 SHALL เพราะยังไม่มีปัจจัยที่สอง) · **เพดาน 1,024 code points** · **ห้ามมีกฎอักขระ** (SHALL NOT) · **normalise NFC** (SHOULD) และนับ code point ละหนึ่งอักขระ (SHALL) · **ใช้กระบวนการเดียวกันทั้งสมัคร login เปลี่ยนรหัสผ่าน และตรวจ blocklist** · **ตรวจ blocklist ในงานนี้** (SHALL) โดย `plan.md` ต้องระบุ **แหล่งที่มา รุ่น และวิธีอัปเดต** ของรายการ |
| **Q-10** | **บอกตรง ๆ ว่าอีเมลถูกใช้แล้ว** + คุมอัตราการเรียกหน้าสมัคร + **บันทึกชัดว่าหน้าสมัครเปิดเผยการมีบัญชี** เป็นข้อจำกัดที่ยอมรับจนกว่าจะส่งอีเมลได้ (T-05) |

## Needs Clarification ที่พบตอนรีวิวโค้ด (2026-10-03)

### NC-14 เจ้าของบัญชีกลับเข้ามาลดความเสี่ยงได้อย่างไร เมื่อ session หมดอายุและบัญชีถูกโจมตีต่อเนื่อง

**สิ่งที่พบ:** เส้นทางเข้าสู่ระบบปฏิเสธคำขอที่ติดหน่วง **ก่อนตรวจรหัสผ่าน** ฉะนั้น
เจ้าของที่กรอกรหัสผ่านถูกก็ถูกปฏิเสธด้วย · ผู้โจมตีที่ตรวจรหัสผิดก่อนเจ้าของทุกครั้งที่
ช่องเปิด จะดันเวลารออกไปได้ซ้ำ ๆ และสลับ IP เพื่อหลบเพดานต่อ IP

**เพดาน 10 วินาทีจึงเป็นเพดานต่อรอบ ไม่ใช่เพดานเวลาที่เจ้าของถูกกันออกจากระบบ**
(ความเสี่ยงที่กลไกล็อกบัญชีถูกใช้ทำ DoS เป็นเรื่องที่ OWASP ระบุไว้)

**ที่ยังปลอดภัยอยู่:** session ที่ยังใช้ได้ไม่ผ่านตัวนับของการเข้าสู่ระบบเลย ฉะนั้นคนที่
ยังเข้าสู่ระบบอยู่กดหยุดบอทได้ทันทีตาม `trading-safety.md` หัวข้อ 8
**ช่องที่เหลือคือ session หมดอายุแล้วเจอการโจมตีต่อเนื่อง**

**มันบล็อกอะไร:** **การยืนยันเหตุผลด้านความปลอดภัยของเพดาน 10 วินาที** ไม่ใช่ตัวเลข
เพดานเอง — และ **ไม่ได้แปลว่าควรเพิ่มเพดานให้สูงขึ้น** ซึ่งจะยิ่งกันเจ้าของนานขึ้น

**ทางที่เป็นไปได้ (ยังไม่เลือก ห้ามเดาแทนเจ้าของ):** ตรวจรหัสผ่านแม้ติดหน่วงแล้วปล่อย
เมื่อถูกต้อง (แลกกับการเปิดช่องเดารหัสผ่าน) · ช่องทางลดความเสี่ยงที่ไม่ผ่านรหัสผ่าน
(ต้องตอบว่าพิสูจน์ตัวตนด้วยอะไร) · แยกตัวนับของเจ้าของที่กรอกถูกออกจากของผู้โจมตี
(ต้องตอบว่าแยกด้วยอะไรเมื่อยังไม่รู้ว่าใครเป็นใคร) · หรือรับความเสี่ยงนี้ไว้อย่างชัดเจน

## ข้อจำกัดที่ยอมรับแล้ว — เขียนไว้เพื่อให้งานถัดไปไม่เข้าใจผิดว่าปลอดภัยกว่าจริง

| ข้อจำกัด | ขอบเขตที่แท้จริง |
|---|---|
| **บทบาท `auth` เป็นบทบาทที่เชื่อถือ** | โครงนี้ **ไม่กัน** ผู้โจมตีที่รัน SQL ได้ตามใจด้วยบทบาท `auth` เพราะบทบาทนี้ตั้งตัวแปรเองและมีสิทธิ์ออก session · ที่กันได้คือบทบาท `api` ซึ่งใช้ในทุก endpoint ปกติ |
| **ยึด process ได้ = ถึงทั้งสอง pool** | การแยกบทบาทลดบั๊กระดับคำสั่ง (SQL injection, ลืมเงื่อนไข) **ไม่ได้กันการยึด process** การแยก auth เป็น service ของตัวเองไม่ทำในงานนี้ |
| **`presented_email` ไม่ได้ปิดการสำรวจบัญชี** | สิ่งที่ได้คือ **SELECT ครั้งเดียว dump ทั้งตารางไม่ได้** ผู้โจมตีด้วยบทบาท `auth` ยังวนถามทีละอีเมลได้ |
| **หน้า "อุปกรณ์ที่เข้าสู่ระบบ" ทำไม่ได้** | policy ชุดนี้อ่าน session พี่น้องไม่ได้ (RQ-20 ห้าม SELECT policy ที่อ้างตัวเอง) งานที่ต้องการหน้านี้ต้องออกแบบเพิ่ม |
| **ลืมรหัสผ่าน = เสียบัญชีถาวร** | จนกว่า T-05 ปิดและมีคำตอบเรื่องอำนาจรีเซ็ต (NC-02) |
| **หน้าสมัครเปิดเผยว่าอีเมลใดมีบัญชี** | แลกกับการที่ผู้ใช้รู้ว่าทำไมสมัครไม่ผ่าน จนกว่าจะส่งอีเมลได้ |
