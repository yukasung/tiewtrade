### สิทธิ์ของฐานข้อมูล — กันด้วยสิทธิ์ ไม่ใช่ด้วยความระวังของโค้ด

| # | เกณฑ์ | ตรวจอย่างไร | มาจาก |
|---|---|---|---|
| V-1 | **`api` ออก session ใหม่ไม่ได้** | เทสต์สั่ง `INSERT INTO sessions` ด้วยบทบาท `api` → ถูกปฏิเสธ | RQ-17 |
| V-2 | **`api` เปลี่ยนเจ้าของ session ไม่ได้** และเปลี่ยนแฮชโทเคน เวลาเริ่ม หรือเพดานรวมไม่ได้ | เทสต์ `UPDATE` ทีละคอลัมน์ → ถูกปฏิเสธทุกคอลัมน์ | RQ-17 |

| V-4 | **ไม่ตั้งตัวแปรเลย → อ่านศูนย์แถวและลบศูนย์แถว** (พลาดแบบปิดประตู) | เทสต์ที่ไม่ตั้งตัวแปร | Q-8 |
| V-5 | **ต่ออายุ session ที่หมดอายุแล้วไม่ได้** และ session ที่ถูกเพิกถอนแล้วอ่านไม่พบตั้งแต่ต้น (เพราะเพิกถอนคือลบแถว) | เทสต์สองกรณีแยกกัน | RQ-21 |
| V-5.1 | **ต่ออายุแล้วเลื่อนเวลาหมดอายุจริง** (เกณฑ์ทางบวกคู่กับ V-5) | เทสต์อ่าน `idle_expires_at` ก่อนและหลัง | Q-2 |
| V-5.2 | **ตัวเลขคือไม่ใช้งาน 12 ชั่วโมง และเพดานรวม 7 วัน** ตามที่ตัดสิน | เทสต์อ่านค่าที่โค้ดใช้ และเดินเวลาถึงวินาทีก่อน/หลังเส้น | Q-2 |
| V-6 | **ต่ออายุเกินเพดานรวมไม่ได้** | เทสต์ตั้ง `idle_expires_at` ให้เกิน `absolute_expires_at` → ถูกปฏิเสธโดยฐานข้อมูล | Q-2 |
| V-7 | **`api` แตะตาราง `user_credentials` ไม่ได้เลย** ทุกคำสั่ง | เทสต์ `SELECT/INSERT/UPDATE/DELETE` ด้วย `api` → ถูกปฏิเสธทั้งสี่ | Q-8 |
| V-8 | **`auth` อ่าน credential ได้ทีละอีเมลที่ระบุ** และ **`SELECT` ครั้งเดียว dump ทั้งตารางไม่ได้** | เทสต์อ่านโดยไม่ตั้ง `presented_email` → ศูนย์แถว · ตั้งแล้วได้แถวเดียว | Q-8 |
| V-9 | **บทบาทที่หกถูกครอบด้วยกฎตารางที่เพิ่มได้อย่างเดียว** | **เทสต์โครงสร้าง** ที่เดินทุกบทบาทใน `DatabaseRole` ยกเว้น migrator แล้วยืนยันว่าแก้/ลบ `audit_events` ไม่ได้ — ไม่ใช่รายชื่อที่เขียนมือ | plan 1.1, F-35 ข้อ 7.1 |
| V-10 | **`auth` ไม่ `BYPASSRLS` และไม่ `SUPERUSER`** | เทสต์อ่าน `pg_roles` ผ่านตัวตรวจบทบาทเดิมของ F-03 | Q-8 |
| V-10.1 | **`auth` ลบ session ของผู้ใช้ที่ระบุตัวแล้วได้จริง** — ไม่ใช่ได้สิทธิ์ `DELETE` แต่ไม่มี policy ให้ใช้ | เทสต์เพิกถอนตอนเปลี่ยนรหัสผ่านต้องลบได้มากกว่าหนึ่งแถว | plan 1.3 (แก้หลังรีวิว) |
| V-10.2 | **สิทธิ์ของบทบาทใหม่ครบทั้งเจ็ดรายการตามตารางใน plan ข้อ 1.3** — รวม `EXECUTE` ของ `tiewtrade_current_user_id()` และของฟังก์ชันอ่านตัวแปรใหม่, `INSERT` บน `sessions`, สิทธิ์รายคอลัมน์ของ `user_credentials` | เทสต์เดินทุกรายการในตารางแล้วลองใช้จริงด้วยบทบาท `auth` — ไม่ใช่เทสต์ว่า "สมัครได้" อย่างเดียว ซึ่งผ่านได้แม้สิทธิ์บางข้อขาด | plan 1.3 (แก้หลังรีวิวรอบสอง) |
| V-10.3 | **`auth` ไม่มีสิทธิ์เปลี่ยนอีเมลและไม่มีสิทธิ์ `UPDATE` บน `sessions`** | เทสต์ลองทั้งสองแล้วถูกปฏิเสธ | plan 1.3 |

## เทสต์ที่ต้องมี

- **ค่าจริงที่ขอบ:** ความยาวรหัสผ่าน 14/15 และ 1,024/1,025 · เวลาหมดอายุที่วินาทีสุดท้าย
  และวินาทีถัดไป · ตัวนับที่ครั้งที่ 4/5 และครั้งที่ 19/20
- **คุณสมบัติ (hypothesis):**
  - รหัสผ่านใด ๆ ที่ผ่านเกณฑ์ แฮชแล้วตรวจกลับต้องผ่านเสมอ และแฮชของสองรหัสผ่านที่ต่างกันต้องไม่เท่ากัน
  - ข้อความ Unicode ใด ๆ ที่ normalise แล้วเท่ากัน ต้อง login ได้ด้วยรูปใดก็ได้
  - ลำดับคำขอใด ๆ ไม่ทำให้ `api` ได้สิทธิ์เกินที่ประกาศ (ลองทุกคำสั่งกับทุกคอลัมน์)
  - ไม่ว่าลำดับของ "เปลี่ยนรหัสผ่าน" กับ "login ด้วยรหัสผ่านเก่า" เป็นอย่างไร เมื่อทั้งคู่จบแล้ว **ต้องไม่มี session ที่ออกด้วยรหัสผ่านเก่าเหลืออยู่**
- **ความปลอดภัย:**
  - สิ่งที่ `api` ทำไม่ได้ ต้องถูก **ฐานข้อมูล** ปฏิเสธ ไม่ใช่ถูกโค้ดเลี่ยงไม่ทำ (V-1, V-2, V-7)
  - ออกทุกเครื่องลบได้จริงมากกว่าหนึ่งแถว (V-12)
  - ไม่มีความลับใน log, traceback และ audit (V-50 ถึง V-54)

**เขียนเทสต์โดยคิดค่าที่คาดหวังขึ้นใหม่เอง ห้ามลอกจากโค้ดที่กำลังทดสอบ**

## ตรวจด้วยมือ

1. สมัคร เข้าสู่ระบบ ออกจากระบบ บนเบราว์เซอร์จริง → เห็นสถานะเปลี่ยนทุกขั้น
2. เข้าสู่ระบบสองเบราว์เซอร์ → กดออกทุกเครื่องจากเครื่องหนึ่ง → อีกเครื่องใช้ต่อไม่ได้
3. คัดลอก cookie ออกไปก่อน logout แล้วใช้ซ้ำหลัง logout → ต้องใช้ไม่ได้
4. ลองสมัครตอนสวิตช์ปิด → ต้องสมัครไม่ได้และข้อความอ่านรู้เรื่อง
5. เปิดหน้าเว็บทิ้งไว้ให้ poll ราคา → session ต้อง **ไม่** ถูกต่ออายุ
6. เปลี่ยนรหัสผ่านจากเครื่องหนึ่งขณะที่อีกเครื่องกด login ด้วยรหัสผ่านเก่า →
   อีกเครื่องต้องไม่ได้ session ที่ใช้งานต่อได้
