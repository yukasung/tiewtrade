## แนวทาง

```
1. บทบาทที่หกและตารางสองตาราง   ← สิทธิ์ของฐานข้อมูลเป็นตัวบังคับ ไม่ใช่ความระวังของโค้ด
2. จุดเดียวที่ตอบว่า "ใคร"        ← ลืมใช้ไม่ได้เพราะไม่มีทางลืม
3. เส้นทางสมัคร / login / logout / เปลี่ยนรหัสผ่าน
4. ตัวนับอัตราการเรียกในฐานข้อมูล ← หลายกระบวนการนับร่วมกันได้
5. นโยบายรหัสผ่านและรายการที่ห้าม
6. หน้าบ้าน: ฟอร์มและสถานะ
```

### 1. บทบาทที่หกและสองตาราง (ตอบข้อ 1)

#### 1.1 บทบาท `tiewtrade_auth`

เพิ่มใน `db/bootstrap/00-roles.sql` และใน `DatabaseRole` — **ไม่ `BYPASSRLS` ไม่ `SUPERUSER`**
URL อยู่ใน `TIEWTRADE_DATABASE_URL_AUTH` ตามผังเดิมที่หนึ่งบทบาทมีหนึ่ง URL

**สิ่งที่ต้องไม่พลาด:** `RUNTIME_ROLES` ที่ migration `0001` ใช้ REVOKE สิทธิ์แก้/ลบ
บนตารางที่เพิ่มได้อย่างเดียว เป็นรายการที่เขียนมือ — **ห้ามแก้ migration ที่รันไปแล้ว**
migration ใหม่จึงต้อง REVOKE ให้บทบาทใหม่เองกับทุกตารางที่เพิ่มได้อย่างเดียว
และมี **เทสต์โครงสร้าง** ที่ยืนยันว่าทุกบทบาทใน `DatabaseRole` (ยกเว้น migrator)
ถูกครอบ — ลืมเพิ่มบทบาทที่เจ็ดในอนาคตแล้วต้องแดง ไม่ใช่เงียบ (บทเรียนจาก F-35 ข้อ 7.1)

#### 1.2 ตาราง `user_credentials`

| คอลัมน์ | ชนิด | หมายเหตุ |
|---|---|---|
| `user_id` | `uuid` PK → `users(id)` | หนึ่งแถวคือผู้ใช้หนึ่งคน |
| `email` | `text NOT NULL UNIQUE` | **เก็บหลัง normalise เป็นตัวพิมพ์เล็กแล้ว** เก็บรูปเดียว (RQ-10) |
| `password_hash` | `text NOT NULL` | argon2 — **ไม่มีคอลัมน์ไหนเก็บรหัสผ่านจริง** |
| `created_at` / `updated_at` | `timestamptz NOT NULL` | เวลามาจากฐานข้อมูล บทบาททำงานไม่มีสิทธิ์เขียน |

RLS: `ENABLE` + `FORCE` · **`tiewtrade_api` ไม่ได้สิทธิ์อะไรเลย**

| policy | คำสั่ง | เงื่อนไข | ให้ใคร |
|---|---|---|---|
| `credentials_by_email` | SELECT | `email = presented_email()` | `auth` |
| `credentials_self` | ALL | `user_id = tiewtrade_current_user_id()` | `auth` |

#### 1.3 ตาราง `sessions`

| คอลัมน์ | ชนิด | หมายเหตุ |
|---|---|---|
| `token_hash` | `text` PK | **แฮช SHA-256 ของโทเคน** — ฐานข้อมูลไม่เคยเห็นโทเคนจริง |
| `user_id` | `uuid NOT NULL` → `users(id)` | เจ้าของ |
| `started_at` | `timestamptz NOT NULL` | เวลาออก session |
| `last_seen_at` | `timestamptz NOT NULL` | ใช้ดูว่าใช้งานล่าสุดเมื่อไร |
| `idle_expires_at` | `timestamptz NOT NULL` | หมดอายุเพราะไม่ใช้งาน — เลื่อนได้ |
| `absolute_expires_at` | `timestamptz NOT NULL` | **เพดานรวม เลื่อนไม่ได้** (ไม่ให้สิทธิ์เขียน) |

**ไม่มีคอลัมน์ `revoked_at`** — การเพิกถอนคือการ **ลบแถว** ที่เดียว ร่างแรกมีทั้งสองแบบ
ซึ่งทำให้ตารางเดียวมีสองความหมายของ "ใช้ไม่ได้แล้ว" และคอลัมน์นั้นจะเป็นค่าว่างเสมอ
จนเงื่อนไขใน policy ไม่มีผลอะไร · โทเคนที่ไม่มีแถวคืออ่านไม่พบ ซึ่งให้ผลเดียวกัน

**เก็บเวลาหมดอายุเป็นค่าในแถว ไม่ใช่ตัวเลขในเงื่อนไขของ policy** — ตัวเลข 12 ชั่วโมง
กับ 7 วันจึงอยู่ในโค้ดที่เดียว และฐานข้อมูลเทียบกับ `now()` อย่างเดียว

RLS: `ENABLE` + `FORCE`

| policy | คำสั่ง | เงื่อนไข | ให้ใคร |
|---|---|---|---|
| `session_presented` | SELECT | `token_hash = presented_token_hash()` | `api`, `auth` |
| `session_renew` | UPDATE | USING: `token_hash = presented_token_hash() AND now() < idle_expires_at AND now() < absolute_expires_at`<br>WITH CHECK: `idle_expires_at <= absolute_expires_at` | `api` |
| `session_end_one` | DELETE | `token_hash = presented_token_hash()` | `api` |
| `session_end_all` | DELETE | `user_id = (SELECT s.user_id FROM sessions s WHERE s.token_hash = presented_token_hash() AND now() < s.idle_expires_at AND now() < s.absolute_expires_at)` | `api` |
| `session_issue` | INSERT | WITH CHECK `user_id = tiewtrade_current_user_id()` | **`auth` เท่านั้น** |
| `session_auth_owner` | ALL | USING และ WITH CHECK: `user_id = tiewtrade_current_user_id()` | **`auth` เท่านั้น** — ครอบทั้งการออก session และการเพิกถอนตอนเปลี่ยนรหัสผ่าน ซึ่งรู้ตัวตนแล้ว |

**policy แยกตามบทบาท (`TO ...`) จึงไม่ทำให้ `api` กว้างขึ้น** — ทดลองแล้ว: `api` ที่ตั้ง
`current_user_id` เป็นเจ้าของ session สามใบ ยังอ่านได้ใบเดียวตามโทเคนที่ถือ

**คำสั่งของแต่ละเส้นทาง — รูปของคำสั่งเป็นส่วนหนึ่งของการออกแบบ ไม่ใช่รายละเอียด**

| เส้นทาง | บทบาท | คำสั่ง | ผลที่ทดลองแล้ว |
|---|---|---|---|
| ออกเครื่องเดียว | `api` | `DELETE FROM sessions` (ตั้งเฉพาะ `presented_token_hash`) | ลบใบที่ถือ |
| ออกทุกเครื่อง | `api` | `DELETE FROM sessions` **ไม่มี `WHERE`** | ลบทุกใบของผู้ใช้นั้น |
| เปลี่ยนรหัสผ่าน (เก็บเครื่องปัจจุบัน) | `auth` | `DELETE FROM sessions WHERE token_hash <> :โทเคนปัจจุบัน` | **ลบใบอื่น เก็บใบปัจจุบัน ไม่แตะของผู้ใช้อื่น** |

เส้นทางที่สามใช้ `WHERE` ได้เพราะ policy ของ `auth` เป็นแบบตามเจ้าของ จึงเห็นใบพี่น้อง
**ของ `api` ใช้ `WHERE` ไม่ได้** เพราะ SELECT policy ของมันเห็นใบเดียว (ร่างแรกพลาดข้อนี้)

สิทธิ์ระดับคอลัมน์ — **นี่คือสิ่งที่กันการยึดบัญชี ไม่ใช่ policy**

```
GRANT SELECT ON sessions TO tiewtrade_api, tiewtrade_auth
GRANT UPDATE (last_seen_at, idle_expires_at) ON sessions TO tiewtrade_api
GRANT DELETE ON sessions TO tiewtrade_api, tiewtrade_auth
-- ไม่มี INSERT ให้ api · ไม่มี UPDATE บน user_id, token_hash, started_at, absolute_expires_at
```

**ตารางสิทธิ์ของบทบาทใหม่ให้ครบ — `policy` ไม่ทดแทน `GRANT`**
`0002`, `0004` และ `0001` ให้สิทธิ์เฉพาะบทบาทที่มีอยู่ตอนนั้น และ **ห้ามแก้ migration
ที่รันไปแล้ว** จึงต้องให้ใน `0007` ทั้งหมด:

| ของ | สิทธิ์ที่ `auth` ต้องได้ | ขาดแล้วเกิดอะไร |
|---|---|---|
| `tiewtrade_current_user_id()` | `EXECUTE` | **policy ทุกตัวที่เรียกฟังก์ชันนี้ล้ม** — `0001` ถอนจาก `PUBLIC` แล้วให้เฉพาะห้าบทบาทเดิม |
| ฟังก์ชันอ่านตัวแปรใหม่สองตัว | `EXECUTE` (ถอนจาก `PUBLIC` ก่อน) | policy ใหม่ล้ม |
| `users` | `INSERT (id)` | สมัครล้ม |
| `audit_events` | `INSERT (คอลัมน์ชุดเดียวกับที่ `0004` ให้)` และ `SELECT` | ลง audit ของการสมัคร/login ล้ม |
| `user_credentials` | `SELECT`, `INSERT (user_id, email, password_hash)`, `UPDATE (password_hash, updated_at)` | สมัคร/เปลี่ยนรหัสผ่านล้ม · **ไม่ให้ `UPDATE` บน `email` และ `user_id`** เพราะงานนี้ไม่เปลี่ยนอีเมล (Q-5) |
| `sessions` | `SELECT`, `INSERT (token_hash, user_id, started_at, idle_expires_at, absolute_expires_at)`, `DELETE` | ออก session และเพิกถอนล้ม · **ไม่ให้ `UPDATE`** เพราะการต่ออายุเป็นงานของ `api` |
| `auth_throttle` | `SELECT`, `INSERT`, `UPDATE`, `DELETE` | ตัวนับล้ม |

`api` ได้เฉพาะที่เขียนไว้ข้างบนเท่านั้น และ **ไม่ได้สิทธิ์ใด ๆ กับ `user_credentials`
และ `auth_throttle`**

**สิ่งที่ฐานข้อมูลบังคับได้จริง** (ยืนยันด้วยการทดลองกับ PostgreSQL 16 แล้ว ดู requirements):
`api` ออก session ไม่ได้ · เปลี่ยนเจ้าของไม่ได้ · ต่ออายุเกินเพดานรวมไม่ได้ ·
ต่ออายุแถวที่หมดอายุหรือถูกเพิกถอนแล้วไม่ได้ · ออกทุกเครื่องได้เฉพาะเมื่อถือโทเคนที่ยังใช้ได้

#### 1.4 กฎการเขียนคำสั่งสองข้อที่ลืมแล้วพังเงียบ

| กฎ | ถ้าลืม | ด่าน |
|---|---|---|
| ออกทุกเครื่องต้องเป็น `DELETE FROM sessions` **ไม่มี `WHERE`** | PostgreSQL นำ SELECT policy มาใช้ด้วย → ลบได้แถวเดียวเงียบ ๆ | เทสต์ที่มีสาม session แล้วต้องเหลือศูนย์ (RQ-19) |
| ห้ามมี SELECT policy ที่อ้าง `sessions` เอง | `infinite recursion detected in policy` | เทสต์ที่อ่าน session สำเร็จหลัง migration (RQ-20) |

### 1.5 logout เพิกถอนจริง (ตอบข้อ 1.1)

**เพิกถอน = ลบแถว** ทั้งสามเส้นทาง (ออกเครื่องเดียว, ออกทุกเครื่อง, เปลี่ยนรหัสผ่าน)
ไม่ใช่แค่ลบ cookie — เทสต์เก็บโทเคนไว้ **ก่อน** logout แล้วยิงซ้ำ ต้องได้
"ไม่รู้จัก session" (RQ-15) · เหตุผลที่ลบไม่ใช่ทำเครื่องหมาย: แถวที่เพิกถอนแล้ว
ไม่มีใครต้องอ่านอีก และตารางที่โตเรื่อย ๆ ต้องมีคนมาเก็บกวาด

### 1.6 การเปลี่ยนรหัสผ่านและการแข่งกับ login ที่กำลังดำเนินอยู่ (RQ-22)

ทั้งสองเส้นทางอยู่บนบทบาท `auth` และ **ต้องล็อกแถว credential ของผู้ใช้นั้นก่อนตรวจ
รหัสผ่านเสมอ** — แต่ลำดับมีข้อบังคับที่ไม่ชัดเจนจากภายนอก:

> **`SELECT ... FOR UPDATE` ต้องผ่าน policy ของ `UPDATE` ด้วย** ไม่ใช่แค่ของ `SELECT`
> ตอน login เรารู้แค่อีเมล ยังไม่ได้ตั้งผู้ใช้ปัจจุบัน จึง **ล็อกไม่ได้ และได้ศูนย์แถว
> โดยไม่มีข้อผิดพลาด** ซึ่งโค้ดจะเข้าใจผิดว่า "ไม่มีบัญชีนี้"
> (ทดลองกับ PostgreSQL 16 แล้ว: อ่านเฉย ๆ ได้แถว · `FOR UPDATE` ได้ศูนย์แถว)

ลำดับที่ใช้ได้ **สามขั้น** และต้องเขียนกำกับไว้ในโค้ด:

```
1. อ่านแบบไม่ล็อกด้วย presented_email  → ได้ user_id (ยังไม่เชื่อรหัสผ่าน)
2. ตั้งผู้ใช้ปัจจุบันเป็น user_id นั้น
3. อ่านซ้ำแบบ FOR UPDATE ด้วย user_id → ได้แฮชที่อยู่ใต้ล็อก แล้วจึงตรวจรหัสผ่าน
```

ขั้นที่ 3 ต้อง **อ่านแฮชใหม่** ไม่ใช่ใช้ค่าจากขั้นที่ 1 เพราะค่าจากขั้นที่ 1 อาจเก่าไปแล้ว

เมื่อทั้งสองเส้นทางล็อกแถวเดียวกัน จึงเกิดลำดับที่แน่นอน:

| ถ้าใครได้ล็อกก่อน | ผล |
|---|---|
| การเปลี่ยนรหัสผ่าน | login ที่รออยู่จะอ่านแฮชใหม่ → รหัสผ่านเก่าใช้ไม่ได้ → **ไม่มี session ใหม่** |
| login | ได้ session ด้วยรหัสผ่านเก่าก่อน แล้วการเปลี่ยนรหัสผ่านที่ตามมา **เพิกถอน session นั้นด้วย** เพราะลบ session อื่นทั้งหมดใน transaction เดียวกัน |

ทั้งสองทางไม่มีช่องที่ session ที่ออกด้วยรหัสผ่านเก่ารอดอยู่หลังการเปลี่ยนเสร็จ
**ร่างแรกพูดถึงล็อกแถวของตัวนับอัตราการเรียกเท่านั้น ซึ่งไม่ใช่แถวนี้**

### 1.7 ปรับทางสร้างผู้ใช้ให้ร่วม transaction เดียวกับการสมัคร

`create_user()` ของ F-03 **เปิด transaction ของตัวเอง** (`async with user_session(...)`)
เรียกจากในเส้นทางสมัครจึงได้ **สอง transaction** ถ้าการสร้าง credential หรือ session
ล้มเหลวภายหลัง จะเหลือแถว `users` กับบันทึก `USER_CREATED` ที่ commit แล้ว —
ผู้ใช้ที่มีตัวตนแต่เข้าสู่ระบบไม่ได้ และสมัครอีเมลเดิมซ้ำก็ไม่ได้

**แยกเป็นสองชั้น:** `create_user_in(session, user_id)` ทำงานบน session ที่ส่งเข้ามา
และ `create_user(engine, ...)` เดิมกลายเป็นตัวห่อบาง ๆ ที่เปิด session แล้วเรียกตัวแรก —
**ลายเซ็นเดิมไม่เปลี่ยน เทสต์ของ F-03 จึงต้องยังเขียวทั้งชุด** และเส้นทางสมัครเรียก
ตัวที่รับ session เพื่อให้ทุกอย่างอยู่ใน transaction เดียว

### 2. จุดเดียวที่ตอบว่า "ผู้ใช้คนไหน" (ตอบข้อ 2)

- **middleware เดียว** อ่าน cookie → แฮช → `session_owner` → ได้ `Authenticated(user_id, token_hash)`
- **ค่าเริ่มต้นคือปฏิเสธ**: เส้นทางที่ไม่อยู่ใน **รายการสาธารณะ** ต้องมี `Authenticated`
  มิฉะนั้นตอบ 401 — รายการสาธารณะมีสี่เส้นทาง: `/health`, สมัคร, login, และ CSRF token
- **ลืมใช้ไม่ได้เพราะมีสองชั้น**: middleware บังคับตอนรัน และ **เทสต์เดินรายการ
  `app.routes` ทุกเส้นทาง** แล้วยืนยันว่าแต่ละเส้นทางอยู่ในรายการสาธารณะ หรือถูก
  middleware คุ้มครอง — เพิ่ม endpoint ใหม่โดยไม่คิดเรื่องสิทธิ์แล้วเทสต์แดงทันที
- CSRF: โทเคนใน cookie ที่อ่านได้ (ไม่ `httpOnly`) และต้องส่งกลับมาใน header
  สำหรับทุกคำขอที่ไม่ใช่ `GET`/`HEAD` — เทียบแบบ constant-time

**กฎการต่ออายุ session (Q-2 ข้อ "poll ราคาไม่นับเป็นการใช้งาน")**
ค่าเริ่มต้นของทุกเส้นทางคือ **ไม่ต่ออายุ** เส้นทางที่เป็นการกระทำของผู้ใช้ประกาศ
`renews=True` ของตัวเอง — ตรงข้ามกับการให้ค่าเริ่มต้นเป็นต่ออายุแล้วไปยกเว้นเส้นทางที่ poll
ซึ่งเป็นการยกเว้นที่คนเพิ่มเส้นทางใหม่ต้องจำ · F-10 ที่เพิ่ม endpoint ราคาจึงต่ออายุ
ไม่ได้โดยไม่ตั้งใจ และ **เทสต์พิมพ์รายการเส้นทางที่ต่ออายุออกมาให้เห็นในรีวิว**

### 3. `SET LOCAL` ตั้งและล้างทุกคำขอ (ตอบข้อ 3)

- ใช้ `user_session()` ของ F-03 ตามเดิมสำหรับงานหลังรู้ตัวตน
- เพิ่ม `presented_session()` สำหรับช่วงก่อนรู้ตัวตน ซึ่งตั้ง
  `tiewtrade.presented_token_hash` (และ `tiewtrade.presented_email` เฉพาะตอน login)
  ด้วย `set_config(..., is_local => true)` ตัวเดียวกับที่ F-03 ใช้
- **ค่าหมดอายุเมื่อ transaction จบ** จึงไม่ค้างไปถึงผู้ใช้คนถัดไปที่ได้ connection เดิม —
  เทสต์เปิด transaction ที่สองบน connection เดิมแล้วต้องอ่านไม่ได้ทั้งสองตัวแปร

### 4. ตัวนับอัตราการเรียก (ตอบข้อ 4 และ 8)

**เก็บในฐานข้อมูล ไม่ใช่ในกระบวนการ** เพราะตัวนับในกระบวนการเดียวหลบได้ด้วยการยิง
ไปอีกกระบวนการ (บทเรียนเดียวกับตัวกั้นอัตราของ F-35 ที่ยอมรับข้อจำกัดนี้ไว้)

ตาราง `auth_throttle`

| คอลัมน์ | หมายเหตุ |
|---|---|
| `bucket_kind` | `ACCOUNT` / `IP` / `SIGNUP_IP` |
| `bucket_key` | **แฮชของอีเมลหรือของ IP** — เพื่อไม่ให้มีอีเมลหรือ IP เป็นตัวอักษรอยู่ในตาราง **ไม่ใช่การปกปิด** เพราะเดาอีเมลแล้วแฮชเทียบได้ |
| `window_started_at`, `failures`, `next_allowed_at` | ตัวนับและเวลาที่ยอมรับคำขอถัดไป |

**ตารางนี้ไม่อยู่ใต้ RLS — แก้เหตุผลตามรีวิว 2026-10-03** (ถ้อยคำเดิมอยู่ท้ายหัวข้อนี้)

เจ้าของอนุมัติข้อยกเว้นจาก `database.md` หัวข้อ 3 ด้วยสองเหตุผลนี้:

1. **หน้าที่ของตารางคือตัวนับร่วมของช่วงก่อนยืนยันตัวตน** — ต้องนับอีเมลที่ยังไม่มีบัญชี
   และ IP ที่คนหลายคนใช้ร่วมกัน การบังคับให้ทุกแถวมีเจ้าของใน `users`
   **ขัดกับหน้าที่ของตารางเอง** ไม่ใช่แค่ไม่สะดวก
2. **ขอบเขตความเสียหายถูกจำกัดด้วยสิทธิ์** — เฉพาะบทบาท `auth` แตะได้
   บทบาทที่รับคำขอทั่วไปไม่มีสิทธิ์ใด ๆ กับตารางนี้

**สองข้อที่เคยเขียนไว้แต่ใช้เป็นเหตุผลไม่ได้:**

| ถ้อยคำเดิม | ทำไมใช้ไม่ได้ |
|---|---|
| "ไม่มีคอลัมน์เจ้าของ จึงไม่ใช่ตารางข้อมูลผู้ใช้" | เป็น **ผลของการออกแบบ** ไม่ใช่หลักฐานว่าไม่มีข้อมูลที่เกี่ยวกับผู้ใช้ |
| "แถวหมดอายุเองตามหน้าต่างเวลา" | **ไม่ตรงกับโค้ด** — `claim()` รีเซ็ตตัวนับเมื่อถูกเรียกอีกครั้งหลังหน้าต่างผ่านไป และการลบแถวเกิดเฉพาะตอนเข้าสู่ระบบสำเร็จของถังบัญชี · **แถวของ IP ที่ไม่กลับมาอีกค้างอยู่** จึงต้องมีงานเก็บกวาดก่อนปล่อยผู้ใช้จริง (บันทึกใน `roadmap.md`) |

ส่วนการแฮชใน `bucket_key` ยังคงไว้เพื่อไม่ให้มีอีเมลหรือ IP เป็นตัวอักษรอยู่ในตาราง
**ไม่ใช่การปกปิด** เพราะเดาอีเมลแล้วแฮชเทียบได้

คีย์ไม่ซ้ำคือ `(bucket_kind, bucket_key)`

**การหน่วงบังคับข้ามคำขอที่ยิงพร้อมกัน (RQ-23)** — ทุกครั้งที่จะตรวจรหัสผ่าน ต้อง
**สร้างหรือล็อกแถวของ bucket ด้วยคำสั่งเดียว**:

```
INSERT INTO auth_throttle (bucket_kind, bucket_key, window_started_at, failures, next_allowed_at)
VALUES (...)
ON CONFLICT (bucket_kind, bucket_key) DO UPDATE SET bucket_key = auth_throttle.bucket_key
RETURNING failures, next_allowed_at, window_started_at
```

`SELECT ... FOR UPDATE` อย่างเดียวไม่พอ เพราะ **ล็อกได้เฉพาะแถวที่มีอยู่แล้ว** คำขอแรก
ที่มาพร้อมกันบนตารางว่างจะไม่มีอะไรให้ล็อก · `ON CONFLICT DO UPDATE` ล็อกแถวที่ชนด้วย
จึงได้ทั้งการสร้างและการล็อกในคำสั่งเดียว แล้วคำขออื่นเข้าคิวที่ล็อกนั้น
**ไม่ใช่การ `sleep` ทีละคำขอซึ่งขนานกันได้**

**ตัวนับความล้มเหลวต้อง commit แม้คำขอนั้นถูกปฏิเสธ** — จึงอยู่ใน transaction ของตัวเอง
ไม่ใช่ transaction เดียวกับการตรวจรหัสผ่าน เพราะถ้า transaction นั้นถูกยกเลิก
ตัวนับจะหายไปด้วย แล้วการเดารหัสผ่านก็ไม่ถูกนับเลย

ตัวเลขตาม Q-4 — บัญชี: ผิด 5 → หน่วง 1, 2, 4, 8 เพดาน 10 วินาที ล้างเมื่อสำเร็จหรือครบ
15 นาที · IP: ผิด 20 ใน 15 นาที → ปฏิเสธ 15 นาที **สำเร็จไม่ล้าง** · สมัคร: 5 ครั้ง/ชั่วโมง/IP

### 5. รหัสผ่านและรายการที่ห้าม (ตอบข้อ 7)

- `argon2-cffi` เป็น dependency ใหม่ · **ค่าความแรงที่เสนอ (argon2id)**:
  `time_cost=3`, `memory_cost=65536` (64 MiB), `parallelism=4`, `hash_len=32`, `salt_len=16`
  — ชุดที่สองที่ RFC 9106 แนะนำ · **งบเวลาที่ยอมรับ: ประมาณ 100 มิลลิวินาทีต่อครั้ง
  บนเครื่อง CI** แรงกว่านี้คือการทำ DoS ใส่ตัวเองเพราะทุก login จ่ายเวลานั้น
  ค่าเหล่านี้อยู่ที่เดียวและมีเกณฑ์วัดใน `validation.md`
- **เวลาตอบของ login ต้องไม่บอกว่าอีเมลมีบัญชีหรือไม่** — ถ้าไม่พบอีเมล
  **ต้องคำนวณ argon2 กับแฮชหลอกคงที่เสมอ** ไม่ใช่ตอบกลับทันที มิฉะนั้นข้อความที่
  เหมือนกันก็ไร้ความหมายเพราะเวลาต่างกันชัดเจน (RQ-8)
- **โทเคน session**: สุ่มจาก `secrets.token_urlsafe(32)` (256 บิต) ส่งให้เบราว์เซอร์
  ครั้งเดียว **เก็บในฐานข้อมูลเป็นแฮช SHA-256 เท่านั้น** ไม่มีที่ไหนเก็บโทเคนจริง
- **อีเมล**: ยาวไม่เกิน 254 ตัวอักษร (ขอบที่ใช้ได้จริงตาม RFC 5321) ตรวจก่อนแตะฐานข้อมูล
- **แยกสองเรื่องที่ร่างแรกรวมกันไว้ผิด**:

  | เรื่อง | ใช้ที่ไหน | ทำอะไร |
  |---|---|---|
  | **ยอมรับรหัสผ่านใหม่** | สมัคร · เปลี่ยนรหัสผ่าน (ค่าใหม่) | normalise NFC → นับ code points → ความยาว 15–1,024 → **ตรวจรายการที่ห้าม** → argon2 |
  | **ตรวจรหัสผ่านที่มีอยู่** | login · ยืนยันรหัสผ่านปัจจุบันตอนเปลี่ยน | normalise NFC → **เทียบแฮชเท่านั้น ไม่ตรวจความยาวและไม่ตรวจรายการที่ห้าม** |

  เหตุผล: ถ้าตรวจรายการที่ห้ามตอน login ด้วย **วันที่อัปเดตรายการแล้วรหัสผ่านเดิมของ
  ผู้ใช้ติดอยู่ในรายการ ผู้ใช้จะเข้าสู่ระบบไม่ได้และเปลี่ยนรหัสผ่านก็ไม่ได้** ซึ่งในงานนี้
  ไม่มีทางกู้บัญชีเลย (Q-6) · NIST กำหนดให้ตรวจรายการ **เมื่อสร้างหรือเปลี่ยน**
  รหัสผ่าน ไม่ใช่เมื่อยืนยัน
- **รายการที่ห้าม — แหล่งที่เลือกและวิธีทำ**

  | เรื่อง | ค่าที่เสนอ |
  |---|---|
  | แหล่ง | **SecLists** `Passwords/Common-Credentials/10-million-password-list-top-100000.txt` |
  | สัญญาอนุญาต | MIT (ของ SecLists) |
  | รุ่น | **ปักด้วย commit SHA ของ SecLists** ไม่ใช่ "ล่าสุด" เพราะรายการต้องทำซ้ำได้ |
  | วิธีแปลงก่อนแฮช | ตัดอักขระท้ายบรรทัด → **normalise NFC** → **ไม่แปลงตัวพิมพ์** (รหัสผ่านแยกตัวพิมพ์) → **ตัดรายการที่สั้นกว่า 15 code points ออก** เพราะกฎความยาวปฏิเสธไปก่อนแล้ว → ตัดรายการซ้ำ → `SHA-256` เป็นเลขฐานสิบหก → เรียง |
  | ไฟล์กำกับ | URL, commit SHA, วันที่ดึง, **จำนวนรายการต้นทาง**, **จำนวนที่เหลือหลังตัด**, สัญญาอนุญาต |

  **ข้อที่ต้องรู้ตรง ๆ:** เมื่อขั้นต่ำคือ 15 ตัวอักษร รหัสผ่านยอดนิยมส่วนใหญ่ถูกกฎ
  ความยาวปฏิเสธไปก่อนแล้ว **จำนวนที่เหลือในรายการจึงอาจน้อยมาก** — ไฟล์กำกับที่บันทึก
  สองจำนวนทำให้เห็นข้อนี้ตอนรีวิว ไม่ใช่ซ่อนไว้ · สคริปต์
  `scripts/refresh_password_blocklist.py` ที่คนสั่งเองใช้ดึงและแปลง (รูปแบบเดียวกับ
  สคริปต์เก็บข้อมูลของ F-35)
- เก็บแฮชไม่เก็บรหัสผ่านต้นฉบับ เพื่อไม่ให้ repo กลายเป็นคลังรหัสผ่าน

### 6. ที่ที่ TOTP ของ F-06 จะเสียบเข้ามา (ตอบข้อ 6)

| สิ่งที่เตรียมไว้ | F-06 ต่อยอดอย่างไร |
|---|---|
| `Authenticated` เป็น dataclass ที่ middleware คืน | เพิ่มช่องได้โดยผู้เรียกเดิมไม่ต้องแก้ |
| middleware เดียวที่ตัดสินสิทธิ์ | เพิ่มรายการ "เส้นทางที่ต้องยืนยัน TOTP ซ้ำ" ที่เดียว |
| เส้นทาง login อยู่ในโมดูลของตัวเองบนบทบาท `auth` | เพิ่มขั้นที่สองของ login ในโมดูลเดียวกัน |
| ตาราง `sessions` มี `started_at` แยกจาก `last_seen_at` | F-06 เพิ่มคอลัมน์เวลายืนยัน TOTP ได้โดยไม่กระทบ policy ที่มี |

**ไม่เพิ่มคอลัมน์หรือ endpoint เผื่อไว้ในงานนี้** ของที่ยังไม่มีผู้ใช้คือของที่เดาผิดได้ฟรี

| อะไรอาจพัง | จะรู้ได้อย่างไร |

| `api` ได้สิทธิ์เกินโดยไม่มีใครเห็น | เทสต์ที่ลองทำสิ่งที่ห้ามทุกข้อแล้วต้องถูกฐานข้อมูลปฏิเสธ |

| ตัวนับอัตราการเรียกถูกหลบด้วยคำขอขนาน | เทสต์ยิงพร้อมกันแล้วนับจำนวนครั้งที่ตรวจรหัสผ่านจริง |
| ผู้ใช้สองคนแย่งอีเมลเดียวกันพร้อมกัน | `UNIQUE` + เทสต์สมัครพร้อมกันสองคำขอ |

## แก้ตามรีวิวรอบสอง 2026-10-02 (7 ข้อ — ทดลองกับ PostgreSQL 16 จริงก่อนแก้)

| # | เดิมผิดอะไร | หลักฐาน / สิ่งที่แก้ |
|---|---|---|
| 1 | ล็อกแถว credential ตอน login ไม่ได้ เพราะ `FOR UPDATE` ต้องผ่าน policy ของ `UPDATE` ซึ่งต้องการผู้ใช้ปัจจุบัน | **ทดลอง: อ่านเฉย ๆ ได้แถว · `FOR UPDATE` ได้ศูนย์แถวโดยไม่มี error** → ข้อ 1.6 เปลี่ยนเป็นสามขั้น (อ่าน → ตั้ง context → ล็อกและอ่านซ้ำ) |
| 2 | เพิกถอน "เครื่องอื่นแต่เก็บเครื่องปัจจุบัน" ทำไม่ได้ด้วย policy ที่เสนอ | **ทดลอง: `auth` + policy ตามเจ้าของ สั่ง `DELETE ... WHERE token_hash <> :ปัจจุบัน` ได้ `DELETE 1` เก็บใบปัจจุบันและไม่แตะของผู้ใช้อื่น** · และ `api` ยังแคบเหมือนเดิมเพราะ policy แยกตามบทบาท |
| 3 | `create_user()` เปิด transaction ของตัวเอง → สมัครไม่เป็นก้อนเดียว | ข้อ 1.7 แยกเป็น `create_user_in(session, ...)` + ตัวห่อเดิม ลายเซ็นไม่เปลี่ยน |
| 4 | รายการสิทธิ์ไม่ครบ — ขาด `EXECUTE` ของ `tiewtrade_current_user_id()`, `INSERT` บน `sessions`, สิทธิ์รายคอลัมน์ของ `user_credentials` | ตารางสิทธิ์เต็มในข้อ 1.3 พร้อมคอลัมน์ "ขาดแล้วเกิดอะไร" |
| 5 | ตรวจรายการที่ห้ามตอน login → รายการที่อัปเดตแล้วอาจล็อกเจ้าของออกจากบัญชีถาวร | แยก **ยอมรับรหัสผ่านใหม่** จาก **ตรวจรหัสผ่านที่มีอยู่** (ข้อ 5) ตามที่ NIST กำหนด |
| 6 | ยังไม่ได้เลือกแหล่งและรุ่นของรายการที่ห้าม | SecLists (MIT) ปักด้วย commit SHA + วิธีแปลงหกขั้น + บันทึกสองจำนวน |
| 7 | `FOR UPDATE` ล็อกแถวที่ยังไม่มีไม่ได้ และตัวนับหายถ้า transaction ถูกยกเลิก | `INSERT ... ON CONFLICT DO UPDATE` เป็นตัวสร้างและล็อก · ตัวนับอยู่ใน transaction ของตัวเอง |
