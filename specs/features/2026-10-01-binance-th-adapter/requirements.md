# F-35 ตัวเชื่อม Binance TH — Requirements

สถานะ: **Approved** — เจ้าของอนุมัติ 2026-10-01
วันที่: 2026-10-01
งานใน roadmap: F-35 — ตลาดเดียวของระบบ, Spot เท่านั้น, `/api/v1`

---

## ทำไมต้องมี

F-33 วางสัญญาไว้แล้วสามชุด (ราคา, กระเป๋า, ข้อจำกัดของเหรียญ) แต่ **ยังไม่มีใครทำตาม
สัญญานั้นกับตลาดจริงเลย** ตอนนี้มีแต่ตัวแทนปลอมที่ใช้พิสูจน์สัญญา

งานนี้คือตัวเชื่อมตัวแรกและตัวเดียวของระบบ และเป็น **บททดสอบว่าสัญญาของ F-33
ออกแบบถูกหรือไม่** — ถ้าประกอบชื่อคู่เทรดของ Binance TH จาก `Symbol` ไม่ได้
หรือแปลรหัสข้อผิดพลาดของตลาดเข้าห้าชนิดไม่ได้ แปลว่าสัญญาผิด ไม่ใช่ตลาดผิด
และ F-33 `plan.md` สั่งไว้ว่าในกรณีนั้น **ให้หยุดและขออนุมัติเปลี่ยน ห้ามแอบใส่ชื่อดิบ
เข้ามาในชนิดกลาง**

**สามงานถัดไปรอตัวเชื่อมนี้** — F-09 (ดึงแท่งเทียน), F-10 (ราคาเรียลไทม์),
F-12 (กราฟ) ล้วนต้องมีราคาจากตลาดจริง

**คนที่เดือดร้อนถ้าไม่มี** — ทุกงานหลังจากนี้ เพราะระบบยังไม่เคยคุยกับตลาดจริงเลย
แม้แต่ครั้งเดียว และข้อสมมติทั้งหมดที่เขียนไว้ใน `mission.md` หัวข้อ 6
ยังไม่ถูกพิสูจน์ด้วยโค้ดของเราเอง

## สิ่งที่รู้แล้วเกี่ยวกับตลาดนี้

จาก `mission.md` หัวข้อ 6 (ตรวจจาก API จริง 2026-09-26) — **ไม่ต้องตรวจซ้ำ แต่ต้องใช้**

| เรื่อง | ค่าที่บันทึกไว้ |
|---|---|
| REST | `https://api.binance.th/api/v1/...` — เป็น `v1` ไม่ใช่ `v3` แบบ `.com` |
| WebSocket | `ws-api.binance.th` |
| คู่เทรด Spot | 519 คู่ สถานะ TRADING ทั้งหมด (รวม 11 คู่ที่จับกับ THB) |
| Futures | **ไม่มี** `fapi.binance.th` ไม่มีใน DNS และ `/fapi/` ตอบ 404 |
| ขีดจำกัด | 6,000 weight/นาที · 6,000 ออเดอร์/นาที · 1,000 ออเดอร์/10 วินาที |
| Sub-account | มี สูงสุด 5 บัญชีย่อย และบัญชีย่อยสร้าง API key ของตัวเองได้ |
| **เว็บเอกสาร API** | **มี** `https://www.binance.th/api-docs/en/` — แก้ข้อมูลใน `mission.md` แล้ว 2026-10-01 |

**ข้อมูลสองแถวในตารางนี้ถูกแก้เมื่อ 2026-10-01** (พบตอนรีวิว requirements ฉบับนี้):

1. **เอกสารทางการมีอยู่** ของเดิมบันทึกว่าไม่พบ เพราะหาจาก `docs.binance.th`
   และ `developers.binance.th` ซึ่งไม่ใช่ที่อยู่จริง — ร่างแรกของเอกสารฉบับนี้
   วางแผนทั้งหมดอยู่บนข้อสรุป "ไม่มีเอกสาร" ซึ่งผิด
2. **ขีดจำกัดการเรียกนับคนละมิติกัน** น้ำหนักนับ **ต่อ IP** (1,000 weight/10 วินาที,
   6,000 weight/นาที) ส่วนจำนวนออเดอร์นับ **ต่อบัญชี** และตัวเลขของออเดอร์
   อ่านจาก `/api/v1/exchangeInfo` ไม่ใช่ค่าที่เขียนไว้เอง

สิ่งที่อ่านจากเอกสารแล้วและมีผลกับงานนี้โดยตรง:

| เรื่อง | ค่าจากเอกสาร |
|---|---|
| ข้อผิดพลาด | ตอบเป็น JSON ที่มี `code` (ไม่ใช่ศูนย์แปลว่าล้มเหลว) กับ `msg` — **เอกสารไม่มีรายการรหัสทั้งหมด** |
| โดนจำกัดอัตรา | `429` เมื่อเกินเพดาน, `418` เมื่อ IP ถูกแบน ทั้งคู่มี `Retry-After` เป็นวินาที |
| ราคาล่าสุด | `/ticker/price` คืนแค่ `symbol` กับ `price` — **ไม่มีเวลา** (ดู Q-7) |
| รายการซื้อขายล่าสุด | `/trades` คืน `id`, `price`, `qty`, `quoteQty`, `time`, `isBuyerMaker`, `isBestMatch` · weight 1 |
| ข้อจำกัดของเหรียญ | `/exchangeInfo` มี `PRICE_FILTER`, `LOT_SIZE`, `MIN_NOTIONAL` · weight 10 |
| เวลาของเซิร์ฟเวอร์ | `/time` คืน `serverTime` · weight 1 |

## ขอบเขต

### ทำ

- ตัวเชื่อมใน `tiewtrade.venues.binance_th` ที่ **ทำตามสัญญาของ F-33** ไม่สร้างสัญญาใหม่
- การประกอบและถอดชื่อคู่เทรดระหว่าง `Symbol` กับรูปแบบของตลาด
- การแปลรหัสข้อผิดพลาดและสถานะ HTTP ของตลาดเข้าสู่ **ห้าชนิดกลางของ F-33**
- การจำกัดอัตราการเรียกตามเพดานที่บันทึกไว้ (ดู Q-4 เรื่องขอบเขต)
- **ข้อมูลตอบกลับที่บันทึกไว้** สำหรับเทสต์ปกติ และ **เทสต์สัญญากับตลาดจริงที่รันเป็นระยะ
  แยกจากเทสต์ปกติ** ตาม `testing.md` หัวข้อ 5
- ด่านที่บังคับว่าโค้ดเฉพาะตลาดไม่หลุดออกนอก package นี้
- **สองงานด่านที่ `roadmap.md` ฝากไว้กับงานนี้** (เพิ่มหลังรีวิว 2026-10-01):
  เลิกพึ่งรายชื่อโมดูลส่วนกลางที่เขียนมือ และให้ package ตัวเชื่อมประกาศคำศัพท์ของตัวเอง
  — งานนี้เป็นงานแรกที่เพิ่ม package ตัวเชื่อม จึงเป็นจุดที่สองเรื่องนั้นจะเริ่มเน่า

### ไม่ทำ

- **ไม่ทำส่วนที่ต้องใช้กุญแจของผู้ใช้** — ดู Q-1 ซึ่งเป็นข้อที่บล็อกได้จริง
- **ไม่ทำ WebSocket และการต่อกลับ** — เป็นงาน F-10 งานนี้ทำเฉพาะ REST
- **ไม่เก็บแท่งเทียน** — เป็นงาน F-09 และติด **NC-09**
- **ไม่ส่งออเดอร์** — สัญญาส่งออเดอร์ยังไม่มีเพราะติด **NC-08** (F-33 Q-6)
- **ไม่ทำ Futures** — ตลาดนี้ไม่มี และ `mission.md` หัวข้อ 6 ห้ามเขียนล่วงหน้า (**NC-12**)
- **ไม่ใช้ Testnet** — เจ้าของตัดสินแล้วว่าไม่ใช้ (`testing.md` หัวข้อ 5)
- ไม่ทำรายการเหรียญที่แพลตฟอร์มรองรับ — เป็นงาน **F-37** ต่างจากรายการที่ตลาดมี

## เรื่องที่เจ้าของตัดสินแล้ว (Q-1 ถึง Q-8)

**ตัดสินครบทุกข้อ (เจ้าของตัดสิน 2026-10-01)** รับแนวทางที่เสนอทั้งแปดข้อ
พร้อมข้อที่ต้องเขียนให้ชัดเพิ่ม ซึ่งเขียนไว้ในแต่ละข้อแล้ว ทางเลือกที่ไม่เลือกยังเก็บไว้ทั้งหมด

### Q-1 — งานนี้ทำส่วนที่ต้องใช้กุญแจของผู้ใช้หรือไม่ (ข้อที่บล็อกได้จริง)

สัญญาสามชุดของ F-33 ต้องการสิทธิ์ไม่เท่ากัน:

| สัญญา | ต้องใช้กุญแจไหม |
|---|---|
| ราคา | **ไม่ต้อง** — endpoint สาธารณะ |
| ข้อจำกัดของเหรียญ | **ไม่ต้อง** — endpoint สาธารณะ |
| กระเป๋า | **ต้องใช้** — ต้องลงลายเซ็นด้วย secret ของผู้ใช้ |

ปัญหาคือการจัดการกุญแจของผู้ใช้เป็นงาน **F-07** ซึ่งยังไม่ได้ทำ และยังติด **T-03**
(เก็บกุญแจเข้ารหัสไว้ที่ไหนบนเครื่องจริง) ส่วนการถอดรหัสทำได้เฉพาะใน `engine`
(`tech-stack.md` หัวข้อ 8) ซึ่งเป็น service ที่ `venues` พึ่งไม่ได้ (RQ-3)

| ทางเลือก | ผล |
|---|---|
| **ก. ทำเฉพาะสองสัญญาที่ไม่ต้องใช้กุญแจ** (ราคา, ข้อจำกัดของเหรียญ) | F-09, F-10, F-12 เดินได้ทันทีเพราะใช้แค่ราคา และไม่ต้องตัดสิน T-03 ก่อนเวลา **แลกกับ** ต้องกลับมาแตะ package นี้อีกครั้งตอนทำ F-07/F-08 |
| ข. ทำทั้งสามสัญญา โดยให้ตัวเชื่อมรับ "ตัวลงลายเซ็น" จากผู้เรียก | ได้ครบในรอบเดียว **แลกกับ** ต้องออกแบบว่ากุญแจเดินทางถึงตัวเชื่ออย่างไร ซึ่งเป็นการตัดสินแทน F-07 และ T-03 |
| ค. รอ F-07 เสร็จก่อนเริ่ม F-35 | ไม่ต้องตัดสินอะไรล่วงหน้า **แลกกับ** หยุด F-09, F-10, F-12 ที่ใช้แค่ราคา และ roadmap วาง F-35 ไว้ก่อน F-07 |

**ตัดสินแล้ว: ก.** (เจ้าของตัดสิน 2026-10-01) — ทำเฉพาะ endpoint สาธารณะ
คือ **ราคา** และ **ข้อจำกัดของคู่เทรด** · **ยังไม่ทำกระเป๋าและไม่ทำส่วนที่ใช้กุญแจ**

เหตุผลที่รับ: งานที่รออยู่ทั้งสามใช้แค่ราคากับข้อจำกัดของเหรียญ และการเลื่อน
ส่วนที่ต้องใช้กุญแจออกไปไม่ปิดประตูอะไร — สัญญากระเป๋าของ F-33 มีอยู่แล้ว
ตัวเชื่อมจะมาทำตามภายหลังได้โดยไม่ต้องแก้สัญญา

### Q-2 — ใช้ไลบรารี HTTP ตัวไหน

`httpx` อยู่ในโปรเจกต์แล้วแต่เป็น dev dependency (ใช้ทดสอบ FastAPI)
งานนี้ต้องเลื่อนขึ้นมาเป็น dependency จริง

**ตัดสินแล้ว: `httpx` เป็น runtime dependency** (เจ้าของตัดสิน 2026-10-01) เพราะมีอยู่แล้ว รองรับ async ตามที่สัญญาของ F-33 บังคับ (RQ-17 ของ F-33)
และเป็นตัวเดียวกับที่เทสต์ใช้อยู่ จึงไม่ต้องเรียนรู้สองตัว
ทางเลือกที่ไม่เลือก: `aiohttp` (เพิ่มของใหม่โดยไม่ได้อะไรเพิ่ม)

### Q-3 — รายการคู่เทรดและข้อจำกัดเก็บไว้นานแค่ไหน

ข้อจำกัดของเหรียญมาจาก endpoint ที่คืนรายการคู่เทรดทั้ง 519 คู่ในครั้งเดียว
ถ้าเรียกใหม่ทุกครั้งที่ต้องตรวจออเดอร์หนึ่งใบ จะเปลืองโควตาและช้า

| ทางเลือก | ผล |
|---|---|
| **ก. เก็บในหน่วยความจำของ process พร้อมเวลาหมดอายุที่ผู้เรียกกำหนด** | ไม่ต้องพึ่ง `infra` (RQ-3) และผู้เรียกเลือกได้ว่ายอมให้เก่าแค่ไหน **แลกกับ** แต่ละ process เก็บของตัวเอง |
| ข. เก็บลงฐานข้อมูล | ใช้ร่วมกันทั้งระบบ **แต่** `venues` พึ่ง `infra` ไม่ได้ ต้องให้ service เป็นคนเก็บ ซึ่งเป็นงาน F-09/F-37 |

**ตัดสินแล้ว: ก.** (เจ้าของตัดสิน 2026-10-01) — cache ในหน่วยความจำ
**ผู้เรียกกำหนดอายุ** และ **ไม่ตั้งเวลาหมดอายุเป็นค่าตายตัวในตัวเชื่อม** — ผู้เรียกส่งเข้ามา
ด้วยเหตุผลเดียวกับเกณฑ์ความเก่าของราคาใน F-33 Q-10

**สองพฤติกรรมที่ร่างแรกไม่ได้ตอบ (แก้หลังรีวิว 2026-10-01)** — ทั้งคู่ต้องตัดสินก่อนเขียน plan
เพราะผู้เรียกคือจุดตรวจออเดอร์ ซึ่งตัดสินใจเรื่องเงินจากค่าเหล่านี้:

| สถานการณ์ | ทางเลือก | ผมเสนอ |
|---|---|---|
| ของในหน่วยความจำหมดอายุแล้ว **และเรียกใหม่ไม่สำเร็จ** | คืนของเก่าเงียบ ๆ / คืนของเก่าพร้อมบอกว่าเก่า / **โยนข้อผิดพลาด** | **โยนข้อผิดพลาด** — ผู้เรียกจะได้ตัดสินใจเอง การคืนของเก่าเงียบ ๆ ทำให้จุดตรวจออเดอร์ใช้ข้อจำกัดที่หมดอายุโดยไม่รู้ตัว ซึ่งเป็นกรณีเดียวกับที่ F-33 ห้ามเรื่องราคาเก่า |
| คู่เทรดที่เคยมี **หายไปจากข้อมูลชุดใหม่** | คืนของเก่าต่อ / **ถือว่าไม่รู้จักคู่เทรดนั้น** | **ถือว่าไม่รู้จัก** (`VenueRejectedError` เหตุผล `UNKNOWN_SYMBOL`) และ **ลบของเก่าทิ้ง** เพราะตลาดถอดคู่เทรดมักเกิดตอนสภาพคล่องแย่ การใช้ข้อจำกัดเก่าต่อคือการเปิดไม้ในคู่ที่ตลาดไม่รับแล้ว |

**ข้อที่เจ้าของระบุเพิ่ม: เมื่อ refresh สำเร็จ ให้แทนข้อมูลชุดเดิมทั้งชุด**
ไม่ใช่ผสมของเก่ากับของใหม่ — คู่เทรดที่ถูกถอนออกต้องหายไปจาก cache ด้วย
เพราะการเก็บของเก่าไว้ปนกับของใหม่คือการให้จุดตรวจเห็นคู่เทรดที่ตลาดไม่รับแล้ว

**ข้อสังเกตที่ต้องเขียนไว้:** การ "ถือว่าไม่รู้จัก" ไม่ได้บังคับให้ผู้ใช้ปิดไม้ที่ค้างอยู่
`mission.md` หัวข้อ 6 สั่งไว้ชัดว่าไม้เดิมไม่ถูกแตะ — การห้ามเปิดไม้ใหม่เป็นเรื่องของ
จุดตรวจ ไม่ใช่ของตัวเชื่อม

### Q-4 — ตัวจำกัดอัตราการเรียกจริงอยู่ที่ไหน

**แต่ `plan.md` ต้องเสนอตัวกั้นที่จะใช้ตอนเรียกตลาดจริงมาให้ตรวจ และห้ามใช้ `NoRateLimit`**

สองเรื่องที่ร่างแรกไม่ได้ตอบ (แก้หลังรีวิว 2026-10-01):

**ก. งานนี้เรียกตลาดจริงสองที่ — ทั้งสองที่ต้องมีตัวกั้น ไม่ใช่ `NoRateLimit`**
F-33 เขียนกำกับไว้ว่า `NoRateLimit` **ห้ามใช้กับตลาดจริง** ฉะนั้นสองเส้นทางนี้
ต้องใช้ตัวกั้นที่นับจริงในกระบวนการเดียว (ไม่ต้องมีสภาพร่วมกันข้าม process
เพราะทั้งสองเส้นทางรันทีละตัวอยู่แล้ว):

| เส้นทางที่เรียกตลาดจริง | ใช้ตัวกั้นอะไร |
|---|---|

**ข. เพดานนับคนละมิติ — ร่างแรกเขียนผิด**

**จำนวนออเดอร์นับต่อบัญชี** ฉะนั้น:

  และตัวเลขเพดานออเดอร์ต้องอ่านจาก `/exchangeInfo` ตอนทำ ไม่ใช่เขียนไว้เอง

### Q-5 — ยืนยันรูปแบบข้อมูลและพฤติกรรมของตลาดอย่างไร

**แก้ฐานของคำถามนี้หลังรีวิว 2026-10-01** — ร่างแรกตั้งอยู่บนข้อสรุปว่าไม่มีเอกสาร
ซึ่งผิด เอกสารทางการมีอยู่ที่ `https://www.binance.th/api-docs/en/`

**เสนอ: ใช้เอกสารเป็นฐาน และใช้ข้อมูลตอบกลับจริงเป็นหลักฐานประกอบ — ไม่ใช่เลือกอย่างใดอย่างหนึ่ง**

| ใช้ทำอะไร | มาจากไหน |
|---|---|
| ชื่อ endpoint, ชื่อฟิลด์, weight ของแต่ละการเรียก, ความหมายของ 429/418 | **เอกสาร** |
| รูปร่างข้อมูลจริงที่ตลาดส่งมา (รวมฟิลด์ที่เอกสารไม่ได้เขียน) | **ข้อมูลตอบกลับที่บันทึกไว้** |
| รหัสข้อผิดพลาดที่เจอจริง | **ข้อมูลตอบกลับที่บันทึกไว้** เพราะเอกสารไม่มีรายการรหัสทั้งหมด |

**ข้อที่รีวิวชี้และผมเห็นด้วย: การบันทึกคำตอบที่สำเร็จครั้งเดียวพิสูจน์ไม่ได้ครบ**
มันไม่บอกว่า weight ที่เราประกาศถูก และไม่บอกว่าการแปลข้อผิดพลาดถูก ฉะนั้นต้องมี:

- **บันทึกคำตอบของกรณีที่ล้มเหลวด้วย** ไม่ใช่เฉพาะกรณีสำเร็จ — อย่างน้อย
  คู่เทรดที่ไม่มีจริง และคำขอที่ผิดรูป ซึ่งเรียกได้โดยไม่ต้องมีกุญแจและไม่เสี่ยงเงิน
- **ตรวจ weight จาก response header** (`X-MBX-USED-WEIGHT-*`) ตอนบันทึก
  **แต่เทียบตรง ๆ กับ weight ของ endpoint ไม่ได้** เพราะ header เป็นยอดสะสมของ IP
  ในหน้าต่างนั้น ไม่ใช่ต้นทุนของคำขอเดียว — วิธีวัดที่ใช้จริงและกรณีที่ **สรุปไม่ได้**
  อยู่ใน `plan.md` ข้อ 2.1 (แก้หลังรีวิว 2026-10-01)
- **ไม่พยายามทำให้ตลาดตอบ 429 เพื่อเก็บตัวอย่าง** เพราะ 418 คือการถูกแบน IP

**อนุมัติแล้ว** (เจ้าของตัดสิน 2026-10-01) — เก็บข้อมูลจากเครื่องนี้ได้
ภายใต้เงื่อนไขสามข้อ: **เฉพาะ endpoint สาธารณะที่งานนี้ต้องใช้** · **ไม่มี credential
ในคำขอใด ๆ** · **ไม่ส่งคำสั่งซื้อขายทุกรูปแบบ**

### Q-7 — ราคามาจาก endpoint ไหน (ข้อที่บล็อก plan)

F-33 บังคับว่าราคาต้องพา **เวลาของตลาด** มาด้วย และ **ความเก่าตัดสินด้วยเวลานั้น**
(F-33 Q-10, RQ-7) แต่ `/ticker/price` คืนแค่ `symbol` กับ `price` **ไม่มีเวลาเลย**

| ทางเลือก | ผล |
|---|---|
| **ก. `/trades` เอารายการล่าสุด** — ได้ `price` กับ `time` ของรายการนั้น weight 1 | **ได้เวลาของราคาจริง** คือเวลาที่การซื้อขายนั้นเกิดที่ตลาด ตรงกับความหมายที่ F-33 ต้องการ **แลกกับ** ราคาที่ได้คือราคาที่เพิ่งซื้อขายจริง ไม่ใช่กลางของ bid/ask |

| ค. `/ticker/price` แล้วเติมเวลาเอง (เวลาที่เรารับ หรือ `/time`) | **ห้าม** — เป็นกรณีที่ F-33 Q-10 ยกมาเป็นเหตุผลว่าทำไมต้องมีสองเวลา: ราคาที่ตลาดค้างส่งมา 10 วินาทีจะดูใหม่เอี่ยมทันที |

**ตัดสินแล้ว: ก.** (เจ้าของตัดสิน 2026-10-01) — ใช้ **รายการล่าสุดจาก `/trades`**
เป็นแหล่งราคาและเวลาที่การซื้อขายนั้นเกิด และถ้าในอนาคตต้องใช้ราคากลางของ bid/ask
(เช่นตอนคิด PnL ที่ยังไม่ปิดไม้) ให้เป็นความสามารถเพิ่มที่มีผู้ใช้จริงก่อน

**สองข้อที่เจ้าของระบุเพิ่ม:**

1. **ไม่มีรายการซื้อขายเลย → `VenueUnavailableError`** (เจ้าของตัดสิน 2026-10-01)
   และ **ขยายความหมายของชนิดนั้นใน F-33** ให้ครอบ "ตลาดหรือข้อมูลที่ร้องขอ
   ไม่พร้อมใช้งานชั่วคราว" · **ห้ามคืนราคาสำรอง ห้ามตีความว่าไม่รู้จักคู่เทรด
   และห้ามถือว่า response ผิดรูป** · ยังไม่เพิ่ม `VenueNoPriceError`
2. **ห้ามใช้เวลาที่ระบบรับหรือ `serverTime` แทนเวลาของราคาเด็ดขาด** แม้ในกรณีที่
   ข้อมูลไม่ครบ — ถ้าไม่มีเวลาของราคา ก็ไม่มีราคาที่ใช้ตัดสินได้

> ข้อนี้ **บล็อก plan** เพราะเลือกผิดแล้วกฎ "ไม่มีราคาที่เชื่อถือได้ ห้ามเปิดไม้ใหม่"
> (`trading-safety.md` หัวข้อ 6) จะทำงานบนเวลาที่ไม่ใช่เวลาของราคา

### Q-8 — ข้อผิดพลาดที่ยังไม่รู้จักแปลเป็นอะไร (ข้อที่บล็อก plan)

เอกสารมี `code` กับ `msg` แต่ **ไม่มีรายการรหัสทั้งหมด** ฉะนั้นจะมีรหัสที่เราไม่รู้จักแน่นอน
และ **ไม่มีชนิดกลางชนิดเดียวที่ใช้แทนได้ทุกกรณี** เพราะสี่กรณีนี้มีความหมายคนละอย่าง

| กรณี | ความหมาย | ชนิดที่ผมเสนอ |
|---|---|---|
| ตลาดตอบมาแล้วด้วยรหัสที่เราไม่รู้จัก (มี HTTP response) | **รู้แน่ว่าคำขอไม่สำเร็จ** และตลาดได้รับคำขอแล้ว | `VenueRejectedError` — แต่ **เหตุผลกลางมีแค่สามค่า** (ไม่รู้จักคู่เทรด / ผิดข้อจำกัด / เงินไม่พอ) จึงยังไม่มีค่าไหนตรง → **ต้องเพิ่มค่าที่สี่ใน F-33 ซึ่งต้องขออนุมัติเปลี่ยน F-33** |
| HTTP error ที่ไม่ใช่ 4xx ของธุรกิจ (5xx, 502, 503) | ตลาดใช้งานไม่ได้ชั่วคราว ยังไม่รู้ว่าคำขอถึงหรือไม่ | `VenueUnavailableError` สำหรับการอ่าน · แต่สำหรับคำขอที่เปลี่ยนสถานะ ต้องเป็น `VenueOutcomeUnknownError` |
| timeout หรือเน็ตหลุดหลังส่งไปแล้ว | **ไม่รู้ผล** ห้ามเดา ห้ามส่งซ้ำ | `VenueOutcomeUnknownError` |
| ตลาดตอบมาแต่รูปแบบข้อมูลผิดจากที่คาด | สัญญาของตลาดเปลี่ยน หรือเราอ่านผิด | **ยังไม่มีชนิดไหนตรง** — ดูข้อถัดไป |

**สองเรื่องที่ต้องตัดสิน:**

1. **รหัสที่ไม่รู้จัก** ให้เพิ่มเหตุผลกลางค่าที่สี่ใน F-33 (เช่น "ตลาดปฏิเสธด้วยเหตุผล
   ที่ยังไม่ได้แปล") หรือให้ใช้ `VenueUnavailableError` ไปก่อน (ซึ่ง **ผิดความหมาย**
   เพราะตลาดตอบมาแล้ว ไม่ใช่ติดต่อไม่ได้)
2. **รูปแบบข้อมูลผิด** ถือเป็นชนิดไหน — ผมเห็นว่าควรเป็นชนิดใหม่ของ F-33
   เพราะมันไม่ใช่ความผิดของคำขอและไม่ใช่ปัญหาการเชื่อมต่อ แต่เป็นสัญญาที่ไม่ตรงกัน
   ซึ่งต้องแจ้งคนให้มาดู ไม่ใช่ลองใหม่

**ตัดสินแล้ว: เปิดให้เสนอการเปลี่ยนแปลง F-33 ได้** (เจ้าของตัดสิน 2026-10-01)

**ตลาดตอบมาแต่รูปแบบข้อมูลผิด**

**การนับหลังการเปลี่ยนนี้** (แก้หลังรีวิว 2026-10-01 ให้ตรงกันทั้งสามเอกสาร):

### Q-6 — เทสต์สัญญากับตลาดจริงรันที่ไหนและเมื่อไหร่

`testing.md` หัวข้อ 5 สั่งว่าต้องมีเทสต์ที่ตรวจว่ารูปแบบข้อมูลของตลาดยังเหมือนเดิม
**รันเป็นระยะ ไม่ใช่ทุกครั้งที่ push**

**ตัดสินแล้ว: งาน CI แยก รันรายวันและสั่งด้วยมือได้** (เจ้าของตัดสิน 2026-10-01)

เหตุผล: ถ้าเอาไปรวมกับด่านปกติ ตลาดล่มหรือเน็ตมีปัญหาจะกลายเป็น "ด่านแดง"
ซึ่งสอนให้คนเลิกเชื่อสีแดง (บทเรียนจาก flake ของ F-33)

**สองข้อที่เจ้าของระบุเพิ่ม:**

2. **ต้องระบุว่าผู้ดูแลเห็นผลได้อย่างไร** ไม่ใช่แค่ "งานแดงใน CI" — `plan.md`

## Needs Clarification ที่พบตอนลงมือ (2026-10-01)

### NC-13 คู่เทรดจริงที่ตลาดรายงาน `stepSize` เป็นศูนย์ — **ตัดสินแล้ว 2026-10-01**

**สิ่งที่พบ:** `/exchangeInfo` ของจริงมีคู่ที่สถานะ `TRADING` สองคู่ (`HYPEUSDC`, `HYPEUSDT`)
รายงาน `LOT_SIZE.stepSize` เป็น `"0.0"` ส่วน `minQty` เป็น `0.001` ตามปกติ

**ที่มันขัดกับอะไร:** `SymbolConstraints` ของ F-33 บังคับว่า **ขั้นของปริมาณต้องมากกว่าศูนย์**
และ `plan.md` ข้อ 3 ของงานนี้กำหนดว่า **คู่ไหนที่อ่านไม่ครบ ทำให้ทั้งชุดเป็น
`VenueProtocolError`** สองข้อนี้รวมกันทำให้ **อ่านข้อจำกัดของคู่เทรดใดเลยไม่ได้**
ตั้งแต่คู่แรก เพราะอ่านทั้งชุดในคราวเดียว

**มันบล็อกอะไร:** เส้นทาง `SymbolConstraintSource` ทั้งเส้น และเทสต์สัญญารายวัน
ส่วนเส้นทางราคายืนยันแล้วว่าทำงานกับตลาดจริงได้ (รวมการวัด weight ที่ได้ผล "ตรง")

**ห้ามเดาแทนเจ้าของ** เพราะการตัดสินว่าคู่เทรดไหนระบบถือว่าเทรดได้เป็นข้อกำหนด
เรื่องความเสี่ยง ไม่ใช่รายละเอียดการเขียนโค้ด (`AGENTS.md` กฎข้อ 2)

**เจ้าของตัดสิน: อ่านทีละคู่ที่ถูกถาม**

| เรื่อง | ที่ตัดสิน |
|---|---|
| ตอนอ่าน `/exchangeInfo` | เก็บคู่เทรดไว้ใน **รูปดิบที่ตลาดส่งมา** ตรวจแค่รูปของซองจดหมาย (เป็นวัตถุ · มีรายการคู่เทรด · ทุกคู่มีชื่อ) |
| ตอนมีคนถามถึงคู่หนึ่ง | แปลงคู่นั้นคู่เดียวเป็น `SymbolConstraints` |
| คู่ที่แปลงไม่ได้ | **`VenueProtocolError` ตอนที่ถูกถาม** — ไม่ข้ามเงียบ ๆ และ **ไม่บอกว่าตลาดไม่รู้จักคู่นั้น** |
| ผลที่ได้ | คู่สองคู่ที่ตลาดรายงานผิดกฎไม่ทำให้อ่านอีกห้าร้อยกว่าคู่ไม่ได้ และยังไม่มีคู่ไหนหายไปจากระบบโดยไม่มีใครรู้ |
