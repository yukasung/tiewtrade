สถานะ: **Approved** — เจ้าของอนุมัติ 2026-10-01 (ฉบับปรับตามข้อรีวิวทั้ง 6 ข้อ)

## แนวทาง

```
1. การเปลี่ยน F-33 (สองชนิดใหม่)   ← ขออนุมัติรายละเอียดก่อน ยังไม่แก้โค้ด
2. ชั้นเรียก HTTP + ตัวกั้นอัตรา     ← ที่เดียวที่รู้จักเครือข่าย
3. การแปลข้อมูลและข้อผิดพลาด       ← ที่เดียวที่รู้จักรูปแบบของตลาด
4. สองสัญญา: ราคา, ข้อจำกัดของเหรียญ
5. ข้อมูลตอบกลับที่บันทึกไว้ + เทสต์
6. งาน CI แยกสำหรับเทสต์สัญญากับตลาดจริง
```

### 1. การเปลี่ยน F-33 — เสนอเพิ่มสองชนิด (Q-8)

เจ้าของอนุมัติให้ **เสนอ** ได้ และกำหนดว่าต้องเขียนชื่อ ความหมาย และผลต่อผู้เรียกให้ชัด
**ยังไม่แก้โค้ดจนกว่ารายละเอียดนี้จะได้รับอนุมัติ**

#### 1.1 เพิ่มเหตุผลกลางค่าที่สี่: `RejectionReason.UNEXPLAINED`

| เรื่อง | รายละเอียด |
|---|---|
| **ชื่อ** | `RejectionReason.UNEXPLAINED` — เพิ่มใน `venues/errors.py` ใช้กับ `VenueRejectedError` ที่มีอยู่แล้ว |
| **ความหมาย** | **ตลาดตอบกลับมาแล้วว่าไม่รับคำขอ** แต่รหัสที่ตลาดส่งมาไม่มีความหมายที่เราแปลได้ — รู้แน่ว่าคำขอไม่สำเร็จและตลาดได้รับคำขอแล้ว |
| **ผลต่อผู้เรียก** | ทำเหมือน `VenueRejectedError` อื่นทุกอย่าง: **ถือว่าไม่เกิดผลที่ตลาด** · **ห้ามส่งซ้ำแบบอัตโนมัติ** เพราะยังไม่รู้สาเหตุ · ต้องแจ้งให้คนมาดู เพราะรหัสที่แปลไม่ได้คือสัญญาณว่าเราตามตลาดไม่ทัน |
| **ทำไมไม่ใช้ของที่มี** | สามค่าเดิมล้วนบอกสาเหตุที่ชัดเจน การยัดรหัสที่ไม่รู้จักเข้าไปในค่าใดค่าหนึ่งคือการโกหกผู้เรียก · และการใช้ `VenueUnavailableError` ก็ผิด เพราะตลาด **ตอบมาแล้ว** ไม่ใช่ติดต่อไม่ได้ ซึ่งจะทำให้ผู้เรียกลองใหม่ในกรณีที่ไม่ควรลอง |

#### 1.2 เพิ่มชนิดที่หก: `VenueProtocolError`

| เรื่อง | รายละเอียด |
|---|---|
| **ชื่อ** | `VenueProtocolError` — ชนิดใหม่ สืบจาก `VenueError` รหัส `VENUE_PROTOCOL` |
| **ความหมาย** | **ตลาดตอบมาแต่รูปแบบข้อมูลไม่ตรงกับที่เราเข้าใจ** — ฟิลด์ที่ต้องมีหายไป ชนิดข้อมูลเปลี่ยน หรืออ่านไม่ออก ไม่ใช่ความผิดของคำขอ และไม่ใช่ปัญหาการเชื่อมต่อ |
| **ผลต่อผู้เรียก** | **ห้ามลองใหม่อัตโนมัติ** เพราะลองอีกกี่ครั้งก็ได้ข้อมูลรูปแบบเดิม · ต้องแจ้งให้คนมาดูเพราะต้องแก้โค้ด · สำหรับการอ่าน ให้ถือว่าไม่มีข้อมูลนั้น (เช่น ไม่มีราคา → ห้ามเปิดไม้ใหม่ ตาม `trading-safety.md` หัวข้อ 6) |
| **กฎที่ต้องเขียนไว้ตั้งแต่ตอนนี้** | **ถ้าคำขอนั้นเปลี่ยนสถานะที่ตลาด (ส่งหรือยกเลิกออเดอร์) และเราอ่านคำตอบไม่ออก ต้องเป็น `VenueOutcomeUnknownError` ไม่ใช่ `VenueProtocolError`** เพราะเมื่ออ่านคำตอบไม่ออก เราไม่รู้ว่าคำสั่งเข้าหรือไม่ — F-35 ยังไม่มีคำขอแบบนั้น แต่เขียนกฎไว้ก่อนเพื่อไม่ให้ตอน F-22 ตีความเอาเอง |
| **ทำไมไม่ใช้ของที่มี** | ห้าชนิดเดิมตอบคำถาม "คำขอเป็นอย่างไร" ชนิดนี้ตอบ "ความเข้าใจของเราเป็นอย่างไร" ซึ่งต้องการการกระทำที่ต่างออกไปทั้งหมด: ไม่ใช่รอ ไม่ใช่แก้คำขอ แต่ต้องแก้โค้ด |

**การนับที่ถูกต้อง** (แก้หลังรีวิว 2026-10-01 — ร่างแรกนับผิดเป็นเจ็ด):

| | ก่อน F-35 | หลัง F-35 |
|---|---|---|
| **ชนิดข้อผิดพลาด** | 5 | **6** (เพิ่ม `VenueProtocolError` หนึ่งชนิด) |
| **เหตุผลของ `VenueRejectedError`** | 3 | **4** (เพิ่ม `UNEXPLAINED` — เป็น **เหตุผล** ไม่ใช่ชนิด) |

**ผลต่อ F-33 ที่ต้องแก้ตามไปด้วย:** `venues/errors.py`, `venues/__init__.py`
(ส่งออกชนิดใหม่), `validation.md` ของ F-33 ข้อ V-19 ที่เขียนว่า "ห้าชนิด" → **หกชนิด**
และเทสต์ของ F-33 ที่นับชนิดกับนับเหตุผล — **ทั้งหมดนี้เป็นการเปลี่ยนงานที่ปิดแล้ว
จึงขออนุมัติเป็นเรื่องแรกของงานนี้**

#### 1.3 ขยายความหมายของ `VenueUnavailableError` (เพิ่มตาม Q-7 (เจ้าของตัดสิน 2026-10-01))

| เรื่อง | รายละเอียด |
|---|---|
| **สิ่งที่เปลี่ยน** | ความหมายในเอกสารของชนิดเดิม **ไม่เปลี่ยนชื่อ ไม่เปลี่ยนรหัส ไม่เพิ่มช่องข้อมูล** |
| **ความหมายเดิม** | ต่อตลาดไม่ได้ หรือตลาดปิดให้บริการชั่วคราว |
| **ความหมายใหม่** | ตลาด **หรือข้อมูลที่ร้องขอ** ไม่พร้อมใช้งานชั่วคราว — ครอบกรณีที่ตลาดตอบมาเรียบร้อยแต่ไม่มีข้อมูลให้ เช่น ยังไม่มีใครเทรดคู่นั้น |
| **ผลต่อผู้เรียก** | **ไม่เปลี่ยน** — ถือว่าไม่มีราคา ห้ามเปิดไม้ใหม่ ส่วนคำสั่งลดความเสี่ยงยังพยายามต่อได้ และลองใหม่ภายหลังได้ปลอดภัย |
| **ทำไมขยายความหมายแทนเพิ่มชนิด** | ผลที่ผู้เรียกต้องทำตรงกันทุกข้อ การเพิ่มชนิดที่เจ็ดจะทำให้ผู้เรียกต้องดักสองชนิดเพื่อทำสิ่งเดียวกัน ซึ่งเป็นที่มาของการลืมดักข้างหนึ่ง |
| **ที่ต้องแก้** | docstring ของชนิดใน `venues/errors.py` และถ้อยคำของ F-33 ที่อธิบายชนิดนี้ |

### 2. ชั้นเรียก HTTP และตัวกั้นอัตรา

- โมดูลเดียวที่ `import httpx` — ที่อื่นในตัวเชื่อมไม่รู้จักเครือข่าย
- ทุกการเรียกผ่านทางเดียวที่ทำสามอย่างตามลำดับ: **จองโควตา → เรียก → แปลผล**
- **timeout เป็นค่าที่ผู้เรียกกำหนด** ไม่ใช่ค่าตายตัวในตัวเชื่อม
  (เหตุผลเดียวกับเกณฑ์ความเก่าของราคา — สเปกยังไม่มีตัวเลขนี้)
- **ไม่ลองใหม่อัตโนมัติเลยในงานนี้** การอ่านลองใหม่ได้ปลอดภัย แต่ **ยังไม่มีใครขอ**
  (RQ-14) และการตัดสินว่าจะลองใหม่กี่ครั้งเป็นเรื่องของผู้เรียกที่รู้ว่างานนั้นด่วนแค่ไหน

#### 2.1 ตัวกั้นที่ใช้ตอนเรียกตลาดจริง (Q-4 — เงื่อนไขที่เจ้าของกำหนด)

**เสนอ: `IpWeightLimiter` — ตัวกั้นในกระบวนการที่นับตามหน้าต่างเวลาจริง**

| เรื่อง | รายละเอียด |
|---|---|
| อยู่ที่ไหน | `venues/binance_th/` เพราะตัวเลขเพดานเป็นของตลาดนี้ ไม่ใช่ของกลาง |
| นับอะไร | **น้ำหนักต่อ IP สองหน้าต่าง**: 1,000 ต่อ 10 วินาที และ 6,000 ต่อ 60 วินาที (จากเอกสาร) |
| ทำอะไรเมื่อเต็ม | **โยน `VenueRateLimitedError` พร้อมเวลาที่ต้องรอ** ตามสัญญาของ F-33 ไม่หลับรอเงียบ ๆ |
| อ่านนาฬิกาจากไหน | **ผู้เรียกส่งตัวอ่านเวลาเข้ามา** เพื่อให้เทสต์เดินเวลาเองได้โดยไม่ต้องรอจริง |
| ใช้ที่ไหนในงานนี้ | **ทั้งสองเส้นทางที่เรียกตลาดจริง**: ตัวเก็บข้อมูลตอบกลับ และเทสต์สัญญารายวัน — **ไม่ใช้ `NoRateLimit` ทั้งสองที่** |
| ข้อจำกัดที่ยอมรับ | นับได้แค่ในกระบวนการเดียว หลายกระบวนการบนเครื่องเดียวกันยังชนเพดานต่อ IP ร่วมกันได้ — **ตัวกั้นที่มีสภาพร่วมกันต้องมาก่อนปล่อยผู้ใช้จริง** (บันทึกใน `roadmap.md` ตอนปิดงาน) |
| ปรับตัวตามของจริง | อ่าน header `X-MBX-USED-WEIGHT-*` ที่ตลาดส่งกลับมา **และถ้าค่าที่ตลาดนับสูงกว่าที่เรานับ ให้เชื่อตลาด** เพราะ IP เดียวอาจถูกใช้โดยอย่างอื่นด้วย |

**วิธีพิสูจน์ว่า weight ที่เราประกาศถูก** (แก้หลังรีวิว 2026-10-01)

ร่างแรกเขียนว่า "เทียบ header กับ weight ของ endpoint" ซึ่ง **ทำตรง ๆ ไม่ได้**
เพราะ header เป็น **ยอดสะสมของ IP ในหน้าต่างนั้น** ไม่ใช่ต้นทุนของคำขอเดียว

วิธีที่ใช้ได้: วัด **ผลต่างของยอดสะสมระหว่างสองคำขอที่ต่อเนื่องกัน** และยอมสรุปเฉพาะ
เมื่อเงื่อนไขครบ มิฉะนั้นถือว่า **สรุปไม่ได้ ไม่ใช่ผิด**

| สถานการณ์ | สรุปว่าอะไร |
|---|---|
| ผลต่างเท่ากันทุกรอบที่วัด (วัดซ้ำสามรอบ) และเท่ากับที่ประกาศ | **ตรง** |
| ผลต่างเท่ากันทุกรอบ แต่ **มากกว่า** ที่ประกาศ | **ไม่ตรง → งานแดง** |
| ยอดสะสมลดลงระหว่างรอบ (หน้าต่างรีเซ็ต) | **สรุปไม่ได้** |
| ผลต่างไม่เท่ากันในรอบที่วัด (มีคนอื่นใช้ IP เดียวกัน) | **สรุปไม่ได้** |
| ไม่มี header มาเลย | **สรุปไม่ได้** |

**"สรุปไม่ได้" ต้องรายงานเป็นข้ามเหมือนเน็ตมีปัญหา ไม่ใช่แดง** — ไม่เช่นนั้นงานรายวัน
จะแดงเพราะจังหวะของหน้าต่างเวลา แล้วคนจะเลิกเชื่อสีแดง

### 3. การแปลข้อมูลและข้อผิดพลาด

- **ตัวเลขทุกตัวอ่านเป็นข้อความก่อน** แล้วส่งเข้า `Money`/`Quantity` (RQ-4, RQ-5)
  ใช้ตัวอ่าน JSON ที่ไม่แปลงเลขเป็นทศนิยมลอยตัวเอง ไม่ใช่แปลงแล้วแปลงกลับ
- ชื่อคู่เทรด: `Symbol(base, quote)` → `f"{base}{quote}"` และทางกลับใช้รายการจาก
  `/exchangeInfo` ซึ่งบอก `baseAsset`/`quoteAsset` มาด้วย — **ไม่เดาว่าตัดตรงไหน**
- ข้อจำกัดของเหรียญมาจาก filter ของ `/exchangeInfo`: `LOT_SIZE` → ปริมาณขั้นต่ำกับขั้น,
  `MIN_NOTIONAL` → มูลค่าขั้นต่ำ · **ไม่อ่าน `PRICE_FILTER` เพราะยังไม่มีใครใช้** (RQ-14)
- **แปลงข้อจำกัดทีละคู่ตอนมีคนถาม ไม่แปลงทั้งชุดตอนอ่าน** (แก้ตาม **NC-13** —
  เจ้าของตัดสิน 2026-10-01 หลังพบว่าตลาดรายงาน `stepSize` เป็นศูนย์ในคู่ที่เปิดเทรดจริง)
  คู่ที่อ่านไม่ได้ยังดังเป็น `VenueProtocolError` ตอนที่ถูกถาม ไม่ข้ามเงียบ ๆ
  รายละเอียดอยู่ใน `requirements.md` หัวข้อ NC-13
- ตารางแปลข้อผิดพลาด (เรียงตามลำดับที่ตรวจ):

| สิ่งที่เจอ | แปลเป็น |
|---|---|
| ต่อไม่ติด, DNS ล้ม, timeout **ก่อน** ส่งครบ | `VenueUnavailableError` |
| timeout **หลัง** ส่งครบแล้ว | `VenueOutcomeUnknownError` |
| `429` หรือ `418` | `VenueRateLimitedError` พร้อม `Retry-After` ถ้ามี (ไม่มีก็เป็นค่าว่าง ไม่เดา) |
| `5xx` | การอ่าน → `VenueUnavailableError` · คำขอที่เปลี่ยนสถานะ → `VenueOutcomeUnknownError` |
| `401` หรือรหัสของตลาดที่ **ยืนยันว่าเป็นเรื่องกุญแจหรือลายเซ็น** | `VenueCredentialRejectedError` |
| **`403`** | **`VenueRejectedError(UNEXPLAINED)` ไม่ใช่เรื่องกุญแจ** (แก้หลังรีวิว 2026-10-01) — เอกสารระบุว่า `403` คือถูกไฟร์วอลล์ของตลาด (WAF) ปฏิเสธ ซึ่ง **ไม่ได้พิสูจน์ว่ากุญแจผิด** ถ้าแปลเป็นเรื่องกุญแจ ผู้เรียกจะไปหยุดบอทด้วยสาเหตุที่ผิด (`trading-safety.md` หัวข้อ 2 สั่งให้หยุดบอททันทีเมื่อกุญแจถูกปฏิเสธ) การปฏิเสธแบบนี้ต้องให้คนมาดู เพราะมักเกิดจากรูปคำขอหรือ IP ไม่ใช่สิทธิ์ |
| รหัสที่รู้จัก: ไม่มีคู่เทรด / ผิดข้อจำกัด / เงินไม่พอ | `VenueRejectedError` พร้อมเหตุผลตรงตัว |
| **รหัสที่ไม่รู้จัก** | `VenueRejectedError(UNEXPLAINED)` — ชนิดใหม่จากข้อ 1.1 |
| **อ่านคำตอบไม่ออก / ฟิลด์ที่ต้องมีหาย** | `VenueProtocolError` — ชนิดใหม่จากข้อ 1.2 |

- **ข้อความของทุกชนิดไม่พา URL, คำขอ, หรือ header ติดไปด้วย** (RQ-9)
  ตัวเชื่อม log เฉพาะ: ชื่อ endpoint แบบย่อ, สถานะ HTTP, รหัสของตลาด — **ไม่ log query string**

#### 4.1 เมื่อไม่มีรายการซื้อขายเลย (Q-7 (เจ้าของตัดสิน 2026-10-01))

`/trades` คืน array ว่างได้ ถ้าคู่เทรดนั้นยังไม่มีใครเทรด

**ตัดสินแล้ว: `VenueUnavailableError`** และ **ขยายความหมายของชนิดนี้ในสัญญาของ F-33**
ให้ครอบ "ตลาด **หรือข้อมูลที่ร้องขอ** ไม่พร้อมใช้งานชั่วคราว" — ดูข้อ 1.3

สามอย่างที่ **ห้ามทำ** ในกรณีนี้:

| ห้าม | เพราะ |
|---|---|
| **คืนราคาสำรองจากที่อื่น** (ราคาก่อนหน้า, ราคาจาก `/ticker/price`, ราคากลางของสมุด) | ไม่มีราคาคือไม่มีราคา การเดาทำให้กฎ "ไม่มีราคาที่เชื่อถือได้ ห้ามเปิดไม้ใหม่" ทำงานบนตัวเลขที่ไม่มีเวลาจริง (`trading-safety.md` หัวข้อ 6) |
| **ตีความว่าไม่รู้จักคู่เทรด** (`VenueRejectedError(UNKNOWN_SYMBOL)`) | คู่เทรดมีจริงและอยู่ในรายการของตลาด การบอกว่าไม่รู้จักจะทำให้ผู้เรียกไปถอดคู่นั้นออกจากระบบโดยไม่มีเหตุ |
| **ถือว่า response ผิดรูป** (`VenueProtocolError`) | array ว่างคือคำตอบที่ถูกต้องตามสัญญาของตลาด ไม่ใช่สัญญาที่เปลี่ยน — ถ้าแปลเป็นชนิดนั้นจะทำให้งาน CI รายวันแดงทุกครั้งที่เจอคู่เทรดเงียบ |

### 5. ข้อมูลตอบกลับที่บันทึกไว้ และเทสต์

- ตัวเก็บข้อมูลเป็นสคริปต์แยกที่คนสั่งเอง **ไม่ใช่เทสต์** เรียกเฉพาะ endpoint สาธารณะ
  ตามที่อนุมัติ (Q-5): `/time`, `/exchangeInfo`, `/trades` และกรณีที่ตลาดปฏิเสธ
  (คู่เทรดที่ไม่มีจริง, คำขอที่ผิดรูป) · บันทึกลง `tests/venues/binance_th/recorded/`
- **บันทึก header ของ weight ที่ตลาดส่งกลับมาด้วย** เพื่อเทียบกับ weight ที่เราประกาศ (Q-5)
- **ไม่พยายามทำให้ตลาดตอบ 429** (Q-5) กรณีนั้นทดสอบด้วยข้อมูลที่เขียนขึ้นเอง
- เทสต์ปกติใช้ข้อมูลที่บันทึกไว้ และ **มีเทสต์ที่ปิด socket ทั้งกระบวนการ** เพื่อพิสูจน์ว่า
  ไม่มีการเรียกออกไปจริง (RQ-10)

### 6. งาน CI แยกสำหรับเทสต์สัญญากับตลาดจริง (Q-6 — เงื่อนไขที่เจ้าของกำหนด)

- งานใหม่ชื่อ `venue-contract` ใน workflow **แยกไฟล์** จาก `ci.yml`
  ตารางเวลา **รายวัน** และกดรันเองได้ (`workflow_dispatch`)
- **ไม่อยู่ในเงื่อนไขการ merge** ของ `ci.yml`

**แยกสองสาเหตุให้เห็นชัด** — เทสต์จบด้วยสามสถานะ ไม่ใช่สองสถานะ:

| สถานะ | หมายถึง | ผู้ดูแลต้องทำ |
|---|---|---|
| **ผ่าน** | สัญญาของตลาดยังเหมือนเดิม | ไม่ต้องทำอะไร |
| **ข้ามเพราะเข้าถึงตลาดไม่ได้** | เน็ตหรือตลาดมีปัญหา — รายงานเป็น **neutral ไม่ใช่ failure** | รอรอบถัดไป ถ้าข้ามติดกันหลายวันค่อยดู |
| **แดง** | **สัญญาไม่ตรงกัน** — ฟิลด์หาย ชนิดเปลี่ยน หรือ weight ที่ตลาดนับต่างจากที่เราประกาศ | ต้องมีคนแก้โค้ด |

การแยกทำโดย **ดักชนิดข้อผิดพลาดของเราเอง**:

| ชนิดที่เจอ | สถานะของงาน | เพราะ |
|---|---|---|
| `VenueUnavailableError` · `VenueRateLimitedError` · **`VenueOutcomeUnknownError`** | **ข้าม** | ทั้งสามคือ "ยังไม่ได้คำตอบจากตลาด" |
| `VenueProtocolError` · การเทียบค่าไม่ตรง | **แดง** | สัญญาไม่ตรงกัน ต้องมีคนแก้โค้ด |
| `VenueRejectedError` ทุกเหตุผล | **แดง** | คำขอที่เราส่งเป็นคำขออ่านอย่างเดียวและคงที่ ถ้าตลาดปฏิเสธ แปลว่าเราเข้าใจผิด |

**ทำไม "ไม่รู้ผล" นับเป็นข้าม ไม่ใช่แดง** (แก้หลังรีวิว 2026-10-01)
ร่างแรกข้ามแค่สองชนิด ทำให้ timeout หลังส่งครบกลายเป็นงานแดง ซึ่งผิดกลุ่ม
**เหตุผลที่ข้ามได้อย่างปลอดภัยคือทุกคำขอในงานนี้เป็นการอ่าน** — การอ่านที่ไม่รู้ผล
คือการอ่านที่ล้มเหลว ไม่ได้ทำให้เกิดอะไรที่ตลาด
**ข้อนี้ใช้ได้เฉพาะงาน CI สัญญานี้** ไม่ใช่กฎทั่วไป — วันที่มีคำขอที่เปลี่ยนสถานะ
(F-22) การจัดกลุ่มนี้ต้องทบทวน และ `VenueOutcomeUnknownError` ที่นั่นห้ามข้าม

นี่คือเหตุผลเพิ่มอีกข้อที่ต้องมี `VenueProtocolError` จากข้อ 1.2

**ผู้ดูแลเห็นผลอย่างไร** (Q-6 ข้อ 2) — สามทางที่ไม่ต้องมีใครไปเปิดดูเอง:

1. **ชื่องานขึ้นหน้า Actions พร้อมสถานะ** และ GitHub ส่งอีเมลให้เจ้าของ repo
   เมื่องานที่มีตารางเวลา **เปลี่ยนจากเขียวเป็นแดง** (พฤติกรรมปริยายของ GitHub)
2. **สรุปผลเขียนลง job summary** — ตารางสั้น ๆ ว่าตรวจกี่ endpoint ผ่านกี่ข้อ
   และถ้าแดง บอกว่าฟิลด์ไหนหายหรือ weight ต่างกันเท่าไร โดยไม่ต้องอ่าน log
3. **ไฟล์ผลลัพธ์แนบไว้กับงาน** (artifact) เก็บคำตอบที่ได้จากตลาดรอบนั้น
   เพื่อเทียบกับของที่บันทึกไว้ได้ทันทีเวลาสัญญาเปลี่ยน

> **ข้อที่ต้องให้เจ้าของทราบ:** การแจ้งเตือนทางอีเมลเป็นของ GitHub ไม่ใช่ของระบบเรา
> ถ้าต้องการแจ้งเตือนทางอื่น (Telegram/LINE) ต้องรอ F-27 และยังติด **T-05**

### 7. งานด่านสองข้อที่ roadmap ฝากไว้กับงานนี้ (แก้หลังรีวิว 2026-10-01)

`roadmap.md` บันทึกไว้ตอนปิด F-33 ว่ามีสองเรื่องต้องจัดการ **ตอนทำ F-35**
ร่างแรกของ plan ไม่ได้รวมไว้ — งานนี้คือจุดที่ทั้งสองเรื่องจะเริ่มเน่า
เพราะเป็นงานแรกที่เพิ่ม package ของตัวเชื่อม **จึงทำในงานนี้ ไม่เลื่อน**

#### 7.1 เลิกพึ่งรายชื่อโมดูลส่วนกลางที่เขียนมือ

ตอนนี้รายชื่ออยู่สามที่ (`pyproject.toml` และ fixture ของด่านสองชุด)
ลืมเติมแล้วกฎจะไม่ครอบไฟล์ใหม่โดยไม่มีอะไรเตือน

**เสนอ: ไม่ย้ายโครงสร้าง แต่ทำให้การลืมดังทันที** — เพิ่มเทสต์ที่เทียบ
`source_modules` ของ contract กับ **รายชื่อที่ได้จากโครงสร้างจริง** (`glob` ของไฟล์
ระดับบนสุดใน `venues/`) ถ้าไม่ตรงให้แดงพร้อมบอกว่าขาดชื่อไหน
และเทียบ fixture ทั้งสองชุดกับรายชื่อเดียวกันด้วย

เหตุผลที่ไม่ย้ายโครงสร้าง (เช่นแยก `venues/contracts/`): การย้ายเป็นการเปลี่ยนผัง
ที่ `architecture.md` วางไว้ และกระทบ import ของทุกงานที่ใช้ชั้นนี้อยู่แล้ว
ส่วนเทสต์เทียบรายชื่อปิดช่องเดียวกันด้วยการแก้ที่เล็กกว่ามาก

#### 7.2 ให้แต่ละ package ตัวเชื่อมประกาศคำศัพท์ของตัวเอง

ตอนนี้คำของตลาด (`binance`, `fapi`, `sapi`, `testnet`) เขียนมือไว้ในไฟล์เทสต์
ซึ่งไกลจากโค้ดที่พาคำเหล่านั้นเข้ามา

**เสนอ: `venues/binance_th/` ประกาศ `VENUE_VOCABULARY` ของตัวเอง** แล้วด่าน
**อ่านคำจากทุก package ย่อยของ `venues` ด้วย AST** (ไม่ import) แล้วรวมเป็นรายการที่ห้าม
ผลคือการเพิ่มตลาดใหม่ **ขยายด่านให้เองโดยไม่ต้องมีใครจำ** และถ้า package ตัวเชื่อมไหน
ไม่ประกาศเลย ให้ด่านแดง เพราะตัวเชื่อมที่ไม่มีคำศัพท์เป็นของตัวเองแปลว่ามีคนลืม
