### 1.2 secret ไม่รั่ว (RQ-2)

| # | เกณฑ์ | ตรวจอย่างไร |
|---|---|---|
| V-5 | **ไม่มี endpoint ใดคืน secret ที่ยืนยันแล้ว** · `setup` และ `replace` คืน secret ใหม่ได้ **ครั้งเดียวต่อการเรียก** เพราะต้องผูกเครื่อง — เรียกซ้ำต้องได้ secret ใหม่ ไม่ใช่ค่าเดิมที่เคยแจก | เทสต์ที่เรียกทุกเส้นทางในวงจรชีวิต แล้วค้นค่าของ secret **ที่ยืนยันแล้ว** ในทุก response body และ header · **แก้ถ้อยคำตามรีวิว 2026-10-03** — ฉบับก่อนห้ามคืนทุกกรณี ซึ่งขัดกับการผูกเครื่องใหม่ |
| V-6 | **secret ไม่อยู่ใน log ไม่อยู่ใน traceback** | canary ของ F-03 ใช้ซ้ำ + เทสต์ที่บังคับให้เกิดข้อผิดพลาดตอนถอดผนึกแล้วค้นค่าใน traceback ทั้งก้อน |
| V-7 | **secret ไม่ลง log ของ PostgreSQL** | canary ของ F-03 (ค่าที่ bind ไม่ลง log) |
| V-8 | **คอลัมน์ใดก็ไม่เก็บ secret ดิบ** | อ่านฐานข้อมูลตรงด้วยบทบาท `migrator` แล้วค้นค่า |
| V-9 | ciphertext ของผู้ใช้คนหนึ่ง **ถอดไม่ออกเมื่อย้ายไปแถวของคนอื่น** | ย้ายค่าในฐานข้อมูลแล้วเรียกถอด ต้องล้มเหลว (associated data ผูก `user_id`) |
| V-10 | **กุญแจไม่มีหรืออ่านไม่ได้ → กระบวนการไม่เริ่ม** ไม่ใช่ล้มตอนมีผู้ใช้คนแรก | เทสต์ที่ลบ environment variable แล้วเริ่มแอป |

### 1.3 เปิดใช้ไม่ได้โดยปริยาย และต้องยืนยันเจ้าของบัญชี (RQ-3, RQ-3.1)

| # | เกณฑ์ | ตรวจอย่างไร |
|---|---|---|
| V-11 | secret ที่ `setup` แล้ว **ยังไม่ `confirm`** ไม่มีผลกับการ login เลย | login ได้เหมือนไม่มี TOTP |
| **V-11.1** | **`replace` แล้วทิ้งกลางทาง → ปัจจัยเดิมยังใช้ได้ครบ** และรหัสสำรองชุดเก่ายังใช้ได้ | เรียก `replace` แล้วไม่ `confirm` · login ด้วยรหัสจากเครื่องเดิมต้องผ่าน · **ข้อนี้คือสิ่งที่ตารางรอยืนยันแยกมีไว้เพื่อ** (`plan.md` 1.6) |
| **V-11.2** | **การสลับ pending → active เป็นก้อนเดียว** — สลับ secret, เพิ่ม `secret_version`, ตั้ง `last_accepted_step` เป็นช่วงที่ยืนยันสำเร็จ, ยกเลิกรหัสสำรองชุดเก่า, ออกชุดใหม่, เพิกถอน session อื่น · ล้มกลางทางแล้วไม่มีสถานะผสม | จำลองความล้มเหลวกลาง transaction แล้วตรวจทั้งหกอย่าง |
| **V-11.3** | **รหัสสำรองชุดเก่าถูกยกเลิกตอน `confirm` ไม่ใช่ตอน `replace`** | เรียก `replace` แล้วตรวจว่ารหัสสำรองเก่ายังใช้ได้ · `confirm` แล้วตรวจว่าใช้ไม่ได้ |
| V-12 | `setup` **ปฏิเสธเมื่อรหัสผ่านผิดหรือไม่ส่งมา** — session อย่างเดียวไม่พอ | เทสต์ที่ถือ session ที่ใช้ได้แต่ไม่มีรหัสผ่าน |
| V-13 | **คนที่มีแต่ session ขโมยมา ผูก authenticator ของตัวเองไม่ได้** | เทสต์ที่จำลองโทเคนที่คัดลอกไว้ แล้วพยายามเดินวงจร `setup` → `confirm` ให้จบ ต้องไม่สำเร็จ |
| V-14 | `confirm` ที่รหัสผิด **ไม่เปิดใช้** และ secret ยังอยู่ในสถานะยังไม่ยืนยัน | |
| V-15 | เรียก `setup` ซ้ำทับ secret ที่ยังไม่ยืนยันได้ และไม่ทำให้ของที่ยืนยันแล้วเสีย | |

### 1.5 ขั้นที่สองของการเข้าสู่ระบบ (RQ-5, RQ-11, RQ-13)

| # | เกณฑ์ | ตรวจอย่างไร |
|---|---|---|
| V-21 | ผู้ใช้ที่เปิด TOTP **ไม่ได้ cookie ของ session จาก `POST /auth/login`** | ตรวจ header ของ response และตรวจว่า **ไม่มีแถวใน `sessions`** |
| V-22 | challenge **ใช้เรียก endpoint อื่นไม่ได้เลย** | ยิง challenge เป็น cookie ของ session ไปทุกเส้นทางที่ต้องมีสิทธิ์ ต้องได้ 401 ทั้งหมด |
| V-23 | challenge **ต่ออายุไม่ได้** และหมดอายุแล้วใช้ไม่ได้ | ไม่มีสิทธิ์ `UPDATE` ให้บทบาทใด — ตรวจที่ระดับสิทธิ์ด้วย ไม่ใช่แค่ที่โค้ด |
| V-24 | ผ่านขั้นที่สองแล้ว **แถว challenge หายไป** และ session ถูกออกใน transaction เดียวกัน | |
| **V-24.1** | **ล้มเหลวกลาง transaction → ไม่มี session ใหม่ และ challenge เดิมยังอยู่** ผู้ใช้ลองอีกครั้งได้ | จำลองความล้มเหลวหลังออก session ก่อน commit · **ฉบับก่อนเขียนว่า "ไม่เหลือทั้งคู่" ซึ่งกลับด้าน** — rollback ย้อนการลบ challenge ด้วย (แก้ตามรีวิว 2026-10-03) |
| **V-24.2** | **กรอกรหัสผิดที่ขั้นที่สองยังถูกนับ** แม้ transaction ของการ login ถูกย้อน | ตัวนับอยู่ใน transaction ของตัวเองตามแบบแผนของ `throttle.py` ("ตัวนับต้องถูกบันทึกแม้คำขอนั้นถูกปฏิเสธ") — ถ้าไม่ทำ การ rollback จะลบร่องรอยการเดาทิ้ง |
| V-25 | **คำตอบของ `login` ไม่บอกว่าบัญชีเปิด TOTP ไว้หรือไม่ แก่คนที่รหัสผ่านผิด** | เทียบ response และ **เวลาตอบ** ของสี่กรณี: ไม่มีบัญชี / รหัสผ่านผิด+ไม่มี TOTP / รหัสผ่านผิด+มี TOTP / รหัสผ่านถูก |
| V-26 | `/auth/totp/login` **ไม่อยู่ใน `RENEWING_ROUTES`** | ด่านที่เดินทุกเส้นทาง (V-30) |
| **V-26.1** | **challenge ที่ออกด้วยรหัสผ่านเก่า ใช้ไม่ได้หลังเปลี่ยนรหัสผ่าน** | ออก challenge → เปลี่ยนรหัสผ่าน → ใช้ challenge เดิมผ่าน TOTP ต้อง**ไม่ได้ session** · **ขัด RQ-22 ของ F-05 ถ้าทำได้** (เพิ่มตามรีวิว 2026-10-03) |
| **V-26.2** | ตรวจสองชั้น — การเปลี่ยนรหัสผ่าน **ลบ challenge ของผู้ใช้** และการใช้ challenge **เทียบรุ่น `credential_updated_at` ใต้ล็อก** | ปิดชั้นแรกแล้วชั้นที่สองต้องยังปฏิเสธ |
| **V-26.3** | **เปลี่ยนรหัสผ่านแข่งกับการใช้ challenge → มีฝ่ายหนึ่งชนะ** | ยิงพร้อมกันจริง ทั้งสองลำดับ · ลำดับล็อกตาม `plan.md` 1.1 |
| **V-26.4** | **ลบ challenge ที่หมดอายุได้จริง** ทั้งที่ policy ของโทเคนที่พามาซ่อนแถวหมดอายุ | ทดสอบด้วยบทบาทจริงบน PostgreSQL — ต้องใช้ policy `auth_owner` หลัง `assume_user` (`plan.md` 1.5) |

## 2. เทสต์ที่ต้องมี

### ตัวเลขจริง

- **ชุดตัวเลขทดสอบของ RFC 6238 Appendix B ทุกแถว** (V-1) — เป็นหลักฐานจากภายนอก
  ไม่ใช่ค่าที่เราคิดขึ้นเอง
- เวลาที่กำหนดเองรอบขอบของช่วงเวลา: วินาทีสุดท้ายของช่วง T และวินาทีแรกของ T+1 (V-17, V-20)

### คุณสมบัติ (hypothesis)

- รหัสที่คำนวณได้ **มีจำนวนหลักคงที่เสมอ** รวมกรณีที่ค่าขึ้นต้นด้วยศูนย์
- ปิดผนึกแล้วเปิดผนึกได้ค่าเดิม สำหรับ secret ที่สุ่มมาทุกค่า (round-trip)
- เปลี่ยนไบต์ใดไบต์หนึ่งของ ciphertext หรือเปลี่ยน `user_id` → **เปิดผนึกล้มเหลวทุกครั้ง**
- `last_accepted_step` **ไม่ลดลงเลย** ไม่ว่าลำดับของคำขอเป็นอย่างไร

### ความปลอดภัยการเทรด

ตาม `testing.md` หัวข้อ 4 — งานนี้ยังไม่ส่งออเดอร์ สิ่งที่พิสูจน์ได้คือข้อที่เกี่ยวกับสิทธิ์:

- **คำสั่งลดความเสี่ยงไม่ถูกบังคับยืนยันซ้ำ** (V-29, V-31) — บังคับด้วยตารางจัดประเภท
  **ก่อน**ที่เส้นทางเหล่านั้นจะมีอยู่ ซึ่งเป็นสิ่งเดียวที่งานนี้ทำได้จริง
- **เปิด Live ไม่ได้ถ้าไม่มี TOTP** (V-59) และ **ปิด TOTP ไม่ได้ถ้า Live เปิดอยู่** (V-60)
- **ไม่อ้างว่าพิสูจน์แล้วว่าเจ้าของกลับเข้ามาลดความเสี่ยงได้ทัน** — ข้อนี้ติด NC-14
  และ `requirements.md` หัวข้อ "สิ่งที่งานนี้ไม่รับประกัน" บันทึกไว้แล้ว

- V-19 รหัสเดียวกันสองคำขอ
