### 1.1 ลำดับการล็อกแถว — ประกาศไว้ที่เดียวและใช้เหมือนกันทุกที่

**หัวข้อนี้เพิ่มตามรีวิว** เพราะข้อบกพร่องสองข้อ (หัวข้อ 1.2 และ 1.6) มีรากเดียวกัน
คือ **อ่านค่าแล้วตัดสินใจโดยไม่ได้ล็อกสิ่งที่ตัดสินใจบนมัน**

ทุกเส้นทางที่ตรวจปัจจัยยืนยันตัวตนต้องล็อกตาม **ลำดับเดียวกันนี้เสมอ**
(ลำดับคงที่คือสิ่งที่กัน deadlock — ไม่ใช่โชค):

```
1. auth_throttle   (ถัง)      ← ล็อกโดย claim() ของ F-05 อยู่แล้ว
2. user_credentials (FOR UPDATE)  ← ลำดับสามขั้นของ F-05: owner_of_email → assume_user → locked_hash
3. user_totp        (FOR UPDATE)  ← ใหม่ในงานนี้
```

F-05 บันทึกไว้แล้วว่าการล็อก `user_credentials` มีข้อบังคับที่มองจากภายนอกไม่เห็น
(`credentials.py` docstring) — งานนี้ต่อท้ายลำดับนั้น ไม่สร้างลำดับใหม่

### 1.2 กันการใช้รหัสซ้ำ — ต้องผูกกับ secret ตัวปัจจุบัน ไม่ใช่แค่ลำดับเวลา

**แก้ตามรีวิว** — ฉบับก่อนตรวจแค่ `user_id` กับลำดับเวลา ซึ่งมีช่องว่าง:
คำขอ A อ่าน secret เก่า → คำขอ B เปลี่ยน secret → คำขอ A สั่ง `UPDATE` ที่ลำดับเวลาผ่าน
**แล้วรหัสจาก secret ที่ถูกยกเลิกไปแล้วก็ถูกรับ**

สองชั้นที่ปิดช่องนี้:

**ชั้นที่หนึ่ง — ล็อกตั้งแต่ก่อนอ่าน secret จนอนุญาตสำเร็จ**

```sql
SELECT secret_sealed, key_version, secret_version, last_accepted_step
FROM user_totp WHERE user_id = :user_id
FOR UPDATE
```

การเปลี่ยน secret ล็อกแถวเดียวกัน จึงเข้าคิวแทนที่จะแข่งกัน

**ชั้นที่สอง — `secret_version` อยู่ในเงื่อนไขของการอนุญาต**

```sql
UPDATE user_totp
SET last_accepted_step = :step
WHERE user_id = :user_id
  AND secret_version = :version_that_was_read
  AND last_accepted_step < :step
```

ศูนย์แถว = รหัสถูกใช้ไปแล้ว **หรือ** secret เปลี่ยนไประหว่างทาง → ปฏิเสธทั้งสองกรณี

**`last_accepted_step` ตอนสลับ secret ต้องเป็นช่วงของรหัสที่ยืนยันสำเร็จ ไม่ใช่ศูนย์**
(แก้ตามรีวิว 2026-10-03) — ถ้าตั้งเป็นศูนย์ **รหัสที่ผู้ใช้ใช้ยืนยันการตั้งค่า
จะถูกนำไปใช้ซ้ำได้ทันที** เพราะช่วงของมันมากกว่าศูนย์ ซึ่งขัด RQ-4 ตรง ๆ
· `secret_version` เพิ่มขึ้นและ `last_accepted_step` ถูกตั้งเป็นช่วงที่เพิ่งผ่าน
**พร้อมกันในคำสั่งเดียว**

เหตุผลที่ยังต้องมีชั้นที่สองทั้งที่ล็อกแล้ว: ล็อกกันได้เฉพาะคำขอที่ผ่านทางที่เรา
เขียนไว้ ถ้าวันหนึ่งมีทางเข้าใหม่ที่ลืมล็อก เงื่อนไขในคำสั่งยังปฏิเสธให้
— สองชั้นแบบเดียวกับแบบแผนของ F-03

**ยังได้สมบัติเดิมไว้ครบ:** รหัสของช่วง T ที่ใช้แล้วถูกปฏิเสธในช่วง T+1 ในฐานะ
"รหัสช่วงก่อนหน้า" โดยอัตโนมัติ, ครอบทุกจุดตรวจเพราะคอลัมน์อยู่กับผู้ใช้,
และ **ไม่สร้างหนี้งานเก็บกวาด** เพราะไม่มีตารางรายการรหัสที่ใช้แล้ว

### 1.3 ขั้นที่สองของ login: ตารางแยก ไม่ใช่คอลัมน์ใน `sessions`

**ต่างจากที่ `plan.md` ของ F-05 คาดไว้ ต้องขออนุมัติเป็นข้อ**

| ทางเลือก | ผลที่ตามมา |
|---|---|
| ก. **ตาราง `login_challenges`** — ออก session จริง **หลัง** ผ่านปัจจัยที่สองเท่านั้น | **RQ-5 เป็นจริงโดยโครงสร้าง** แถวที่ยืนยันครึ่งเดียวไม่ได้อยู่ในตารางที่ให้สิทธิ์ **แลกกับ** ตารางใหม่และต้องจัดการการหมดอายุ (หัวข้อ 1.5) |
| ข. คอลัมน์ `totp_verified_at` ใน `sessions` (ตามที่ F-05 คาด) | ใช้ตารางเดิม **แลกกับ** แถวที่ยืนยันครึ่งเดียวอยู่ใน**ตารางที่ให้สิทธิ์ทุกอย่าง** ลืมตรวจที่ใดที่หนึ่ง = รหัสผ่านอย่างเดียวผ่านเข้าไป |

**ผมเสนอ ก.** เพราะ `security.md` หัวข้อ 2 สั่งว่าค่าเริ่มต้นคือปฏิเสธ

### 1.4 challenge ต้องตายเมื่อรหัสผ่านเปลี่ยน (RQ-22 ของ F-05)

**เพิ่มตามรีวิว** — challenge ที่ออกด้วยรหัสผ่านเก่าต้องใช้ต่อไม่ได้
มิฉะนั้นการเปลี่ยนรหัสผ่านที่เพิกถอน session ทั้งหมดก็ยังไม่ตัดทางผู้โจมตี
ที่ถือ challenge ค้างไว้แล้วไปผ่าน TOTP ทีหลัง

สองชั้น:

| ชั้น | ทำอย่างไร |
|---|---|
| **ลบตรง ๆ** | การเปลี่ยนรหัสผ่านลบ challenge ทุกใบของผู้ใช้ **ใน transaction เดียวกับการเปลี่ยนแฮช** ต่อท้ายการเพิกถอน session ที่ F-05 ทำอยู่แล้ว (`end_others()`) |
| **ตรวจรุ่นตอนใช้** | challenge เก็บ `credential_updated_at` ที่อ่านมาตอนออก · ตอนใช้ต้องตรงกับ `user_credentials.updated_at` ที่อ่าน**ใต้ล็อก** มิฉะนั้นปฏิเสธ |

**ไม่เพิ่มคอลัมน์ให้ `user_credentials`** — `updated_at` มีอยู่แล้วและ
`replace_password_hash()` ของ F-05 อัปเดตมันอยู่แล้ว จึงใช้เป็นรุ่นได้โดยไม่แตะ F-05

ชั้นที่สองจำเป็นทั้งที่มีชั้นที่หนึ่ง เพราะการลบกับการเปลี่ยนแฮชอาจถูกเขียนแยกกัน
ในอนาคต และเพราะคำขอที่กำลังวิ่งอยู่ตอนรหัสผ่านเปลี่ยนต้องแพ้ด้วย

**ลำดับล็อกของการใช้ challenge** ตามหัวข้อ 1.1: อ่าน challenge (ด้วยโทเคนที่พามา)
→ `assume_user` → ล็อก `user_credentials` แล้วเทียบรุ่น → ล็อก `user_totp`
→ ตรวจรหัส → ลบ challenge + ออก session · **การเปลี่ยนรหัสผ่านล็อกลำดับเดียวกัน**
จึงมีฝ่ายหนึ่งชนะเสมอ ไม่มีสถานะกลาง

### 1.5 การหมดอายุของ challenge กับ RLS — **และหนี้งานเก็บกวาดที่ต้องยอมรับ**

**แก้ตามรีวิว** — ฉบับก่อนอ้างว่า "ไม่เป็นหนี้งานเก็บกวาด" ซึ่ง **ผิดสองชั้น**

ชั้นแรก คือเรื่อง RLS: policy ที่ให้เห็นเฉพาะโทเคนที่พามา **และยังไม่หมดอายุ**
ทำให้แถวที่หมดอายุแล้ว **มองไม่เห็น** และคำสั่งลบที่อ้างคอลัมน์จะดึง SELECT policy
มาใช้ด้วย (ข้อเดียวกับที่ `sessions.py` ของ F-05 บันทึกไว้) → ลบไม่ได้

**ทางแก้: สอง policy เหมือนที่ F-05 ทำกับ `sessions`**

| policy | ให้ใคร | เห็นอะไร |
|---|---|---|
| `login_challenges_presented` | `tiewtrade_auth` | `SELECT` แถวที่ตรงกับโทเคนที่พามา **และยังไม่หมดอายุ** |
| `login_challenges_auth_owner` | `tiewtrade_auth` | `ALL` แถวของผู้ใช้ปัจจุบัน **รวมที่หมดอายุ** — ใช้ตอนลบ ซึ่งต้องอ้างคอลัมน์ได้ |

การลบจึงทำหลัง `assume_user` แล้วเท่านั้น และอ้างคอลัมน์ได้ตามปกติ

ชั้นที่สอง คือข้อที่ผมอ้างเกิน: **การลบตอนผู้ใช้กลับมา login ไม่ครอบผู้ใช้ที่ไม่กลับมา**
แถวของคนที่ทิ้งกลางทางแล้วไม่กลับมาอีกจะค้างอยู่ — **หนี้ชนิดเดียวกับ `auth_throttle`
ของ F-05** ที่ `roadmap.md` บันทึกว่าต้องมีงานเก็บกวาดก่อนปล่อยผู้ใช้จริง

| ทางเลือก | ผลที่ตามมา |
|---|---|
| **ก. ทำงานเก็บกวาดในงานนี้ ครอบทั้ง `auth_throttle` และ `login_challenges`** | ปิดหนี้ของ F-05 ไปด้วยในที่เดียว **แลกกับ** ขอบเขตงานกว้างขึ้น และต้องตัดสินว่ารันด้วยอะไร (งานตามเวลาใน `engine` หรือคำสั่งที่คนสั่ง) |
| ข. บันทึกเป็นหนี้เพิ่มอีกหนึ่งตาราง | เร็วที่สุด **แลกกับ** ก่อนปล่อยผู้ใช้จริงมีสองตารางที่ต้องเก็บกวาดแทนหนึ่ง |

**ผมเสนอ ก.** เพราะหนี้นี้มีอยู่แล้วและงานนี้กำลังเพิ่มของให้มันอีกชิ้น
การเขียนตัวเก็บกวาดหนึ่งตัวที่ครอบทั้งสองตารางถูกกว่าการมาทำสองรอบ —
แต่ **เป็นการขยายขอบเขตงาน จึงต้องให้เจ้าของตัดสิน ไม่ใช่ผมตัดสิน**

### 1.6 การเปิดและการเปลี่ยน secret — **ต้องมีสถานะรอยืนยัน แยกจากตัวจริง**

**แก้ตามรีวิว** — ฉบับก่อนมี secret ช่องเดียวใน `user_totp` และใช้ `confirmed_at IS NULL`
แทนสถานะรอยืนยัน ซึ่งพอสำหรับการเปิดครั้งแรก **แต่พังสำหรับการเปลี่ยนเครื่อง**:
เขียนทับก่อนยืนยัน = เปิดใช้ปัจจัยที่ยังไม่พิสูจน์ หรือปิด TOTP ชั่วคราวโดยที่ผู้ใช้ไม่ได้สั่ง
ซึ่งขัด RQ-3 และทำให้ผู้ใช้ล็อกตัวเองออกได้

**ทางแก้: ตารางแยก `user_totp_pending` และใช้กลไกเดียวกันทั้งการเปิดครั้งแรกและการเปลี่ยน**

```
user_totp          ← มีแถว = เปิดใช้แล้ว (ไม่มี confirmed_at อีก ไม่กำกวม)
user_totp_pending  ← secret ที่ยังไม่พิสูจน์ หนึ่งแถวต่อผู้ใช้ เขียนทับได้
```

| ขั้น | เกิดอะไร |
|---|---|
| `setup` หรือ `replace` | เขียน `user_totp_pending` (ทับของเดิมถ้ามี) และ **คืน otpauth URI ครั้งเดียว** · **ปัจจัยเดิมยังทำงานปกติทุกอย่าง** |
| `confirm` | ใน **transaction เดียว**: ตรวจรหัสจาก pending → ย้ายเข้า `user_totp` พร้อม `secret_version + 1` และ **`last_accepted_step` = ช่วงของรหัสที่เพิ่งยืนยันสำเร็จ** (ไม่ใช่ศูนย์ — ดู 1.2) → ลบแถว pending → **ยกเลิกรหัสสำรองชุดเก่าทั้งชุดและออกชุดใหม่** (RQ-15) → เพิกถอน session อื่น (Q-3.4) |
| ผู้ใช้ทิ้งกลางทาง | แถว pending ค้างแต่ **ไม่มีผลกับอะไรเลย** · ปัจจัยเดิมยังใช้ได้ · เรียก `setup`/`replace` ใหม่ทับได้ |

**ข้อสำคัญ: รหัสสำรองชุดเก่าถูกยกเลิกตอน `confirm` ไม่ใช่ตอน `replace`**
เพราะถ้ายกเลิกก่อนยืนยัน ผู้ใช้ที่ทิ้งกลางทางจะเสียทั้งรหัสสำรองและเครื่องใหม่
ฉบับก่อนเขียนว่า `replace` "เปลี่ยน + ยกเลิกรหัสสำรองทันที" ซึ่ง **ผิด**

**ผลต่อ `validation.md`:** V-5 เดิมบอกว่าไม่มี endpoint ใดคืน secret —
ต้องแก้เป็น **"ไม่มี endpoint คืน secret ที่ยืนยันแล้ว"** เพราะ `setup`/`replace`
ต้องคืน secret ใหม่ครั้งเดียวเพื่อให้ผูกเครื่องได้ (แก้แล้วใน `validation.md` V-5)

### 1.7 การจัดประเภทเส้นทางที่ลืมไม่ได้ (RQ-6)

เปลี่ยน `routing_policy.py` จากสองรายการลอย ๆ เป็น **ตารางเดียวที่ทุกเส้นทาง
ต้องมีแถวของตัวเอง**:

```python
@dataclass(frozen=True, slots=True)
class RouteRule:
    public: bool
    renews: bool
    reverify: bool       # ต้องยืนยัน TOTP ซ้ำ
    risk_reducing: bool  # เป็นคำสั่งลดความเสี่ยง (RQ-7 ก.)
```

| กลไก | ทำอย่างไร |
|---|---|
| เส้นทางใหม่ที่ไม่มีแถว | เทสต์เดินทุกเส้นทางใน `app.routes` แล้ว **แดง** |
| middleware เจอ path ที่ไม่มีแถว ตอนรัน | **ปฏิเสธ** — สองชั้นแบบแผนของ F-03/F-05 |
| `risk_reducing` และ `reverify` จริงพร้อมกัน | **เทสต์แดง** — บังคับ RQ-7 (ก) **ก่อน**ที่เส้นทางเหล่านั้นจะมีจริง |
| สับสน (ข) กับ (ก) | รีเซ็ตเพดานและเปิดบอทกลับได้ `reverify=False, risk_reducing=False` + เทสต์ตรึงค่า + คอมเมนต์อ้าง RQ-7 (ข) |

**ของเดิมไม่เสียไป** — `is_public()` และ `renews_session()` ชื่อเดิม พฤติกรรมเดิม
เทสต์ของ F-05 ต้องเขียวโดยไม่แก้

### 1.8 สิทธิ์กู้บัญชี (Q-3.3)

ตาราง `recovery_grants` หนึ่งแถวต่อการกู้หนึ่งครั้ง ออกใน transaction เดียวกับ
การออก session ของขั้นที่สองที่ผ่าน**ด้วยรหัสสำรอง**

| ข้อบังคับ | ทำอย่างไร |
|---|---|
| ผูกกับ session ใบนั้นใบเดียว | คีย์คือแฮชโทเคนของ session ที่เพิ่งออก |
| ใช้ได้ที่ `replace` และ `disable` เท่านั้น | ตรวจที่ endpoint ทั้งสอง **ไม่ใช่สิทธิ์ทั่วไป** |
| ใช้ครั้งเดียว | `WHERE used_at IS NULL` แล้วดูจำนวนแถว |
| **ไม่แทนรหัสผ่าน** | ยังต้องกรอกรหัสผ่านปัจจุบันตาม Q-4 · สิทธิ์นี้แทนเฉพาะ**รหัส TOTP** |
| หายไปพร้อม session | `ON DELETE CASCADE` จากแถว session |
| **session นั้นต้องยังใช้ได้จริง** | **ตรวจอายุของ session ในเงื่อนไขของการใช้สิทธิ์** ไม่พึ่ง `ON DELETE CASCADE` อย่างเดียว เพราะ **แถว session ที่หมดอายุยังอยู่ในตารางจนถูกลบ** — `CASCADE` ทำงานตอนลบ ไม่ใช่ตอนหมดอายุ (แก้ตามรีวิว 2026-10-03) |

**อายุของสิทธิ์ยังไม่มีคำตอบ → Q-11** (หัวข้อ 12)

## 2. ข้อบกพร่องของ F-05 ที่ต้องตัดสินก่อน — **ตัวนับการเดาถูกย้อนทิ้ง**

**เรื่องนี้ใหญ่กว่างานนี้ และต้องให้เจ้าของตัดสิน** (`AGENTS.md`: โค้ดกับ spec
ไม่ตรงกัน ให้หยุดถาม) · พบตอนรีวิวแผนนี้ 2026-10-03

### 2.1 อาการ

`throttled()` ให้ `ThrottleGuard` อยู่ **ข้างใน** transaction ที่เปิดด้วย
`engine.begin()` (`services/api/throttling.py` → `infra/db/session.py` `_begin()`)
และ `_begin()` **rollback เมื่อมีข้อผิดพลาดใด ๆ หลุดออกมา รวม `HTTPException`**

เส้นทาง login ของ F-05 เขียนว่า:

```python
await guard.count_attempt()
raise HTTPException(status.HTTP_401_UNAUTHORIZED, LOGIN_FAILED)
```

`HTTPException` หลุดออกจาก `async with throttled(...)` → `_begin()` rollback
→ **การนับหายไป** · ผลคือ **การเข้าสู่ระบบที่ล้มเหลวไม่ถูกนับเลย**
และการคุมอัตราการเรียกหน้า login ของ F-05 **ไม่ทำงานจริง**
(เส้นทางสมัครที่ชน 409 ก็เหมือนกัน)

**ยืนยันแล้วสองทาง:** อ่านโค้ด `_begin()` ที่ rollback บน `BaseException`
และรีวิวรายงานผลทดลองกับ PostgreSQL จริงว่าได้ `[]` แทน `[1]`

### 2.2 ทำไมไม่มีใครจับได้

`backend/tests/infra/auth/test_throttle_rules.py` เรียก `count_failure()` ตรง ๆ
บน session ที่ commit ตามปกติ จึงเขียวเสมอ · **ไม่มีเทสต์ใดในทั้ง repo เรียก
`count_attempt` ผ่านเส้นทาง HTTP ที่ถูกปฏิเสธ** (ค้นแล้ว) — ด่านที่ F-05 อ้างว่าครบ
จึงไม่ครอบข้อนี้

### 2.3 ทำไมงานนี้เลี่ยงไม่ได้

RQ-8 ของงานนี้บังคับให้จำกัดการเดารหัส TOTP **อย่างมีผลจริง** และ V-24.2 บังคับว่า
ตัวนับต้องรอด rollback · ถ้าใช้ `throttled()` ตามที่เป็น **ถังของ TOTP จะพังแบบเดียวกัน**
ฉะนั้น **ข้อนี้ไม่ขึ้นกับตัวเลขของ Q-7 เลย** และต้องแก้ก่อนถังใหม่จะมีความหมาย

### 2.4 ทางแก้ที่เสนอ

ตัวนับต้อง **commit แม้คำขอถูกปฏิเสธ** แต่ต้อง **ยังล็อกถังไว้ตลอดช่วงที่ตรวจ**
(ถ้าปล่อยล็อกก่อนตรวจ การยิง 20 คำขอพร้อมกันจะผ่านด่านทั้งหมด — เหตุผลเดิมของ F-05)
ฉะนั้นแยก transaction เฉย ๆ ไม่พอ และนับหลังปล่อยล็อกก็ไม่ได้

| ทางเลือก | ผลที่ตามมา |
|---|---|
| **ก. `throttled()` จับ *ชนิดข้อผิดพลาดของเราเอง* ไว้ *ภายใน* transaction แล้วโยนต่อ *หลัง* commit** | **ไม่ต้องแก้ `infra/db/session.py` เลย** (แก้ตามรีวิว) — ข้อผิดพลาดไม่หลุดออกจาก `async with presented_session(...)` จึง commit ตามปกติ แล้วค่อยโยนหลังออกจากบล็อก **แลกกับ** เส้นทางต้องโยนชนิดของเราแทน `HTTPException` ตรง ๆ ซึ่งแก้ที่ `auth_routes.py` ไฟล์เดียว |
| ข. จับ `HTTPException` **ทุกชนิด** | **ผมไม่เสนอแล้ว** (เดิมเสนอข้อนี้ — **ผิด**) · `HTTPException` ครอบ 500/503 ด้วย การ commit เมื่อเจอความผิดพลาดของระบบคือการ commit สถานะที่ไม่ได้ตั้งใจ |
| ค. ให้เส้นทางเรียก `raise` **หลัง** ออกจาก guard | ไม่แก้ infra **แลกกับ** ลืมเรียกได้ และการลืมหมายถึง "login ที่ล้มเหลวผ่านเข้าไป" — ความพลาดที่แพงที่สุด |
| ง. นับบน connection อีกเส้นที่ commit แยก | ตัวนับรอด **แลกกับ** การนับไม่ได้อยู่ใต้ล็อกเดียวกับการตัดสิน จึงนับผิดตอนยิงพร้อมกัน |

**ผมเสนอ ก.** รูปร่างคือ:

```python
rejection: AuthRejected | None = None
async with presented_session(engine, role=DatabaseRole.AUTH) as session:
    ...claim ทุกถัง...
    try:
        yield ThrottleGuard(...)
    except AuthRejected as caught:   # ชนิดของเราเท่านั้น
        rejection = caught
        # ไม่โยนต่อที่นี่ → transaction จบปกติ → ตัวนับถูก commit
if rejection is not None:
    raise rejection.as_http_exception()
```

**เส้นแบ่งที่ต้องชัด:** `AuthRejected` คือ "คำขอนี้ถูกปฏิเสธตามกฎ" ซึ่งเป็น**ผลลัพธ์ปกติ**
ของเส้นทางยืนยันตัวตน · ส่วน bug, ฐานข้อมูลล่ม, 500/503 **ไม่ใช่ชนิดนี้ และยัง rollback
ตามเดิม** — เกณฑ์ V-68 บังคับข้อนี้ และเกณฑ์ V-69 บังคับว่าล็อกยังถูกถือไว้เหมือนเดิม

### 2.5 ขอบเขตของการแก้ — **เจ้าของต้องเลือก**

| ทางเลือก | ผลที่ตามมา |
|---|---|
| **ก. แก้ในงานนี้** พร้อมเทสต์ถดถอยที่ครอบ **เส้นทางของ F-05 ด้วย** (login, register) | ถังของ TOTP มีความหมายทันที และข้อบกพร่องที่มีอยู่ถูกปิด **แลกกับ** งานนี้แตะโค้ดของ F-05 ซึ่ง `AGENTS.md` ข้อ 10 ห้ามโดยปริยาย — **จึงต้องได้อนุมัติชัดเจน** |
| ข. แยกเป็นงานแก้ของ F-05 แล้วทำก่อน F-06 | ขอบเขตสะอาด **แลกกับ** F-06 รออีกหนึ่งงาน |
| ค. ปล่อยไว้ | **ผมไม่เสนอ** — RQ-8 เป็นจริงไม่ได้ และ F-05 ยังไม่มีการคุมอัตราจริงบนหน้า login |

**ผมเสนอ ก.** เพราะกลไกเดียวกันและเทสต์ชุดเดียวกัน · ถ้าเลือก ข. ขอให้บันทึกใน
`roadmap.md` ว่า F-05 มีข้อบกพร่องนี้ค้างอยู่ **และมันกระทบ NC-14** เพราะคำอธิบาย
ของ NC-14 สมมติว่าการหน่วงทำงาน

## 4. กุญแจเข้ารหัส: รอยต่อ T-03 และขอบเขตที่แยกจาก F-07

### 4.1 ที่มาของกุญแจ — ตัดสินเฉพาะ dev/CI (Q-1 ทาง ก.)

```
KeySource (สัญญา)   ← รอยต่อของ T-03
   └── EnvKeySource   — environment variable (dev และ CI)
   └── (อนาคต F-31)   — ไฟล์บนเครื่อง + สิทธิ์เข้ม หรือบริการจัดการกุญแจ
```

| ข้อ | ทำอย่างไร |
|---|---|
| ที่มาใน dev/CI | environment variable ตามแบบแผนที่ F-01 วางไว้ |
| เปลี่ยนที่มาได้ภายหลัง | ผู้เรียกรู้จักแต่สัญญา · **ทุก ciphertext พา `key_version` ติดไปในแถว** |
| **T-03 ฝั่ง VPS ยังไม่ปิด** | เขียนกำกับใน docstring และในหัวข้อ 11 — เป็นงาน **F-31** |
| กุญแจไม่มี/อ่านไม่ได้ | **ดังตอนเริ่มกระบวนการ** ไม่ใช่ตอนมีผู้ใช้คนแรก |

### 4.2 ขอบเขตสิทธิ์ที่แยกจาก F-07 (RQ-14)

| แชร์ได้ | **ห้าม**แชร์ |
|---|---|
| **โครงสร้าง** — สัญญา `KeySource`, รูป ciphertext, `key_version`, วิธีหมุนกุญแจ | **กุญแจตัวเดียวกัน** |
| แบบแผนการตั้งชื่อและการทดสอบ | **ขอบเขตบทบาท** — `tiewtrade_auth` อ่าน secret ของ TOTP ได้ แต่ต้องอ่าน secret ของตลาดไม่ได้เลย · `tiewtrade_api` อ่านไม่ได้ทั้งคู่ |

`tech-stack.md` หัวข้อ 8 บังคับว่า API secret ของตลาดถอดได้เฉพาะใน `engine`
ใช้กุญแจเดียวกันเท่ากับยกเลิกข้อนั้นโดยไม่แก้ spec

### 4.3 ไลบรารีเข้ารหัส — **ต้องขออนุมัติเพราะ `tech-stack.md` ไม่ได้ครอบ**

เสนอ **AES-GCM จาก `cryptography`** โดยใช้ `user_id` เป็น associated data
เพื่อให้ ciphertext ที่ถูกย้ายไปแถวของคนอื่นถอดไม่ออก

| ทางเลือก | ผลที่ตามมา |
|---|---|
| **ก. `cryptography` (AES-GCM)** | ไลบรารีมาตรฐาน มี AEAD ให้ตรง ๆ **แลกกับ** dependency ที่มีส่วนคอมไพล์ |
| ข. เขียนเองจาก `hashlib`/`hmac` | ไม่เพิ่ม dependency **แลกกับ** เขียนโค้ดเข้ารหัสเอง ซึ่งไม่ควรทำ |
| ค. `pgcrypto` | กุญแจต้องเดินทางเข้า SQL จึงเสี่ยงลง log ของฐานข้อมูล — ขัด `security.md` หัวข้อ 4 |

**ผมเสนอ ก.** · ถ้าอนุมัติ **ต้องเพิ่มบรรทัดใน `tech-stack.md` ด้วย**

### 4.4 ตัวคำนวณ TOTP — ไม่เพิ่ม dependency

`core/totp.py` ใช้ `hmac` + `hashlib` + `struct` + `base64` จาก standard library
**ไม่ใช้ไลบรารี TOTP สำเร็จ** เพราะหลายตัวรับ `secrets` หรืออ่านนาฬิกาเอง
ซึ่งตัวตรวจความบริสุทธิ์ของ `core` ห้าม · และ **RFC 6238 มีชุดตัวเลขทดสอบมาให้**

## 6. ผลต่อฐานข้อมูล — `0008_totp.py`

ทุกตารางทำตามกฎที่ F-03 ทิ้งไว้: คอลัมน์เจ้าของ, `ENABLE` + `FORCE ROW LEVEL SECURITY`,
สิทธิ์ทีละคอลัมน์ (RQ-10) · `tiewtrade_api` **ไม่มีสิทธิ์ใด ๆ บนทั้งห้าตาราง**

### 6.1 `user_totp` — มีแถว = เปิดใช้แล้ว

| คอลัมน์ | หมายเหตุ |
|---|---|
| `user_id uuid PRIMARY KEY REFERENCES users (id)` | บังคับ "หนึ่ง active secret ต่อผู้ใช้" ที่ระดับฐานข้อมูล (Q-10) |
| `secret_sealed bytea NOT NULL` | ปิดผนึกแล้ว |
| `key_version text NOT NULL` | รอยต่อการหมุนกุญแจ |
| `secret_version integer NOT NULL DEFAULT 1` | **ชั้นที่สองของการกันใช้ซ้ำ** (1.2) |
| `last_accepted_step bigint NOT NULL` | **ตอนสลับ secret ตั้งเป็นช่วงของรหัสที่ยืนยันสำเร็จ ไม่ใช่ศูนย์** (1.2) — ไม่มี `DEFAULT` เพราะไม่มีกรณีที่แถวเกิดขึ้นโดยไม่รู้ช่วงที่ผ่าน |
| `created_at`, `updated_at` | เวลามาจากฐานข้อมูล |

**ไม่มี `confirmed_at`** — สถานะรอยืนยันอยู่ในตารางแยก (1.6) จึงไม่มีสถานะกำกวม

### 6.2 `user_totp_pending` — secret ที่ยังไม่พิสูจน์

`user_id` PK, `secret_sealed`, `key_version`, `created_at` · เขียนทับได้
· **ไม่มีผลกับการยืนยันตัวตนใด ๆ** · สิทธิ์: `tiewtrade_auth` เท่านั้น

### 6.3 `user_recovery_codes`

`id` PK, `user_id` (เจ้าของ), `code_hash` (**argon2 ด้วย `hash_password()` ตัวเดิม**),
`used_at`, `created_at`

ใช้ครั้งเดียวจริง: `UPDATE ... WHERE id = :id AND used_at IS NULL` แล้วดูจำนวนแถว
· **ยกเลิกทั้งชุดเป็น atomic** — `DELETE` ทุกแถวของผู้ใช้แล้ว `INSERT` ชุดใหม่
**ใน transaction เดียวกับการสลับ secret** (1.6)

**ข้อแลกเปลี่ยน:** argon2 ต่อใบราว 100 มิลลิวินาที การตรวจต้องเทียบทุกใบที่ยังไม่ใช้
จึงแพงตามจำนวนใบ — เหตุผลที่จำนวนใบไม่ควรมาก และที่ถังของรหัสสำรองใน Q-7 ต้องคุม

### 6.4 `login_challenges`

| คอลัมน์ | หมายเหตุ |
|---|---|
| `token_hash text PRIMARY KEY` | แฮช SHA-256 รูปแบบเดียวกับ `sessions` |
| `user_id uuid NOT NULL REFERENCES users (id)` | คอลัมน์เจ้าของ |
| `credential_updated_at timestamptz NOT NULL` | **รุ่นของรหัสผ่าน** (1.4) |
| `expires_at timestamptz NOT NULL` | **ไม่มีสิทธิ์ `UPDATE` ให้ใครเลย** → ต่ออายุไม่ได้ |
| `created_at` | |

**สอง policy** ตาม 1.5 — `presented` (SELECT, โทเคน + ยังไม่หมดอายุ) และ
`auth_owner` (ALL, แถวของผู้ใช้ปัจจุบัน รวมที่หมดอายุ เพื่อให้ลบได้)

### 6.5 `recovery_grants`

`session_token_hash` PK `REFERENCES sessions (token_hash) ON DELETE CASCADE`,
`user_id`, `used_at`, `created_at` · policy อ่านด้วยโทเคนที่พามา
· **`ON DELETE CASCADE` เป็นส่วนของการออกแบบ** — Q-3.4 เพิกถอน session อื่นทั้งหมด
ถ้าใบนี้ถูกเพิกถอนภายหลัง สิทธิ์ต้องหมดทันที

**แต่ `CASCADE` อย่างเดียวไม่พอ** (แก้ตามรีวิว) — มันทำงานตอน **ลบ** แถว session
ไม่ใช่ตอน session **หมดอายุ** และ F-05 ไม่ลบแถวที่หมดอายุทิ้ง (ปล่อยให้ policy
กรองด้วย `now() <` เท่านั้น) ฉะนั้น policy ของ `recovery_grants` ต้อง
**join กับ `sessions` แล้วตรวจทั้งสองเส้นตาย** เหมือนที่ `sessions_presented`
ของ F-05 ทำ — ไม่ใช่เชื่อว่าแถวที่ยังอยู่คือ session ที่ยังใช้ได้

### 6.6 ข้อที่ต้องระวังเรื่อง RLS กับรูปของคำสั่ง

`sessions.py` ของ F-05 บันทึกว่า PostgreSQL ดึง SELECT policy มาใช้เมื่อคำสั่ง
**อ้างคอลัมน์** และใช้ `rowcount` ไม่ใช่ `RETURNING` เพราะเหตุนี้
**ทุกคำสั่งของงานนี้ที่พึ่งจำนวนแถวต้องใช้กฎเดียวกัน** และต้องมีเทสต์พิสูจน์ด้วยสองบทบาท
· **ข้อนี้เป็นรากของข้อบกพร่องที่รีวิวจับได้ในหัวข้อ 1.5** — ไม่ใช่รายละเอียด

### 12.3 ข้อเสนอของผู้รีวิว — **ยังไม่ใช่คำอนุมัติของเจ้าของ**

บันทึกไว้เพื่อให้เจ้าของเห็นว่ามีผู้รีวิวเสนออะไร **และเพื่อไม่ให้ใครเข้าใจผิดว่า
ข้อเหล่านี้ผ่านแล้ว** — ความผิดพลาดชนิดนี้เกิดขึ้นครั้งหนึ่งแล้วใน `requirements.md`
และถูกแก้ไปแล้ว **"ไม่ค้านถือว่าผ่าน" ใช้แทนด่านอนุมัติไม่ได้**

| เรื่อง | ผู้รีวิวเสนอ | สถานะ |
|---|---|---|
| แก้ตัวนับของ F-05 | รวมใน F-06 เป็นงานแรก พร้อมเทสต์ถดถอยของ F-05 | **รอเจ้าของ** |
| แตะไฟล์เดิม | ได้เฉพาะส่วนที่จำเป็นกับตัวนับและการเพิกถอน challenge **ไม่บังคับว่าต้องครบทุกไฟล์** | **รอเจ้าของ** |
| งานเก็บกวาด | ครอบทั้ง `auth_throttle` และ `login_challenges` · **ต้องไม่ลบถังที่ยังมีผลจำกัดการเดาอยู่** | **รอเจ้าของ** |
| **Q-11** | ผูกกับ session **ที่ยังใช้ได้** และใช้ครั้งเดียว · **ต้องตรวจอายุ session จริงด้วย เพราะ `ON DELETE CASCADE` ไม่ตรวจการหมดอายุ** (ถูกต้อง — แถวที่หมดอายุยังอยู่จนถูกลบ) | **รอเจ้าของ** |
| **Q-6** | ไม่มีช่วงผ่อนผัน + แสดงให้ผู้ใช้รู้ว่าต้องรอรหัสช่วงใหม่เมื่อรหัสเดิมถูกใช้แล้ว | **รอเจ้าของ** |
| ห้าแนวทางเทคนิค (12.2 ข้อ 2–6) | เห็นด้วยกับทิศทาง | **รอเจ้าของ** |

**ข้อที่ผู้รีวิวชี้ว่าผิดและผมแก้แล้ว ไม่ใช่ข้อที่รออนุมัติ** — สองข้อ:
`last_accepted_step` ตอนสลับ secret (1.2, 1.6) และการจับชนิดข้อผิดพลาดที่แคบลง (2.4)
· **และข้อสังเกตเรื่องอายุ session ใน Q-11 ทำให้ `recovery_grants` ต้องตรวจอายุของ
session ด้วย ไม่ใช่พึ่ง `ON DELETE CASCADE` อย่างเดียว** — แก้ใน 1.8 และ 6.5 ตามนั้น
