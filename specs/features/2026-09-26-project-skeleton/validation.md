## เทสต์ที่ต้องมี

### ตัวเลขจริง

**ไม่มีในงานนี้** เพราะยังไม่มีโค้ดที่คำนวณอะไร

เกณฑ์นี้เริ่มบังคับที่ F-02 ซึ่งเป็นงานแรกที่แตะเงิน
([`standards/testing.md`](../../standards/testing.md) หัวข้อ 2)

### คุณสมบัติ (hypothesis)

**ไม่มีในงานนี้** ด้วยเหตุผลเดียวกัน แต่ต้องติดตั้ง `hypothesis` ไว้และพิสูจน์ว่ารันได้
ด้วยเทสต์ตัวอย่างหนึ่งตัว เพื่อไม่ให้ F-02 ต้องมาตั้งค่าเครื่องมือเองอีก

### ความปลอดภัยการเทรด

งานนี้ไม่แตะเงินและไม่ส่งออเดอร์ จึงยังไม่มีเทสต์ตาม
[`standards/testing.md`](../../standards/testing.md) หัวข้อ 4 ได้

**แต่ต้องมีเทสต์ที่พิสูจน์ว่าด่านซึ่งจะบังคับกฎเหล่านั้นทำงานจริง**

ต้องมีครบทุกแถวใน **ตารางจับคู่ กฎ ↔ กรณีทดสอบ** ของ [plan.md](plan.md)
ซึ่งครอบ 12 กฎ ใน 4 ด่าน

**เกณฑ์ผ่านของเทสต์กลุ่มนี้เข้มกว่าปกติ** แค่ "เครื่องมือไม่สำเร็จ" ไม่นับว่าผ่าน
ทุกกรณีต้องครบสามข้อ:

| # | ต้องพิสูจน์ | ถ้าไม่มีข้อนี้จะพลาดอะไร |
|---|---|---|
| 1 | แดง **เพราะกฎที่ตั้งใจทดสอบ** ไม่ใช่เพราะ config ผิดหรือหา package ไม่เจอ | เครื่องมือพังแล้วเทสต์เขียว |
| 2 | **กรณีที่ถูกต้องคู่กันต้องผ่าน** ภายใต้ config เดียวกัน | แยกไม่ออกว่าเครื่องมือจับความผิดได้ หรือรันไม่ได้เลย |
| 3 | รันด้วยชุดตั้งค่าเดียวกับด่านจริง | ด่านจริงตั้งหย่อนกว่าที่เทสต์พิสูจน์ |

**กลุ่มนี้คือหัวใจของงานนี้** ถ้ากรณีใดไม่แดงตามคาด แปลว่าด่านนั้นเสีย
และทุกงานหลังจากนี้จะเชื่อถือด่านนั้นไม่ได้

**การอ่านไฟล์กับการต่อเครือข่ายต้องทดสอบแยกจากกฎ import** เพราะทั้งสองอย่าง
อยู่ใน standard library จึงผ่าน import-linter ได้ ต้องพึ่งตัวตรวจความบริสุทธิ์

## ตรวจด้วยมือ

ขั้นตอนที่คนต้องลองเอง เรียงตามลำดับ

1. **โคลน repo ใหม่ในโฟลเดอร์เปล่า** แล้วทำตาม README เท่านั้น ห้ามใช้ความรู้ที่มีอยู่ในหัว
   — ถ้าทำตามไม่ได้ ถือว่างานยังไม่เสร็จ

   **ข้อควรระวังที่เจอตอนตรวจจริง 2026-09-27:** การโคลนใหม่บนเครื่องเดิมไม่พอ
   สำหรับเครื่องมือที่เก็บของไว้ที่ระดับผู้ใช้ เช่นเบราว์เซอร์ของ Playwright
   ซึ่งอยู่นอกโฟลเดอร์โปรเจกต์ การทดสอบบนเครื่องเดิมจะผ่านทั้งที่เครื่องใหม่จะพัง
   ต้องไล่อ่าน README เทียบกับสิ่งที่เครื่องมือแต่ละตัวต้องการด้วย
2. รันสี่คำสั่งตรวจ ดูว่าเขียวทั้งหมด
3. `docker compose up` แล้วเปิดเบราว์เซอร์ **เห็นข้อมูลจาก `/health` บนหน้าเว็บ**
4. **ลองทำให้ด่านแดงด้วยมือ** — แก้ไฟล์ใน `core` ให้ใช้ `float` แล้วรันเทสต์
   ต้องแดง แล้วย้อนการแก้นั้นคืน
5. เปิดผลรัน CI ของ commit ล่าสุด ดูว่ารันด่านครบและเขียว
6. ปิด `engine` กับ `market_data` ออกจากความคิดไปเลย — ยืนยันว่าไม่มีอะไรใน Compose
   พยายามรันมัน
7. **แก้ `/health` ให้เปลี่ยนชื่อช่องที่คืนมา** สร้างชนิดข้อมูลใหม่ แล้วรัน typecheck
   ของหน้าบ้าน ต้องแดง แล้วย้อนคืน (V-16)

ข้อ 4 กับข้อ 7 สำคัญที่สุด เพราะเป็นสองข้อที่พิสูจน์ว่าด่านตรวจไม่ใช่ของประดับ —
ข้อ 4 พิสูจน์ด่านหลังบ้าน ข้อ 7 พิสูจน์ว่าทางเดินหลังบ้านถึงหน้าบ้านมีจริง

## ด่านที่ต้องเขียว

ทุกด่านต้องเขียวก่อน merge **ไม่มีข้อยกเว้น**
([`standards/testing.md`](../../standards/testing.md) หัวข้อ 1)

### หลังบ้าน

```sh
uv run ruff check . && uv run ruff format --check .
uv run mypy
uv run lint-imports
uv run pytest
```

### หน้าบ้าน

```sh
npm run lint
npm run typecheck
npm run test          # vitest
npm run test:e2e      # Playwright
```

### ตรวจความตรงกันของชนิดข้อมูล

สร้างชนิดข้อมูลจาก OpenAPI ใหม่ แล้วเทียบกับที่ commit ไว้ — **ถ้าต่างกัน ถือว่าแดง**

และ typecheck ของหน้าบ้านต้องรันกับโค้ดที่**ใช้ชนิดจากไฟล์ที่สร้าง** ไม่ใช่ชนิดที่เขียนเอง
(V-15) พร้อมกรณีพิสูจน์ว่าเปลี่ยนสัญญาแล้วแดงจริง (V-16)

## สิ่งที่ validation นี้ **ไม่** ครอบ

บันทึกไว้ให้ชัดเพื่อไม่ให้ใครเข้าใจว่างานนี้พิสูจน์มากกว่าที่พิสูจน์จริง

- ไม่พิสูจน์ว่าการคำนวณเงินถูก — ยังไม่มีการคำนวณ (F-02)
- ไม่พิสูจน์ว่าต่อ Binance ได้ — ยังไม่ต่อ (F-35)
- ไม่พิสูจน์ว่าระบบทนทานต่อการเชื่อมต่อหลุด — ยังไม่มีการเชื่อมต่อ (F-10)
- ไม่พิสูจน์อะไรเกี่ยวกับความปลอดภัยของเงินหรือออเดอร์ เพราะยังไม่มีทั้งคู่
- ไม่พิสูจน์ว่า deploy บน VPS จริงได้ (F-31)
