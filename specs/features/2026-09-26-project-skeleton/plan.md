## แนวทาง

ทำ 5 ชั้นตามลำดับ แต่ละชั้นพิสูจน์ตัวเองได้ก่อนขึ้นชั้นถัดไป
ถ้าชั้นใดยังไม่เขียว ไม่ขึ้นชั้นถัดไป

| ลำดับ | ทำอะไร | พิสูจน์อะไร |
|---|---|---|
| 1 | โครงโฟลเดอร์และชั้นโค้ด | ขอบเขตการพึ่งพามีจริงและบังคับได้ |
| 2 | เครื่องมือและด่านตรวจในเครื่อง | คำสั่งเดียวรู้ผลว่าผ่านหรือไม่ |
| 3 | `api` กับหน้าบ้านบางที่สุด | ชนิดข้อมูลสองฝั่งตรงกัน และตรวจได้ |
| 4 | Docker Compose | รันใน container ได้จริง |
| 5 | CI | ทุกด่านรันเองทุกครั้งที่ push |

**เหตุผลที่เรียงแบบนี้** — ด่านตรวจต้องมาก่อนโค้ดที่มันตรวจ ถ้าเขียนโค้ดก่อนแล้วค่อยตั้งด่าน
เราจะปรับด่านให้เข้ากับโค้ดที่เขียนไปแล้ว ซึ่งกลับหัวกับเจตนาของ RQ-6 และ RQ-12

## โครงโฟลเดอร์ที่เสนอ

```
tiewtrade/
├── backend/
│   ├── pyproject.toml          ← uv, ruff, mypy, pytest, import-linter ที่เดียว
│   ├── src/tiewtrade/          ← namespace ของโปรเจกต์ (เจ้าของตัดสิน 2026-09-27)
│   │   ├── core/               ← ตรรกะโดเมนบริสุทธิ์ (ยังว่าง)
│   │   ├── strategies/         ← ยังว่าง
│   │   ├── venues/             ← ยังว่าง (RQ-5 ห้ามออกแบบส่วนต่อประสาน)
│   │   ├── infra/              ← ยังว่าง
│   │   └── services/
│   │       ├── api/            ← FastAPI มี endpoint เดียว
│   │       ├── engine/         ← มีจุดเริ่มโปรแกรมเปล่า ไม่มีตรรกะ
│   │       └── market_data/    ← มีจุดเริ่มโปรแกรมเปล่า ไม่มีตรรกะ
│   └── tests/
│       ├── test_core_purity.py     ← RQ-7
│       └── gates/                  ← RQ-12 กรณีที่ต้องถูกปฏิเสธ
├── frontend/
│   ├── package.json            ← vite, vitest, playwright
│   └── src/
│       ├── api-types.ts        ← สร้างจาก OpenAPI ห้ามแก้มือ
│       └── App.tsx             ← หน้าเปล่าหนึ่งหน้า
├── compose.yaml                ← api + frontend เท่านั้น (RQ-18)
└── .github/workflows/ci.yml
```

**`engine` และ `market_data` มีจุดเริ่มโปรแกรมเปล่า** เพราะ RQ-2 บอกว่าโครงสร้างต้อง
รองรับสามโปรเซสแยกกัน ถ้าไม่สร้างไว้ กฎ import-linter จะไม่มีอะไรให้ตรวจ
แต่ทั้งสองตัวไม่อยู่ใน Compose เพราะยังไม่มีอะไรให้รัน (RQ-18)

## จุดตัดสินทางเทคนิคในแผนนี้

ทุกข้อเป็นเรื่องเครื่องมือ ไม่ใช่เรื่องธุรกิจ แต่เจ้าของควรเห็นก่อนอนุมัติ

| # | เลือก | เหตุผล |
|---|---|---|
| P-1 | ใช้ `src/` layout ใน backend | กันการ import โค้ดจากโฟลเดอร์ที่ไม่ได้ติดตั้ง ซึ่งทำให้เทสต์ผ่านในเครื่องแต่พังใน container |
| P-2 | ตั้งค่าเครื่องมือทั้งหมดใน `pyproject.toml` ไฟล์เดียว | RQ-9 บอกว่าคำสั่งในเครื่องต้องเหมือน CI ยิ่งมีที่ตั้งค่าน้อย ยิ่งหลุดกันยาก |
| P-3 | `mypy` เปิด strict ทั้ง backend และเข้มเพิ่มอีกชั้นกับ `core` | RQ-10 สั่งให้เข้มที่สุดกับโค้ดคำนวณเงิน ซึ่งจะอยู่ใน `core` ทั้งหมด |
| P-4 | สร้างชนิดข้อมูลหน้าบ้านด้วย `openapi-typescript` | แปลง OpenAPI เป็น TypeScript ตรง ๆ ไม่สร้างโค้ดเรียก API ให้ด้วย จึงไม่ผูกเรากับรูปแบบของเครื่องมือ |
| P-5 | **CI ตรวจความตรงกันด้วยการสร้างใหม่แล้วเทียบ** ถ้าต่างจากที่ commit ไว้ ให้ CI แดง | RQ-16 ต้องตรวจได้ ไม่ใช่เชื่อว่าคนจะสร้างใหม่ทุกครั้ง |
| P-6 | endpoint เดียวคือ `GET /health` คืนสถานะและเวลาของเซิร์ฟเวอร์ | เล็กพอที่จะไม่กลายเป็นการออกแบบ API จริง แต่มีข้อมูลให้หน้าบ้านแสดงพอพิสูจน์ทางเดิน |
| P-9 | **โค้ดหน้าบ้านที่รับและแสดง `/health` ต้องใช้ชนิดจากไฟล์ที่สร้าง** ห้ามเขียนชนิดเอง ห้ามใช้ `any` และ ruff/eslint ต้องห้าม `any` ไว้ | ถ้าหน้าบ้านไม่ได้ใช้ไฟล์ที่สร้าง การเทียบไฟล์จะผ่านโดยที่โค้ดจริงไม่ผูกกับสัญญา API เลย (รีวิวข้อ 4) |
| P-10 | ต้องมีกรณีทดสอบว่า **เปลี่ยนสัญญา API แล้วด่านชนิดข้อมูลของหน้าบ้านต้องแดง** | พิสูจน์ว่าทางเดินครบวงมีจริง ไม่ใช่สองฝั่งตรงกันโดยบังเอิญ |
| P-7 | ตรวจ `core` บริสุทธิ์ด้วยการอ่านโครงสร้างโค้ด (AST) ไม่ใช่ค้นข้อความ | ค้นข้อความจะพลาดทั้งสองทาง — จับคำในคอมเมนต์ผิด ๆ และไม่เห็นการเรียกที่เขียนอ้อม |
| P-8 | Python 3.12, Node 22 LTS ระบุเวอร์ชันตายตัวทั้งในเครื่องและ CI | เวอร์ชันต่างกันคือสาเหตุอันดับหนึ่งของ "ในเครื่องผ่านแต่ CI แดง" |

## ด่านตรวจและกฎที่จะตั้ง

### import-linter (RQ-6)

| กฎ | ห้ามอะไร |
|---|---|
| `core` เป็นชั้นล่างสุด | `core` ห้าม import อะไรเลยนอกจาก standard library |
| `strategies`, `venues`, `infra` พึ่งได้แค่ `core` | ห้ามพึ่งกันเอง และห้ามพึ่ง service |
| service ทั้งสามห้าม import กันเอง | `api` ห้ามเห็น `engine` และกลับกัน |

### ตรวจ `core` บริสุทธิ์ (RQ-7)

ห้ามใน `core`: การอ่านนาฬิกา, ค่าสุ่ม, การอ่านไฟล์, การต่อเครือข่าย, `float`

### กรณีที่ต้องถูกปฏิเสธ (RQ-12)

เก็บไว้ถาวรใน `backend/tests/gates/` แต่**อยู่นอกเส้นทางที่ด่านปกติสแกน**
แล้วมีเทสต์ที่รันเครื่องมือกับไฟล์เหล่านั้น

**การ "แดง" เฉย ๆ ไม่นับว่าผ่าน** เทสต์ต้องตรวจสามอย่างทุกครั้ง:

1. **แดงเพราะกฎที่ตั้งใจทดสอบ** ไม่ใช่แดงเพราะ config ผิด หา package ไม่เจอ
   หรือเครื่องมือเริ่มไม่ได้ — ต้องเทียบว่าข้อความผิดพลาดชี้ไปที่กฎข้อนั้นจริง
2. **มีกรณีที่ถูกต้องคู่กันเสมอ** และกรณีนั้นต้อง **ผ่าน** ภายใต้ config เดียวกัน
   ถ้าทั้งกรณีผิดและกรณีถูกแดงทั้งคู่ แปลว่าเครื่องมือรันไม่ได้ ไม่ใช่จับความผิดได้
3. **รันด้วยชุดตั้งค่าเดียวกับด่านจริง** ไม่ใช่ตั้งค่าพิเศษเฉพาะเทสต์

เหตุผล: เทสต์ที่คาดหวังแค่ "ไม่สำเร็จ" จะขึ้นเขียวเมื่อเครื่องมือพัง ซึ่งเป็นกรณีที่
เราต้องการให้ดังที่สุด แต่กลับกลายเป็นเงียบที่สุด
(แก้ตามรีวิว `specs/reviews/2026-09-27-project-skeleton-plan-validation.md` ข้อ 2)

### ตารางจับคู่ กฎ ↔ กรณีทดสอบ

ทุกด่านและทุกกฎต้องมีอย่างน้อยหนึ่งแถว ตาม RQ-12

| กฎที่ต้องพิสูจน์ | กรณีที่ต้องถูกปฏิเสธ | ด่าน |
|---|---|---|
| `core` ห้ามพึ่งอะไรนอก standard library | `core` ที่ `import httpx` | import-linter |
| `strategies`, `venues`, `infra` ห้ามพึ่งกันเอง | `strategies` ที่ import `venues` | import-linter |
| ชั้นเหล่านั้นห้ามพึ่ง service | `venues` ที่ import `services.api` | import-linter |
| service ห้าม import กันเอง | `api` ที่ import `engine` | import-linter |
| `core` ห้ามใช้ `float` | `core` ที่ประกาศ `x: float` | ตรวจความบริสุทธิ์ |
| `core` ห้ามอ่านนาฬิกา | `core` ที่เรียก `datetime.now()` | ตรวจความบริสุทธิ์ |
| `core` ห้ามใช้ค่าสุ่ม | `core` ที่เรียก `random.random()` | ตรวจความบริสุทธิ์ |
| `core` ห้ามอ่านไฟล์ | `core` ที่เรียก `open()` หรือ `pathlib.Path.read_text()` | ตรวจความบริสุทธิ์ |
| `core` ห้ามต่อเครือข่าย | `core` ที่ `import socket` และเรียกใช้ | ตรวจความบริสุทธิ์ |
| ต้องระบุชนิดข้อมูลครบ | ฟังก์ชันที่ไม่ระบุชนิด | mypy |
| ต้องไม่มีของที่ import แล้วไม่ใช้ และกฎ lint อื่น | ไฟล์ที่ import แล้วไม่ใช้ | ruff check |
| รูปแบบโค้ดต้องตรงตามที่กำหนด | ไฟล์ที่จัดรูปแบบผิด | ruff format --check |

**การอ่านไฟล์และการต่อเครือข่ายอยู่ใน standard library** จึงผ่าน import-linter ได้
ต้องพึ่งตัวตรวจความบริสุทธิ์ ไม่ใช่กฎ import — สองเรื่องนี้แยกกัน

**ถ้าเครื่องมือไม่จับไฟล์เหล่านี้ เทสต์จะแดง** ซึ่งหมายความว่าด่านเสีย ไม่ใช่โค้ดผิด

## ความเสี่ยง

| ความเสี่ยง | จะรู้ได้อย่างไร | ถ้าเกิดแล้วทำอะไร |
|---|---|---|
| **ด่านตรวจเขียวเพราะไม่มีอะไรให้ตรวจ** — ความเสี่ยงหลักของงานนี้ | กรณีใน `tests/gates/` จะไม่ถูกจับ แล้วเทสต์แดง | แก้การตั้งค่าเครื่องมือ ไม่ใช่แก้เทสต์ |
| ชนิดข้อมูลหน้าบ้านหลุดจากหลังบ้าน | CI สร้างใหม่แล้วเทียบ ถ้าต่างจะแดง (P-5) | สร้างใหม่แล้ว commit |
| กฎ import-linter เขียนผิดจนไม่ครอบอะไรเลย | กรณีที่ต้องถูกปฏิเสธจะผ่าน แล้วเทสต์แดง | แก้กฎ |
| ตัวตรวจความบริสุทธิ์จับผิดตัว (false positive) จนกวนงานภายหลัง | F-02 จะเป็นงานแรกที่โดนตรวจจริง ถ้ากวนจะเห็นทันที | ปรับตัวตรวจ **ห้ามปิดการตรวจ** |
| Docker build ช้าจนไม่มีใครอยากรัน | จับเวลาตอนทำ | แยกชั้น cache ให้ dependency ไม่ถูก build ใหม่ทุกครั้ง |
| เวอร์ชันเครื่องมือในเครื่องกับ CI ต่างกัน | CI แดงทั้งที่ในเครื่องเขียว | P-8 ระบุเวอร์ชันตายตัว และล็อก dependency |

### ความเสี่ยงที่ผมอยากให้เจ้าของรู้ก่อนอนุมัติ

**งานนี้ไม่มีอะไรให้ดูบนหน้าจอเลยนอกจากข้อความสั้น ๆ หนึ่งบรรทัด**

เวลาส่วนใหญ่หมดไปกับการตั้งด่านตรวจและพิสูจน์ว่าด่านทำงาน ซึ่งมองจากข้างนอกเหมือนไม่มีความคืบหน้า

ถ้าเจ้าของอยากเห็นความคืบหน้าที่จับต้องได้เร็วกว่านี้ ต้องคุยกันตอนนี้ ไม่ใช่ตอนงานเสร็จ
