### 1. ขยายกลไก append-only ให้รองรับพาร์ทิชัน

F-03 สร้าง `tiewtrade_make_append_only(regclass)` ไว้ตอนที่ยังไม่มีตารางที่แบ่งพาร์ทิชัน
พอมาถึงตารางแบบนี้จะมีสองช่องที่ยังไม่ถูกปิด:

| ช่อง | เพราะอะไร |
|---|---|
| `TRUNCATE` ที่พาร์ทิชันโดยตรง | trigger ระดับ statement ที่ผูกกับตารางแม่ **ไม่ถูกโคลนไปที่พาร์ทิชัน** สั่ง `TRUNCATE` ที่พาร์ทิชันตรง ๆ จึงไม่ถูกดัก |
| สิทธิ์ของพาร์ทิชัน | พาร์ทิชันมี ACL ของตัวเอง ไม่ได้รับมาจากตารางแม่ การ `REVOKE` ที่แม่จึงไม่ครอบพาร์ทิชัน |

ส่วน trigger **ระดับแถว** (`UPDATE`/`DELETE`) ที่สร้างบนตารางแม่ PostgreSQL โคลนไปให้
พาร์ทิชันเองอยู่แล้ว ถ้าเราไปสร้างซ้ำที่พาร์ทิชันจะชนชื่อกัน

**เสนอ: แก้ฟังก์ชันเดิมใน migration ใหม่ของงานนี้ ไม่สร้างฟังก์ชันที่สอง**
ให้ฟังก์ชันเดิมทำเพิ่มสองอย่างเมื่อเป้าหมายเป็นตารางที่แบ่งพาร์ทิชัน: ไล่พาร์ทิชันที่มีอยู่
เพื่อ `REVOKE` สิทธิ์และผูก trigger `BEFORE TRUNCATE` ให้ทีละตัว โดย**ไม่**สร้าง trigger
ระดับแถวซ้ำ

เหตุผลที่แก้ของเดิมแทนการเพิ่มตัวใหม่: ถ้ามีสองฟังก์ชัน คนที่มาทีหลังต้องรู้ว่าตารางของตัวเอง
เป็นแบบไหนแล้วเลือกให้ถูก ซึ่งเป็นการเลือกที่พลาดได้และไม่มีอะไรเตือน
(`AGENTS.md` — ตรรกะเดียวกันต้องอยู่ที่เดียว)

**ทางเลือกที่ไม่เลือก:** เพิ่ม `tiewtrade_make_partition_append_only()` แยก —
ง่ายกว่าเพราะไม่แตะของที่ merge แล้ว แต่ทิ้งทางเลือกที่พลาดได้ไว้ให้ทุกงานหลังจากนี้

**กฎที่ต้องเขียนไว้:** พาร์ทิชันที่สร้างเพิ่มในอนาคตต้องผ่านฟังก์ชันนี้ด้วย
งานนี้จึงห่อการสร้างพาร์ทิชันไว้ในฟังก์ชันเดียวที่ทำทั้งสองขั้นให้เสร็จในตัว
เพื่อไม่ให้มีทางสร้างพาร์ทิชันที่ลืมเปิดกลไก

### 1.1 บังคับด้วยกลไก ไม่ใช่ด้วยการจำ (เจ้าของอนุมัติเพิ่ม 2026-09-27)

ฟังก์ชันสร้างพาร์ทิชันกันได้เฉพาะคนที่เรียกมัน **คนที่สร้างพาร์ทิชันด้วยมือยังหลุด**
ซึ่งอ่อนกว่ากฎอื่นในสเปกที่บังคับด้วยกลไกทั้งหมด จึงเพิ่ม **event trigger** ที่ดักการสร้าง
และการผูกพาร์ทิชัน แล้วปิดพาร์ทิชันใหม่ให้เองทันที

**ขอบเขตที่เจ้าของกำหนด: กันการสร้างพาร์ทิชันผิดพลาด ไม่ใช่รับประกันป้องกัน superuser**
คนที่เป็น superuser ปิด event trigger ได้เหมือนที่ปิด trigger อื่นได้ ข้อจำกัดนี้เหมือนเดิม
(F-04 RQ-20) สิ่งที่เพิ่มขึ้นคือความผิดพลาดของคนทำงานปกติจะไม่กลายเป็นช่องถาวร

เงื่อนไขที่ต้องครบ:

| # | เงื่อนไข |
|---|---|
| ก | ครอบทั้ง **`CREATE TABLE ... PARTITION OF`** และ **`ALTER TABLE ... ATTACH PARTITION`** |
| ข | พาร์ทิชันใหม่ต้องได้ทั้ง **append-only และ RLS/policy** ครบ ไม่ใช่อย่างใดอย่างหนึ่ง |
| ค | **ตั้งการป้องกันไม่สำเร็จ ต้องยกเลิก DDL ทั้งคำสั่ง** ไม่ใช่ปล่อยพาร์ทิชันที่ไม่มีการป้องกันไว้ — PostgreSQL ย้อน DDL ให้เมื่อ event trigger โยนข้อผิดพลาด |
| ง | **ต้องมีวิธีติดตั้งกับฐานข้อมูลที่ bootstrap ไปแล้ว** ไม่ใช่ได้เฉพาะฐานข้อมูลที่สร้างใหม่ |

วิธีทำ:

- `CREATE EVENT TRIGGER` ต้องใช้ superuser จึงอยู่ใน **bootstrap** เหมือนการสร้างบทบาท
  ไฟล์แยกและ **เขียนให้รันซ้ำได้** เพื่อให้ใช้ติดตั้งกับฐานข้อมูลเดิมได้ด้วย (เงื่อนไข ง)
- ตัวฟังก์ชันที่ event trigger เรียก อยู่ใน migration เหมือนกลไกอื่น
  และ **ตรวจก่อนว่าฟังก์ชันนั้นมีอยู่จริง** ถ้ายังไม่มี (ฐานข้อมูลใหม่ที่ยังไม่รัน migration)
  ให้ผ่านไปเงียบ ๆ ไม่ใช่ทำให้ migration แรกล้มเหลว
- คัดลอก policy จากตารางแม่ **ด้วยข้อความของเงื่อนไขเดิม** ไม่ใช่เดาชื่อคอลัมน์เจ้าของ
  รูปแบบ policy ที่ยังไม่รองรับต้อง **ล้มเหลว** ไม่ใช่ข้าม (เงื่อนไข ค)
- ฟังก์ชันที่ปิดพาร์ทิชันต้อง **รันซ้ำได้** เพราะทั้งฟังก์ชันสร้างพาร์ทิชันและ event trigger
  จะเรียกมันในคำสั่งเดียวกัน

### 2. ตาราง `audit_events`

| คอลัมน์ | ชนิด | กฎ |
|---|---|---|
| `id` | `UUID` | รหัสของแถว — UUID เพราะรหัสอาจโผล่ออกไปข้างนอกตอนตอบผู้ใช้ (F-03 Q-6) |
| `recorded_at` | `TIMESTAMPTZ` | `NOT NULL DEFAULT now()` — **คีย์ของพาร์ทิชัน** และผู้เรียกใส่เองไม่ได้ (RQ-6) |
| `owner_user_id` | `UUID` | `NOT NULL` — เจ้าของข้อมูล ใช้โดย RLS (RQ-7) **ไม่มี foreign key** ดูเหตุผลข้างล่าง |
| `actor_kind` | `TEXT` | `USER` / `BOT` / `SYSTEM` / `PLATFORM` (RQ-1, Q-8) |
| `actor_id` | `UUID` | ว่างได้ เพราะผู้กระทำที่เป็นระบบไม่มีรหัส |
| `action` | `TEXT` | ชนิดเหตุการณ์ จำกัดด้วยรายการที่ประกาศใน migration |
| `subject_kind` | `TEXT` | "กับอะไร" — เช่น `USER`, ภายหลังจะมี `ORDER`, `WALLET` |
| `subject_id` | `TEXT` | รหัสของสิ่งนั้น เก็บเป็นข้อความเพราะบางอย่างไม่ใช่ UUID (เช่น รหัสออเดอร์ของ Binance) |
| `mode` | `TEXT` | `PAPER` / `LIVE` / `NOT_APPLICABLE` (RQ-19) |
| `outcome` | `TEXT` | `SUCCEEDED` / `FAILED` / `REJECTED` (RQ-1 — "ผลเป็นอย่างไร") |
| `failure_code` | `TEXT` | ว่างได้ เป็น **รหัส** ไม่ใช่ข้อความอิสระ (`backend.md` หัวข้อ 4) |
| `details` | `JSONB` | `NOT NULL DEFAULT '{}'` ต้องเป็น object และห้ามมีข้อมูลระบุตัวตน (RQ-18) |

- คีย์หลักคือ `(recorded_at, id)` เพราะ PostgreSQL บังคับให้คีย์หลักของตารางที่แบ่ง
  พาร์ทิชันต้องมีคีย์ของพาร์ทิชันอยู่ด้วย
- **ไม่มี foreign key ไปตาราง `users`** (RQ-17) — สองทางที่เป็นไปได้ล้วนผิด:
  ผูกแบบลบต่อกันจะลบบันทึกทิ้งเมื่อลบผู้ใช้ ซึ่ง `trading-safety.md` หัวข้อ 9 ห้าม
  ส่วนผูกแบบห้ามลบจะทำให้ลบผู้ใช้ไม่ได้เลย ซึ่งเป็นการตัดสิน NC-11 ล่วงหน้า
  จึงไม่ผูก และมีเทสต์ว่าบันทึกอยู่รอดเมื่อแถวผู้ใช้หายไป
- **`details` จำกัดด้วยรายการที่อนุญาต ไม่ใช่รายการที่ห้าม** (แก้หลังรีวิว 2026-09-27)
  `CHECK` ตัวเดียวทำสองอย่างพร้อมกัน: จำกัดชนิดเหตุการณ์ และจำกัดรูปร่างของ
  `details` ของเหตุการณ์นั้น

  ```sql
  CHECK (
      CASE action
          WHEN 'USER_CREATED' THEN details = '{}'::jsonb
          ELSE false            -- ชนิดที่ไม่ได้ประกาศไว้ เขียนไม่ได้เลย
      END
  )
  ```

  `ELSE false` ทำให้ **ชนิดเหตุการณ์ที่ยังไม่ได้ประกาศเขียนไม่ได้** และทุกชนิดที่เพิ่ม
  ภายหลังต้องประกาศรูปร่างของ `details` ของตัวเองใน migration เดียวกัน
  **การเพิ่มชนิดใหม่จึงต้องมี migration** ซึ่งเป็นสิ่งที่ตั้งใจ (Q-1)

  เหตุผลที่ต้องเป็นรายการที่อนุญาต: รายการที่ห้ามครอบไม่ได้จริง —
  `{"note": "ชื่อคนหรือค่าลับ"}` ผ่านทุกรายการที่ห้าม ซึ่งขัดกับ RQ-4 และ RQ-18
  ที่อนุมัติแล้ว และบันทึกที่เขียนแล้วลบไม่ได้ ความผิดพลาดจึงถาวร
  **ช่องข้อความอิสระเป็นสิ่งที่ห้ามโดยปริยาย** ถ้าเหตุการณ์ไหนต้องมีจริง
  ต้องขออนุมัติเป็นรายช่อง ไม่ใช่เปิดไว้ก่อน
- ดัชนีเริ่มต้นสองตัวเท่าที่ใช้จริง: `(owner_user_id, recorded_at DESC)` สำหรับการไล่ดู
  เหตุการณ์ของผู้ใช้หนึ่งคน และ `(action, recorded_at DESC)` สำหรับการสืบสวนตามชนิด

### 3. พาร์ทิชันและอายุข้อมูล

- แบ่งตามช่วงเวลาของ `recorded_at` **รายเดือน** (RQ-5)
- สร้างล่วงหน้า 12 เดือนใน migration และมี **พาร์ทิชันปลายทาง (default)** รับแถวที่ไม่ตรง
  ช่วงไหนเลย เพื่อไม่ให้การเขียนล้มเหลวเพราะไม่มีพาร์ทิชัน — บันทึกหายไม่ได้
  และมีเทสต์ว่าแถวที่ตกไปอยู่พาร์ทิชันปลายทางยังเขียนได้และยังแก้ย้อนหลังไม่ได้
- **แถวที่เข้าพาร์ทิชันปลายทางแล้วอยู่ที่นั่นถาวร ห้ามย้าย** (แก้หลังรีวิว 2026-09-27)

  การย้ายแถวออกจากพาร์ทิชันปลายทางต้อง `DELETE` ที่นั่นแล้ว `INSERT` ที่ใหม่
  ซึ่งกลไก append-only ห้ามไว้ ทางเดียวที่จะย้ายได้คือปิด trigger ชั่วคราว
  ซึ่งเป็น**ช่องเดียวกับที่กลไกทั้งงานนี้ตั้งใจปิด** จึงไม่ทำ ไม่มีขั้นตอนย้ายข้อมูล
  และไม่มีเครื่องมือให้ย้าย

  ผลที่ตามมาซึ่งต้องยอมรับ: ถ้าเดือนหนึ่งไม่มีพาร์ทิชันเจาะจง แถวของเดือนนั้นจะอยู่ใน
  พาร์ทิชันปลายทางตลอดไป และ **จะสร้างพาร์ทิชันของเดือนนั้นย้อนหลังไม่ได้อีก**
  เพราะ PostgreSQL ปฏิเสธการสร้างพาร์ทิชันที่ช่วงทับกับแถวที่อยู่ใน default
  การอ่านผ่านตารางแม่ยังได้ข้อมูลครบเหมือนเดิม สิ่งที่เสียคือประโยชน์ของการแบ่ง
  พาร์ทิชันสำหรับเดือนนั้น ไม่ใช่ข้อมูล

  **ข้อนี้ต้องดังเมื่อเกิด ไม่ใช่เงียบ:** ฟังก์ชันสร้างพาร์ทิชันต้องล้มเหลวพร้อมข้อความ
  ที่บอกสาเหตุ (ไม่ใช่ข้ามไปเงียบ ๆ) และมีเทสต์ลำดับ
  **เขียนเข้า default → สร้างพาร์ทิชันเดือนนั้น → ต้องล้มเหลว และข้อมูลยังครบและยังปิดตาย**
  เพื่อให้คนที่เจอในอนาคตรู้ทันทีว่าเกิดอะไรขึ้น ไม่ใช่มาค้นหาเอง

  ทางที่กันไม่ให้เกิดคือสร้างพาร์ทิชันล่วงหน้าให้พอ — 12 เดือนในงานนี้
  และต้องมีตัวสร้างเป็นระยะก่อนขึ้นเครื่องจริง (F-31)
- **ยังไม่ลบอะไรเลย** และ **เขียนกำกับในหัวตาราง (comment) ว่าเป็นข้อยกเว้นชั่วคราว
  จาก `database.md` หัวข้อ 7** (RQ-21) เงื่อนไขก่อนเปิดให้คนนอกใช้อยู่ใน `roadmap.md` แล้ว
- การสร้างพาร์ทิชันของเดือนถัด ๆ ไปเป็นงานที่ต้องทำเป็นระยะ — **งานนี้ยังไม่ทำตัวตั้งเวลา**
  เพราะยังไม่มีตัวตั้งเวลาในระบบเลย พาร์ทิชันปลายทางทำให้ **บันทึกไม่หาย** ในระหว่างนั้น
  (ไม่ใช่ทำให้ทุกอย่างเหมือนเดิม — ดูข้อข้างบน)
  และจะบันทึกไว้ใน `roadmap.md` ว่าต้องมีก่อนขึ้นเครื่องจริง (F-31)

### 4. RLS และสิทธิ์

- เปิด `ENABLE` + `FORCE ROW LEVEL SECURITY` **ทั้งที่ตารางแม่และที่ทุกพาร์ทิชัน**
  policy เทียบ `owner_user_id = tiewtrade_current_user_id()` ทั้ง `USING` และ `WITH CHECK`
  (แก้หลังรีวิว 2026-09-27)

  เหตุผลที่ต้องตั้งที่พาร์ทิชันด้วย: เมื่อ query ระบุชื่อพาร์ทิชันโดยตรง PostgreSQL
  ใช้ policy **ของพาร์ทิชันนั้น** ไม่ใช่ของตารางแม่ ถ้าตั้งแต่ที่แม่ เจ้าของตาราง
  (`migrator`) จะอ่านข้ามผู้ใช้ได้โดยไม่ตั้ง identity ซึ่งขัดกับคำรับรองของ F-03
  ว่าเจ้าของตารางก็อยู่ใต้ `FORCE ROW LEVEL SECURITY` — ตอนนี้บทบาททำงานปกติ
  ยังไม่ได้สิทธิ์อ่านพาร์ทิชันจึงยังไม่ใช่ช่องรั่วของ runtime แต่เป็นช่องที่เปิดรอไว้
  ให้คนที่มา `GRANT` ผิดในอนาคต
- **ฟังก์ชันสร้างพาร์ทิชันต้องตั้ง RLS, `FORCE` และ policy ให้พาร์ทิชันใหม่ทุกครั้ง**
  พร้อมกับเปิดกลไก append-only — สามอย่างนี้อยู่ในฟังก์ชันเดียว จึงลืมทีละอย่างไม่ได้
- สิทธิ์: `INSERT` ทุกคอลัมน์ยกเว้น `recorded_at` และ `SELECT` ให้ `tiewtrade_api`
  กับ `tiewtrade_engine` — **ไม่มีบทบาทไหนได้ `UPDATE`, `DELETE`, `TRUNCATE`** (RQ-8)
- **บทบาทกวาดรายการ (`tiewtrade_engine_scan`) ไม่ได้สิทธิ์อะไรเลยกับตารางนี้**
  งานกวาดไม่ต้องอ่าน audit log และการให้สิทธิ์อ่านข้ามผู้ใช้กับบันทึกทั้งระบบ
  คือการเปิดช่องที่ไม่มีใครขอ
- ไม่มี endpoint และไม่มีหน้าจอในงานนี้ (Q-3)

### 5. ชนิดเหตุการณ์ที่มีในงานนี้

มีชนิดเดียว: **`USER_CREATED`** — ผู้ผลิตจริงคือ `create_user()` ของ F-03 (Q-1, RQ-16)

- `actor_kind = USER`, `actor_id` = ผู้ใช้คนนั้น, `subject_kind = USER`, `mode = NOT_APPLICABLE`
- กฎที่เขียนไว้ให้งานหลัง: **งานที่แตะเงินต้องเพิ่มชนิดเหตุการณ์ของตัวเอง
  พร้อม migration และเทสต์ ในงานเดียวกัน** ไม่ใช่ตามเก็บทีหลัง

### 6. ทางเขียน

- `record_event(session, event)` ใน `tiewtrade.infra.audit` รับ **`UserSession` เท่านั้น**
  ผ่าน `require_user_session` ของ F-03 — จึงอยู่ใน transaction เดียวกับการกระทำโดยปริยาย
  ไม่ใช่โดยความตั้งใจของผู้เรียก (RQ-10, Q-7)
- `AuditEvent` เป็น dataclass ที่สร้างแล้วแก้ไม่ได้ ตรวจความถูกต้องตั้งแต่ตอนสร้าง
  อยู่ใน `infra` **ไม่ใช่ `core`** เพราะเป็นรูปแบบของบันทึกในฐานข้อมูล ไม่ใช่ตรรกะโดเมน
- จำนวนเงินใน `details` ส่งเป็น `Money`/`Quantity` แล้วตัวเขียนแปลงเป็น
  `{"amount": "...", "unit": "..."}` ด้วยตัวแปลงของ F-03 — **ห้ามผู้เรียกใส่ตัวเลข JSON เอง**
- **รูปร่างของ `details` ถูกกำหนดต่อเหตุการณ์ (allowlist)** ทั้งในโค้ดและในฐานข้อมูล
  — ผู้เรียกส่ง **payload ที่มีชนิดข้อมูลของตัวเองต่อเหตุการณ์** ไม่ใช่ dict อิสระ
  ตัวเขียนจึงไม่มีทางรับช่องที่ไม่ได้ประกาศไว้ และ `CHECK` ของฐานข้อมูลปฏิเสธซ้ำอีกชั้น
  แม้มีคนเขียนตรงโดยไม่ผ่านตัวเขียน (แก้หลังรีวิว 2026-09-27)
  สำหรับ `USER_CREATED` **`details` ต้องเป็น object ว่าง** ไม่มีช่องไหนเลย
- **คอลัมน์แกนที่เป็นข้อความก็จำกัดตามชนิดเหตุการณ์** (เพิ่มหลังรีวิว 2026-09-27)
  `details` ไม่ใช่ช่องเดียวที่รับข้อความ — `subject_id` และ `failure_code` ก็รับ
  ถ้าไม่ผูกกับเหตุการณ์ สองช่องนี้จะเป็นทางที่ค่าลับและข้อมูลระบุตัวตนเข้ามาได้
  ทำสองชั้นเหมือนกัน: ข้อบังคับรายเหตุการณ์ในโค้ด (`USER_CREATED` ต้องมีผู้กระทำ
  และเป้าหมายเป็นผู้ใช้ที่ถูกสร้าง) และ `CHECK` ของฐานข้อมูลที่ครอบคอลัมน์แกนด้วย
  ส่วน `failure_code` **ต้องเป็นรหัสที่ประกาศไว้แล้ว** ตอนนี้ยังไม่มีรหัสไหนเลย
  จึงบังคับให้เป็นค่าว่าง และการเพิ่มรหัสต้องมี migration เหมือนการเพิ่มชนิดเหตุการณ์
- **ตัวกรองคำที่ห้าม เป็นตาข่ายชั้นที่สอง ไม่ใช่หลักประกันหลัก** ครอบทั้ง `details`
  และคอลัมน์แกนที่เป็นข้อความ ทำสองอย่างก่อนเขียน:
  1. ปฏิเสธคีย์ที่อยู่ในรายการห้าม ทุกระดับความลึกของ `JSONB`
     (`email`, `name`, `phone`, `ip`, `address`, `password`, `secret`, `token`, `cookie`,
     `api_key` และคำที่มีคำเหล่านี้เป็นส่วนประกอบ)
  2. ปฏิเสธค่าที่มีรูปแบบเป็นอีเมล
  ตรวจ **ที่ทางเขียน ไม่ใช่ที่ผู้เรียก** เพราะผู้เรียกจะมีหลายที่และจะลืม
  ชั้นนี้มีไว้จับกรณีที่ payload ของเหตุการณ์ในอนาคตเปิดช่องข้อความไว้โดยไม่ควรเปิด
  **หลักประกันหลักคือ allowlist ข้างบน** ไม่ใช่ชั้นนี้
- ข้อผิดพลาดเป็นชนิดที่ระบุได้ ต่อยอดจาก `InfraError` ของ F-03 (RQ-12)

## ความเสี่ยง

| อะไรอาจพัง | จะรู้ได้อย่างไร |
|---|---|
| `TRUNCATE` ที่พาร์ทิชันโดยตรงหลุดกลไก | เทสต์สั่ง `TRUNCATE` ที่พาร์ทิชันตรง ๆ ด้วยทั้งบทบาททำงานปกติและเจ้าของตาราง |
| พาร์ทิชันที่สร้างเพิ่มในอนาคตลืมเปิดกลไก | ฟังก์ชันที่เปิดกลไกให้ในตัว **และ** event trigger ที่ดักการสร้างและการผูกพาร์ทิชัน + เทสต์ที่สร้างพาร์ทิชันด้วยมือแล้วตรวจว่าถูกปิดให้เอง |
| ตั้งการป้องกันไม่สำเร็จแล้วเหลือพาร์ทิชันที่ไม่มีการป้องกัน | event trigger โยนข้อผิดพลาด แล้ว PostgreSQL ย้อน DDL ทั้งคำสั่ง + เทสต์ด้วย policy รูปแบบที่ยังไม่รองรับ |
| ฐานข้อมูลที่ bootstrap ไปแล้วไม่มี event trigger | ไฟล์ bootstrap รันซ้ำได้ + migration ปิดพาร์ทิชันที่ค้างอยู่ให้ + เทสต์ที่ถอดการป้องกันออกแล้วเรียกฟังก์ชันซ่อมกลับ |
| เดือนใหม่มาถึงแล้วไม่มีพาร์ทิชัน แล้วบันทึกเขียนไม่ได้ | พาร์ทิชันปลายทาง + เทสต์ที่เขียนแถวของปีที่ไม่มีพาร์ทิชันเจาะจง |
| ข้อมูลระบุตัวตนหลุดเข้า `details` | รูปร่างของ `details` เป็นรายการที่อนุญาตต่อเหตุการณ์ บังคับทั้งในโค้ดและด้วย `CHECK` + เทสต์ที่ใส่ค่าลับใต้คีย์ทั่วไปแล้วต้องถูกปฏิเสธ |
| อ่านพาร์ทิชันโดยตรงแล้วข้าม policy ของตารางแม่ | RLS + `FORCE` + policy ตั้งที่ทุกพาร์ทิชัน + เทสต์ query ระบุชื่อพาร์ทิชันตรง ๆ ครบทั้งรายเดือน ปลายทาง และพาร์ทิชันที่สร้างใหม่ |
| แถวตกไปอยู่พาร์ทิชันปลายทางแล้วมีคนพยายามย้ายทีหลัง | ไม่มีเครื่องมือให้ย้าย และฟังก์ชันสร้างพาร์ทิชันล้มเหลวพร้อมบอกสาเหตุ + เทสต์ลำดับทั้งสามขั้น |
| การลงบันทึกกับการกระทำแยก transaction กันโดยไม่มีใครรู้ | เทสต์ที่ทำให้การกระทำล้มเหลวแล้วตรวจว่าบันทึกไม่ถูกเขียน และกลับกัน |
| มีใครเพิ่มชนิดเหตุการณ์ในโค้ดแต่ลืม migration | `CHECK` ของฐานข้อมูลปฏิเสธ + เทสต์ที่ลองชนิดที่ไม่ได้ประกาศ |
| เงินใน `details` กลายเป็นตัวเลขทศนิยมลอยตัว | ทางเขียนรับเฉพาะ `Money`/`Quantity` + เทสต์ที่ส่งตัวเลขเข้าไปแล้วต้องถูกปฏิเสธ |
