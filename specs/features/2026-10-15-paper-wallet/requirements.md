# F-13 — กระเป๋า Paper และเงินตั้งต้น — Requirements

สถานะ: **Approved** — เจ้าของอนุมัติ requirements วันที่ 2026-10-15 และอนุมัติ implementation ตาม plan.md กับ validation.md วันที่ 2026-10-15

วันที่: 2026-10-15

## ทำไมต้องมี

Paper Trading ต้องมีกระเป๋าเงินจำลองก่อนสร้าง position, คำนวณ margin/PnL หรือจำลอง
การจับคู่ออเดอร์ใน F-14/F-15 ผู้ใช้ต้องเลือกทุนตั้งต้นให้ใกล้กับเงินที่ตั้งใจใช้จริงได้
โดยเงินจำลองต้องไม่ปะปนกับเงินจริง ไม่เรียก Binance และไม่ทำให้การเติมหรือรีเซ็ตทุน
กลายเป็นกำไรเทียม

NC-03 ปิดเมื่อ 2026-10-15: เจ้าของยืนยันให้ผู้ใช้กำหนดทุนตั้งต้นเป็น USDT ได้เอง
โดยไม่มีเพดานธุรกิจเพิ่มเติม, ห้ามเติมเงินกลางรอบ, เปลี่ยนทุนด้วยการรีเซ็ตเป็นรอบใหม่
เมื่อไม่มี position หรือออเดอร์ค้าง และไม่นับทุนตั้งต้นหรือยอดจากการรีเซ็ตเป็นกำไร
เจ้าของยืนยันเพิ่มเติมว่าทุนตั้งต้นของทุกรอบต้องมากกว่า 1,000 USDT

## ขอบเขต

### ทำ

- ให้ผู้ใช้สร้างกระเป๋า Paper หนึ่งกระเป๋าสำหรับบัญชีเทรดของตนด้วยทุนตั้งต้น USDT
- เก็บเงินเป็นรายการเดินบัญชีแบบเพิ่มอย่างเดียว และคำนวณยอดจากรายการของรอบปัจจุบัน
- แบ่งอายุของกระเป๋าเป็นรอบ (episode) เพื่อให้การรีเซ็ตเริ่มทุนและฐานวัดผลใหม่
- ให้ผู้ใช้ดูทุนตั้งต้น, ยอดปัจจุบัน, รหัสรอบ และเวลาที่เริ่มรอบปัจจุบัน
- ให้ผู้ใช้รีเซ็ตกระเป๋าเป็นรอบใหม่เมื่อพิสูจน์ได้ว่าไม่มี position และออเดอร์ค้าง
- เก็บประวัติรอบและรายการเดิมไว้ ไม่ลบหรือแก้ยอดย้อนหลัง
- ลง audit log สำหรับการสร้างและรีเซ็ต รวมทั้งผลของคำขอที่ถูกปฏิเสธตามกฎ audit เดิม
- แยกข้อมูลและสิทธิ์ของผู้ใช้ด้วย RLS และกันคำขอสร้าง/รีเซ็ตซ้ำ

### ไม่ทำ

- ไม่เติมเงินเข้ารอบที่กำลังใช้งาน และไม่มี endpoint หรือ UI สำหรับ top-up
- ไม่คำนวณ position, margin, realized/unrealized PnL, leverage หรือ liquidation — เป็น F-14
- ไม่สร้างหรือจับคู่ออเดอร์ Paper — เป็น F-15/F-16
- ไม่ทำ TP/SL, risk limit, kill switch, bot หรือ performance dashboard — เป็นงานถัดไป
- ไม่แตะยอดเงินจริง, API key, Binance balance หรือส่งคำขอใดไป Binance
- ไม่เปิด Live Trading และไม่สร้างทางแปลงกระเป๋า Paper เป็น Live
- ไม่ลบประวัติรอบเก่าเมื่อรีเซ็ต; การแสดงประวัติผลงานรวมเป็น F-28

## ข้อกำหนด

| รหัส | ข้อกำหนด | ที่มา |
|---|---|---|
| RQ-1 | ผู้ใช้หนึ่งคนมีกระเป๋า Paper ที่ใช้งานอยู่ได้หนึ่งกระเป๋าภายใต้บัญชีเทรดเดียวของ F-08; กระเป๋าและทุกรายการต้องระบุโหมด `PAPER` ตั้งแต่สร้างและเปลี่ยนโหมดภายหลังไม่ได้ | mission §4–5; trading-safety §1 |
| RQ-2 | ผู้ใช้ต้องระบุทุนตั้งต้นเป็นข้อความจำนวนเงินหน่วย `USDT` และค่าต้องมากกว่า `1,000 USDT`; ไม่มีเพดานธุรกิจเพิ่มเติม แต่ค่าต้องผ่าน `Money` และขอบเขตการเก็บที่อนุมัติ ห้ามรับ JSON float และห้ามให้ฐานข้อมูลปัดค่าเอง | คำตัดสิน NC-03 และ NC-F13-01; F-02; security §3 |
| RQ-3 | การสร้างกระเป๋าต้องสร้างรอบแรกและรายการเครดิตทุนตั้งต้นใน transaction เดียวกัน; หากส่วนใดล้มต้องไม่เหลือกระเป๋า รอบ รายการเงิน หรือ audit state ครึ่งชุด | database §2/4; error recovery |
| RQ-4 | รายการเดินบัญชีและรอบที่จบแล้วเพิ่มได้อย่างเดียว ห้าม `UPDATE` หรือ `DELETE`; ยอดรอบปัจจุบันต้อง derive จากผลรวมรายการที่บันทึกด้วย `Money` ห้ามเก็บยอดที่เขียนทับเป็นแหล่งความจริงอีกชุด | trading-safety §9; database §4 |
| RQ-5 | ห้ามเติมเงินหรือแก้ทุนตั้งต้นของรอบที่เริ่มแล้ว การเปลี่ยนทุนทำได้ด้วย reset ที่ปิดรอบปัจจุบันและสร้างรอบใหม่เท่านั้น | คำตัดสิน NC-03 |
| RQ-6 | reset ต้องสำเร็จเฉพาะเมื่อ server พิสูจน์จากข้อมูล authoritative ได้ว่าไม่มี position และไม่มีออเดอร์ค้าง หากข้อมูลไม่พร้อม, ตรวจไม่ได้ หรือเปลี่ยนระหว่างตรวจ ต้องปฏิเสธแบบ fail-closed และห้ามสร้างรอบใหม่ | คำตัดสิน NC-03; trading-safety §10/12 |
| RQ-7 | reset ต้องปิดรอบเดิม, สร้างรอบใหม่ และเพิ่มเครดิตทุนใหม่แบบ atomic ภายใต้ single-writer/lock เดียวกัน; คำขอพร้อมกันต้องมีผู้ชนะไม่เกินหนึ่งรายการและห้ามเกิด active episode ซ้ำ | concurrency; database transaction correctness |
| RQ-8 | คำขอสร้างและ reset ต้องมี idempotency key ที่ผูกกับผู้ใช้และชนิดการกระทำ คำขอเดิมที่ retry ต้องคืนผลเดิมโดยไม่สร้างกระเป๋า รอบ ledger entry หรือ audit event ซ้ำ; key เดิมกับ payload ต่างกันต้องถูกปฏิเสธ | retry safety; duplicate prevention |
| RQ-9 | ทุนตั้งต้นและเครดิตจาก reset เป็น external capital ของรอบ ไม่ใช่ realized/unrealized PnL; F-13 ต้องเก็บข้อมูลฐานที่ทำให้ F-14/F-28 คำนวณผลแยกต่อรอบได้โดยไม่ตีความ ledger credit เป็นกำไร | คำตัดสิน NC-03; roadmap F-14/F-28 |
| RQ-10 | API และ UI ต้องแสดงจำนวนเงินจากข้อความ exact ตามสัญญา `Money`; ห้ามแปลงเป็น `Number`/`float` เพื่อคำนวณยอด เปรียบเทียบสิทธิ์ หรือบันทึกข้อมูล | AGENTS.md; F-02 |
| RQ-11 | ทุก read/write ต้องอยู่ใต้ RLS และผูก user context ฝั่ง server ผู้ใช้ต้องอ่านหรือเปลี่ยนกระเป๋า รอบ idempotency record หรือ ledger ของผู้อื่นไม่ได้ และการอ้าง resource ของผู้อื่นต้องตอบแบบไม่เปิดเผยว่ามีอยู่ | database §3; security §2 |
| RQ-12 | การสร้าง/reset และการปฏิเสธที่แตะเงินต้องลง audit log ว่าใครทำ อะไร เมื่อใด เป้าหมายใด และผลเป็นอย่างไร โดยไม่บันทึก session, cookie หรือข้อมูลลับ | trading-safety §9; security §4 |
| RQ-13 | เส้นทาง Paper wallet ต้องไม่อ่าน API credential, ไม่เรียก venue/network client และไม่สามารถส่งออเดอร์ไป Binance ได้ ต้องมี automated gate พิสูจน์ข้อห้ามนี้ | mission §4; trading-safety §1 |
| RQ-14 | การอ่านกระเป๋าต้องคืน snapshot ที่สอดคล้องกันของ active episode, ทุนตั้งต้นและยอดที่ derive ภายใต้ transaction เดียว; ห้ามประกอบค่าจากคนละ revision จนดูเหมือนเป็นสถานะเดียวกัน | consistency; architecture boundaries |
| RQ-15 | ข้อผิดพลาดจาก input, duplicate conflict, กระเป๋ามีอยู่แล้ว, reset ไม่ปลอดภัย และ dependency unavailable ต้องแยกชนิดได้ โดยไม่คืน stack trace หรือรายละเอียดฐานข้อมูล และ retry ได้เฉพาะกรณีที่ idempotency semantics รับรอง | security §3/4; retry safety |

## กติกาของรอบ Paper

- รอบแรกเริ่มเมื่อสร้างกระเป๋าสำเร็จ
- รอบปัจจุบันมีได้หนึ่งรอบต่อกระเป๋าเท่านั้น
- reset ทำให้รอบเดิมสิ้นสุดและเริ่มรอบใหม่ด้วยทุนที่ผู้ใช้ระบุ
- รายการและผลของรอบเดิมยังอยู่เพื่อ audit และการสรุปผลงานภายหลัง
- การเริ่มรอบใหม่ไม่ทำให้กำไรหรือขาดทุนของรอบเดิมย้ายมารวมกับรอบใหม่
- การคำนวณ PnL จริงเป็น F-14; F-13 เก็บทุนภายนอกและขอบเขตรอบให้ตีความได้แน่นอน
