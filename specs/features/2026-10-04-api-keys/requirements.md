# F-07 จัดการ API key ของผู้ใช้ — Requirements

สถานะ: **Approved** — เจ้าของอนุมัติ 2026-10-04

## ทำไมต้องมี

ระบบยังไม่รู้จัก API key ของผู้ใช้เลย ฉะนั้นวันนี้มันเห็นได้แค่ราคาและข้อจำกัดของเหรียญ
ซึ่งเป็น endpoint สาธารณะที่ F-35 ทำไว้ **ยอดในกระเป๋าจริงอ่านไม่ได้ และออเดอร์จริง
ส่งไม่ได้** เพราะทั้งสองอย่างต้องลงลายเซ็นด้วย secret ของผู้ใช้

งานที่รออยู่หลังข้อนี้: F-08 (เชื่อม Sub-account เป็นกระเป๋า) ต้องมี key ก่อนจึงจะมี
กระเป๋าให้ผูก · F-24 (เปิด Live) ต้องมี key ที่ตรวจสิทธิ์แล้ว · F-35 เหลือสัญญากระเป๋า
ที่ยังไม่ได้ทำเพราะรอข้อนี้ (F-35 Q-1 เลือกช่อง ก. ไว้)

ใครเดือดร้อนถ้าไม่มี: ผู้ใช้จริงคนเดียวในตอนนี้คือเจ้าของ ซึ่งยังเทรดผ่านระบบนี้ไม่ได้เลย

## ขอบเขต

### ทำ

- ผู้ใช้เพิ่ม API key ของตลาดเข้าบัญชีตัวเองได้ผ่านหน้าเว็บ (key + secret)
- `api` เข้ารหัสทันทีที่รับ เก็บลงฐานข้อมูล **และอ่านกลับไม่ได้อีก**
- ถอดรหัสได้เฉพาะ `engine` บังคับที่ระดับสิทธิ์ฐานข้อมูล
- **พิสูจน์ว่า key ใช้งานได้จริง** ตอนเพิ่ม · **ไม่ตรวจสิทธิ์ เพราะตลาดนี้ไม่รายงานสิทธิ์ของ key**
  (NC-16) และ **ห้ามใช้ `canTrade`/`canWithdraw`/`canDeposit` มาแทน**
- ผู้ใช้ดูรายการ key ของตัวเองได้ โดยเห็นเฉพาะส่วนที่ไม่เป็นความลับ (ดู Q-5)
- ผู้ใช้ลบ key ได้ และของที่ลบแล้วใช้ต่อไม่ได้
- audit log ของทุกการกระทำที่แตะ key
- กุญแจเข้ารหัสของงานนี้ **เป็นกุญแจของตัวเอง** แยกจากกุญแจ TOTP ของ F-06

### ไม่ทำ

| ไม่ทำ | เป็นงานของ |
|---|---|
| แนวคิด "กระเป๋า" และการผูก key เข้ากับบัญชีย่อย | **F-08** |
| ส่งออเดอร์ หรืออ่านยอดกระเป๋ามาแสดง | F-08, F-16 |
| เปิด Live Trading และการบังคับว่าต้องมี key ก่อน | **F-24** |
| ที่มาของกุญแจเข้ารหัสบนเครื่องจริง และการหมุนกุญแจ | **F-31** (T-03 ยังไม่ปิด) |
| ตรวจ key ซ้ำเป็นรอบ ๆ และ "key ถูกปฏิเสธ → หยุดบอททันที" | ดู Q-7 — ยังไม่มีบอทให้หยุด |
| ตัวตั้งเวลาเรียกงานเก็บกวาด | **F-31** (ข้อเดียวกับที่ F-06 ฝากไว้) |

## กฎความปลอดภัยที่เกี่ยวข้อง

`trading-safety.md` หัวข้อ 2 — ทั้งหัวข้อเป็นของงานนี้โดยตรง:

1. secret เข้ารหัสก่อนบันทึกเสมอ ถอดเฉพาะตอนใช้ ไม่เก็บค่าที่ถอดแล้ว → RQ-2, RQ-3
2. `api` ไม่มีสิทธิ์อ่านคอลัมน์ secret ที่ระดับฐานข้อมูล → RQ-3
3. `api` รับ secret ได้เฉพาะตอนผู้ใช้กรอกครั้งแรก → RQ-2
4. ไม่มี endpoint/log/error ใดคืน secret → RQ-5
5. ตอนเพิ่ม key ต้อง **พิสูจน์ว่า key ใช้งานได้จริง** และยอมรับเฉพาะสิทธิ์ในรายการ
   ที่อนุญาต **ถ้าตลาดรายงานสิทธิ์** (ซึ่งตลาดนี้ไม่รายงาน) → **RQ-6, RQ-6.1, RQ-16**
   · ถ้อยคำเดิม "ปฏิเสธ key ที่เปิดสิทธิ์ถอนเงิน" ถูกแทนที่แล้วเมื่อ 2026-10-04
6. **key ที่ตลาดปฏิเสธต้องหยุดบอทที่ใช้ key นั้นทันทีและแจ้งผู้ใช้** → ยังไม่มีบอท ดู Q-7

`security.md` หัวข้อ 1 (ยืนยันซ้ำ), 2 (สิทธิ์), 3 (ข้อมูลเข้า), 4 (log) → RQ-7, RQ-10, RQ-11, RQ-13, RQ-5

`mission.md` หัวข้อ 5 — **key ของบัญชีหลักมีอำนาจกว้างกว่าที่การเทรดต้องใช้**
(จัดการบัญชีย่อยและโอนเงินระหว่างบัญชีได้) **แต่หน้าสร้าง key ไม่มีช่องให้ปิดอำนาจนั้น**
ฉะนั้นกฎ "สิทธิ์เท่าที่จำเป็น" บังคับที่ฝั่งเราไม่ได้ → **RQ-16** (โค้ดไปถึง endpoint
ที่ย้ายเงินไม่ได้) เป็นสิ่งที่ทำแทน และข้อนี้ยังเป็นส่วนที่เปิดอยู่ของ **NC-16**

ต่อไม่ได้จริงถ้ายังไม่มีคำตอบ

### NC-16 — สิทธิ์ของ key บนตลาดนี้ · **ยังเปิดอยู่** (ปิดได้เฉพาะส่วนที่ระบุ)

**เจ้าของยืนยันจากหน้าสร้าง API key ของบัญชีจริงเมื่อ 2026-10-04:**
หน้านั้นมีช่อง API restrictions **สองช่องเท่านั้น** คือ `Enable Reading`
(ติ๊กไว้และแก้ไม่ได้) กับ `Enable Spot Trading` — **ไม่มีสิทธิ์ถอนเงินให้เปิดเลย**

**และหน้าที่ยืนยันมาคือของ `บัญชีหลัก`** ซึ่งเป็นกรณีที่หนักที่สุดตาม `mission.md`
หัวข้อ 5 ("key ของบัญชีหลักมีอำนาจกว้างกว่าที่การเทรดต้องใช้") ฉะนั้นหลักฐานนี้
ครอบกรณีที่ spec สั่งให้ระวังที่สุดอยู่แล้ว ไม่ต้องตรวจบัญชีย่อยซ้ำเพื่อปิดชั้น (ก)

**แก้ข้อสรุปเดิม 2026-10-04 (รีวิวจับได้)** — ผมเคยเขียนที่นี่ว่า "ความเสี่ยงไม่มีอยู่จริง
บนตลาดนี้" **ข้อสรุปนั้นผิด** เพราะ **การไม่มีช่องให้ติ๊ก ไม่ได้แปลว่า key ไม่มีอำนาจนั้น**

เอกสารของตลาดมี `POST /api/v1/capital/withdraw` ซึ่งเป็น **คำขอที่ลงลายเซ็น**
จึงเรียกด้วย API key ได้โดยนิยาม อ่านได้สองทาง:

|---|---|
| ก. key เรียก endpoint นั้นไม่ได้ (ต้องมีสิทธิ์ที่ไม่มีให้เปิด) | ความเสี่ยงไม่มีจริง — ข้อสรุปเดิมถูก |
| **ข. key ทุกอันเรียกได้ เพราะไม่มีสิทธิ์ให้ปิด** | **แย่กว่าสภาพเดิมที่กฎกันไว้** — ผู้ใช้ปิดความสามารถนี้ไม่ได้เลย |

**ยังไม่มีหลักฐานว่าทางไหน และ `canWithdraw = True` ก็อ่านเข้าทาง ข. ได้เท่า ๆ กัน**
ฉะนั้น **NC-16 ส่วนนี้เปิดอยู่** และห้ามใช้เป็นเหตุลดข้อกำหนดความปลอดภัย

**ผลที่ตามมา:**

1. **จนกว่าจะปิด ให้ถือว่าความเสี่ยงมีอยู่และเราตรวจไม่ได้** — สิ่งที่กันความเสียหายจริง
   ไม่ใช่การตรวจสิทธิ์ แต่คือ **โค้ดของเราต้องไม่มีเส้นทางเรียก endpoint ที่ย้ายเงิน
   ออกจากบัญชีผู้ใช้เลย บังคับด้วยด่านอัตโนมัติ** (RQ-16) · และแนะนำให้ผู้ใช้เปิด
   whitelist ที่อยู่ถอนเงินที่ตลาด ซึ่งเป็นการตั้งค่าที่ผู้ใช้คุมได้เอง (RQ-17)
2. **แต่ถ้อยคำของกฎต้องแก้** มิฉะนั้นมันจะเป็นข้อที่ spec สั่งให้ทำ แล้วโค้ดไม่ทำ
   ซึ่งคือสภาพที่ `AGENTS.md` ห้าม (spec กับโค้ดขัดกัน) — ดูถ้อยคำที่เสนอใน Q-4
3. **ข้อสรุปนี้ผูกกับตลาดและเวลา ไม่ใช่ความจริงถาวร** วันที่ Binance TH เพิ่มสิทธิ์ใหม่
   ให้ API key ข้อสรุปนี้หมดอายุเงียบ ๆ โดยไม่มีอะไรเตือน — เป็นเหตุที่ข้อเสนอใน Q-4
   ต้องเป็น "ปฏิเสธสิทธิ์ที่ไม่รู้จัก" ไม่ใช่ "ไม่ต้องตรวจ"

**ยังเหลือชั้น (ข) และความหมายของมันเปลี่ยนไปแล้ว**

เดิมชั้น (ข) มีไว้ตรวจสิทธิ์ถอนเงิน ตอนนี้ไม่ใช่แล้ว — สิ่งที่ต้องรู้คือ
**เราอ่านได้หรือไม่ว่า key อันนี้เปิด `Enable Spot Trading` ไว้** เพราะ key ที่อ่าน
ได้อย่างเดียวจะใช้เทรดไม่ได้ และ `trading-safety.md` ไม่ควรปล่อยให้ผู้ใช้รู้เรื่องนี้
ตอนออเดอร์แรกถูกตลาดปฏิเสธ · **เอกสารไม่มี test-order endpoint** ฉะนั้นทางสำรองที่จะ
"ลองสั่งแบบไม่เกิดธุรกรรม" ไม่มี เหลือทางเดียวคือดูว่า endpoint ข้อมูลบัญชีคืนช่อง
อย่าง `canTrade` หรือ `permissions` มาหรือไม่ และค่านั้นเปลี่ยนตาม key จริงหรือไม่

**ผลจากการเรียกจริง (2026-10-04) — `canWithdraw` ใช้ตัดสินสิทธิ์ของ key ไม่ได้ เด็ดขาด**

เรียก `/api/v1/accountV2` และ `/api/v1/account` ด้วย key จริง ได้ช่องชุดเดียวกันทั้งสองเส้นทาง:

```
balances, buyerCommission, canDeposit, canTrade, canWithdraw,
makerCommission, sellerCommission, takerCommission, updateTime
```

- `canTrade = True` · `canDeposit = True` · **`canWithdraw = True`**
- **ไม่มีช่อง `permissions` และไม่มี `accountType`**

**`canWithdraw = True` ทั้งที่หน้าสร้าง key ไม่มีสิทธิ์ถอนเงินให้เปิดเลย** — สองข้อนี้
ขัดกันไม่ได้ ฉะนั้นข้อสรุปเดียวที่เป็นไปได้คือ **ช่องพวกนี้พูดถึงสถานะของ "บัญชี"
ไม่ใช่สิทธิ์ของ "key"** ซึ่งเป็นข้อสงสัยที่ตั้งไว้ตั้งแต่ต้นของ NC-16 และตอนนี้พิสูจน์แล้ว

**ผลที่บังคับกับโค้ดของ F-07:**

- **ห้ามใช้ `canWithdraw` ตัดสินอะไรเกี่ยวกับ key ไม่ว่ากรณีใด** — มันเป็นสถานะของบัญชี
  ฉะนั้นไม่ว่าจะตีความทางไหนก็ผิด: ใช้ตรงด้านก็ปฏิเสธ key ของทุกคน ใช้กลับด้านก็กลายเป็น
  การประกาศว่า "ตรวจแล้ว" โดยไม่ได้ตรวจ
  · **และข้อนี้ไม่ได้แปลว่า key ถอนเงินไม่ได้** — เรื่องนั้นยังไม่มีคำตอบ (NC-16 ส่วนที่
  ยังเปิด) สิ่งที่พิสูจน์แล้วคือ "เราอ่านสิทธิ์ของ key ไม่ได้" เท่านั้น
- **ตลาดนี้ไม่มีช่องที่บอกสิทธิ์ของ key เลย** (ไม่มี `permissions`) ฉะนั้นสัญญาใน Q-2
  ต้องออกแบบบนความจริงข้อนี้ ไม่ใช่บนสมมติฐานว่าถามได้
- สองเส้นทางคืนของเหมือนกัน จึงไม่ต้องเลือกว่าจะเรียกอันไหน

**NC-16 ชั้น (ข) ปิดแล้ว 2026-10-04 — เจ้าของตัดสินว่า "ถือว่าอ่านสิทธิ์ของ key ไม่ได้"**

ไม่รันรอบที่สองเพื่อพิสูจน์ `canTrade` เพราะหลักฐานชี้ทางเดียวอยู่แล้ว (ไม่มีช่อง
`permissions` และ `canWithdraw` พิสูจน์แล้วว่าเป็นระดับบัญชี) และ **ระบบที่ไม่พึ่ง
การอ่านสิทธิ์ปลอดภัยกว่าในทุกกรณี** ถ้าภายหลังพบว่าอ่านได้ ก็เป็นของแถมที่ไม่ต้องรื้อ

**สิ่งที่ยอมรับแล้วพร้อมกับการตัดสินนี้:** ผู้ใช้ที่ใส่ key ซึ่งไม่ได้ติ๊ก
`Enable Spot Trading` จะรู้ตัวตอนสั่งออเดอร์ครั้งแรก ไม่ใช่ตอนเพิ่ม key —
ชดเชยด้วยข้อความบนหน้าจอตอนเพิ่ม (RQ-6.3)

**ชั้น (ค) ที่เพิ่งเปิดขึ้นจากหลักฐานนี้ — อำนาจที่ไม่มีช่องให้ติ๊ก**

`mission.md` หัวข้อ 5 บันทึกไว้ว่า key ของบัญชีหลัก **จัดการบัญชีย่อยและโอนเงิน
ระหว่างบัญชีได้** แต่หน้าสร้าง key ไม่มีช่องสำหรับอำนาจสองอย่างนั้นเลย อ่านได้สองทาง:

| อ่านได้ว่า | ผลกับงานนี้ |
|---|---|
| **ก. ตลาดนี้ไม่เปิดให้ API key ทำสองอย่างนั้นได้** | ข้อห่วงใยใน `mission.md` หัวข้อ 5 ไม่มีผลจริงบนตลาดนี้ — ควรบันทึกไว้ให้ชัด |
| **ข. ทำได้โดยไม่ต้องติ๊กอะไร** เพราะถือว่ารวมอยู่ในสิทธิ์อ่าน/เทรดแล้ว | **แย่กว่าเดิม** เพราะแปลว่าเงินย้ายระหว่างบัญชีได้โดยไม่มีสิทธิ์ให้ปิด และผู้ใช้ปิดไม่ได้ด้วย |

**ยังไม่มีหลักฐานว่าทางไหน** และข้อนี้ **ไม่บล็อก F-07** เพราะ F-07 ไม่ส่งคำสั่งโอน
แต่ **ต้องตอบก่อน F-08** (ซึ่งเอา key ของบัญชีหลักมาใช้เป็นกระเป๋า) และก่อน F-24
พิสูจน์ได้ด้วยการดูว่าเอกสารของตลาดมี endpoint โอนเงินระหว่างบัญชีหรือจัดการบัญชีย่อย
อยู่หรือไม่ — **ไม่ต้องลองเรียกจริง** เพราะการเรียกคือการโอนเงิน

**ยังไม่ใช่ข้อที่บล็อก plan ทั้งฉบับอีกต่อไป** — บล็อกเฉพาะข้อความของ RQ-6 และ Q-4

### NC-16 เดิม — บันทึกไว้ว่าทำไมถึงถาม

Q-2 ถามเรื่อง **รูปแบบ** ของสัญญา แต่ข้ามคำถามที่มาก่อนนั้น: **ตลาดบอกเราได้จริงหรือไม่
ว่า key ที่ส่งมาเปิดสิทธิ์อะไรไว้** ถ้าตอบไม่ได้ RQ-6 กับ Q-4 บังคับไม่ได้เลย
ไม่ว่าสัญญาจะสวยแค่ไหน

สิ่งที่รู้ตอนนี้ (ตรวจเอกสาร `api-docs` ของ Binance TH เมื่อ 2026-10-04):

- **ไม่พบ endpoint ที่บอกสิทธิ์ของ API key โดยตรง** เอกสารมีแต่คำแนะนำให้ผู้ใช้
  เปิดสิทธิ์เท่าที่จำเป็น ไม่มีเส้นทางให้ถาม
- Account Information มีช่องชื่อ `canWithdraw` **แต่เอกสารไม่ได้ระบุว่าค่านี้หมายถึง
  สิทธิ์ของ key ที่ส่งมา** — อ่านได้อีกทางว่าเป็นสถานะของ **บัญชี** (เช่น บัญชีถูกระงับ
  การถอน) ซึ่งเป็นคนละเรื่องกับสิทธิ์ของ key และถ้าตีความผิด ระบบจะ **ประกาศว่า
  ตรวจแล้ว ทั้งที่ไม่ได้ตรวจอะไรเลย** ซึ่งแย่กว่าไม่ตรวจ เพราะมันสร้างความมั่นใจปลอม
- การตรวจเอกสารด้วยเครื่องมืออ่านหน้าเว็บครั้งเดียวไม่ใช่หลักฐานที่พอ — **ต้องยืนยันกับ
  บัญชีจริงของเจ้าของ** เหมือนที่ NC-04 ต้องให้เจ้าของยืนยันเรื่อง sub-account

**สิ่งที่เจ้าของตรวจมาเพิ่ม (2026-10-04)** — จากเอกสาร `api-docs` และ FAQ ของ Binance TH:

- สิทธิ์ของ API key บน Binance TH ที่เอกสารระบุมีเพียง **อ่าน** และ **เทรด Spot**
  (`Enable reading`, `Enable spot trading`) หน้าจัดการ API ของบัญชีย่อยก็มีสองข้อนี้
- **ไม่พบสิทธิ์ถอนเงินในระดับ API key เลย** — การถอนเป็น **การตั้งค่าความปลอดภัย
  ของบัญชี** (รวม withdrawal whitelist) ไม่ใช่สิทธิ์ของ key
- เอกสารไม่มี endpoint สำหรับทดสอบออเดอร์ (test order) ซึ่งตรงกับที่ผมอ่านได้
  ฉะนั้น **ทางสำรองที่จะใช้ "ลองสั่งแบบไม่เกิดธุรกรรม" เพื่อแยกว่า key มีสิทธิ์เทรดไหม
  ก็ไม่มี**

**ข้อนี้เปลี่ยนรูปของ NC-16 ไปเลย** — เดิมผมถามว่า "อ่านสิทธิ์ได้ไหม" แต่คำถามจริงมีสองชั้น:

| | คำถาม | ถ้าตอบว่า... |
|---|---|---|
| **(ก)** | key ของตลาดนี้ **เปิดสิทธิ์ถอนเงินได้หรือไม่ตั้งแต่ต้น** | **ไม่ได้** → ความเสี่ยงที่ `trading-safety.md` กันไว้ **ไม่มีอยู่จริงบนตลาดนี้** กฎข้อนั้นเป็นจริงโดยสภาพของตลาด ไม่ใช่โดยการตรวจของเรา · **ได้** → ต้องตอบ (ข) |
| **(ข)** | เราอ่านสิทธิ์ของ key ที่ส่งไปได้หรือไม่ | **ได้** → RQ-6 บังคับได้ตามเดิม · **ไม่ได้** → ต้องตอบ Q-4.1 |

**(ก) เป็นข่าวดีถ้าจริง** แต่ "เอกสารไม่พบ" ไม่เท่ากับ "ตลาดไม่มี" และเรายังอ่านเอกสาร
หน้านั้นไม่ครบทั้งสองรอบ (หน้าไม่คายส่วน Account Information ออกมา) ฉะนั้นข้อนี้
**ยังไม่ใช่หลักฐาน** และข้อสรุปที่ผิดทางนี้แพงกว่าปกติ เพราะมันทำให้เราเลิกตรวจของ
ที่ควรตรวจ

**หลักฐานที่พอ ใช้คำขอเดียว** — ผมเตรียมสคริปต์ไว้ที่
`probe_key_permissions.py` (อยู่นอก repo เพราะ F-07 ยังไม่อนุมัติ) มันเรียกเฉพาะ
endpoint ที่อ่านข้อมูลบัญชี ไม่ส่งออเดอร์ ไม่โอน ไม่ถอน และไม่พิมพ์ key หรือ secret
ทำกับ key ทดสอบสองอัน (อ่านอย่างเดียว / อ่าน+เทรด) แล้วดูว่า:

1. มีช่อง `canTrade`, `canWithdraw`, `permissions` คืนมาหรือไม่
2. ค่าของช่องนั้น **ต่างกันตามสิทธิ์ของ key ทั้งสองอันหรือไม่** — ถ้าเหมือนกัน
   แปลว่าช่องนั้นพูดถึง **บัญชี** ไม่ใช่ **key** ซึ่งเป็นข้อที่จะหลงได้ง่ายที่สุด

สิ่งที่ต้องยืนยันก่อนเขียน `plan.md`:

1. **(ก)** — key ของตลาดนี้เปิดสิทธิ์ถอนเงินได้หรือไม่ (ยืนยันจากหน้าสร้าง key ของบัญชีจริง)
2. **(ข)** — endpoint ไหนคืนสิทธิ์ของ key และช่องนั้นเปลี่ยนตาม key จริงหรือไม่
3. ถ้า (ก) ตอบว่า "เปิดได้" และ (ข) ตอบว่า "อ่านไม่ได้" **จะทำอย่างไร** ดู Q-4.1

### Q-1 — ตรวจสิทธิ์ของ key ที่ process ไหน (**บล็อก plan**)

**ตัดสินแล้ว: ช่อง ข.** (เจ้าของตัดสิน 2026-10-04) — `api` ปิดผนึกเก็บเป็นสถานะ
"ยังไม่ตรวจ" แล้ว `engine` เป็นผู้ตรวจ · **งานนี้จึงสร้าง worker ตัวแรกของ `engine`**
และผู้ใช้เห็นผลแบบไม่ทันที ซึ่งเป็นราคาที่รับแล้ว

`trading-safety.md` บังคับว่าต้องตรวจตอนเพิ่ม แต่การตรวจต้องยิงคำขอที่ **ลงลายเซ็นด้วย
secret** ไปที่ตลาด และ `architecture.md` หัวข้อ 3 ให้ `engine` เท่านั้นถอดรหัสได้
ขณะที่ secret ดิบอยู่ในมือ `api` เพียงชั่วขณะเดียวคือตอนผู้ใช้กรอก

| ทางเลือก | ผล |
|---|---|
| **ก. `api` ตรวจตอนยังถือ plaintext แล้วค่อยปิดผนึก** | ผู้ใช้ได้คำตอบในคำขอเดียว และ key ที่สิทธิ์เกิน **ไม่ถูกบันทึกเลย** **แลกกับ** `api` ต้องยิงคำขอออกเน็ตไปตลาด ซึ่ง `architecture.md` หัวข้อ 3 ไม่ได้ให้ไว้ และ "ถือ plaintext ไม่นานกว่าที่จำเป็น" ยืดออกเท่าเวลารอตลาดตอบ |
| **ข. `api` ปิดผนึกเก็บเป็นสถานะ "ยังไม่ตรวจ" แล้ว `engine` ตรวจ** | ตรงกับ `architecture.md` ทุกข้อ (ถอดรหัสที่ `engine`, `api` ไม่แตะตลาด, "บันทึกก่อนแล้วค่อยประกาศ" ตามหัวข้อ 5) **แลกกับ** ต้องสร้าง **worker ตัวแรกของ `engine`** ในงานนี้ (วันนี้ `services/engine/main.py` ยังไม่ทำอะไรเลย) ผู้ใช้เห็นผลแบบไม่ทันที และ key ที่สิทธิ์เกินถูกเก็บลงฐานข้อมูลก่อนถูกปฏิเสธ |
| **ค. `api` ปิดผนึกแล้วรอผลจาก `engine` ภายในคำขอเดียวกัน** (ส่งงานและรับผลผ่าน PostgreSQL/Redis) | ได้ทั้งสองอย่าง: ผู้ใช้เห็นผลทันที และ `api` ไม่แตะตลาด · **`architecture.md` ไม่ได้ห้ามทางนี้** — หัวข้อ 1 ห้าม service **เรียก HTTP หากัน** และบังคับให้คุยผ่าน PostgreSQL/Redis ซึ่งทางนี้ทำตาม **แลกกับ** คำขอของผู้ใช้ไปผูกกับเวลาตอบของ `engine` จึงต้องออกแบบ timeout, พฤติกรรมเมื่อ `engine` ไม่ทำงาน และกรณีที่ผลมาถึงหลังผู้ใช้เลิกรอแล้ว (งานตรวจเดินต่อไปแล้ว) · ต้องสร้าง worker ตัวแรกของ `engine` เหมือนช่อง ข. |

**ผมแนะนำ ข.** เพราะมันไม่ต้องแก้หรือยืดกฎสถาปัตยกรรมข้อใดเลย และกฎที่ว่า

เหตุผล: ส่วนที่เปิดเผยได้ไม่ใช่ความลับอยู่แล้ว (มันเดินทางไปกับทุกคำขอที่ส่งตลาด)
มันพอให้ผู้ใช้แยก key หลายอันออกจากกัน ซึ่งเป็นงานที่ข้อนี้มีไว้ทำ ส่วนการโชว์
4 ตัวท้ายของ secret คือการให้ข้อมูลของความลับฟรี ๆ โดยไม่ได้ประโยชน์เพิ่ม
และ RQ-5 ห้ามอยู่แล้ว

**คำว่า "เปิดเผยได้" ที่นี่หมายถึง "ไม่ใช่ความลับที่ใช้ลงลายเซ็น" เท่านั้น
ไม่ได้หมายถึง "เอาไปใส่ log ได้"** — `security.md` หัวข้อ 4 ห้าม API key ใน log
ทุกกรณี ฉะนั้นค่าเต็มของมันแสดงให้เจ้าของบัญชีเห็นบนหน้าจอได้ (ถ้าเจ้าของสั่ง)
แต่เข้า log, audit `details`, metric หรือข้อความ error ไม่ได้เลย (RQ-9.1, RQ-9.2)

**ถ้าเจ้าของยืนยันข้อนี้ ผมจะขอแก้ถ้อยคำใน `mission.md` และ `tech-stack.md`
ให้ชัดในงานเดียวกัน** เพราะข้อความปัจจุบันอ่านได้สองทาง

### Q-6 — เปลี่ยน key ทำอย่างไร

**ตัดสินแล้ว: ลบแล้วเพิ่มใหม่** (เจ้าของตัดสิน 2026-10-04) — ไม่มีเส้นทาง "เปลี่ยน" แยกต่างหาก

ลบแล้วเพิ่มใหม่ (สองคำขอ) หรือมีเส้นทาง "เปลี่ยน" เส้นเดียว ผมเสนอ **ลบแล้วเพิ่มใหม่**
เพราะไม่มีสถานะกลางให้ดูแล และ F-06 แสดงให้เห็นแล้วว่าการ "เขียนทับ secret" ต้องการ
ช่องพักของตัวเอง ซึ่งยังไม่มีเหตุผลที่นี่ — ไม่บล็อก plan ถ้าเจ้าของรับข้อเสนอนี้

### Q-7 — ผลของการตรวจแต่ละแบบ (**บล็อก plan**)

**ตัดสินแล้วสี่ข้อ** (เจ้าของตัดสิน 2026-10-04):

- **สถานะที่ผู้ใช้เห็นมีสี่สถานะ**: กำลังตรวจ · ใช้งานได้ · ตรวจไม่ผ่าน (key ผิดจริง)
  · ตรวจไม่ได้ ลองใหม่ได้ (ตลาดหรือเน็ตมีปัญหา) — **สองสถานะหลังต้องแยกกัน**
  เพราะคนใช้ต้องทำคนละอย่าง: อันหนึ่งไปแก้ที่ Binance อีกอันแค่รอ
- **การกดลองใหม่ไม่ต้องใส่รหัส TOTP ซ้ำ** เพราะ secret เข้าระบบไปแล้วตอนเพิ่ม
  ซึ่งผ่านการยืนยันไปแล้ว การลองใหม่ไม่ได้เพิ่มความเสี่ยงใหม่ · และ `security.md`
  ไม่มีช่วงผ่อนผัน ถ้าบังคับยืนยัน ผู้ใช้ต้องรอรหัสช่วงใหม่ทุกครั้งที่กด

- **ลองใหม่: ระบบลองเอง และผู้ใช้กดลองใหม่เองได้ด้วย** — ครอบทั้งกรณีเน็ตสะดุด
  ชั่วคราว (ระบบจัดการเอง) และกรณีตลาดล่มยาว (ผู้ใช้ไม่ต้องนั่งรอเฉย ๆ)
- **เพดาน 24 ชั่วโมง ครอบ *ทุกสถานะที่ยังไม่ผ่านการตรวจ*** ไม่ใช่เฉพาะ "กำลังตรวจ"
  (แก้หลังรีวิว 2026-10-04 — เดิมเขียนครอบสถานะเดียว ซึ่งเปิดช่องให้ secret ของ
  สถานะ "ตรวจไม่ได้ ลองใหม่ได้" ค้างตลอดไป):
  - **นับจากเวลาที่ผู้ใช้เพิ่ม key** — **ไม่ใช่นับใหม่ทุกครั้งที่ลองใหม่** เพราะการนับใหม่
    ทำให้ key ที่ลองใหม่เรื่อย ๆ ไม่มีวันหมดอายุ ซึ่งเท่ากับไม่มีเพดาน
  - ครบ 24 ชั่วโมงแล้วยังไม่ผ่าน → **ลบค่าที่ปิดผนึกทิ้ง** เหลือไว้แต่สถานะและ
    รหัสเหตุผล · ผู้ใช้เพิ่มใหม่ได้เสมอ (ข้อมูลที่หายคือ secret ซึ่งผู้ใช้มีอยู่แล้ว)
  - **ผลตรวจที่มาถึงช้ากว่าเพดาน ต้องเปิดใช้งาน key นั้นไม่ได้** — ของที่หมดอายุแล้ว
    กลับมามีชีวิตไม่ได้ ไม่ว่าผลจะเป็นบวกแค่ไหน

การตรวจหนึ่งครั้งจบได้ **สามแบบ ไม่ใช่สองแบบ** และข้อเสนอเดิมของผมรวมสองแบบหลัง
เข้าด้วยกันผิด ซึ่งจะทำให้ **ลบ key ที่ถูกต้องทิ้งเพราะตลาดล่มชั่วคราว**
F-33 แยกชนิดข้อผิดพลาดไว้ให้แล้ว (หมดเวลา, ถูกจำกัดอัตรา, ตลาดตอบไม่ตรงสัญญา,
คำรับรองไม่ผ่าน) ฉะนั้นการแยกสามแบบนี้ทำได้จริงด้วยของที่มีอยู่:

| ผลการตรวจ | ตัวอย่าง | ต้องตัดสินว่า |
|---|---|---|
| **ก. key ใช้ไม่ได้จริง** | ตลาดบอกว่าคำรับรองไม่ถูกต้อง หรือสิทธิ์เกินที่ยอมรับ | **ตัดสินแล้ว 2026-10-04: ลบค่าที่ปิดผนึกทิ้งทันที** เหลือสถานะกับรหัสเหตุผลให้ผู้ใช้เห็น · key ที่ใช้ไม่ได้ไม่มีเหตุให้เก็บความลับของมันต่อ และผู้ใช้เพิ่มใหม่ได้เสมอ |
| **ข. ตรวจไม่ได้ชั่วคราว** | หมดเวลา, ตลาดล่ม, ถูกจำกัดอัตรา, เน็ตมีปัญหา | **ห้ามลบ secret** · ลองใหม่กี่ครั้ง ห่างแค่ไหน ผู้ใช้เห็นสถานะอะไร และสั่งลองใหม่เองได้ไหม |
| **ค. ตลาดตอบไม่ตรงสัญญา** | ช่องที่ควรมีหายไป หรือรูปแบบเปลี่ยน | **ตัดสินแล้ว 2026-10-04: นับเป็นแบบ ข. (ชั่วคราว) ห้ามลบ secret · และต้องแจ้งผู้ดูแลแยกจากกรณีเน็ตสะดุด** เพราะสองอย่างนี้ต้องการคนละการกระทำ — อย่างหนึ่งรอ อีกอย่างมีคนต้องแก้โค้ด (บทเรียนจาก F-35) · `plan.md` ต้องระบุช่องทางที่ผู้ดูแลเห็นจริง |

ข้อที่ต้องเจ้าของตัดสินเป็นรายข้อ:

1. **สถานะที่ผู้ใช้เห็น** มีกี่สถานะ และเขียนว่าอะไร ("กำลังตรวจ", "ตรวจไม่ผ่าน",
   "ตรวจไม่ได้ ลองใหม่")
2. **ทางลองใหม่** — ระบบลองเองเป็นรอบ ๆ, ผู้ใช้กดลองใหม่, หรือทั้งสอง
   · ถ้าผู้ใช้กดลองใหม่ ต้องยืนยัน TOTP ซ้ำอีกครั้งหรือไม่ (การลองใหม่ไม่ได้เพิ่ม
   ความเสี่ยงใหม่ เพราะ secret เข้าระบบไปแล้ว — แต่ข้อนี้ผมไม่เดา)
3. **เพดานของ "กำลังตรวจ"** — ค้างได้นานแค่ไหนก่อนกลายเป็นแบบ ก. หรือก่อนลบ secret
   **การไม่มีเพดานคือการปล่อย secret ที่ไม่มีใครใช้ให้ค้างในฐานข้อมูลตลอดไป**
4. **key ที่ยังไม่ผ่านการตรวจต้องใช้ทำอะไรไม่ได้เลย** (RQ-6) — ข้อนี้ผมถือเป็น
   ข้อกำหนดแล้ว ไม่ใช่คำถาม เพราะมันมาจาก `trading-safety.md` โดยตรง

### Q-7.1 — key ที่ตลาดปฏิเสธภายหลัง
