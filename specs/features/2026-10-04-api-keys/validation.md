## "เสร็จ" หมายถึง

### ก. ความลับไม่รั่ว — ด่านที่ทั้งงานตั้งอยู่บน

| # | เกณฑ์ | ตรวจอย่างไร |
|---|---|---|
| V-1 | **บทบาท `api` อ่าน `secret_sealed` ไม่ได้** | `SELECT secret_sealed` ด้วยบทบาท `api` ต้องถูกฐานข้อมูลปฏิเสธ · และ `SELECT *` ต้องล้ม ไม่ใช่คืนค่า |
| V-2 | **บทบาท `engine_scan` ก็อ่านไม่ได้** | เหมือน V-1 ด้วยบทบาทนั้น |
| V-3 | `engine` อ่านได้และเปิดผนึกได้ | อ่านแล้วเปิดผนึกได้ค่าเดิมที่ปิดผนึกไว้ |
| V-4 | **ไม่มี endpoint ใดคืน secret** ไม่ว่าเต็มหรือบางส่วน | เดินทุกเส้นทางของ `app.routes` แล้วตรวจว่าไม่มีคำตอบใดมีค่าที่ปิดผนึกหรือค่าดิบ |
| V-5 | **ลายเซ็นไม่ลง log แม้เปิด log ระดับ INFO ของไลบรารี HTTP** | ตั้ง log ระดับ INFO แล้วเรียกคำขอที่ลงลายเซ็น จับบันทึกทั้งหมด ต้องไม่มีลายเซ็นและไม่มี query string |
| V-6 | **`details` ของ audit ไม่มี secret และไม่มี API key** | ตรวจทุกชนิดเหตุการณ์ใหม่ว่า `details` **มีได้แค่ `key_id`** · สาเหตุความล้มเหลวอยู่ใน **คอลัมน์ `failure_code` ของตาราง audit** ไม่ใช่ใน `details` (`plan.md` ข้อ 4.4) · `CHECK` ในฐานข้อมูลต้องปฏิเสธรูปอื่น |
| V-7 | ข้อความ error ไม่พาค่าดิบไปด้วย | ทำให้ทุกเส้นทางล้มทีละแบบ แล้วตรวจข้อความที่ออกมา |
| V-8 | **secret ไม่ค้างในหน้าเว็บ** | ตรวจว่า `localStorage`/`sessionStorage` ว่าง และช่อง secret ถูกล้างหลังส่ง |

### ค. การตรวจ key และสถานะ

| # | เกณฑ์ | ตรวจอย่างไร |
|---|---|---|
| V-13 | key ที่ใช้ได้ → `ACTIVE` | `FakeVenue` ตอบกระเป๋าสำเร็จ |
| V-14 | **key ที่คำรับรองไม่ถูกต้อง → `REJECTED` และ secret ถูกลบทันที** | ตรวจทั้งสถานะและคอลัมน์ที่ต้องเป็น `NULL` |
| V-15 | **ตลาดล่ม/หมดเวลา/ถูกจำกัดอัตรา → `UNVERIFIABLE` และ secret ยังอยู่** | เดินครบทุกชนิดข้อผิดพลาดชั่วคราวของ `venues/errors.py` |
| V-15.1 | **คำขอถูกปฏิเสธโดยไม่พิสูจน์ว่าคำรับรองผิด ต้องเก็บ secret และไม่ตรวจซ้ำอัตโนมัติ** (NC-20 เจ้าของอนุมัติ 2026-10-06) | WAF/timestamp/รหัสไม่รู้จัก → UNVERIFIABLE + ERROR + audit · รอบอัตโนมัติไม่ส่งคำขอ · กดลองใหม่เองได้ภายใต้โควตา/market wait เดิม · ไม่กดจน 24 ชม. ต้องลบ secret |
| V-16 | **ตอบไม่ตรงสัญญา → `UNVERIFIABLE` + บันทึกระดับ ERROR ที่มีรหัสของตัวเอง** | แยกจากกรณีเน็ตสะดุดได้จริงในบันทึก ไม่ใช่รหัสเดียวกัน |
| V-17 | **ครบ 24 ชม. นับจากเวลาที่เพิ่ม → `REJECTED` และ secret ถูกลบ** | เลื่อนเวลาที่ส่งเข้าไป ไม่ใช่รอจริง |
| V-18 | **การลองใหม่ไม่รีเซ็ตเพดาน** | ลองใหม่หลายครั้งแล้วเพดานยังนับจาก `created_at` เดิม |
| V-19 | **ผลสำเร็จที่มาถึงหลังเพดาน ต้องไม่ทำให้ key เป็น `ACTIVE`** | เริ่มรอบตรวจตอนเหลืออายุ 1 วินาที ให้ตลาดตอบสำเร็จหลังครบ 24 ชม. · **ห้ามให้ worker อื่นเปลี่ยนสถานะให้ก่อน** — แถวต้องยังเป็น `PENDING` ตอนผลกลับมา และต้องจบที่ `REJECTED` + `VERIFICATION_EXPIRED` พร้อม secret ถูกลบ |
| V-19.1 | ฐานข้อมูลเป็นผู้ชี้ขาด ไม่ใช่ลำดับคำสั่งในโค้ด | `UPDATE` ที่เขียน `ACTIVE` ต้องมีเงื่อนไขเวลาอยู่ในคำสั่ง — ลบเงื่อนไขนั้นออกแล้วเทสต์ V-19 ต้องแดง |
| V-19.2 | **เงื่อนไขเวลาใช้ `clock_timestamp()` ไม่ใช่ `now()`** | เปิด transaction **ก่อน** เส้นตาย แล้วเขียนผลหลังเส้นตายใน transaction เดียวกัน · ต้องจบที่ `REJECTED` · เปลี่ยนเป็น `now()` แล้วเทสต์นี้ต้องแดง (`now()` คือเวลาที่ transaction เริ่ม) |
| V-20 | **key ที่ผู้ใช้ลบระหว่างรอ ไม่ถูกเขียนผลทับ** | ลบแถวระหว่างที่รอบตรวจกำลังทำงาน แล้วต้องไม่มีแถวกลับมา |
| V-21 | **key ที่ยังไม่ `ACTIVE` ใช้ทำอะไรไม่ได้** | ทุกทางที่หยิบ key ไปใช้ต้องมองไม่เห็นแถวที่ยังไม่ผ่าน |
| V-22 | worker สองตัวพร้อมกันไม่ตรวจแถวเดียวกันซ้ำ | รันสองรอบพร้อมกันบนฐานข้อมูลเดียว |
| V-22.1 | **กดลองใหม่ระหว่าง worker ตัวแรกรอตลาด ต้องไม่เกิดรอบซ้อน** | worker หนึ่งจองแถวแล้วค้างอยู่ที่การเรียกตลาด → ผู้ใช้กดลองใหม่ → worker สองต้องหยิบแถวนั้นไม่ได้ · ความพยายามเพิ่มเกิดขึ้น **หลัง** รอบแรกจบเท่านั้น |
| V-22.2 | **ผลของรอบที่ช้าเขียนทับผลของรอบใหม่ไม่ได้** | ปล่อยให้การจองของรอบแรกหมดอายุ รอบสองตรวจจบและเขียน `ACTIVE` แล้วให้ผลของรอบแรกกลับมาทีหลัง → ต้องถูกปฏิเสธ ไม่ใช่เขียนทับ |
| V-22.3 | **worker ตายแล้วแถวไม่ค้างตลอดไป** | ฆ่า worker ระหว่างถือการจอง → เมื่อการจองหมดอายุ แถวต้องถูกหยิบไปตรวจใหม่ได้เอง |
| V-22.4 | **คำสั่งของตลาดให้รอ ถูกบังคับที่ตอนจอง ไม่ใช่ที่ endpoint** | worker สองตัว scan เจอแถวเดียวกัน → ตัวแรกตรวจแล้วบันทึก `not_before` ในอนาคตและปลดการจอง → **ตัวที่สองต้องจองไม่ได้และต้องไม่เรียกตลาดเลย** (นับจำนวนคำขอที่ออกไปจริง) |
| V-22.5 | **ผล scan ที่เก่าแล้วไม่ทำให้ข้าม backoff** | worker แรกตรวจเสร็จจน `attempts` เพิ่มและช่วงรอเปลี่ยนจาก 1 เป็น 5 นาที → worker ที่ถือค่าเก่าพยายามจองที่นาทีที่ 2 → **ต้องได้ศูนย์แถวและไม่เรียกตลาด** |
| V-22.6 | **ตอนจองไม่มีการคำนวณ backoff เลย** | คำสั่งจองต้องเทียบ `next_attempt_at` อย่างเดียว · ถ้ามีใครย้ายการคำนวณกลับมาที่จุดจอง เทสต์ V-22.5 ต้องแดง |
| V-22.7 | **แถวที่รออยู่ต้องไม่บังงานใหม่ใน batch** (เจ้าของสั่งซ่อม review ข้อ 3 วันที่ 2026-10-06) | มีแถวเก่าเต็ม batch ที่รอ backoff/market wait/live lease/manual-only คู่กับ PENDING ใหม่และ expired · ใหม่ต้องถูกตรวจ expired ต้องลบ secret โดยไม่เรียกตลาดด้วยแถวรอ · claim ยังตรวจ eligibility ซ้ำ |

## ตรวจด้วยมือ

ทำกับบัญชี Binance TH จริงของเจ้าของ **และห้ามใช้ key ที่ใช้เทรดจริงอยู่**

1. สร้าง key ทดสอบ → เพิ่มผ่านหน้าเว็บ → ต้องเห็นสถานะเปลี่ยนเป็น "ใช้งานได้" เอง
2. เพิ่ม key ที่พิมพ์ secret ผิดหนึ่งตัว → ต้องได้ "ตรวจไม่ผ่าน" และ **แถวนั้นต้องไม่มี
   secret เหลืออยู่** (ตรวจในฐานข้อมูลด้วยบทบาท `engine`)
3. ตัดเน็ตของ `engine` ชั่วคราว → ต้องได้ "ตรวจไม่ได้ ลองใหม่ได้" **ไม่ใช่ "ตรวจไม่ผ่าน"**
   แล้วต่อเน็ตกลับ กดลองใหม่ → ต้องกลายเป็น "ใช้งานได้"
4. ลบ key → หายจากรายการ และเพิ่มชื่อเดิมใหม่ได้
5. เปิดหน้าเว็บด้วยบัญชีที่ยังไม่เปิด TOTP → ต้องเห็นทางออกที่ชัด ไม่ใช่ข้อความกลาง ๆ
6. **ตรวจ log ของทั้งสอง process ด้วยตา** ว่าไม่มี key ไม่มี secret ไม่มีลายเซ็น
7. ถอน key ทดสอบทั้งหมดที่ Binance เมื่อเสร็จ
