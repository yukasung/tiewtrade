# Review: F-01 Project Skeleton — Requirements

รีวิวนี้เป็นข้อค้นพบและข้อเสนอ ไม่ใช่การอนุมัติ requirements หรืออนุญาตให้เริ่มเขียนแผนหรือโค้ด เลขบรรทัดอ้างถึงฉบับที่ตรวจและอาจเปลี่ยนเมื่อแก้เอกสาร

## 1. RQ-5 ทับกับงาน F-33 เรื่องส่วนต่อประสานตลาด — ✅ แก้แล้ว ตรวจยืนยัน 2026-09-27

ที่มา: `requirements.md` บรรทัด 53 (RQ-5), `roadmap.md` F-33

RQ-5 กำหนดว่า `venues` ต้องมีส่วนต่อประสานกลาง แต่ Roadmap แยกการสร้างส่วนต่อประสานราคา ออเดอร์ กระเป๋า และข้อจำกัดเหรียญไว้ใน F-33 ผู้ทำงานอาจตีความว่าต้องออกแบบ interface เหล่านั้นใน F-01 ซึ่งเริ่มแตะโมเดลโดเมนและเกินขอบเขต “โครง repo”

**ผลกระทบ:** ขอบเขตส่งมอบระหว่าง F-01 และ F-33 ไม่ชัด เสี่ยงทำซ้ำหรือออกแบบโดเมนก่อนมีข้อกำหนดของงานนั้น

**ข้อเสนอ:** ระบุว่า F-01 ทำถึงระดับโครง package และกฎการพึ่งพา หรือรวม interface จริงด้วย หากรวม ต้องปรับขอบเขต F-33 ให้ไม่ซ้ำกัน การเลือกขอบเขตต้องให้เจ้าของตัดสินใจ

## 2. RQ-12 อนุญาตให้ลบหลักฐานที่ใช้พิสูจน์ว่าด่านตรวจทำงาน — ✅ แก้แล้ว 2026-09-26

ที่มา: `requirements.md` บรรทัด 60 (RQ-12) และหัวข้อ “ข้อที่ผมเพิ่มเอง”

ข้อกำหนดให้สร้างกรณีที่จงใจผิด “แล้วลบหรือปิดไว้” หลังพิสูจน์ว่าด่านจับได้ ทำให้ผู้ตรวจงานภายหลังรันซ้ำไม่ได้ และการแก้ config ในอนาคตอาจทำให้ด่านตรวจเสียโดยไม่มีอะไรจับ

**ผลกระทบ:** หลักฐานว่าด่านตรวจจับความผิดได้อาจมีเฉพาะตอนตั้งระบบครั้งแรก แต่ตรวจซ้ำจากสิ่งที่ส่งมอบไม่ได้

**ข้อเสนอ:** เก็บกรณีตัวอย่างที่ละเมิดกฎไว้ และมีการตรวจอัตโนมัติที่คาดหวังว่าด่านจะปฏิเสธกรณีนั้น ชุดตรวจหลักจึงยังผ่านได้เมื่อเครื่องมือจับความผิดถูกต้อง ส่วนวิธีแยกไฟล์และรันให้กำหนดใน `plan.md` หลังข้อกำหนดได้รับอนุมัติ ข้อเสนอนี้ยังไม่ใช่คำตัดสินแทนเจ้าของเกี่ยวกับ RQ-12

## 3. RQ-13 ยังไม่ชัดว่าต้องส่งมอบอะไรเรื่องชนิดข้อมูลหน้าบ้าน — ✅ แก้แล้ว ตรวจยืนยัน 2026-09-27

ที่มา: `requirements.md` บรรทัด 61 (RQ-13) และบรรทัด 86 (Q-2)

RQ-13 ระบุว่า OpenAPI ต้องสร้างชนิดข้อมูลหน้าบ้านอัตโนมัติ “ได้” แต่ Q-2 ยังไม่ตัดสินว่าจะรวมโครงหน้าบ้านหรือไม่ จึงมีเกณฑ์จบงานได้สองแบบ: เพียงเตรียม schema หรือมีคำสั่งสร้างชนิดข้อมูลและผลลัพธ์ที่ตรวจสอบได้จริง

**ผลกระทบ:** ผู้ทำงานกับผู้ตรวจอาจเข้าใจผลส่งมอบต่างกัน และไม่สามารถกำหนดเกณฑ์ validation ที่ตรงกันได้

**ข้อเสนอ:** ระบุผลส่งมอบขั้นต่ำของ F-01 ให้ชัดและผูกกับคำตอบ Q-2 โดยไม่จำเป็นต้องสร้างหน้าจอผู้ใช้ รายละเอียดเครื่องมือและคำสั่งค่อยกำหนดใน `plan.md`

## 4. สถานะเรื่องที่บล็อกงานไม่ตรงกับเอกสารกลาง — ✅ แก้แล้ว 2026-09-26

ที่มา: `requirements.md` บรรทัด 81–91, `roadmap.md` บรรทัด 27 (F-01), `tech-stack.md` หัวข้อ 9 และ AGENTS.md หัวข้อ “เมื่อไรต้องอัปเดต spec”

Requirements ระบุ Q-1 ถึง Q-5 ว่าต้องตอบก่อนเขียนแผน แต่ Roadmap ระบุ F-01 ว่า “ไม่มีข้อที่บล็อกแล้ว” และคำถามใหม่ยังไม่ได้เชื่อมเข้ารายการกลางใน Mission ตาม AGENTS.md

นอกจากนี้ Q-3 ถามว่าจะใช้ CI อะไร ทั้งที่ Tech Stack ระบุ GitHub Actions อยู่แล้ว หากยังรออนุมัติตัวเลือกนี้ ควรเขียนว่า “รอยืนยันข้อเสนอเดิม” ให้ชัด

**ผลกระทบ:** Agent ที่เริ่มอ่านคนละไฟล์อาจเข้าใจสถานะความพร้อมของ F-01 ต่างกัน หรือถามเรื่องเดิมโดยไม่อ้างข้อเสนอที่มีอยู่

**ข้อเสนอ:** ปรับ Roadmap ให้สะท้อนข้อที่ยังค้าง และเพิ่มรายการอ้างอิงคำถามใน Mission หัวข้อ 9 พร้อมสิ่งที่บล็อก โดยอ้างกลับมาที่ requirements เพื่อไม่ให้รายละเอียดคำถามซ้ำกันหลายที่

## แนวทางส่งต่อให้ Claude Code

**อัปเดต 2026-09-27:** คำถามขอบเขตด้านล่างตอบครบแล้ว ข้อความและบันทึกวันที่ 2026-09-26 เก็บไว้เป็นประวัติ ให้ใช้ [รีวิวรอบสอง](2026-09-27-project-skeleton-requirements.md) สำหรับสถานะล่าสุด Requirements ยังรอเจ้าของอนุมัติ

อ่านสเปกต้นทางล่าสุดก่อนแก้ และแยกการปรับถ้อยคำหรือสถานะให้สอดคล้องกันออกจากการตัดสินขอบเขตที่ต้องได้คำตอบจากเจ้าของ Q-1, Q-2, Q-4 และ Q-5 เป็นคำถามเรื่องขอบเขตที่เหมาะสมแล้ว ห้ามเลือกคำตอบแทนเจ้าของ

รายละเอียดอย่างรูปแบบ Dockerfile และการตั้งค่าเครื่องมือแต่ละตัวค่อยลงใน `plan.md` หลัง requirements ได้รับอนุมัติ เมื่อแก้แล้วให้บันทึกสถานะแต่ละข้อและอ้างอิงไฟล์ที่แก้เพื่อให้ตรวจซ้ำได้

## บันทึกการแก้ไข 2026-09-26

**ข้อ 1** — RQ-5 เพิ่มหมายเหตุว่าระดับที่ทำใน F-01 ยังไม่ชัด และเพิ่ม **Q-6** ในหัวข้อ "ยังไม่ชัด"
ให้เจ้าของตัดสินว่า F-01 ทำแค่โครง package หรือออกแบบส่วนต่อประสานจริง
ถ้าทำจริงต้องหั่นขอบเขต F-33 ใหม่ **ไม่เลือกแทนเจ้าของ**

**ข้อ 2** — RQ-12 แก้จาก "ทดสอบแล้วลบหรือปิดไว้" เป็น **เก็บกรณีที่ละเมิดกฎไว้ถาวร

ว่าฉบับแรกผิดเพราะอะไร RQ-12 ยังเป็นข้อที่เจ้าของยังไม่อนุมัติ ตัดออกได้

**ข้อ 3** — RQ-13 เพิ่มหมายเหตุว่าผลส่งมอบขั้นต่ำขึ้นกับคำตอบ Q-2 ยังไม่กำหนดแทนเจ้าของ

**ข้อ 4** — แก้สองที่:
- `roadmap.md` F-01 เปลี่ยนจาก "ไม่มีข้อที่บล็อกแล้ว" เป็นระบุว่าตัวเลือกเทคโนโลยีปิดครบ

- เพิ่ม **NC-14** ใน `mission.md` หัวข้อ 9 ชี้กลับมาที่ requirements ไม่เขียนรายละเอียดซ้ำ
