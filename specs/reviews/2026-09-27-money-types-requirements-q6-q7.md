# Review: F-02 Requirements หลังเพิ่ม Q-6/Q-7

วันที่: 2026-09-27  
ไฟล์: [requirements.md](../features/2026-09-27-money-types/requirements.md) ฉบับ Proposed  
ผล: แก้ครบแล้ว 2026-09-27 — requirements พร้อมเสนอเจ้าของอนุมัติ

## ข้อค้นพบ

### R-1 [P2] ท้าย Q-2 ยังห้ามการปัดที่ Q-6 อนุญาต — ✅ แก้แล้ว 2026-09-27

ตำแหน่ง: requirements บรรทัด 218–220 เทียบกับ RQ-23 บรรทัด 78 และ Q-6 บรรทัด 359–369

ท้าย Q-2 ยังระบุว่า “จังหวะที่ปัดคือ ตอนจะเก็บลงฐานข้อมูลและตอนหารไม่ลงตัว … ระหว่างคำนวณห้ามปัด” แต่ Q-6 อนุญาตให้การคูณปัดผลเหลือ 18 ตำแหน่งเมื่อผู้เรียกระบุทิศทาง

ตัวอย่าง `1E-18 × 0.1` พร้อมทิศทางการปัดจึงถูกอนุญาตโดย Q-6 แต่ถูกห้ามโดย Q-2 หากยังไม่ได้กำลังบันทึกฐานข้อมูล ทำให้ผู้เขียน plan เลือกพฤติกรรมจากเอกสารเดียวกันได้สองแบบ

ข้อเสนอ: แทนย่อหน้าเดิมด้วยข้อความที่สอดคล้องกับ Q-6 เช่น:

> ห้ามปัดโดยปริยายระหว่างคำนวณ สำหรับ F-02 การคูณที่ผลมีทศนิยมจริงเกิน 18 ตำแหน่งปัดได้ตาม Q-6 เมื่อผู้เรียกระบุทิศทาง โดยความละเอียดปลายทางคือ 18 ตำแหน่ง ส่วนการปัดในงานอื่นต้องมีข้อกำหนดอนุญาตเฉพาะจุดนั้น

ไม่ต้องเปิดคำถามนโยบายใหม่ เป็นการทำข้อความเก่าให้ตรงกับ Q-6 ที่บันทึกแล้ว

## สถานะที่ต้องทำให้ชัดก่อนเสนออนุมัติ

- **RQ-21 (บรรทัด 76, 82–88):** ยังติดป้ายว่าเป็นข้ออนุมานที่เจ้าของไม่ได้ยืนยัน จึงไม่ควรสรุปว่าไม่มีประเด็นรอยืนยันเหลือ ข้อความนี้มีประโยชน์ในฐานะกฎรวม แต่ควรนำเข้าการอนุมัติ requirements ฉบับนี้อย่างชัดเจน หรือจำกัดให้เป็นข้อความสรุปกฎที่ตัดสินแล้ว สำหรับ Q-6 ความละเอียดปลายทาง 18 ถูกกำหนดโดย operation อยู่แล้ว ไม่ต้องเพิ่ม parameter ให้ผู้เรียกเลือก scale โดยปริยาย
- **NC-15 ใน mission.md บรรทัด 271:** ยังบอกว่าเหลือสองเรื่องคือผลคูณและ scalar แต่ Q-6/Q-7 ตัดสินแล้ว ควรเปลี่ยนให้สะท้อนว่าปิดสองเรื่องนี้แล้วและ requirements ยังรออนุมัติ ไม่ถือว่าการตอบคำถามเท่ากับอนุมัติเอกสารทั้งฉบับ

## ผลติดตามรีวิวรอบก่อน

| ประเด็น | ผล |
|---|---|
| จุดปัดถูกจำกัดเกินคำตัดสิน | RQ-21 แก้ถ้อยคำแล้ว แต่ท้าย Q-2 ยังตกค้างตาม R-1 |
| ผลคูณ exact ที่เกิน scale | ปิดด้วย Q-6: exact / ปัดเมื่อระบุ / error เมื่อไม่ระบุ / error เมื่อล้น และห้ามปัด operand |
| หน่วยผิดต้องตรวจ runtime | ปิดแล้วในตาราง Q-3 และย่อหน้าบรรทัด 257–263 |
| scalar ไม่มีขอบเขต | ปิดด้วย Q-7 และ RQ-22/RQ-24: finite, ชนิด input ที่อนุญาต, ค่าสัมบูรณ์น้อยกว่า 10^20 และทศนิยมจริงไม่เกิน 18 |

ขอบเขตการรับประกัน 80 หลักถูกจำกัดเป็น operation สอง operand ที่อยู่ในช่วงแล้ว การหารยังอยู่นอก F-02 และการปฏิเสธค่าล้นไม่สั่งหยุดทั้งระบบ เหล่านี้ตรงกับคำตอบในบทสนทนา

## ข้อสรุปสำหรับขั้นถัดไป

ไม่พบความจำเป็นต้องเพิ่มคำถามการเงินชุดใหม่จาก Q-6/Q-7 รอบนี้ หลังแก้ท้าย Q-2 และจัดสถานะ RQ-21/NC-15 ให้ชัด สามารถเสนอ requirements ฉบับรวมให้เจ้าของอนุมัติได้ จากนั้นจึงเขียน plan และ validation ตามขั้นตอนเดิม

## ขอบเขตการตรวจ

ตรวจ requirements ฉบับเต็ม เทียบคำตอบ Q-1–Q-7 รีวิวรอบก่อน และสถานะ NC-15 ไม่ได้แก้ requirements ไม่ได้เปลี่ยนสถานะอนุมัติ ไม่ได้เขียน implementation หรือรัน tests และไม่ได้ตรวจข้อมูลตลาดย้อนหลังที่เอกสารอ้างใหม่

## บันทึกการแก้ไข 2026-09-27

**R-1** — ท้าย Q-2 เขียนไว้ตั้งแต่ก่อนมี Q-6 แล้วไม่ได้กลับไปแก้ ฉบับเดิมบอกว่า
"ระหว่างคำนวณห้ามปัด ปัดเฉพาะตอนเก็บและตอนหารไม่ลงตัว" ซึ่งห้ามสิ่งที่ Q-6 อนุญาต

แทนด้วยตารางจุดที่ปัดได้สามจุด พร้อมระบุว่า **ความละเอียดปลายทางของการคูณคือ
18 ตำแหน่ง กำหนดโดยตัวการคำนวณเอง** และการปัดในงานอื่นต้องมีข้อกำหนดอนุญาตเฉพาะจุด

**RQ-21** — เลิกติดป้ายว่าเป็นข้ออนุมาน เพราะทุกส่วนของข้อนี้มีที่มาจากคำตัดสิน
ของเจ้าของแล้ว (Q-1.2, Q-1.3, Q-2, Q-6) เขียนใหม่เป็น **การรวมกฎที่ตัดสินแล้ว
มาไว้ที่เดียว ไม่ใช่กฎใหม่** และแก้ตามที่รีวิวชี้ว่าความละเอียดปลายทาง
กำหนดโดยจุดที่ปัด ไม่ใช่ให้ผู้เรียกเลือกเอง

**NC-15** — อัปเดตเป็นตัดสินครบทั้ง 7 เรื่อง พร้อมระบุชัดว่า
**การตอบคำถามครบไม่เท่ากับอนุมัติเอกสารทั้งฉบับ** requirements ยังรออนุมัติ

## ผลตรวจซ้ำหลังแก้ — 2026-09-27

อ่าน requirements ฉบับล่าสุดและตรวจการเปลี่ยนแปลงของ requirements/mission แล้ว ยืนยันว่าทั้งสามจุดแก้ครบ: ท้าย Q-2 สอดคล้องกับ Q-6, RQ-21 เป็นข้อสรุปกฎที่ระบุที่มา และ NC-15 ระบุว่าตัดสินครบแต่เอกสารยังรออนุมัติ

ทวน RQ-1–RQ-24 เทียบ Q-1–Q-7 แล้ว **ไม่พบข้อค้นพบใหม่ที่บล็อกการเสนออนุมัติในขอบเขต F-02** constructor ปฏิเสธทศนิยมส่วนเกิน ส่วนการคูณมีเส้นทางปัดที่อนุญาตแยกชัด; scalar ใช้ช่วงเดียวกับเงิน/ปริมาณ; overflow คืน typed error; หน่วยตรวจที่ runtime; serialization รักษาค่า ชนิด และหน่วย

พร้อมเสนอเจ้าของอนุมัติ requirements ผลรีวิวไม่ใช่การอนุมัติแทนเจ้าของ หลังอนุมัติจึงเขียน plan/validation โดยครอบคลุมค่าขอบช่วง ค่าบวก/ลบ การปัดที่ทำให้ล้น และการเปลี่ยน context ภายนอก

รอบตรวจซ้ำอัปเดตเฉพาะรายงาน ไม่แก้ requirements/mission ไม่รัน tests เพราะเป็นการตรวจ spec และไม่รับรอง implementation ที่ยังไม่ได้เขียน
