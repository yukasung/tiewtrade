## ข้อค้นพบ

### R-1 [P1] ขั้นตัดศูนย์ท้ายก่อนตรวจค่าต้องรับประกันว่าไม่ปัด input — ✅ แก้แล้ว 2026-09-27

ตำแหน่ง: plan P-5 บรรทัด 33; validation V-5 บรรทัด 18

P-5 ระบุให้นับ exponent หลังตัดศูนย์ท้าย แต่ยังไม่ระบุว่าต้องเป็นการแปลงแบบไม่สูญเสียค่า การใช้ Decimal.normalize() ซึ่งเป็นทางเลือกตรงไปตรงมา จะปัดตาม context ก่อนตัดศูนย์ แม้ตั้ง precision เป็น 80 แล้วก็ตาม เพราะ input ที่ยังไม่ผ่าน validation อาจมีมากกว่า 80 หลัก

หลักฐานจาก Python ใน repo: ข้อความ `1.` ตามด้วยศูนย์ 80 ตัวแล้วตามด้วย `1` มี exponent -81 และต้องถูกปฏิเสธตาม RQ-16 แต่ normalize() ภายใต้ precision 80 ให้ค่า `1` ถ้าตรวจหลังขั้นนี้จะรับค่าที่ควรปฏิเสธ หากเปิด trap แทนก็อาจปฏิเสธข้อความศูนย์ท้ายยาวที่ค่าจริงถูกต้อง จึงต้องแยกการตรวจ input ออกจากการปัด arithmetic

ข้อเสนอ: ระบุใน P-5 ว่าตรวจ coefficient/exponent และตัดศูนย์ท้ายแบบ exact ก่อน operation ที่อาจปัด ไม่ใช้ normalize/quantize เพื่อทำให้ input ผ่านกฎ เพิ่มคู่ทดสอบ input ยาวเกิน 80 หลัก: ศูนย์ท้ายล้วนที่ยังมีค่าถูกต้องต้องผ่าน และ nonzero ที่ตำแหน่ง 81 ต้องถูกปฏิเสธ ทั้ง str และ Decimal

นี่เป็นช่องว่างของแผน ไม่ใช่การกล่าวว่า implementation ใช้ normalize แล้ว

### R-2 [P2] Property tests กำหนดกฎที่ไม่จริงสำหรับชนิดข้อมูลที่จำกัดช่วง — ✅ แก้แล้ว 2026-09-27

ตำแหน่ง: validation บรรทัด 57–62

ข้อความ “กฎที่ต้องจริงเสมอ ไม่ว่าใส่ค่าอะไร” รวม `(a+b)-b = a` และลำดับการบวกไม่เปลี่ยนผล โดยไม่ได้กำหนดว่าผลระหว่างทางต้องอยู่ในช่วง

ให้ M = `99999999999999999999.999999999999999999` และ u = `1E-18` ทั้งสองค่ารับได้ แต่ M+u เท่ากับ `10^20` ซึ่งต้อง error ดังนั้น `(M+u)-u` ไม่มีผลลัพธ์ให้เทียบกับ M และการรวม `[M,u,-u]` ล้น ขณะที่ `[u,-u,M]` ไม่ล้น

ผลกระทบ: implementation ที่ปฏิเสธ overflow ถูกต้องอาจทำให้ property test แดง หรือผู้เขียนแก้โค้ดให้ยอมรับค่าระหว่างทางเกินช่วงเพื่อให้ผ่าน ซึ่งขัดกับ requirements

ข้อเสนอ: ระบุ precondition ของ property ว่า operand มีชนิด/หน่วยตรงกันและผลระหว่างทางของแต่ละเส้นทางอยู่ในช่วง แยก property/cases ที่ต้องได้ typed overflow error ออกมาต่างหาก อย่าคาดหวังว่าทุก permutation ต้องให้ผลสำเร็จเหมือนกัน

### R-3 [P2] Validation ของ context ทดสอบเฉพาะ precision แต่ P-2 รับประกันมากกว่านั้น — ✅ แก้แล้ว 2026-09-27

ตำแหน่ง: plan P-2/P-3 บรรทัด 30–31; validation V-1/V-2 บรรทัด 14–15 และ manual check บรรทัด 80–81

แผนระบุว่าต้องควบคุม precision, rounding, traps และ exponent limits แต่ V-1 เปลี่ยนเฉพาะ precision 6/28/80 implementation ที่คัดลอก context ผู้เรียกแล้วเปลี่ยนแค่ precision จึงยังผ่านวิธีตรวจที่เขียนไว้ได้ ทั้งที่ trap Inexact หรือ exponent limits จากภายนอกยังเปลี่ยนผลหรือชนิดข้อผิดพลาดของการคูณ/ปัดได้

ข้อเสนอ: เพิ่ม matrix ของ rounding, traps และ Emin/Emax ภายนอกด้วย ตรวจทั้งผลสำเร็จและชนิด error เทียบ baseline; V-2 ต้องเทียบ settings และ flags ก่อน/หลังทั้งเส้นทางสำเร็จและ error โดย snapshot ค่า ไม่เก็บเพียง reference ของ context เดิม

แผนควรระบุ context policy ที่จะใช้จริงและการแปลง Decimal exceptions เป็น typed errors ของโมดูล รวมถึงวิธีอนุญาต Inexact เฉพาะการปัดที่ได้รับอนุญาต รายละเอียดนี้เป็นการออกแบบทางเทคนิค ไม่ต้องเลือกนโยบายการเงินใหม่

### R-4 [P2] V-13 ไม่ได้ทดสอบการปัดแล้วล้น และยังขาด overflow จากบวก/ลบ — ✅ แก้แล้ว 2026-09-27

ตำแหน่ง: validation V-13 บรรทัด 26 และกลุ่มตัวเลขจริงบรรทัด 49–52

เกณฑ์เขียนว่าครอบคลุมทั้งล้นและปัดแล้วล้น แต่วิธีตรวจมีแค่ “คูณให้ผลเกิน 10^20” ซึ่ง error ได้ก่อนปัด จึงไม่พิสูจน์ว่ามีการตรวจช่วงซ้ำหลังปัด ส่วนการบวก/ลบที่ขอบช่วงก็ยังไม่มีกรณี error ชัดเจน

ตัวอย่างแยกเส้นทางที่ทดลองยืนยันแล้ว:

- a = `9999999999.999999999999999999`
- b = `10000000000.000000000000000001`
- ผล exact = `10^20 - 10^-36` ซึ่งยังน้อยกว่า `10^20`
- ปัดผลไปทางบวกอนันต์เหลือ 18 ตำแหน่งจะได้ `10^20` และต้อง error

ข้อเสนอ: เพิ่มกรณีนี้คู่กับการปัดไปทางลบอนันต์ที่ได้ค่าสูงสุดซึ่งเก็บได้ เพิ่มด้านค่าลบแบบสมมาตร และกรณี `M + 1E-18` / `-M - 1E-18` ต้องเป็น typed error ทั้ง Money และ Quantity

## สิ่งที่เหมาะแล้ว

- แผนเริ่มจาก context และ shared validation ก่อนชนิดข้อมูล ลดการทำกฎซ้ำ
- ใช้ core, purity gate, import-linter และ hypothesis เดิม มี path ของของเดิมให้ค้นต่อ
- คงการหาร PnL และฐานข้อมูลจริงไว้นอกขอบเขต
- validation ครอบ runtime unit checking, bool/float, non-finite, negative zero, canonical serialization และ immutability
- แยกผลรีวิวออกจากการอนุมัติ เอกสารทั้งสองยังเป็น Proposed ถูกต้อง

## หมายเหตุสำหรับเก็บรายละเอียดในแผน

- P-9/P-10 ยังไม่ระบุ representation ของหน่วยและรายการ rounding directions ที่รองรับ ก่อนลงมือควรมี public interface ที่ชัด รวมตัวอย่าง input/output และประเภท error เพื่อให้คำว่า “ครบทุกทิศทาง” กับ “หน่วยผิด” ใน validation ตรวจได้จริง ถ้าการเลือกทำให้เปลี่ยนหน่วยที่ธุรกิจยอมรับ ต้องถามเจ้าของแทนการกำหนดรายชื่อเอง
- types.py กล่าวถึงชนิด scalar เพิ่มเติม ขณะที่ requirements ส่งมอบสองชนิดที่ผูกหน่วย ควรระบุว่า scalar เป็น internal validation/helper หรือเป็น public type ไม่ให้เพิ่ม public abstraction โดยไม่มีความจำเป็น
- purity gate ตรวจชื่อ float และ relative imports แบบ AST ควรวาง runtime rejection โดยไม่เพิ่มการอ้าง float ที่ทำให้ gate เดิมแดง และใช้ import ที่เข้ากับ gate เดิมตามแผน ไม่ลดความเข้มของด่านเพื่อให้ implementation ผ่าน
- V-23 ควรตรวจว่าไม่มีตรรกะธุรกิจจริง ไม่ใช้เพียงการห้ามคำ เช่นคำว่า order อาจหมายถึงลำดับเปรียบเทียบ ไม่ใช่ออเดอร์เทรด

## หลักฐานและข้อจำกัด

อ่าน plan/validation, requirements ที่อนุมัติ และ purity gate เดิม ทดลองเฉพาะพฤติกรรม Decimal ใน backend venv เพื่อยืนยัน normalization และค่าขอบ ไม่ได้เขียน implementation หรือรันชุด tests ของแอป ไม่แก้เอกสารต้นฉบับและไม่เปลี่ยนสถานะอนุมัติ

พฤติกรรม context และ normalize อ้างอิง [Python 3.12 Decimal](https://docs.python.org/3.12/library/decimal.html) ซึ่งตรวจประกอบไว้ในการสนทนานี้

### R-1 — แก้แล้ว พร้อมหลักฐาน

| input | ทศนิยมจริง | `normalize()` ที่ precision 80 |
|---|---|---|
| `1.` + ศูนย์ 80 ตัว + `1` | 81 → **ต้องปฏิเสธ** | `1` |
| `1.` + ศูนย์ 80 ตัว | 0 → **ต้องรับได้** | `1` |

**ทั้งสองให้ผลเหมือนกัน** ตรวจหลังขั้นนี้จะรับค่าที่ควรปฏิเสธ

P-5 เขียนใหม่ให้ตรวจจาก coefficient และ exponent ตรง ๆ ตัดศูนย์ท้ายแบบ exact
**ห้ามใช้ `normalize()` หรือ `quantize()` ในขั้นตรวจ input**
เพิ่ม V-5.1 เป็นคู่ทดสอบทั้ง `str` และ `Decimal`

### R-2 — แก้แล้ว

เพิ่มเงื่อนไขในทุกกฎว่า operand ต้องชนิดและหน่วยตรงกัน และ
**ผลระหว่างทางของเส้นทางนั้นต้องอยู่ในช่วง** พร้อมตัวอย่าง `M + u` ที่รีวิวยกมา

แยก **"เส้นทางที่ผลระหว่างทางเกินช่วงต้องได้ข้อผิดพลาด"** ออกมาเป็นกฎของตัวเอง
และเขียนเตือนไว้ว่า **ห้ามแก้โค้ดให้ยอมรับค่าที่เกินช่วงเพื่อให้เทสต์ผ่าน**

### R-3 — แก้แล้ว

V-1 เปลี่ยนจากตรวจแค่ precision เป็น **ตารางผสมของ precision, rounding ทุกแบบ,
traps (`Inexact`, `Rounded`, `Overflow`) และ Emin/Emax ที่แคบผิดปกติ**
ตรวจทั้งผลและ **ชนิดข้อผิดพลาด**

เพิ่ม V-1.1 ที่จะแดงถ้า implementation คัดลอก context ผู้เรียกแล้วแก้แต่ precision
และเพิ่ม P-3.1 ว่า **สร้าง context ใหม่จากศูนย์ ห้ามคัดลอกของผู้เรียก**
กับ P-3.2 เรื่องแปลงข้อผิดพลาดของ `Decimal` เป็นชนิดของโมดูล

V-2 เปลี่ยนเป็น **เก็บสำเนาของค่าตั้งและ flags ทั้งหมดแล้วเทียบทีละค่า**
ไม่ใช่เทียบว่าเป็น context ตัวเดิม

### R-4 — แก้แล้ว พร้อมแก้ตัวเลขในรีวิว

**ตัวอย่างในรีวิวมาจากการคูณ ไม่ใช่การบวก** ทดลองแล้ว:

| | ผล |
|---|---|
| `a + b` | `20000000000.000000000000000000` — ไม่ล้น |
| `a × b` | `99999999999999999999.999…` — **ยังน้อยกว่า `10^20`** |
| `a × b` ปัด 18 ตำแหน่งออกจากศูนย์ | `10^20` พอดี → **ต้องเป็นข้อผิดพลาด** |

แยกเป็น V-13 (ล้นตั้งแต่ผลดิบ), **V-13.1 (ปัดแล้วจึงล้น ต้องตรวจช่วงซ้ำหลังปัด)**
และ **V-13.2 (บวกลบที่ขอบช่วงก็ล้นได้)** พร้อมด้านค่าลบแบบสมมาตร
