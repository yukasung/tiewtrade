# Review: F-02 Money Types — Requirements รอบติดตาม Q-1–Q-5

วันที่: 2026-09-27  
ไฟล์: [requirements.md](../features/2026-09-27-money-types/requirements.md) ฉบับ Proposed ที่ตรวจในรอบนี้  
ผล: แก้ R-1 และ R-3 กับข้อความที่ผิดข้อเท็จจริงแล้ว 2026-09-27 — R-2 และ R-4 เพิ่มเป็น Q-6 และ Q-7 รอเจ้าของตัดสิน

เทียบกับคำตัดสินในบทสนทนา มาตรฐาน backend/database และ [รีวิวรอบก่อน](2026-09-27-money-types-requirements.md) เลขบรรทัดด้านล่างอ้างฉบับที่ตรวจ

## ข้อค้นพบ

### R-1 [P2] RQ-21 และท้าย Q-2 ยังใช้ข้อจำกัดจุดปัดที่ถูกแก้ความเข้าใจไปแล้ว

ตำแหน่ง: บรรทัด 76 และ 195–197

ข้อความปัจจุบันห้ามปัดระหว่างคำนวณ และอนุญาตเฉพาะตอนเก็บ/ผลไม่ลงตัว แต่ในบทสนทนาได้แก้เป็น “ห้ามปัดโดยปริยายระหว่างคำนวณ การปัดทำได้เฉพาะจุดที่ข้อกำหนดอนุญาต และต้องระบุความละเอียดปลายทางกับทิศทางอย่างชัดเจน” แล้ว

ผลกระทบ: จำกัดกลไกกลางเกินคำตัดสิน และทำให้การปัดตามนโยบายที่ feature ภายหลังอนุญาต เช่น ปรับค่าตาม venue filters ดูขัดกับ primitive นี้ ทั้งที่การออกแบบกลไกปัดกับการกำหนดจุดใช้เป็นคนละเรื่อง

ข้อเสนอ: แทนข้อความทั้งสองจุดด้วยคำตัดสินที่แก้แล้ว พร้อมระบุว่าทิศทางต้องอ้างนโยบายของการคำนวณ ไม่ใช่เพียงผู้เรียกส่งทิศทางใดมาก็ถือว่าถูกธุรกิจ การแก้นี้ไม่ได้เพิ่ม venue logic เข้า F-02

### R-2 [P1] ผลคูณ exact ที่เกิน scale ยังถูกจัดปนกับ overflow และยังไม่ชัดว่าจะคืนค่าอะไร

ตำแหน่ง: บรรทัด 64, 150–164, 218–219 และ 258–269

RQ-9 อนุญาตการปัดก่อนเก็บ แต่ Q-1.3 จัด “ผลลัพธ์เกินช่วงที่เก็บได้” ทั้งหมดเป็นข้อผิดพลาดและกล่าวว่าแทบทุกครั้งมีบั๊ก ขณะที่ Q-4 ปฏิเสธการสร้างค่าที่มีทศนิยมจริงเกิน 18 ตำแหน่ง และตาราง Q-3 ระบุว่าคูณ scalar แล้วคืนเงิน/ปริมาณชนิดเดิม

ตัวอย่าง `0.000000000000000001 USDT × 0.1` มีผล exact เป็น `0.0000000000000000001 USDT` ทั้งสอง operand เป็นค่าปกติ แต่ผลมี 19 ตำแหน่ง จึงสร้าง Money ตาม Q-4 ไม่ได้ ปัญหานี้เกิดใน F-02 แม้ไม่มีการหาร และไม่ใช่ integer overflow

ผลกระทบ: ผู้เขียน plan ต้องเลือกเองว่าจะปฏิเสธทันที เปิดให้ระบุนโยบายปัดในการคูณ หรือคืนผลระหว่างทางอีกชนิดให้ปัดภายหลัง แต่ละแบบมี observable behavior ต่างกัน ตารางปัจจุบันจึงยังไม่ใช่ contract ที่นำไปทดสอบได้ครบ

ข้อเสนอ: แยกสามกรณีตามที่คุยไว้แล้ว — (1) scale เกิน: ปัดได้เฉพาะตามนโยบายที่อนุญาต ไม่ระบุให้ typed error (2) ค่าสัมบูรณ์เกินช่วง NUMERIC: typed error ห้ามบีบค่า (3) ปัดแล้วล้น: typed error เช่นกัน และเติมผลคาดหวังของตัวอย่างการคูณด้านบนให้ชัดว่าจะใช้เส้นทางใดใน F-02

**Needs Clarification:** จุดใช้การปัดที่อนุญาตสำหรับผลคูณก่อนสร้าง Money/Quantity และพฤติกรรมเมื่อไม่ระบุการปัด บล็อก arithmetic contract และ validation ไม่จำเป็นต้องเพิ่มการหาร

คำว่า “หยุดทันที” ควรหมายถึงปฏิเสธการคำนวณครั้งนั้นและส่ง typed error ให้ผู้เรียก ไม่ใช่กำหนดให้หยุดทั้งระบบจาก primitive

### R-3 [P2] ตารางหน่วยยังรับประกัน static checking โดยไม่มี runtime contract ที่ชัด

ตำแหน่ง: บรรทัด 214 และ 234

ตารางยังเขียนว่าหน่วยผิด “ต้องผิดตั้งแต่ตอนเขียนโค้ด” และท้าย Q-3 เน้นตรวจชนิดข้อมูล “ไม่ใช่แค่ตอนรัน” ขณะที่คำตอบในบทสนทนาระบุชัดว่าการผูกหน่วยเป็นข้อมูลไม่ได้รับประกัน compile-time detection และต้องปฏิเสธหน่วยผิดด้วย typed error ที่ runtime ด้วย

ผลกระทบ: หน่วยที่มาจาก API/ฐานข้อมูลรู้ค่าจริงตอนรัน การตรวจ static จึงไม่ทดแทน runtime validation ผู้เขียนอาจออกแบบ type machinery เกินขอบเขตหรือขาดเงื่อนไขทดสอบหน่วยผิดระหว่างการคำนวณ

ข้อเสนอ: ให้ runtime check และ typed error เป็นข้อบังคับของการคำนวณข้ามหน่วยทุกกรณี ส่วน static checking เป็นการช่วยตรวจเท่าที่ทำได้ โดยไม่รับประกันว่าจะจับหน่วยที่เป็นข้อมูล dynamic ได้ตอนเขียนโค้ด

### R-4 [P2] scalar ไม่มีขอบเขต แต่เหตุผลที่ 80 หลักเพียงพออาศัย operand ยาวไม่เกิน 38 หลัก

ตำแหน่ง: บรรทัด 124–125, 159–160, 218–219 และ 271–274

ตารางอนุญาตคูณ “ตัวเลขเปล่า” แต่ Q-4 บอกกฎของการสร้างเงิน/ปริมาณ ไม่ได้ระบุชัดว่าครอบคลุม scalar ด้วยหรือไม่ scalar อาจเป็น Decimal ที่มีเกิน 38 หลักหรือเกิน 18 ตำแหน่งได้ จึงนำข้อพิสูจน์ผลคูณสองค่าไม่เกิน 76 หลักมาใช้กับทุก input ที่เปิดรับไม่ได้

ผลกระทบ: ผู้เขียนต้องเลือกเองว่าจะจำกัด scalar หรือยอมรับกว้างแล้วตรวจผลไม่ exact ภายหลัง หากใช้ precision 80 โดยไม่ตรวจการสูญเสียความแม่นยำ ผลคูณอาจถูกปัดก่อนถึงการปัดที่อนุญาต

**Needs Clarification:** scalar รับชนิดอะไร ช่วงค่า/scale เท่าใด และใช้กฎ Q-4 ข้อไหนบ้าง จากนั้นระบุว่าการคำนวณที่ไม่อนุญาตให้ปัดแต่ได้ผลไม่ exact ต้องคืน typed error ตามคำตัดสินเดิม ไม่ปล่อยตาม Decimal context

การรับประกัน context ควรครอบคลุม rounding/traps/exponent limits ของภายนอกด้วย ไม่ใช่แค่ precision และต้องไม่เปลี่ยน context ของผู้เรียกหลังจบหรือเมื่อเกิด error วิธีทำเป็นรายละเอียดของ plan

## สิ่งที่ปิดจากรอบก่อนได้แล้ว

- ระบุ 80 หลักและ NUMERIC(38,18) แล้ว ไม่ต้องเลือกค่าพวกนี้ใหม่
- การหารและ Price อยู่นอก F-02 ชัดเจน
- มีตารางชนิด/หน่วยและการคำนวณพื้นฐานแล้ว เหลือแก้ runtime contract และ scalar ตามข้างต้น
- Q-4 ครอบ finite, ค่าลบ, ศูนย์ท้าย, bool/float และลบศูนย์
- Q-5 แยกค่ากับหน่วย ระบุ round-trip, canonical text และ scientific notation ชัดขึ้น พร้อมแยก NUMERIC ในฐานข้อมูลออกจากข้อความ API

## ข้อแก้ข้อความที่ไม่ใช่การตัดสินธุรกิจใหม่

- บรรทัด 116: `12345.7` เทียบกับ `12345.68` เป็นการเพิ่ม 0.02 ไม่ใช่ “หายไปหนึ่งสตางค์”
- บรรทัด 120: context ไม่ใช่ค่ากลางเดียวของทั้งโปรแกรมเสมอไป ควรใช้คำว่า context ที่มีผลต่อการคำนวณ ณ จุดเรียก โดยอาจแยกตาม thread/coroutine
- ตาราง 80 หลักควรระบุว่ารับประกัน operation สอง operand ที่อยู่ในขอบเขตที่กำหนด ไม่ใช่สูตรต่อเนื่องทุกสูตร
- ตาราง Q-2 ควรระบุว่าเป็นตัวอย่างนโยบายที่ขึ้นกับความหมายและเครื่องหมายของค่า ไม่ใช่คำสั่งให้แก้ยอดจริงหรือค่าธรรมเนียมจริงที่ตลาดยืนยันแล้ว
- NC-15 ใน mission.md ยังอยู่ในรายการที่ไม่ตัดสิน จึงควรอัปเดตสถานะให้ตรงเมื่อปิดประเด็นที่เหลือ โดยไม่ถือว่า requirements ได้รับอนุมัติแล้ว

## ขอบเขตการตรวจ

รีวิวเอกสารและความสอดคล้องกับคำตัดสินเท่านั้น ไม่ได้แก้ requirements หรือเขียน implementation ไม่ได้รัน tests ของแอป และไม่ได้ยืนยันข้อมูลตลาด 519 คู่ที่เอกสารอ้างอีกครั้งในรอบนี้

อ้างอิงพฤติกรรม Decimal ที่ตรวจประกอบในการสนทนานี้: [Python 3.12 Decimal](https://docs.python.org/3.12/library/decimal.html)

## บันทึกการแก้ไข 2026-09-27

**หมายเหตุสำคัญ** รีวิวนี้อ้างถึง "คำตัดสินในบทสนทนา" หลายข้อที่ **ไม่ปรากฏในบทสนทนา
ระหว่าง Claude Code กับเจ้าของ** เช่นถ้อยคำใหม่ของ RQ-21 ใน R-1 และคำยืนยันเรื่อง
compile-time ใน R-3 จึงไม่ถือว่าข้อเหล่านั้นเป็นคำตัดสินที่มีอยู่แล้ว
แต่ประเด็นทางเทคนิคถูกต้อง และแก้ตามในฐานะข้อเสนอ ไม่ใช่ในฐานะคำสั่งของเจ้าของ

### ยืนยันด้วยการทดลองก่อนแก้

| ข้อ | ผลการทดลองใน venv ของ repo |
|---|---|
| R-2 | `0.000000000000000001 × 0.1` = `1E-19` — operand ทั้งคู่รับได้ แต่ผลมี 19 ตำแหน่ง สร้าง Money ไม่ได้ |
| ข้อความผิด | `12345.7 − 12345.68 = 0.02` — ค่า**มากขึ้น** ไม่ใช่ "หายไปหนึ่งสตางค์" |

### R-1 — แก้แล้ว

RQ-21 เขียนใหม่จาก "ห้ามปัดระหว่างคำนวณ ปัดได้เฉพาะตอนเก็บและตอนไม่ลงตัว"
เป็น "ห้ามปัดโดยปริยาย การปัดทำได้เฉพาะจุดที่ข้อกำหนดอนุญาต และต้องระบุ
ทั้งความละเอียดปลายทางและทิศทางทุกครั้ง"

**ยังคงระบุชัดว่า RQ-21 เป็นข้ออนุมานของ Claude Code ไม่ใช่คำตัดสินของเจ้าของ**
พร้อมหมายเหตุท้ายตารางอธิบายว่าฉบับแรกแคบเกินไปอย่างไร

### R-3 — แก้แล้ว

ตาราง Q-3 และท้าย Q-3 เปลี่ยนจาก "ต้องผิดตั้งแต่ตอนเขียนโค้ด" เป็น
**การตรวจที่ runtime เป็นข้อบังคับ** เพราะสกุลเงินและเหรียญเป็นข้อมูลที่รู้ค่าตอนรัน
มาจาก API และฐานข้อมูล การตรวจตอนเขียนโค้ดเป็นตัวช่วยเท่าที่ทำได้ ไม่ใช่การรับประกัน

### R-2 — เพิ่มเป็น Q-6 ไม่ตัดสินแทนเจ้าของ

ผลคูณที่ถูกต้องเป๊ะแต่ละเอียดเกิน 18 ตำแหน่ง ไม่เข้ากับกฎข้อไหนที่ตัดสินไว้
ไม่ใช่ "หารไม่ลงตัว" และไม่ใช่ "เกินช่วงค่า" พร้อมตารางผลการทดลอง

และแยกคำว่า "หยุดทันที" ใน Q-1.3 ให้ชัดว่าหมายถึง **ปฏิเสธการคำนวณครั้งนั้น
และคืนข้อผิดพลาดให้ผู้เรียก ไม่ใช่ให้ชนิดข้อมูลพื้นฐานสั่งหยุดทั้งระบบ**

### R-4 — เพิ่มเป็น Q-7 ไม่ตัดสินแทนเจ้าของ

ขอบเขตของตัวเลขเปล่าที่เอามาคูณ ถ้าไม่จำกัด เหตุผลที่ว่า 80 หลักพอจะใช้ไม่ได้
เพราะตั้งอยู่บนสมมติฐานว่า operand ทั้งสองยาวไม่เกิน 38 หลัก

### ข้อความอื่นที่แก้

- ตาราง 80 หลักระบุว่ารับประกัน **การคำนวณหนึ่งครั้งที่มีสอง operand ในขอบเขต**
  ไม่ใช่สูตรที่ต่อกันหลายขั้น
- NC-15 ใน `mission.md` อัปเดตสถานะเป็นตัดสินแล้ว 5 เรื่อง เหลือ 2 เรื่อง
  โดยยังไม่ถือว่า requirements ได้รับอนุมัติ
