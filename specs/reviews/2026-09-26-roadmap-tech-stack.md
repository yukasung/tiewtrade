## 1. Roadmap ยังไม่มีงานรองรับ Binance TH ตามขอบเขตใหม่ — ✅ แก้แล้ว 2026-09-26

ที่มา: `specs/roadmap.md` บรรทัด 80 และ `specs/mission.md` หัวข้อ 6

Roadmap ระบุเพียงส่งออเดอร์ไป “Binance” ขณะที่ Mission เปลี่ยนให้ Binance.com ใช้ทดสอบ และ Binance TH เป็นตลาดผู้ใช้จริง โดยต้อง implement ทั้งสองตลาด ยังไม่มีงานหรือเกณฑ์สำเร็จที่แสดงว่าการรองรับ Binance TH จะเสร็จเมื่อใด

**ผลกระทบ:** ทำครบ Roadmap แล้วอาจยังเปิดตลาดสำหรับผู้ใช้จริงไม่ได้ และอาจผูกโครงสร้างกับ Binance.com ซึ่ง Mission กำหนดให้ถอดออกได้ในอนาคต

**ข้อเสนอ:** แยกขอบเขตงานเชื่อมต่อและทดสอบแต่ละตลาด รวมเงื่อนไขเปิดให้ผู้ใช้จริง ส่วน Tech Stack ต้องระบุขอบเขตโมดูลที่รองรับการถอด Binance.com ออก ประเด็นกำหนดเปิด Live และการรอ Futures บน Binance TH ต้องอ้างคำตัดสินเจ้าของ ไม่เลือกแทน

F-13 ถึง F-17 เป็นจุดปล่อยให้คนลองใช้ ก่อนทำ F-18 และ F-19 แต่ Trading Safety กำหนดให้ Paper ใช้กฎเพดานขาดทุนเหมือน Live ทุกข้อ อีกทั้ง Mission ระบุ NC-11 ว่าบล็อกการเปิดให้คนนอกใช้ ขณะที่ F-32 อยู่ช่วงท้าย

**ผลกระทบ:** จุดปล่อยทดลองยังไม่ผ่านข้อกำหนดที่มีอยู่ และคำว่า “ให้คนลองใช้” ไม่ชัดว่าหมายถึงภายในทีมหรือคนนอก

**ข้อเสนอ:** กำหนดให้ความสามารถด้านความเสี่ยงและการหยุดที่ Paper ต้องใช้เสร็จก่อนปล่อยทดลอง แยก milestone ทดสอบภายในกับเปิดให้คนนอก และผูก NC-11 กับจุดเปิดให้คนนอกตาม Mission การเลือกปล่อย Paper ก่อน Live ยังต้องได้คำตัดสินเจ้าของตามข้อสังเกตท้าย Roadmap

## 5. ทางรับ API secret ยังไม่มีแบบที่สอดคล้องกับขอบเขต process — ✅ แก้แล้ว 2026-09-26

ที่มา: `specs/tech-stack.md` บรรทัด 100–106, 132–140 และ `specs/standards/architecture.md` หัวข้อ 3

สเปกห้าม `api` ถือ secret และห้าม `engine` รับคำขอจากอินเทอร์เน็ตโดยตรง แต่ผู้ใช้ต้องกรอก secret ผ่านเว็บ ยังไม่ระบุว่าใครรับและเข้ารหัสข้อมูลครั้งแรก หากส่ง secret แบบปกติผ่าน `api` ก็ขัดกับถ้อยคำ “ห้ามถือ” แม้ภายหลังจะห้ามอ่านจากฐานข้อมูลแล้วก็ตาม

**ผลกระทบ:** F-07 ต้องตัดสินใจเรื่องขอบเขตความปลอดภัยที่สเปกยังไม่ชัดก่อน implement

**Needs Clarification:** อนุญาตให้ `api` รับ secret ชั่วคราวเพื่อเข้ารหัสหรือไม่ หรือจะใช้เส้นทางรับ credential แบบอื่น ต้องให้เจ้าของตัดสินใจและบันทึกขอบเขตในสถาปัตยกรรมก่อนลงมือ ห้ามตีความข้อยกเว้นขึ้นเอง

## 7. คำอธิบาย TanStack Query เกินสิ่งที่ได้อัตโนมัติ — ✅ แก้แล้ว 2026-09-26

ที่มา: `specs/tech-stack.md` บรรทัด 57

เอกสารระบุว่า TanStack Query จัดการ “การรวมข้อมูล snapshot กับ stream ให้” แต่เครื่องมืออัปเดต cache เช่น `setQueryData` ยังต้องมีโค้ดของระบบกำหนดวิธีอัปเดตเอง การมี cache ไม่ได้กำหนดกติกาการเรียงเหตุการณ์หรือแก้ข้อมูลเก่าทับข้อมูลใหม่ให้กับโดเมนการเทรด

**ผลกระทบ:** หน้าจออาจถูก snapshot เก่าเขียนทับข้อมูลออเดอร์ที่ใหม่กว่าจาก stream หากไม่มีข้อกำหนดเรื่องการรวมข้อมูล

**ข้อเสนอ:** แก้คำอธิบายให้ชัดว่าใช้ TanStack Query จัดการ cache และสถานะการดึงข้อมูล ส่วนระบบต้องรับผิดชอบการเรียงเหตุการณ์ กันข้อมูลซ้ำ และดึงข้อมูลใหม่หลังเชื่อมต่อกลับ

แหล่งอ้างอิง: [เอกสาร QueryClient ของ TanStack — setQueryData](https://github.com/TanStack/query/blob/main/docs/reference/QueryClient.md)
