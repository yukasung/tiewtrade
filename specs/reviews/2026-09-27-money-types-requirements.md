## ข้อค้นพบ

### R-1 [P1] Q-1 ถามเฉพาะจำนวนทศนิยม แต่ยังไม่กำหนดสัญญาความแม่นยำระหว่างคำนวณ — ✅ ขยายแล้ว 2026-09-27

ตำแหน่ง: requirements บรรทัด 54–59, 61 และ 88–95

RQ-2/RQ-3/RQ-7 ต้องการความละเอียดกลาง การปัดอย่างตั้งใจ และผลที่เหมือนเดิม แต่ Q-1 ถามเพียงว่าเก็บกี่ตำแหน่งทศนิยม แม้เจ้าของตอบ Q-1 ก็ยังไม่ทราบจำนวนหลักรวมที่รองรับ ความละเอียดผลคูณ/ผลรวมระหว่างทาง และพฤติกรรมเมื่อผลลัพธ์เกินขอบเขต

ความละเอียดการคำนวณของ Decimal กับ scale ที่เก็บเป็นคนละเรื่อง ทดลองใน Python ของ repo: `12345.67 + 0.01` ได้ `12345.7` ที่ precision 6 แต่ได้ `12345.68` ที่ precision 12 โดยไม่ได้สั่ง quantize เลย นี่เป็นหลักฐานพฤติกรรมของ Decimal ไม่ใช่ข้อผิดพลาดของ implementation F-02 ซึ่งยังไม่มี

ผลกระทบ: ผู้เขียนแผนอาจเลือก precision เองหรือพึ่ง context ของผู้เรียก ทำให้ตัวเลขถูกปัดก่อนถึงขั้นปัดที่ระบุ หรือผลต่างกันตามสภาพแวดล้อม ขัดกับเป้าหมายผลรวมรายการที่ไม่เพี้ยน

**Needs Clarification:** แยกนโยบาย computation precision, storage precision/scale, ขอบเขตค่าที่รองรับ และกรณีผลไม่ exact/เกินขอบเขต ระบุว่าการเปลี่ยน Decimal context ภายนอกต้องไม่เปลี่ยนผลหรือข้อผิดพลาดของการเรียกเดียวกัน ส่วนวิธีจัดการ context ค่อยเลือกใน plan

**บล็อก:** arithmetic contract, การจัดประเภท error และสัญญาที่ส่งต่อให้ F-03

### R-2 [P1] “ตรวจความถูกต้องตั้งแต่ตอนสร้าง” ยังไม่มีนิยามค่าที่ถูกต้อง — ✅ เพิ่มเป็น Q-4 แล้ว 2026-09-27

ตำแหน่ง: requirements บรรทัด 31, 53, 60 และ 66

RQ-8 ไม่ระบุค่าที่รับหรือปฏิเสธ ขณะที่ Decimal สร้าง `NaN` และ `Infinity` ได้ตามปกติ การใช้ Decimal จึงยังไม่เท่ากับการได้จำนวนเงินที่ใช้คำนวณและเปรียบเทียบได้อย่างปลอดภัย

ยังขาดเงื่อนไขของศูนย์ ค่าลบ ค่าลบศูนย์ ค่าที่ทศนิยมเกินกำหนด และชนิด input ที่ยอมรับ โดยเฉพาะเส้นทางรับ float ต้องมีผลปฏิเสธที่ทดสอบได้ ไม่ใช่อาศัยเพียง type hint

ผลกระทบ: implementation หลายแบบที่รับค่าคนละชุดยังอ้างว่าทำตาม RQ-8 ได้ อีกทั้งการห้ามค่าลบทั้งหมดโดยเดาเองอาจทำให้ผลลบหรือรายการบัญชีใช้ชนิดนี้ไม่ได้

**Needs Clarification:** กำหนด invariants แยกตามชนิดข้อมูลและผลลัพธ์การคำนวณ พร้อมรายการกรณีผิดและประเภท error ที่คาดหมาย เสนอให้ปฏิเสธค่าที่ไม่ finite แต่ต้องบันทึกเป็นข้อกำหนดก่อนนำไปใช้

**บล็อก:** constructor/parser, subtraction และ validation ของค่าเงิน

### R-3 [P2] Q-3 ครอบคลุมสกุลเงิน แต่ยังไม่ครอบคลุมหน่วยของปริมาณและคู่ operand — ✅ ขยายแล้ว 2026-09-27

ตำแหน่ง: requirements บรรทัด 31–33 และ 104–108

ขอบเขตสัญญาว่ามีทั้งจำนวนเงินและปริมาณ แต่ Q-3 ถามเพียงการบวก USDT กับ THB ยังไม่ตอบว่า quantity ผูกกับ asset หรือไม่ เช่น BTC กับ ETH และคำว่า “คูณด้วยจำนวน” หมายถึง scalar ไม่มีหน่วย หรือปริมาณสินทรัพย์

ผลกระทบ: แม้ตอบ Q-3 แล้ว ผู้เขียนแผนยังต้องคิดกฎเองว่าอะไรบวก ลบ เทียบ หรือคูณกันได้ รวมถึงผลลัพธ์เป็นชนิดใด อาจเกิดการคำนวณข้ามหน่วยโดยตัวเลขถูกแต่ความหมายผิด

**Needs Clarification:** ระบุชนิดที่จะส่งมอบจริงใน F-02 และตาราง operand/result สำหรับการคำนวณที่อยู่ในขอบเขต รวมพฤติกรรมเมื่อหน่วยต่างกัน และให้ชัดว่ารับประกันที่ runtime หรือ static typing ไม่จำเป็นต้องเพิ่ม Price/Rate หรือการหารหากยังไม่ใช่ขอบเขตที่เจ้าของต้องการ

**บล็อก:** นิยามชนิดข้อมูลและ public interface ของ arithmetic

### R-4 [P2] การแปลงเข้าออกข้อความยังไม่มีสัญญาว่ารักษาค่าและหน่วยอย่างไร — ✅ เพิ่มเป็น Q-5 แล้ว 2026-09-27

ตำแหน่ง: requirements บรรทัด 34, 44, 57 และ 61

ระบุเพียงว่าเป็นข้อความ แต่ยังไม่กำหนดรูปแบบที่รับ/ส่งและพฤติกรรมเมื่อข้อความมีความละเอียดเกินที่จัดเก็บ เช่น `1e-8`, `1.2300` และค่าที่ต้องปัดก่อนเก็บ หากเลือกผูกหน่วยตาม Q-3 ก็ต้องบอกด้วยว่าหน่วยถูกส่งแยกหรืออยู่ใน representation ใด

ผลกระทบ: parser และ formatter อาจตีความไม่ตรงกัน หรือค่าใน core ถูกเปลี่ยนตอนเก็บ PostgreSQL เพราะ NUMERIC(p,s) ปัดค่าที่มี scale เกินเองได้ แม้ฝั่ง API จะไม่ใช้ float ก็ตาม

**Needs Clarification:** ระบุ input/output contract, การรักษาค่าและหน่วยเมื่อ serialize แล้ว parse กลับ, จุดที่อนุญาตให้ปัด และข้อผิดพลาดเมื่อเก็บค่าไม่ได้ โดยคง database adapter และ migration ไว้ใน F-03 ตามขอบเขตเดิม

**บล็อก:** serialization contract และการส่งต่อสัญญาค่าเงินให้ API/ฐานข้อมูล

## สิ่งที่เอกสารทำถูกแล้ว

- แยก primitive arithmetic ออกจาก PnL, position, matching และ venue filters
- อ้างมาตรฐานเดิมและไม่กำหนดจำนวนทศนิยมหรือ rounding policy เอง
- ระบุ Q-1–Q-3 และห้ามเริ่ม plan ก่อนตอบชัดเจน
- กำหนด immutability, deterministic behavior, typed errors และการทดสอบสองชนิด

Q-2 เป็นช่องว่างที่เอกสารยอมรับอยู่แล้ว ไม่ได้นับซ้ำเป็นข้อค้นพบใหม่ เมื่อปิดคำถามควรมีตัวอย่างค่าบวกและค่าลบเพื่อให้คำว่า “ปัดขึ้น/ลง” มีความหมายแน่นอน รวมทั้งแยกทิศทางการปัดออกจากจังหวะที่อนุญาตให้ปัด

## ข้อเสนอสำหรับรอบถัดไป

ขยาย Q-1 และ Q-3 ให้ครอบคลุมประเด็นข้างต้น เพิ่มคำถามเรื่อง valid values และ serialization แล้วนำคำตอบที่เจ้าของตัดสินมาเขียนเป็น RQ ที่ตรวจสอบผลได้ ไม่ต้องออกแบบคลาสหรือรายละเอียด implementation ใน requirements

เมื่อยืนยันรายการ Needs Clarification ให้เชื่อมกับรายการกลางใน mission.md หัวข้อ 9 ตาม AGENTS.md รายงานนี้บันทึกข้อค้นพบไว้ก่อน โดยไม่ได้แก้ requirements หรือเลือกนโยบายการเงินแทนเจ้าของ

## หลักฐานและข้อจำกัด

- อ่าน requirements เทียบ backend, database, architecture, testing, trading-safety, mission, roadmap และ template feature specs
- ทดลอง Decimal ใน backend venv เพื่อยืนยันผลของ context และการสร้างค่าที่ไม่ finite เท่านั้น ไม่ได้รันชุด tests ของแอป เพราะงานนี้เป็นการรีวิว requirements
- ไม่ได้ตรวจความละเอียดรายคู่ของ Binance TH และไม่ได้เสนอจำนวน precision/scale จากการคาดเดา
- ไม่มีการแก้ source, requirements หรือสถานะอนุมัติ

เอกสารทางการที่ตรวจประกอบ:

- [Python 3.12 Decimal](https://docs.python.org/3.12/library/decimal.html): context มีผลต่อ arithmetic; รองรับ special values และการส่งสัญญาณเมื่อผลไม่ exact
- [PostgreSQL 16 Numeric Types](https://www.postgresql.org/docs/16/datatype-numeric.html): precision/scale และการปัดเมื่อเก็บค่าใน NUMERIC ที่กำหนด scale
