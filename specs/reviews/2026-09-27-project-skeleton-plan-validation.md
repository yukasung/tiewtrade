## 1. กรณีทดสอบด่านตรวจยังไม่ครบตาม requirements — ✅ แก้แล้ว 2026-09-27

ที่มา: `plan.md` บรรทัด 96–102; `requirements.md` หัวข้อขอบเขตและ RQ-12; `validation.md` ตารางเทสต์ด่านตรวจ

แผนมีกรณีสำหรับ import-linter, ความบริสุทธิ์ของ `core` และ mypy แต่ไม่มีกรณีพิสูจน์ว่าด่าน lint และ format จับความผิดได้ ทั้งที่ requirements กำหนดอย่างน้อยหนึ่งกรณีต่อด่าน

ยังไม่มีกรณีพิสูจน์กฎห้าม `strategies`, `venues`, `infra` พึ่งกันเอง และการห้ามอ่านไฟล์หรือใช้เครือข่ายผ่าน standard library

**ผลกระทบ:** บางด่านหรือบางกฎอาจตั้งค่าผิดโดยที่กรณีตัวอย่างทั้งหมดในแผนยังผ่าน ทำให้หลักฐานไม่ครอบคลุมสิ่งที่ requirements ต้องการ

**ข้อเสนอ:** เพิ่มตารางจับคู่กฎกับกรณีทดสอบให้ครบ แล้วสะท้อนใน validation ด้วย แยกการทดสอบขอบเขต import ออกจากการทดสอบพฤติกรรมที่ห้ามใน `core`

## 2. การคาดหวังเพียงผลแดงอาจผ่านเพราะเครื่องมือรันผิด — ✅ แก้แล้ว 2026-09-27

ที่มา: `plan.md` บรรทัด 93–104 และ `validation.md` หัวข้อเทสต์ที่ต้องมี

แผนให้รันเครื่องมือกับกรณีละเมิดและคาดหวังผลแดง แต่ไม่ได้กำหนดว่าต้องแดงด้วยเหตุใด หาก config ผิด หา package ไม่เจอ หรือเครื่องมือเริ่มทำงานไม่ได้ ก็อาจถูกนับว่าจับความผิดสำเร็จ

**ผลกระทบ:** เทสต์ของด่านอาจเขียวทั้งที่เครื่องมือไม่ได้ตรวจพบการละเมิดกฎที่ตั้งใจทดสอบ

**ข้อเสนอ:** ตรวจว่าข้อผิดพลาดตรงกับกฎที่ตั้งใจทดสอบ และมีกรณีถูกต้องที่ต้องผ่านภายใต้ config เดียวกัน เพื่อแยกการตรวจจับความผิดออกจากความล้มเหลวในการรันเครื่องมือ

## 3. V-14 ไม่มีทางผ่านตามถ้อยคำปัจจุบัน — ✅ แก้แล้ว 2026-09-27

ที่มา: `validation.md` บรรทัด 27 (V-14); `mission.md` มี URL ของ Binance ในเอกสารอ้างอิงอยู่แล้ว

V-14 กำหนดว่า “ค้นทั้ง repo ต้องไม่มี URL หรือไลบรารีของ Binance” แต่ Mission มี URL ของ Binance อยู่แล้ว การพบ URL ในสเปกไม่ได้แปลว่าระบบเชื่อมต่อ Binance

**ผลกระทบ:** งานที่ไม่ต่อ Binance ตามขอบเขตก็ยังไม่ผ่าน validation หากทำตามถ้อยคำนี้

**ข้อเสนอ:** จำกัดการตรวจไว้ที่โค้ดและ dependency ของงานนี้ พร้อมตรวจว่าการรันตัวอย่างและเทสต์ไม่เรียก Binance โดยไม่กำหนดให้ลบข้อมูลอ้างอิงจากเอกสาร

## 4. การตรวจชนิดข้อมูลยังไม่พิสูจน์ว่าหน้าบ้านใช้ชนิดที่สร้างจริง — ✅ แก้แล้ว 2026-09-27

ที่มา: `validation.md` บรรทัด 21–22 (V-8, V-9); `requirements.md` RQ-13, RQ-16, RQ-17

V-9 ตรวจเพียงสร้างไฟล์ชนิดข้อมูลใหม่แล้วเทียบ ส่วน V-8 ตรวจว่าหน้าเว็บแสดงข้อมูลจาก API ได้ ทั้งสองข้อผ่านได้แม้ `App.tsx` ใช้ชนิดที่เขียนเองหรือ `any` และไม่ได้ใช้ไฟล์ที่สร้างเลย

**ผลกระทบ:** ไฟล์ชนิดข้อมูลตรงกับหลังบ้าน แต่โค้ดหน้าบ้านที่ใช้งานจริงอาจไม่ถูกตรวจตามสัญญา API จึงยังไม่พิสูจน์ทางเดินครบวงตาม requirements

**ข้อเสนอ:** ระบุให้โค้ดรับและแสดงผล `/health` ใช้ชนิดจากไฟล์ที่สร้าง พร้อมกรณีทดสอบว่าเมื่อเปลี่ยนสัญญา API จนไม่เข้ากับโค้ดหน้าบ้าน ด่านตรวจต้องจับได้

## ข้อความค้างระดับเล็กน้อย — ✅ แก้แล้ว 2026-09-27

`requirements.md` บรรทัด 106 ยังระบุว่า “เหลือแค่เจ้าของอนุมัติ requirements” ทั้งที่หัวไฟล์เป็น Approved แล้ว ควรปรับข้อความให้ตรงกับสถานะ โดยคงการรออนุมัติ `plan.md` และ `validation.md` ตามขั้นตอนของ repo

## แนวทางส่งต่อให้ Claude Code

ตรวจเอกสารล่าสุดก่อนแก้ เพิ่มรายละเอียดใน `plan.md` และ `validation.md` เพื่อให้ครอบคลุมข้อกำหนดที่อนุมัติแล้ว หากต้องเปลี่ยนข้อกำหนดที่อนุมัติ ให้แก้ requirements และขออนุมัติใหม่ตาม AGENTS.md ก่อนลงมือเขียนโค้ด

เมื่อแก้แต่ละข้อแล้ว ให้บันทึกสถานะพร้อมอ้างอิงส่วนที่แก้เพื่อให้ตรวจซ้ำได้ การปิดประเด็นรีวิวไม่ถือเป็นการอนุมัติแผนโดยเจ้าของ

## บันทึกการแก้ไข 2026-09-27

**ข้อ 1** — เพิ่ม **ตารางจับคู่ กฎ ↔ กรณีทดสอบ** ใน `plan.md` ครอบ 12 กฎ ใน 4 ด่าน
เพิ่มกรณีที่ขาดไป: ruff check, ruff format, กฎห้าม `strategies`/`venues`/`infra` พึ่งกันเอง,
กฎห้ามชั้นเหล่านั้นพึ่ง service, `core` อ่านไฟล์, `core` ต่อเครือข่าย
และระบุไว้ทั้งใน plan และ validation ว่า **การอ่านไฟล์กับการต่อเครือข่ายต้องทดสอบแยก
จากกฎ import** เพราะอยู่ใน standard library จึงผ่าน import-linter ได้

**ข้อ 2** — เปลี่ยนเกณฑ์ผ่านของเทสต์ด่านจาก "คาดหวังผลแดง" เป็นต้องครบสามข้อ:
แดงเพราะกฎที่ตั้งใจทดสอบจริง, มีกรณีที่ถูกต้องคู่กันซึ่งต้องผ่านภายใต้ config เดียวกัน,
และรันด้วยชุดตั้งค่าเดียวกับด่านจริง — บันทึกเหตุผลไว้ว่าเทสต์ที่คาดหวังแค่
"ไม่สำเร็จ" จะขึ้นเขียวตอนเครื่องมือพัง ซึ่งเป็นกรณีที่ต้องดังที่สุดแต่กลับเงียบที่สุด

**ข้อ 3** — V-14 จำกัดการตรวจไว้ที่ `backend/` และ `frontend/` เท่านั้น
ไม่ตรวจ `specs/` และเพิ่มเกณฑ์ว่าเทสต์ทั้งหมดต้องรันได้โดยไม่ต่อออกเน็ต

**ข้อ 4** — เพิ่ม **P-9** (โค้ดหน้าบ้านต้องใช้ชนิดจากไฟล์ที่สร้าง ห้ามเขียนเอง ห้าม `any`)
และ **P-10** (ต้องมีกรณีพิสูจน์ว่าเปลี่ยนสัญญา API แล้วด่านหน้าบ้านแดง)
