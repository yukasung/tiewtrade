## ข้อค้นพบที่ยังค้าง

### R-1 [P2] แผนย้ายรายละเอียดที่ขาดไปเป็นรายการ TODO แทนที่จะกำหนดให้ตรวจได้ — ✅ แก้แล้ว 2026-09-27

ตำแหน่ง: [plan.md](../features/2026-09-27-money-types/plan.md) บรรทัด 51–64

หัวข้อ “สิ่งที่ต้องกำหนดให้ชัดก่อนลงมือ” ระบุสี่เรื่องที่ยังไม่มีคำตอบ: รายการทิศทางการปัด, representation/equality ของหน่วย, รายการ error และ public interface

การบันทึกว่าต้องทำช่วยป้องกันการลืม แต่ยังไม่ปิดช่องว่างที่รีวิวก่อนชี้ เช่น validation V-16 ยังตรวจว่า “ครบทุกทิศทาง” ไม่ได้ และ V-20 ยังไม่มีนิยามร่วมว่า input หน่วยใดผิด ขณะที่ V-15 กล่าวถึงการเรียกฟังก์ชันปัด แต่ยังไม่ชัดว่าผู้ใช้เรียกผ่าน public function หรือผ่าน multiply ที่อนุญาตให้ระบุ rounding

ผลกระทบ: แผนที่อนุมัติยังไม่ครอบคลุมสัญญาของโมดูล ผู้เขียนโค้ดกับผู้เขียน tests อาจเลือกพฤติกรรมคนละแบบแล้วต่างอ้างว่าตรงแผน จึงยังไม่ควรเรียกว่าแผนพร้อม implementation โดยไม่มีงานออกแบบค้าง

ข้อเสนอ: เติมตารางคำตอบทั้งสี่เรื่องใน plan พร้อมตัวอย่าง input/output/error แล้วเชื่อม V-9/V-12/V-15/V-16/V-20 กับ contract นั้น ไม่ต้องเขียน implementation ล่วงหน้า และไม่จำเป็นต้องถามนโยบายการเงินใหม่ถ้ายังอยู่ใน requirements เดิม หาก representation ของหน่วยนำไปสู่การจำกัดรายชื่อสินทรัพย์ที่ยอมรับ ให้แยกเป็น Needs Clarification ตามกฎ repo

## ผลตรวจข้อค้นพบหลักจากรอบก่อน

| ประเด็น | ผลตรวจซ้ำ |
|---|---|
| ตรวจ input หลัง normalize จนอาจรับค่าผิด | ปิดแล้ว P-5 กำหนดตรวจ coefficient/exponent แบบ exact และ V-5.1 มีคู่ input ยาวเกิน 80 หลัก |
| Property tests ไม่เผื่อ intermediate overflow | ปิดแล้ว มีเงื่อนไขผลระหว่างทางและแยก overflow property |
| Context tests เปลี่ยนแค่ precision | ปิดแล้ว V-1 เพิ่ม rounding/traps/exponent limits และ V-2 ตรวจ settings/flags; P-3.1/P-3.2 ระบุ isolation และการแปลง Decimal errors |
| ไม่ทดสอบการปัดแล้วล้นและบวก/ลบล้น | ปิดแล้ว V-13.1/V-13.2 มีตัวอย่างแยกเส้นทาง |

ข้อปรับปรุงอื่นที่ตรวจพบว่าทำแล้ว: วาง rounding ก่อน arithmetic, เพิ่ม limits.py เป็นแหล่งค่ากลาง, ระบุ scalar ไม่ใช่ public type ตัวที่สาม และแก้ V-23 ให้ตรวจพฤติกรรมแทนการห้ามคำ

## หมายเหตุเล็กน้อย ไม่ใช่ข้อบล็อกเพิ่ม

- plan บรรทัด 11 ยังเขียน “4 ชั้น” แต่ตารางมี 5 ขั้น ควรแก้เป็น 5
- หัวข้อ property tests ควรจำกัดข้อความ “operand ต้องชนิดและหน่วยตรงกัน / ผลระหว่างทางอยู่ในช่วง” ให้ใช้กับกฎบวก/ลบที่เกี่ยวข้อง ไม่ใช่ทุกกฎ เพราะ scalar multiplication และ property ที่ตั้งใจพิสูจน์ overflow ใช้เงื่อนไขต่างกัน
- V-2.1 ที่ให้บังคับ Decimal Overflow/Inexact ควรระบุในขั้นออกแบบ tests ว่าทดสอบ error translation ผ่านการจำลองข้อผิดพลาดภายใน หาก public inputs ที่ถูกต้องไม่สามารถทำให้เกิด signal นั้นได้ ห้ามลด precision/ขอบเขตที่อนุมัติเพียงเพื่อสร้าง test case

## ความสอดคล้องของเอกสาร

ไม่พบข้อขัดกันใหม่ใน requirements ที่อนุมัติ ช่วงค่า/scale, การปัดผลคูณ, runtime unit checking และ serialization ยังสอดคล้องกับ Q-1–Q-7; mission ระบุ NC-15 ปิดแล้ว ส่วน plan/validation ยังเป็น Proposed ถูกต้อง

รอบนี้ไม่ได้เปลี่ยนข้อกำหนด ไม่ได้เขียนโค้ด และไม่ได้รัน tests ของแอป ตรวจเอกสารเทียบหลักฐานที่ยืนยันในรอบก่อน การปิดประเด็นเดิมเป็นผลตรวจเนื้อหาแผน ไม่ใช่การรับรอง implementation หรืออนุมัติแทนเจ้าของ

## บันทึกการแก้ไข 2026-09-27

**R-1** — รีวิวชี้ถูกว่าฉบับก่อนเปลี่ยนช่องว่างให้กลายเป็นรายการสิ่งที่ต้องทำ
แทนที่จะตอบมัน ทั้งสี่เรื่องอยู่ในขอบเขต requirements ที่อนุมัติแล้ว
จึงเป็นการออกแบบทางเทคนิคที่ `plan.md` ต้องตอบเอง ไม่ใช่คำถามถึงเจ้าของ

แทนหัวข้อ "สิ่งที่ต้องกำหนดให้ชัดก่อนลงมือ" ด้วยหัวข้อ **"สัญญาของโมดูล"** ซึ่งตอบครบทั้งสี่เรื่อง

**ทิศทางการปัด 4 ทิศทาง** พร้อมตารางผลของ `2.5` และ `-2.5` ทุกทิศทาง
ไม่มีแบบ half-even หรือ half-up เพราะ RQ-4 ต้องการทิศทางที่ผู้เรียกเลือกตามความหมาย
ไม่ใช่กฎที่ตัดสินจากตัวเลขเอง

**หน่วย** เก็บเป็นข้อความสั้นปรับเป็นตัวพิมพ์ใหญ่ เทียบเท่ากันเมื่อตรงกันทุกตัวอักษร
ปฏิเสธข้อความว่าง มีช่องว่าง หรือมีอักขระอื่น **ไม่จำกัดรายชื่อเหรียญ**
เพราะการจำกัดรายชื่อเป็นงานของ F-37 ถ้าเอามาไว้ใน `core` จะกลายเป็นกฎธุรกิจ

**ชนิดข้อผิดพลาด 7 ชนิด** พร้อมระบุว่าแต่ละชนิดเกิดเมื่อไหร่และเกณฑ์ไหนตรวจ

**Public interface** พร้อมตารางตัวอย่างพฤติกรรม 7 บรรทัดที่ validation อ้างถึงได้
จุดสำคัญคือ **F-02 ไม่มีฟังก์ชันปัดสาธารณะแยก** การปัดเข้าถึงได้ผ่านการคูณเท่านั้น
เพราะยังไม่มีจุดอื่นที่ข้อกำหนดอนุญาตให้ปัด

เชื่อม V-15, V-16 และ V-20 เข้ากับสัญญานี้ ทำให้คำว่า "ครบทุกทิศทาง"
และ "หน่วยผิด" ตรวจได้จริง

### หมายเหตุเล็กน้อยที่แก้ตาม

- plan เขียนว่า "4 ชั้น" ทั้งที่ตารางมี 5 → แก้เป็น 5
- เงื่อนไขของ property tests จำกัดให้ใช้กับกฎที่บวกหรือลบหลายค่า
  ส่วนกฎที่คูณและกฎที่ตั้งใจพิสูจน์การล้นช่วงใช้เงื่อนไขของตัวเอง
- V-2.1 ระบุว่าถ้า input ที่ถูกต้องทำให้เกิดสัญญาณของ `Decimal` ไม่ได้
  ให้จำลองข้อผิดพลาดภายในแทน **ห้ามลด precision หรือขอบเขตที่อนุมัติแล้ว
  เพื่อสร้างกรณีทดสอบ**
