# Standard — Security

สถานะ: **Proposed**

รายละเอียดเรื่อง API credential อยู่ใน `trading-safety.md` หัวข้อ 2 ไม่เขียนซ้ำที่นี่

---

## 1. การยืนยันตัวตน

- session เก็บฝั่งเซิร์ฟเวอร์ใน PostgreSQL เพิกถอนได้ทันที
- cookie แบบ httpOnly + Secure + SameSite พร้อมโทเคนกัน CSRF
- รหัสผ่านแฮชด้วย argon2 **ห้ามเก็บรหัสผ่านในรูปที่อ่านได้**
- **นโยบายรหัสผ่าน** (เจ้าของตัดสิน 2026-10-02 พร้อม F-05 — อ้าง NIST SP 800-63B-4):
  - **ขั้นต่ำ 15 ตัวอักษรเมื่อรหัสผ่านเป็นปัจจัยเดียว** (มาตรฐานใช้คำว่า SHALL)
    ลดเป็น 8 ได้เฉพาะเมื่อมีปัจจัยที่สองบังคับแล้ว ซึ่งจะเกิดเมื่อ F-06 เสร็จ
  - **เพดาน 1,024 ตัวอักษร** — มีไว้กันการใช้ต้นทุนของ argon2 ถล่มเซิร์ฟเวอร์
    ไม่ใช่กันผู้ใช้ (มาตรฐานบอกให้รองรับอย่างน้อย 64)
  - **ห้ามมีกฎบังคับชนิดอักขระ** (มาตรฐานใช้คำว่า SHALL NOT) ความยาวกันการเดาได้ดีกว่า
  - **normalise ด้วย NFC ก่อนแฮชและก่อนเทียบ** และ **นับหนึ่ง code point เป็นหนึ่งอักขระ**
    ต้องใช้กระบวนการเดียวกันทุกจุด: สมัคร, เข้าสู่ระบบ, เปลี่ยนรหัสผ่าน, ตรวจรายการที่ห้าม
  - **ต้องตรวจกับรายการรหัสผ่านที่พบบ่อยหรือที่เคยรั่ว** (มาตรฐานใช้คำว่า SHALL)
    และต้องบันทึกแหล่งที่มา รุ่น และวิธีอัปเดตของรายการนั้น — การมีรายการไม่ได้แปลว่า
    ตรงมาตรฐานโดยอัตโนมัติ
- **TOTP บังคับก่อนเปิด Live** (R-19)
- ต้องยืนยัน TOTP ซ้ำเมื่อทำสิ่งที่เพิ่มความเสี่ยง: เพิ่ม/เปลี่ยน API key, เปิด Live,
  **ขยายเพดานขาดทุน** (เจ้าของตัดสิน 2026-09-26) เพราะเปลี่ยนขอบเขตความเสียหายถาวร
- **การลดความเสี่ยงไม่ต้องยืนยันซ้ำ** — ปิดไม้ ยกเลิกออเดอร์ หยุดบอท กดปุ่มหยุดบอท
  ต้องทำได้เร็วที่สุดเสมอ
- **สิ่งที่ไม่ต้องยืนยัน TOTP ซ้ำ** (เจ้าของตัดสิน 2026-09-26):
  - **กดรีเซ็ตเพดานขาดทุน** — เพดานไม่ได้เปลี่ยน แค่เริ่มนับใหม่
    และอาจต้องกดบ่อยเวลาตลาดแกว่ง (`trading-safety.md` หัวข้อ 13)
  - **เปิดบอทกลับหลังหยุด** — สิ่งที่กันการเปิดพลาดคือหน้าสรุปก่อนกด ไม่ใช่ TOTP
    และคนที่เข้าถึงบัญชีได้ก็เทรดมือได้อยู่แล้วโดยไม่ต้อง TOTP (หัวข้อ 8)

## 2. สิทธิ์

- ตรวจสิทธิ์ที่จุดเดียว ไม่กระจายเงื่อนไขไปทั่วโค้ด
- ตรวจทุกครั้งที่ฝั่งเซิร์ฟเวอร์ **ไม่เชื่อสิ่งที่หน้าบ้านส่งมา**
- ขอข้อมูลของผู้ใช้อื่นต้องได้ "ไม่พบ" ไม่ใช่ "ไม่มีสิทธิ์" เพื่อไม่ให้รู้ว่ามีอยู่จริง
- ค่าเริ่มต้นคือปฏิเสธ แล้วค่อยเปิดสิทธิ์ที่จำเป็น

## 3. ข้อมูลเข้า

- ตรวจทุกอย่างที่รับเข้ามาด้วย schema ที่ระบุชัด
- ตัวเลขเงินรับเป็นข้อความแล้วแปลงเป็น decimal ไม่ใช่รับเป็นตัวเลข JSON
- คุมอัตราการเรียกต่อผู้ใช้ โดยเฉพาะหน้า login และหน้าที่สั่งออเดอร์

## 4. Log

- **ห้ามมี secret, API key, รหัสผ่าน, โทเคน หรือ cookie ใน log ทุกกรณี**
- audit log แยกจาก log ทั่วไป และแก้ย้อนหลังไม่ได้ (ดู `database.md` ข้อ 4)

## 5. ข้อมูลส่วนบุคคล

- เก็บเท่าที่จำเป็นต่อการให้บริการ
- ต้องลบข้อมูลผู้ใช้ได้เมื่อผู้ใช้ขอ
