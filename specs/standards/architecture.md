# Standard — Architecture

สถานะ: **Proposed**

---

## 1. ทิศทางการพึ่งพา

```
   ทุกอย่างอยู่ใต้ package `tiewtrade`

       ┌──────────────────────────────┐
       │  core — ตรรกะโดเมนบริสุทธิ์   │  ← ไม่พึ่งอะไรเลย
       └──────────────┬───────────────┘
        ┌─────────────┼─────────────┐
   strategies       venues         infra
                      └── binance_th
        └─────────────┼─────────────┘
              api / engine / market-data
```

ชื่อเต็มคือ `tiewtrade.core`, `tiewtrade.venues`, `tiewtrade.services.api` และอื่น ๆ
(เจ้าของตัดสิน 2026-09-27) เพราะชื่ออย่าง `core` หรือ `services` เป็นชื่อทั่วไป
อาจชนกับ package อื่นและไม่บอกว่าเป็นของใคร

- **`core` ต้องไม่พึ่งอะไรทั้งสิ้น** — ไม่ต่อเน็ต ไม่แตะฐานข้อมูล ไม่อ่านไฟล์
  ไม่อ่านนาฬิกา ไม่ใช้ค่าสุ่ม
- `strategies` พึ่ง `core` เท่านั้น — กลยุทธ์ต้องยิงตลาดเองไม่ได้เด็ดขาด
- `venues` และ `infra` พึ่ง `core` เท่านั้น และพึ่งกันเองไม่ได้
- **`venues` มีส่วนต่อประสานกลางหนึ่งชุด** — ราคา, ออเดอร์, กระเป๋า, ข้อจำกัดของเหรียญ
  ตัวปรับของแต่ละตลาดอยู่ข้างใน **โค้ดนอก `venues` ต้องไม่รู้ว่ากำลังคุยกับตลาดไหน**
  (เจ้าของตัดสิน 2026-09-26) ตอนนี้มีตัวเดียวคือ `binance_th` แต่ยังต้องมีชั้นนี้
  เพื่อเพิ่ม Futures หรือตลาดอื่นภายหลังโดยไม่ต้องรื้อ
- service ต่าง ๆ ประกอบของพวกนี้เข้าด้วยกัน และ **ห้าม import กันเอง**
- service คุยกันผ่าน PostgreSQL และ Redis เท่านั้น ไม่เรียก HTTP หากัน

**บังคับด้วย import-linter ใน CI** ไม่ใช่ด้วยการรีวิว

## 2. ทำไม core ต้องบริสุทธิ์

เพราะโค้ดที่คิดเงินต้องให้ผลเหมือนเดิมทุกครั้งที่ใส่ค่าเดิม
ถ้ามันอ่านนาฬิกาหรือต่อเน็ตได้ จะทดสอบไม่ได้ว่าคิดถูก และจะหาสาเหตุไม่ได้เวลาผิด

เวลา, รหัสที่สร้างใหม่, ราคา, ค่าตั้งต่าง ๆ — **ผู้เรียกต้องส่งเข้ามา** core ไม่ไปหาเอง

## 3. หน้าที่ของแต่ละ process

| Process | ทำ | ห้ามทำ |
|---|---|---|
| `api` | รับคำขอ, ยืนยันตัวตน, ส่งข้อมูลให้หน้าจอ, รับ secret ตอนผู้ใช้กรอกครั้งแรกเพื่อเข้ารหัสทันที | ห้ามอ่าน secret ที่บันทึกแล้ว, ห้ามถอดรหัส, ห้ามบันทึกหรือ log ค่าดิบ, ห้ามแก้สถานะการเทรดโดยตรง |
| `engine` | รันบอท, คิดเงิน, ตัดสินใจ, ส่งออเดอร์ | ห้ามรับคำขอจากอินเทอร์เน็ตโดยตรง |
| `market-data` | รับราคาผ่าน `venues`, เก็บแท่งเทียน | ห้ามแตะออเดอร์หรือเงิน |

**ทางรับ secret** (เจ้าของตัดสิน 2026-09-26) ผู้ใช้กรอกผ่านหน้าเว็บ จึงต้องผ่าน `api`
เงื่อนไขครบอยู่ใน `tech-stack.md` หัวข้อ 8 และ `trading-safety.md` หัวข้อ 2

## 4. หนึ่งบัญชีเทรด หนึ่งผู้เขียน

ในเวลาหนึ่ง บัญชีเทรดของผู้ใช้หนึ่งคนต้องมี `engine` เดียวที่แก้ไขสถานะได้
ไม่เช่นนั้นจะเกิดการสั่งซ้อนกันจนเงินไม่ตรง

## 5. บันทึกก่อน แล้วค่อยประกาศ

ทุกอย่างที่หายไม่ได้ ต้องเขียนลง PostgreSQL ก่อน แล้วจึงส่งต่อผ่าน Redis
**Redis หายได้ PostgreSQL หายไม่ได้** — ถ้า Redis ล่ม ระบบต้องสร้างข้อมูลกลับมาได้

## 6. เมื่อจะเปลี่ยนสถาปัตยกรรม

แนวทางใช้โค้ด Paper/Live ร่วมกันที่เจ้าของยืนยัน 2026-10-15 อยู่ใน
[ADR-004](../decisions/004-shared-paper-live-trading.md) ใช้เป็นข้อกำหนดสำหรับ
feature ที่เกี่ยวข้อง โดยคง dependency boundaries และ import-linter เดิม

1. เขียนเหตุผลเป็นบันทึกที่มีหมายเลข เก็บไว้ที่เดียว (โฟลเดอร์นี้จะสร้างตอนมีบันทึกแรก)
2. แก้กฎ import-linter ในการเปลี่ยนแปลงครั้งเดียวกัน
3. ถ้าโค้ดกับ spec ขัดกัน **ให้หยุดแล้วถามเจ้าของ** ห้ามเลือกข้างเอง
