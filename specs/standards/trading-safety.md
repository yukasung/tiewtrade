# Standard — Trading Safety

สถานะ: **Proposed**

ระบบนี้สั่งเงินจริงของผู้ใช้ได้ กฎในไฟล์นี้จึงเข้มกว่าแอปทั่วไป
**ถ้ากฎข้อไหนขัดกับกำหนดเวลา ให้กฎชนะ**

---

## 1. การแยก Paper กับ Live

- Live **ต้องไม่เปิดเอง** ไม่ว่ากรณีใด ต้องมีการกระทำที่ชัดเจนของผู้ใช้ + ผ่าน TOTP
- ค่าตั้งต้นของทุกอย่างคือ Paper เสมอ
- ทุกออเดอร์ ทุกกระเป๋า ทุก position ต้องมีโหมดกำกับอย่างชัดเจน และ **เปลี่ยนโหมดทีหลังไม่ได้**
- ทางเดินของคำสั่งต้องแยกจนถึงจุดสุดท้าย — ห้ามมีทางที่ออเดอร์ Paper หลุดไป Binance ได้
- ตรรกะโดเมน (margin, PnL, TP/SL, position) ใช้ชุดเดียวกันทั้งสองโหมด ต่างกันแค่ชั้นส่งออเดอร์
- ต้องมีเทสต์ที่พิสูจน์ว่าออเดอร์ Paper ไม่เคยเรียกเครือข่ายออกไปข้างนอก

## 2. การป้องกัน API credential

- secret เข้ารหัสก่อนบันทึกเสมอ ถอดรหัสเฉพาะตอนจะใช้ และไม่เก็บค่าที่ถอดแล้วไว้
- `api` ต้องไม่มีสิทธิ์อ่านคอลัมน์ secret ที่ระดับฐานข้อมูล
- `api` รับ secret ได้เฉพาะตอนผู้ใช้กรอกครั้งแรก เพื่อเข้ารหัสทันทีแล้วส่งต่อ
  ห้ามบันทึกค่าดิบ ห้าม log ห้ามเก็บไว้เกินจำเป็น และอ่านกลับไม่ได้อีกหลังบันทึก
  (เจ้าของตัดสิน 2026-09-26 — ดู `tech-stack.md` หัวข้อ 8)
- ไม่มี endpoint ไหน log ไหน หรือข้อความ error ไหน คืนค่า secret **ไม่ว่าเต็มหรือบางส่วน**
  · สิ่งที่แสดงได้คือ **4 หลักท้ายของ API key เท่านั้น** ซึ่งเป็นส่วนที่ไม่เป็นความลับ
  **ห้ามแสดงส่วนใดของ secret เลย แม้แต่หลักเดียว** (เจ้าของตัดสิน 2026-10-04 พร้อม F-07
  — ถ้อยคำเดิม "แสดงได้แค่ 4 หลักท้าย" อ่านได้ว่าโชว์ท้าย secret ได้)
  · และ "ไม่เป็นความลับ" ไม่ได้แปลว่าใส่ log ได้ — `security.md` หัวข้อ 4 ห้าม API key
  ใน log ทุกกรณี
- ตอนเพิ่ม key ต้องพิสูจน์ว่า **key ใช้งานได้จริง** ด้วยคำขอที่ลงลายเซ็นหนึ่งครั้ง
  และ **ถ้าตลาดรายงานสิทธิ์ของ key** ให้ **ยอมรับเฉพาะสิทธิ์ที่อยู่ในรายการที่อนุญาต ·
  สิทธิ์ชนิดที่ระบบไม่รู้จักให้ปฏิเสธ key นั้น**
  (เจ้าของตัดสิน 2026-10-04 พร้อม F-07 — แทนข้อความเดิม "ปฏิเสธ key ที่เปิดสิทธิ์ถอนเงิน")
  - **บน Binance TH ตลาดไม่รายงานสิทธิ์ของ key** — ตรวจด้วยการเรียกจริงเมื่อ 2026-10-04
    `/api/v1/account` และ `/api/v1/accountV2` ไม่มีช่อง `permissions` เลย
    **ฉะนั้นวันนี้ไม่มีการตรวจจับสิทธิ์ใด ๆ เกิดขึ้นจริงบนตลาดนี้** ประโยคข้างบน
    เป็นกฎที่จะทำงานก็ต่อเมื่อตลาดเริ่มรายงานเท่านั้น — **ห้ามอ่านว่าเป็นการรับประกัน
    ว่าสิทธิ์ใหม่จะถูกปฏิเสธเอง** การตรวจจับการเปลี่ยนแปลงของตลาดต้องทำด้วยมือ
    ตามเงื่อนไขทบทวนข้างล่าง
  - **ห้ามใช้ `canTrade`, `canWithdraw`, `canDeposit` ตัดสินสิทธิ์ของ key เด็ดขาด**
    ทั้งสามเป็น **สถานะของบัญชี ไม่ใช่ของ key** — พิสูจน์แล้วเพราะหน้าสร้าง key
    ไม่มีช่องสิทธิ์ถอนเงินให้เปิด แต่ `canWithdraw` คืนค่าจริง
    **นี่เป็นกับดัก** ชื่อของมันอ่านเหมือนสิทธิ์ของ key ทุกประการ
  - **หน้าสร้าง API key ของ Binance TH มีให้เปิดสองอย่าง** คือ อ่าน และ เทรด Spot
    (เจ้าของยืนยันจากหน้าของ **บัญชีหลัก** เมื่อ 2026-10-04)
    **แต่การไม่มีช่องให้ปิด ไม่ได้แปลว่า key ไม่มีอำนาจนั้น** — เอกสารของตลาดมี
    `POST /api/v1/capital/withdraw` ซึ่งเป็นคำขอที่ลงลายเซ็น **จึงเรียกด้วย API key ได้
    โดยนิยาม** อ่านได้สองทาง และทางร้ายคือ **key ทุกอันถอนเงินได้ และผู้ใช้ปิดไม่ได้**
    ซึ่งแย่กว่าสภาพเดิมที่กฎนี้เคยกันไว้ — **ยังไม่มีหลักฐานว่าทางไหน ดู NC-16**
  - **จนกว่า NC-16 จะปิด ให้ถือว่าความเสี่ยงนี้มีอยู่และเราตรวจไม่ได้** และบังคับ
    สองข้อที่ไม่ต้องพึ่งการตรวจสิทธิ์:
    1. **โค้ดของระบบต้องไม่มีเส้นทางเรียก endpoint ที่ย้ายเงินออกจากบัญชีผู้ใช้**
       (ถอน, โอนระหว่างบัญชี, จัดการบัญชีย่อย) — บังคับด้วยด่านอัตโนมัติ ไม่ใช่การรีวิว
       **นี่คือสิ่งที่กันความเสียหายจริงเมื่อเราตรวจสิทธิ์ไม่ได้**
    2. ตอนเพิ่ม key ต้อง **แนะนำให้ผู้ใช้เปิด whitelist ที่อยู่ถอนเงินที่ตลาด**
       ซึ่งเป็นการตั้งค่าระดับบัญชีที่ผู้ใช้คุมได้เอง
  - **เงื่อนไขทบทวนด้วยมือ** — ต้องทบทวนข้อนี้ทั้งข้อ **ก่อนเปิด Live (F-24)**
    และเมื่อตลาดประกาศเปลี่ยน API · การทบทวนคือการอ่านเอกสารสิทธิ์ของ key ใหม่
    ไม่ใช่การรอให้ระบบแจ้ง เพราะระบบแจ้งไม่ได้
  - **ผลที่ยอมรับแล้ว** (เจ้าของตัดสิน 2026-10-04): key ที่ไม่ได้ติ๊กสิทธิ์เทรด
    จะรู้ตัวตอนสั่งออเดอร์ครั้งแรก ไม่ใช่ตอนเพิ่ม key — ชดเชยด้วยข้อความตอนเพิ่ม key
- key ที่ Binance ปฏิเสธต้องหยุดบอทที่ใช้ key นั้นทันที และแจ้งผู้ใช้

## 3. การตรวจออเดอร์ก่อนส่ง

ทุกออเดอร์ ไม่ว่ามาจากคนหรือบอท ต้องผ่านจุดตรวจเดียวกันก่อนออกจากระบบ
**ห้ามมีทางลัด** — ไม่มีเส้นทางไหนข้ามจุดตรวจนี้ได้ แม้แต่การปิด position ฉุกเฉิน

จุดตรวจแยกคำสั่งเป็นสองชนิด และใช้เกณฑ์ไม่เหมือนกัน (เจ้าของตัดสิน 2026-09-26)

**คำสั่งลดความเสี่ยง** — คำสั่งที่ปิดหรือลด position ที่เปิดอยู่ โดยขนาดไม่เกินที่ถืออยู่:
- ตรงตามข้อจำกัดของเหรียญนั้น (ขนาดขั้นต่ำ, ทศนิยม, มูลค่าขั้นต่ำ)
- ขนาดคำสั่งไม่เกิน position ที่ถืออยู่จริง
- ผลของคำสั่งต้องทำให้ความเสี่ยงของกระเป๋าลดลงหรือเท่าเดิม ไม่เพิ่ม
- **ต้องส่งแบบ reduce-only ไปที่ Binance** (เจ้าของตัดสิน 2026-09-26)
  ห้ามเชื่อ position ที่บันทึกไว้ในระบบเราเพียงอย่างเดียว ถ้าข้อมูลเราเก่า
  คำสั่งปิดไม้จะกลายเป็นการเปิดไม้ฝั่งตรงข้าม การติด reduce-only ทำให้
  Binance ปฏิเสธเมื่อไม่มีไม้ให้ลด แทนที่จะเปิดไม้ใหม่ให้
- **ห้ามปฏิเสธเพราะกระเป๋าเกินเพดานความเสี่ยงอยู่ก่อนแล้ว** — คำสั่งนี้คือทางออกจากสถานะนั้น

**คำสั่งเพิ่มความเสี่ยง** — คำสั่งอื่นทั้งหมด:
- เหรียญนั้นอยู่ในรายการที่ระบบรองรับ (`mission.md` หัวข้อ 6)
- ตรงตามข้อจำกัดของเหรียญนั้น (ขนาดขั้นต่ำ, ทศนิยม, มูลค่าขั้นต่ำ)
- กระเป๋านั้นยังไม่ชนเพดานขาดทุนที่ผู้ใช้ตั้งไว้ (หัวข้อ 13)
- มีเงินพอจริงหลังหักออเดอร์ที่ค้างอยู่
- ไม่ใช่ออเดอร์ที่ทำให้ position เกินสิ่งที่ผู้ใช้อนุญาต

คำสั่งที่ขนาดเกิน position ที่ถืออยู่ **ไม่ใช่คำสั่งลดความเสี่ยง** เช่น ถือ Long 1 เหรียญ
แล้วสั่งขาย 3 เหรียญ ผลคือ Short 2 เหรียญ ซึ่งเป็นการเปิดไม้ใหม่ ต้องตรวจเต็มชุด

การตัดสินว่าคำสั่งใดลดความเสี่ยง ต้องคำนวณจาก position ที่บันทึกไว้ ห้ามเดา

**คำสั่งลดความเสี่ยงไม่ต้องตรวจว่าเหรียญอยู่ในรายการที่รองรับ** เพราะเหรียญที่ถูกถอน
ออกจากรายการภายหลัง ผู้ใช้ยังต้องปิดไม้ที่ค้างอยู่ได้ (`mission.md` หัวข้อ 6)

กฎเรื่อง TP/SL และ bracket อยู่ในหัวข้อ 11

## 4. กันสั่งซ้ำ (Idempotency)

- ทุกออเดอร์ต้องมีรหัสที่ระบบสร้างเอง และส่งรหัสนั้นให้ Binance ด้วย
- คำขอเดียวกันที่ส่งซ้ำ ต้องได้ผลลัพธ์เดิม ไม่ใช่ออเดอร์ใบใหม่
- **บันทึกว่ากำลังจะส่ง ลงฐานข้อมูลก่อน แล้วค่อยส่งจริง** ไม่ใช่ส่งก่อนแล้วค่อยบันทึก
- ถ้าส่งแล้วไม่รู้ผล (เน็ตหลุด, timeout) ห้ามเดา — ต้องไปถาม Binance ด้วยรหัสนั้นว่าเข้าหรือไม่
- หนึ่งกระเป๋าต้องมีผู้เขียนคนเดียวในเวลาหนึ่ง ห้ามมีสอง process สั่งพร้อมกัน

## 5. ความจริงอยู่ที่ Binance

- สำหรับ Live **Binance คือความจริง** ข้อมูลในระบบเราคือสำเนา
- เมื่อไม่ตรงกัน ให้เชื่อ Binance แล้วแก้ข้อมูลเรา พร้อมบันทึกว่าไม่ตรงตรงไหน
- ต้องกระทบยอดกับ Binance:
  - ทุกครั้งที่ `engine` เริ่มทำงานหรือรับกระเป๋ามาดูแล
  - หลัง WebSocket หลุดแล้วต่อกลับ
  - เป็นระยะระหว่างทำงานปกติ
- **ห้ามให้บอทเริ่มทำงานก่อนกระทบยอดเสร็จ**
- ออเดอร์หรือ position ที่เกิดนอกระบบ (ผู้ใช้ไปสั่งเองบน Binance) ต้องตรวจจับได้
  และต้องหยุดบอทที่ดูแลกระเป๋านั้น

## 6. WebSocket หลุดและการกู้คืน

- ถือว่า "หลุดเมื่อไหร่ก็ได้" เป็นเรื่องปกติ ไม่ใช่กรณียกเว้น
- ต่อกลับโดยเว้นระยะเพิ่มขึ้นเรื่อย ๆ และสุ่มเวลาเล็กน้อย ไม่ใช่วนต่อรัว ๆ
- ระหว่างที่หลุด ห้ามถือว่าราคาล่าสุดยังใช้ได้ — ราคาที่เก่าเกินกำหนดต้องถือว่าไม่มีราคา
- **ถ้าไม่มีราคาที่เชื่อถือได้ ห้ามเปิดไม้ใหม่** แต่คำสั่งลดความเสี่ยง (หัวข้อ 3) ส่งได้เสมอ
- หลังต่อกลับ ต้องกระทบยอดก่อน แล้วจึงกลับมาทำงานปกติ

**"ส่งได้เสมอ" หมายถึงระบบยอมให้ส่งคำสั่งออกไป ไม่ใช่รับประกันว่าปิดสำเร็จ**
(เจ้าของตัดสิน 2026-09-26) ตลาดอาจไม่มีสภาพคล่องพอ ดังนั้น:
- ปิดไม่สำเร็จต้องแจ้งเตือนผู้ใช้จริง ไม่ใช่เขียนลง log เงียบ ๆ
- หน้าจอต้องแยกสถานะ "ส่งคำสั่งแล้ว" ออกจาก "ปิดเรียบร้อย" ให้ชัด
- ห้ามแสดงว่าปิดแล้วก่อนที่ Binance จะยืนยัน

## 7. ขีดจำกัดการเรียก Binance และการลองใหม่

- ต้องนับและจำกัดอัตราการเรียกในระดับทั้งระบบ ไม่ใช่ต่างคนต่างเรียก
- ลองใหม่ได้เฉพาะคำสั่งที่ทำซ้ำแล้วไม่เกิดผลสองครั้ง — **การส่งออเดอร์ไม่ใช่หนึ่งในนั้น**
  ถ้าส่งแล้วไม่รู้ผล ให้ไปถามสถานะ ไม่ใช่ส่งซ้ำ
- เมื่อโดน Binance ปฏิเสธเพราะเรียกถี่เกิน ต้องหยุดรอตามที่ Binance บอก
- ความผิดพลาดที่เกิดซ้ำ ๆ ต้องตัดวงจรและแจ้งเตือน ไม่ใช่ลองต่อไปเงียบ ๆ

## 8. ปุ่มหยุดบอท (Kill Switch)

- ผู้ใช้ต้องสั่งหยุดได้ **ในคลิกเดียว** จากทุกหน้าจอ
- ปุ่มนี้ **หยุดบอทโดยไม่เปลี่ยนประเภทการใช้งานบัญชี**
  (ปรับตามคำตัดสินหนึ่งบัญชี/เลือกทีละแบบ และคำสั่งแก้ review issue4 วันที่ 2026-10-07)
  บัญชีที่เลือก BOT ยังเป็น BOT หลังหยุด จึง **เปิดไม้ใหม่ด้วยมือไม่ได้**
  ต้องเปลี่ยนเป็น MANUAL ตามเงื่อนไขใน `mission.md` หัวข้อ5 ก่อน
  บัญชี MANUAL เปิดไม้ใหม่ด้วยมือได้เมื่อผ่าน safety gates เดิมทั้งหมด
  **การปิด/ลด position และยกเลิกออเดอร์ทำได้ทุกประเภท** ตามหัวข้อ3
  การไปสั่งเองบนเว็บหรือแอป Binance อยู่นอกการควบคุมของระบบอยู่แล้ว (หัวข้อ5)
- ปุ่มหยุดของผู้ใช้มี **สองระดับ** (เจ้าของตัดสิน 2026-09-26):
  - **หยุดทั้งหมด** — ครอบคลุมบัญชีตลาดของผู้ใช้คนนั้น
  - **หยุดรายบัญชีของผู้ใช้** — ครอบคลุมบัญชีตลาดเดียวของผู้ใช้คนนั้น
  บัญชีของผู้ใช้อื่นทำงานต่อได้ ตาม `mission.md` หัวข้อ 5 ที่เจ้าของเปลี่ยน 2026-10-07
- ต้องมีตัวหยุดระดับทั้งระบบ **สำหรับ Platform Owner และ Platform Admin**
  (เจ้าของตัดสิน 2026-09-26 — ดูขอบเขตบทบาทใน `mission.md` หัวข้อ 2)
  ตัวหยุดนี้ทำและไม่ทำตามนี้:
  - **ทำ** — หยุดบอททุกตัวของทุกคน, ห้ามระบบส่งคำสั่งเพิ่มความเสี่ยงใหม่,
    แจ้งผู้ใช้ทุกคนว่าถูกหยุดและเพราะอะไร, ลง audit log ว่าใครสั่งและเมื่อไหร่
  - **ไม่ทำ** — ไม่ยกเลิกออเดอร์ที่ผู้ใช้สั่งด้วยมือ, ไม่แตะ position, ไม่แตะ TP/SL
  - **ผู้ใช้ต้องปิดไม้ได้ตลอด แม้ในระหว่างที่แพลตฟอร์มสั่งหยุด** เงินเป็นของผู้ใช้
    ถ้าหยุดแล้วผู้ใช้ออกจากตลาดไม่ได้ แพลตฟอร์มเป็นผู้ทำให้เขาขาดทุน
  - ต่างจากปุ่มหยุดของผู้ใช้เองที่ยกเลิกออเดอร์มือด้วย เพราะกรณีนั้นผู้ใช้เป็นคนสั่ง
  - **เปิดกลับได้เฉพาะ Platform Owner** การหยุดต้องทันท่วงที แต่การเปิดกลับรอได้
- การหยุดต้อง: หยุดบอททั้งหมดในขอบเขตที่เลือก และ **ยกเลิกออเดอร์ที่ยังไม่เข้า
  ทั้งของบอทและที่ผู้ใช้สั่งด้วยมือ** (เจ้าของตัดสิน 2026-09-26)
  **ยกเว้น TP/SL ซึ่งห้ามยกเลิกทุกกรณี** (ดูข้อถัดไป)
- หลังหยุด การตั้งออเดอร์เพิ่มความเสี่ยงด้วยมือขึ้นกับประเภท MANUAL และ safety gates
  ไม่ใช้การหยุดบอทเป็นสิทธิ์ข้ามประเภท BOT; คำสั่งลดความเสี่ยงยังทำได้ทุกประเภท
  ออเดอร์เดิมที่ค้างอยู่ถูกยกเลิกตามขอบเขตข้างต้น ต้องแสดงรายการที่ยกเลิกให้ผู้ใช้เห็น
- **ห้ามปิด position ของผู้ใช้เองโดยไม่ได้สั่ง** และ **ห้ามยกเลิก TP/SL**
  เพราะจะทำให้ไม้ที่เปิดอยู่ไม่มีอะไรป้องกัน
- การปิดไม้ตามคำสั่ง bracket ที่ผู้ใช้ตั้งไว้ล่วงหน้า และการปิดคืนเมื่อตั้ง TP/SL ไม่สำเร็จ
  (หัวข้อ 11) **ไม่ถือว่าระบบปิดเอง** เพราะผู้ใช้สั่งไว้ล่วงหน้าแล้ว (เจ้าของตัดสิน 2026-09-26)
- คำสั่งหยุดต้องทำงานได้แม้ส่วนอื่นของระบบมีปัญหา
- **ไม่มีปุ่มพักเทรดมือแยกต่างหาก** (คงคำตัดสิน 2026-09-26)
  เงื่อนไขประเภทบัญชีและตัวหยุดระดับแพลตฟอร์มข้างต้นยังบังคับตามปกติ
  ปุ่มหยุดบอทไม่เปลี่ยนประเภทเป็น MANUAL และไม่ขวางคำสั่งลดความเสี่ยง
  หากต้องเพิ่มการบังคับพักเทรดมือ เป็นงานอีกชุดที่ต้องกำหนดก่อน:
  การให้ผู้ใช้บังคับตัวเองพักเทรด (cooling-off) **ยังไม่มีข้อกำหนด** ยังไม่ตัดสินว่าจะทำหรือไม่
  การระงับบัญชีที่มีปัญหาเป็นอำนาจฝั่งแพลตฟอร์ม (**รอ NC-02**)

**คำสั่งที่ยังอยู่ในคิวตอนกดหยุด** (เจ้าของตัดสิน 2026-09-26)

- คำสั่ง **เพิ่มความเสี่ยง** ที่ยังไม่ออกจากระบบ → **ทิ้ง ห้ามส่ง**
  ทั้งของบอทและที่ผู้ใช้สั่งด้วยมือ (เจ้าของตัดสิน 2026-09-26)
  คำสั่งในคิวยังไม่มีไม้และไม่มีเงินติดอยู่ ทิ้งแล้วเสียแค่โอกาส
  แต่ถ้าส่งต่อจะได้ไม้ที่ผู้ใช้เพิ่งสั่งให้หยุด
- คำสั่ง **ลดความเสี่ยง** ที่อยู่ในคิว → **ส่งต่อตามปกติ** (หัวข้อ 3)
  ทิ้งไปจะทำให้ไม้ที่กำลังจะถูกปิดค้างเปิดอยู่
- ใบที่ทิ้ง ต้องเปลี่ยนสถานะเป็น "ยกเลิกเพราะกดหยุด" **ห้ามปล่อยค้างสถานะ "กำลังจะส่ง"**
  (หัวข้อ 4) ไม่เช่นนั้นตัวไล่เก็บจะไปถาม Binance หาออเดอร์ที่ Binance ไม่เคยเห็น
  ต้องลง audit log และแสดงให้ผู้ใช้เห็นว่าทิ้งไปกี่ใบ อะไรบ้าง
- ชั้นส่งออเดอร์ต้อง **ตรวจสถานะหยุดอีกครั้งก่อนยิงจริง** ใบที่ออกไปแล้วห้ามพยายามทิ้ง
  ให้ถือเป็นออเดอร์ที่ส่งแล้วไม่รู้ผล และจัดการตามหัวข้อ 4 และ 10

**ออเดอร์ที่ส่งแล้วไม่รู้ผล ขณะอยู่ในสถานะหยุด** (เจ้าของตัดสิน 2026-09-26)

- ตัวไล่เก็บ (หัวข้อ 10) **ทำงานต่อ ห้ามหยุด** การถาม Binance ไม่สร้างความเสี่ยงใหม่
  การไม่ถามไม่ได้ทำให้ไม้หายไป แค่ทำให้เราไม่รู้ว่ามีไม้อยู่ ซึ่งขัดกับหัวข้อ 5
- **แยก "ถาม" ออกจาก "ทำ"** ถามสถานะได้จนรู้ผลทุกใบ แต่กระทำได้เท่านี้:
  - ผลว่ายังไม่เข้าหรือยังค้างอยู่ → ยกเลิกออเดอร์นั้น
  - ผลว่าเข้าแล้วหรือเข้าบางส่วน → บันทึกตามที่เข้าจริง และ **แจ้งเตือนผู้ใช้ทันที**
    ว่ามีไม้เกิดขึ้นหลังกดหยุด ระบุว่าไม้อะไรและขนาดเท่าไหร่
- **ห้ามเปิดไม้ใหม่ และห้ามปลุกบอทกลับมาทำงาน**
- ตัวไล่เก็บทำงานจบ **ไม่ใช่การเปิดกลับ** สถานะหยุดยังคงอยู่จนมีคนสั่งเปิด
- พบว่าออเดอร์ bracket เข้าแล้วแต่ยังไม่ได้ตั้ง TP/SL ขณะอยู่ในสถานะหยุด
  → **ต้องตั้ง TP/SL ให้** เพราะ TP/SL เป็นคำสั่งลดความเสี่ยง และการปล่อยไม้ไว้
  โดยไม่มีอะไรป้องกันคือสิ่งที่หัวข้อนี้ห้ามอยู่แล้ว ใช้กฎการลองใหม่และการแจ้งเตือน
  ตามหัวข้อ 11 ทุกข้อ — นี่เป็นข้อยกเว้นเดียวที่ระบบส่งคำสั่งออกไปได้ขณะอยู่ในสถานะหยุด
  นอกเหนือจากการยกเลิกออเดอร์และคำสั่งลดความเสี่ยงของผู้ใช้

**สถานะหยุดหลังระบบเริ่มใหม่ และการเปิดกลับ** (เจ้าของตัดสิน 2026-09-26)

- สถานะหยุดต้อง **บันทึกลงฐานข้อมูล** ว่ากระเป๋าไหนถูกหยุด เมื่อไหร่ ใครสั่ง
  และต้องเขียนสำเร็จ **ก่อน** จะแสดงต่อผู้ใช้ว่าหยุดแล้ว
  เก็บไว้ในหน่วยความจำอย่างเดียวไม่ได้ เพราะจะหายเมื่อ restart
- ต้องบันทึก **สาเหตุ** ที่บอทหยุดด้วย หลังระบบเริ่มใหม่ให้ทำต่างกันตามสาเหตุ:
  - ผู้ใช้กดหยุด → **ยังหยุด** รอผู้ใช้สั่งเปิด
  - เจ้าของแพลตฟอร์มสั่งหยุด → **ยังหยุด** ผู้ใช้เปิดเองไม่ได้
  - ระบบหยุดเอง (key ถูกปฏิเสธ, เจอออเดอร์นอกระบบ, ตั้ง TP/SL ไม่สำเร็จ)
    → **ยังหยุด** ต้องแก้ต้นเหตุก่อน
  - ระบบล่มหรือ deploy → กระทบยอดเสร็จแล้วทำงานต่อได้
  - **อ่านสาเหตุไม่ได้หรือไม่มีบันทึก → ถือว่ายังหยุด** (หัวข้อ 10)
- การเปิดกลับ:
  - ผู้ใช้เปิดเองได้ เฉพาะการหยุดที่ตัวเองสั่ง และบัญชียังเลือกประเภท BOT
  - เปิดกลับตามระดับที่หยุด — หยุดรายบัญชีผู้ใช้ ก็เปิดกลับเฉพาะบัญชีนั้น
  - ก่อนกดเปิด ผู้ใช้ต้องเห็นสรุป: ไม้ที่เปิดค้างอยู่, ออเดอร์ที่ถูกยกเลิกไป,
    ออเดอร์ที่ยกเลิกไม่สำเร็จ **หน้าสรุปนี้คือสิ่งที่กันการเปิดพลาด**
  - กระทบยอดต้องเสร็จก่อน (หัวข้อ 5 และ 10)
  - **ไม่ต้องผ่าน 2FA** คงข้อยกเว้นที่เจ้าของตัดสินไว้เดิม
    ต้องผ่านเงื่อนไขประเภท BOT หน้าสรุป และการกระทบยอดข้างต้น
  - การหยุดระดับแพลตฟอร์ม ผู้ใช้เปิดเองไม่ได้ เปิดกลับได้เฉพาะ Platform Owner
- ลง audit log ทั้งตอนหยุดและตอนเปิดกลับ

**เมื่อยกเลิกออเดอร์ไม่สำเร็จ** (เจ้าของตัดสิน 2026-09-26)

- **บอทหยุดทันทีเสมอ ไม่รอผลการยกเลิก** สองเรื่องนี้แยกกัน
  บอทคือสิ่งที่หยุดได้ในมือเรา การยกเลิกออเดอร์คือสิ่งที่ต้องขอ Binance
- ปุ่มหยุดมี **3 สถานะ ห้ามมีแค่ 2**:
  - **กำลังหยุด** — ยังเหลือ n ใบที่รอผล
  - **หยุดแล้วครบ** — ทุกใบรู้ผลและจัดการเรียบร้อย
  - **หยุดแล้วแต่มีปัญหา** — เหลือ n ใบที่ยกเลิกไม่สำเร็จ พร้อมรายการ
  **ห้ามแสดง "หยุดแล้วครบ" จนกว่าทุกใบจะรู้ผล**
- ระบบต้องลองยกเลิกต่อเอง แบบเว้นระยะเพิ่มขึ้น (หัวข้อ 7)
  การยกเลิกลองซ้ำได้ปลอดภัย ต่างจากการส่งออเดอร์
  ลองจนได้ผลอย่างใดอย่างหนึ่ง: ยกเลิกสำเร็จ / รู้ว่าออเดอร์เข้าไปแล้ว / เกินเวลาที่กำหนด
- ออเดอร์ที่ **เข้าไปแล้วพอดี ไม่ใช่การยกเลิกที่ล้มเหลว** ให้เข้าเส้นทางเดียวกับ
  ออเดอร์ที่ส่งแล้วไม่รู้ผล: บันทึกไม้ แจ้งเตือนทันที และตั้ง TP/SL ที่ขาด
- **ห้ามยอมแพ้เงียบ** เกินเวลาแล้วยังไม่สำเร็จต้องแจ้งเตือนทุกช่องทาง
  แสดงรายการใบที่ค้าง และบอกผู้ใช้ว่าสามารถไปยกเลิกเองบน Binance ได้
  (กรณี key ถูกเพิกถอน ระบบเราทำอะไรไม่ได้เลย ต้องบอกทางออกที่ใช้ได้จริง)
- ทุกใบที่ยกเลิกไม่สำเร็จต้องปรากฏในหน้าสรุปก่อนเปิดบอทกลับ และลง audit log ทุกใบ
- **"เกินเวลา" คือ 1 นาที** (เจ้าของตัดสิน 2026-09-26) ลองยกเลิกเงียบ ๆ ได้ 1 นาที
  ยังไม่สำเร็จต้องแจ้งเตือนผู้ใช้ **แต่ยังลองต่อในเบื้องหลังจนรู้ผล**
  ตัวเลขนี้คือเวลาที่ต้องปลุกผู้ใช้ ไม่ใช่เวลาที่เลิกลอง

## 9. Audit log

**NC-F16-01 — Approved 2026-10-25:** หากฐานข้อมูลล่มหรือบันทึก durable intent/audit
ไม่ได้ ต้องปฏิเสธคำสั่ง รวมคำสั่งลดความเสี่ยงและยกเลิก ไม่ส่งคำสั่งโดยข้ามการบันทึก
สำหรับ Live ต้องแจ้งให้ผู้ใช้จัดการตรงที่ตลาด ข้อยกเว้นนี้ใช้กับข้อความ “ส่งได้เสมอ”
และ “ผู้ใช้สั่งด้วยมือได้ตามปกติ” ทุกแห่งในเอกสารนี้: ไม่ได้ยกเว้นเงื่อนไขการบันทึก
หากผล commit ของคำขอเดิมไม่ทราบ ต้องคงสถานะไม่ทราบและตรวจผลเดิมก่อน
ไม่ถือว่าฐานข้อมูลล่มแปลว่าคำขอนั้นไม่เคยสำเร็จ

- ทุกการกระทำที่แตะเงินต้องบันทึก: ใครทำ ทำอะไร กับอะไร เมื่อไหร่ ผลเป็นอย่างไร
- **แก้ไขหรือลบย้อนหลังไม่ได้** บังคับที่ระดับสิทธิ์ฐานข้อมูล ไม่ใช่แค่ตกลงกันในทีม
- เก็บเงินเป็นรายการเดินบัญชีแบบเพิ่มอย่างเดียว ยอดคงเหลือคือผลรวม ไม่ใช่ตัวเลขที่เขียนทับ
- ห้ามมี secret หรือรหัสผ่านอยู่ใน log

## 10. การกู้คืนเมื่อเกิดข้อผิดพลาด

- เมื่อไม่แน่ใจ ให้เลือกทางที่ปลอดภัยกว่าเสมอ: หยุด ไม่ใช่เดาแล้วทำต่อ
- สถานะที่ค้างคา (ส่งไปแล้วแต่ไม่รู้ผล) ต้องมีตัวไล่เก็บ ไม่ใช่ปล่อยค้าง
- ข้อผิดพลาดที่ผู้ใช้ควรรู้ ต้องแจ้งเตือนจริง ไม่ใช่แค่เขียนลง log
- หลังระบบล่มแล้วกลับมา ต้องกระทบยอดก่อนเสมอ ก่อนจะให้บอททำงานต่อ

## 11. TP / SL และ Bracket

(เจ้าของตัดสิน 2026-09-26)

**ใครกำหนดว่าต้องมี**
- กลยุทธ์แต่ละตัว **ประกาศเอง** ว่าต้องมี TP/SL หรือไม่ ระบบบังคับตามที่ประกาศ
- **ห้ามระบบบังคับเพิ่มเอง และห้ามตั้ง SL กันภัยที่กลยุทธ์ไม่ได้ขอ** เพราะจะเปลี่ยนผลของกลยุทธ์
- เทรดมือไม่บังคับ ผู้ใช้เลือกเอง
- กลยุทธ์ที่ไม่ใช้ SL จบไม้ด้วยสัญญาณปิดของกลยุทธ์เอง หรือผู้ใช้ปิดเอง

**เมื่อตั้ง TP/SL ไม่สำเร็จ** (ใช้เฉพาะไม้ที่กลยุทธ์หรือผู้ใช้สั่งให้มี)
- ตั้งซ้ำด้วยรหัสเดิมได้ ไม่เกิดคำสั่งสองใบ (หัวข้อ 4) ลองใหม่ได้ **ไม่เกิน 3 ครั้ง**
- ครบ 3 ครั้งแล้วยังไม่สำเร็จ:
  - **เทรดมือ** — ห้ามปิดไม้ให้ ต้องแจ้งเตือนทุกช่องทางที่ผู้ใช้เปิดไว้
    และแสดงเครื่องหมายบนไม้นั้นว่าไม่มีการป้องกัน
  - **บอท** — ปิดไม้คืนทันที หยุดบอทตัวนั้น และแจ้งเตือน
    หน้าจอเปิดบอทต้องบอกผู้ใช้เรื่องนี้ไว้ล่วงหน้า
- ทุกกรณีต้องลง audit log

**ออเดอร์เข้าไม่ครบ (partial fill)**
- ตั้ง TP/SL ตามขนาดที่เข้าจริง **ทันที ห้ามรอให้เข้าครบ**
- เข้าเพิ่มภายหลัง ต้องขยาย TP/SL ให้ครอบคลุมขนาดใหม่
- ระหว่างนั้นห้ามถือว่าไม้ได้รับการป้องกันครบแล้ว

**บอทหยุดผิดปกติขณะยังมีไม้เปิดอยู่**
- ต้องแจ้งเตือนผู้ใช้ทันที ระบุว่ามีไม้อะไรค้างอยู่
  และไม้นั้นมีคำสั่งป้องกันอยู่ที่ Binance หรือไม่
- ระบบ **ไม่แตะไม้** ไม่ปิดให้ ไม่ตั้ง SL ให้
- การปิดโดยผู้ใช้เป็นคำสั่งลดความเสี่ยง (หัวข้อ 3) ต้องส่งได้เสมอ

## 12. ความพร้อมของข้อมูลบัญชี

(เจ้าของตัดสิน 2026-09-26)

ข้อมูลจาก Binance มาสองทางที่หลุดแยกกันได้ ต้องแยกดูแลคนละเรื่อง:
**ราคาตลาด** (หัวข้อ 6) และ **ข้อมูลบัญชี** — เงิน, ออเดอร์ค้าง, position

**ถือว่าข้อมูลบัญชีไม่พร้อมเมื่อ**
- ยังไม่กระทบยอดครั้งแรกหลังรับกระเป๋ามาดูแล
- ท่อข้อมูลบัญชีหลุด และยังกระทบยอดไม่เสร็จหลังต่อกลับ
- ตรวจพบว่าข้อมูลเราไม่ตรงกับ Binance และยังแก้ไม่เสร็จ

**ไม่ใช้เกณฑ์เวลาแบบราคา** ราคาเปลี่ยนทุกวินาทีจึงวัดด้วยอายุได้
แต่ยอดเงินไม่เปลี่ยนเองถ้าไม่มีใครทำอะไร เกณฑ์คือ **เรารู้ตัวว่าคลาดสายตาไป**
ไม่ใช่ข้อมูลเก่ากี่นาที

**เมื่อข้อมูลบัญชีไม่พร้อม**
**Amendment — Approved 2026-10-25 (NC-F18-08):** ข้ออนุญาต manual ด้านล่าง
ไม่ยกเว้น loss gate ของ §3/13 คำสั่งเพิ่มความเสี่ยงทั้ง manual/bot ของทั้งสองโหมด
ต้องถูกบล็อกเมื่อคำนวณ loss ไม่ได้ อ่าน latch ไม่ได้ หรือ latch ชนแล้วและยังไม่ reset
ข้อยกเว้นของการตรวจยอดเบื้องต้นและเงื่อนไข reduce-only สำหรับลดความเสี่ยงคงเดิม
ไม่บังคับ loss gate กับการลดความเสี่ยงและ cancel และยังต้องบันทึกตาม §9

- **บอทห้ามทำงาน** (หัวข้อ 5)
- **ผู้ใช้สั่งด้วยมือได้ภายใต้ loss gate ข้างต้น** และต้องมีทั้งสามข้อนี้:
  - หน้าจอต้องบอกว่าข้อมูลบัญชีเป็นของเมื่อไหร่ และกำลังกระทบยอดอยู่
    ห้ามแสดงตัวเลขเฉย ๆ เหมือนทุกอย่างปกติ
  - การตรวจ "มีเงินพอ" (หัวข้อ 3) ถือเป็น **การตรวจเบื้องต้น ไม่ใช่การรับประกัน**
    ผู้ตัดสินสุดท้ายคือ Binance ถ้า Binance ปฏิเสธ ต้องแสดงเหตุผลจริงให้ผู้ใช้เห็น
  - คำสั่งลดความเสี่ยงต้องส่งแบบ **reduce-only** (หัวข้อ 3)

## 13. เพดานความเสี่ยงของกระเป๋า

(เจ้าของตัดสิน 2026-09-26 — ปิด NC-07)

**ระบบไม่กำหนดเพดานของตัวเองนอกจากที่ Binance บังคับอยู่แล้ว**
เพดานเดียวที่ระบบบังคับใช้คือเพดานขาดทุนที่ผู้ใช้เป็นคนกรอก

| เรื่อง | ใครกำหนด |
|---|---|
| leverage | **Binance** — ระบบไม่ตรวจซ้ำ ปล่อยให้ Binance ปฏิเสธ และแสดงเหตุผลจริงให้ผู้ใช้เห็น |
| ขนาดไม้ของบอท | กลยุทธ์ให้ค่าเริ่มต้น แต่ **ผู้ใช้ปรับได้อิสระ ไม่มีขอบ** ผู้กำหนดจริงคือผู้ใช้ |
| ขนาดไม้เทรดมือ | ผู้ใช้ **ไม่มีเพดาน** |
| ขาดทุน | **ผู้ใช้ กรอกเอง บังคับกรอกก่อนเปิด Live** |

**เพดานขาดทุน**

- ผู้ใช้ต้องกรอกตัวเลขก่อนเปิด Live **เว้นว่างไม่ได้** จะตั้งใหญ่แค่ไหนก็ได้
  แต่ต้องเห็นตัวเลขนั้นด้วยตาตัวเองก่อนเงินจริงเริ่มเดิน
- นับ **ต่อกระเป๋า** แต่ละกระเป๋ามีเพดานของตัวเอง
- นับจาก **ไม้ที่ปิดแล้วรวมกับไม้ที่ยังเปิดอยู่ที่กำลังติดลบ**
- **ไม่รีเซ็ตเองตามเวลา** ชนแล้วค้างอยู่จนผู้ใช้มากดรีเซ็ต แนวเดียวกับปุ่มหยุดบอท (หัวข้อ 8)
- เมื่อรีเซ็ต ให้ **เริ่มนับใหม่จากศูนย์ ณ เวลาที่กดรีเซ็ต ไม่นับขาดทุนค้างของไม้ที่ยังเปิดอยู่**
  ไม่เช่นนั้นปุ่มรีเซ็ตจะกดไม่ขึ้นตราบใดที่ยังถือไม้ติดลบ ซึ่งเท่ากับบังคับให้ผู้ใช้ขายขาดทุน
- ลง audit log ทั้งตอนชนเพดานและตอนรีเซ็ต

**เมื่อชนเพดาน**

- **หยุดบอททั้งหมดในกระเป๋านั้น** ใช้กลไกเดียวกับปุ่มหยุดบอท (หัวข้อ 8)
- การหยุดเพราะชนเพดานไม่เปลี่ยน BOT เป็น MANUAL และไม่เปิดสิทธิ์เปิดไม้ใหม่ด้วยมือ
  บัญชี MANUAL ใช้กฎเทรดมือเดิม; ทุกประเภทปิด/ลด position และยกเลิกออเดอร์ได้ตามหัวข้อ3
- ไม่ปิด position ให้ ไม่ยกเลิก TP/SL

**Paper ใช้กฎชุดนี้เหมือน Live ทุกข้อ** ถ้า Paper ไม่มีเพดาน ผลที่ผู้ใช้เห็นตอนฝึก
จะไม่เหมือนตอนใช้เงินจริง ซึ่งทำลายจุดประสงค์ของ Paper

**ข้อจำกัดที่ต้องรู้ตัว ไม่ใช่ความบกพร่องที่ลืม**

1. ระบบนี้ไม่มีตาข่ายชั้นอื่นเลย ขนาดไม้ไม่จำกัด เทรดมือไม่จำกัด leverage ตาม Binance
   เพดานขาดทุนคือชั้นเดียวที่มี
2. การนับไม้ที่ยังเปิดอยู่ทำให้บอทอาจถูกหยุดเพราะราคาแกว่งลงชั่วคราวแล้วเด้งกลับ
3. การรีเซ็ตแบบเริ่มนับใหม่จากศูนย์ ทำให้ผู้ใช้กดรีเซ็ตซ้ำ ๆ เพื่อเทรดต่อได้เรื่อย ๆ
   โดยที่ขาดทุนค้างไม่เคยถูกนับ **นี่เป็นผลที่ยอมรับแล้ว** เพื่อไม่ให้ระบบบังคับผู้ใช้ขายขาดทุน

**เมื่อไม่มีราคาที่เชื่อถือได้** (เจ้าของตัดสิน 2026-09-26)

การนับไม้ที่ยังเปิดอยู่ต้องใช้ราคาปัจจุบัน ถ้าราคาเก่าเกินกำหนดจนถือว่าไม่มีราคา
(หัวข้อ 6) จะคำนวณขาดทุนไม่ได้ ในกรณีนี้:

- **บอทพักทำงาน** และไม่นับเพดานขาดทุนในช่วงนั้น
  ห้ามใช้ราคาเก่ามาคำนวณ เพราะพลาดได้ทั้งสองทาง — ชนเพดานไปแล้วแต่ระบบไม่รู้
  หรือหยุดบอททั้งที่ราคาจริงเด้งกลับแล้ว
- **นี่คือ "พัก" ไม่ใช่ "หยุด"** ต้องแยกจากกันให้ชัด:

| | พัก — ไม่มีราคา | หยุด — key ถูกปฏิเสธ, ตั้ง TP/SL ไม่สำเร็จ |
|---|---|---|
| กลับมาทำงาน | **เอง** เมื่อมีราคาที่เชื่อถือได้และกระทบยอดเสร็จ | ต้องมีคนกดเปิด (หัวข้อ 8) |
| แจ้งผู้ใช้ | เฉพาะเมื่อพักนานเกินกำหนด | ทุกครั้ง |

- ถ้าไม่แยกสองอย่างนี้ ท่อราคาหลุดห้าวินาทีจะทำให้บอทหยุดค้างรอคนมากดเปิด
  ซึ่งใช้งานจริงไม่ได้ เพราะหัวข้อ 6 ระบุว่าท่อหลุดเป็นเรื่องปกติ ไม่ใช่กรณียกเว้น
- **เมื่อราคากลับมา ต้องคำนวณขาดทุนใหม่ทันที** ถ้าปรากฏว่าชนเพดานไปแล้ว
  ระหว่างที่ไม่มีราคา ให้เข้าสู่การหยุดจริงตามหัวข้อนี้
- เทรดมือไม่กระทบ ผู้ใช้เปิดไม้ใหม่ไม่ได้ตามกฎราคาในหัวข้อ 6 แต่ปิดไม้ได้เสมอ
- พักเพราะราคาไม่พร้อมต่อเนื่อง **5 นาที** ต้องแจ้งเหตุพักตาม NC-F18-06
  (Approved 2026-10-25); คำเตือนตลาดไม่พร้อม 60 วินาทีของ F-10 คงเดิม
  ขอบเขตข้อความในหน้า Paper และ dependency ช่องทางแจ้งเตือนอยู่ในคำตัดสิน F-18

**รายละเอียด F-18 — Approved 2026-10-25:** หน่วย/first-use, สูตร realized สุทธิและ
unrealized loss, การยกเว้นขาดทุนค้างหลัง reset, lifecycle ของเพดาน/latch,
