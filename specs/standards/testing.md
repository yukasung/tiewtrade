## 1. ต้องเขียวก่อน merge

ด่านก่อน merge ต้องผ่านครบ ไม่อนุญาตข้าม lint/type/architecture/CI หรือเทสต์ความถูกต้อง
ความปลอดภัย การคำนวณเงิน และ regression ที่เกี่ยวข้อง

**การแบ่งด่านที่เจ้าของอนุมัติ 2026-10-11:** อนุญาต merge เพื่อพัฒนาต่อได้เมื่อ
implementation/review และด่านที่ไม่เลื่อนผ่านครบ โดยเฉพาะ F-11 ให้เลื่อนเฉพาะ
การตรวจรับโหลด/ความเสถียรระยะยาวและผลรวมที่ต้องพึ่งรอบนั้นไปชุดที่ 9
ตาม [ทะเบียนตรวจรับ](../roadmap.md#ทะเบียนงานค้างสำหรับชุดที่-9)
ด่านอื่นที่ยังล้มต้องแก้ก่อน merge ห้าม skip/xfail หรือลดเกณฑ์ CI เพื่อให้ผ่าน
ผล Failed/Partial ของการตรวจรับที่เลื่อนต้องเก็บไว้ ไม่แปลงเป็น Passed
**การปรับ workflow ที่เจ้าของอนุมัติ 2026-10-12:** ย้ายการตรวจ performance/workload/
stress/endurance/resource ชุดเต็มไป release checkpoint ตามหัวข้อ 7 รวม F-12 V-17
โดยระบุรายการใน validation/roadmap เป็น `Pending Full Validation`
ไม่ใช่สิทธิ์เลื่อนเทสต์ความถูกต้องหรือความปลอดภัย และไม่เปลี่ยนผล Failed/Partial เดิม

การ merge นี้ไม่รับรองพร้อมใช้งานจริง ไม่อนุญาต production activation หรือ Completed
จนผ่าน validation ครบ และยังต้องให้เจ้าของสั่ง commit/push/merge ตามขั้นตอนเดิม
ข้อกำหนดนี้แทนข้อความเก่าที่ผูกการตรวจรับระยะยาวทั้งหมดกับ merge เท่านั้น

| ด่าน | ตรวจอะไร |
|---|---|
| รูปแบบและ lint | โค้ดสะอาดตามมาตรฐาน |
| ตรวจชนิดข้อมูล | เข้มที่สุดกับโค้ดที่คำนวณเงิน |
| ขอบเขตสถาปัตยกรรม | import-linter ตามกฎใน `architecture.md` |
| เทสต์ | ด่านบังคับก่อน merge ผ่านทั้งหมด; ชุดยาวที่เลื่อนติดตามใน checkpoint ท้ายชุด; ระบบรวมคงชุดที่ 9 ตามหัวข้อ 7 |

**Amendment — Approved 2026-10-26:** การเลือก full regression ก่อน merge ใช้เกณฑ์
ตามหัวข้อ 7 ไม่บังคับทุก feature โดยอัตโนมัติ; required CI checks และเทสต์ correctness/
trading safety ที่เกี่ยวข้องยังต้องผ่าน การอนุมัตินี้ไม่เปลี่ยน CI configuration

## 2. โค้ดที่คำนวณเงิน

ทุกฟังก์ชันที่คิดเงินต้องมี **ทั้งสองอย่าง**:
1. **เทสต์ด้วยตัวเลขจริง** ที่คำนวณมือแล้วเทียบ พร้อมเขียนที่มาของคำตอบไว้
2. **เทสต์คุณสมบัติ** (hypothesis) ที่พิสูจน์กฎที่ต้องจริงเสมอ เช่น ปิดไม้หมดแล้ว
   ยอดต้องกลับมาตรง, ปิดครึ่งเดียวกำไรต้องได้ครึ่งหนึ่ง

**เวลาเขียนเทสต์ ให้คิดสูตรขึ้นมาใหม่เอง ห้ามลอกจากโค้ดที่กำลังทดสอบ**
ไม่เช่นนั้นเทสต์จะแค่ยืนยันว่าโค้ดทำสิ่งที่มันทำ

## 3. ความบริสุทธิ์ของ core

ต้องมีเทสต์ที่ตรวจโดยอัตโนมัติว่า `core` ไม่มี:
- การอ่านนาฬิกา, ค่าสุ่ม, การอ่านไฟล์, การต่อเครือข่าย
- การใช้ `float` ที่ไหนก็ตาม

**ถ้าเทสต์พวกนี้แดง ให้แก้โค้ด ไม่ใช่แก้เทสต์**

## 4. ความปลอดภัยการเทรด

ต้องมีเทสต์ที่พิสูจน์ว่า:
- ออเดอร์ Paper ไม่เคยเรียกเครือข่ายออกไปข้างนอก
- คำสั่งซ้ำไม่ทำให้เกิดออเดอร์สองใบ
- **ทุกเส้นทางการสั่งออเดอร์ผ่านจุดตรวจ ไม่มีทางลัด** รวมคำสั่งลดความเสี่ยง
  ซึ่งผ่านจุดตรวจเดียวกันแต่ใช้เกณฑ์ต่างกัน ไม่ใช่ข้ามจุดตรวจ
- Live ไม่เปิดเองจากค่าตั้งต้น

## 5. การต่อกับ Binance

- เทสต์ปกติ **ห้ามยิงไป Binance จริง** ใช้ข้อมูลตอบกลับที่บันทึกไว้
- ตลาดเดียวของระบบคือ **Binance TH** (`/api/v1`) ไม่ทำ Binance.com
- ต้องมีเทสต์แยกที่ตรวจว่ารูปแบบข้อมูลของ Binance ยังเหมือนเดิม รันเป็นระยะ ไม่ใช่ทุกครั้งที่ push
- **ไม่ใช้ Testnet** (เจ้าของตัดสิน 2026-09-26) จึงไม่มีขั้นทดสอบกับตลาดจำลอง
  ก่อนเงินจริง — น้ำหนักจึงตกอยู่ที่เทสต์อัตโนมัติและ Paper Trading ทั้งหมด
  และการเริ่มใช้เงินจริงต้องเริ่มด้วยจำนวนน้อยและมีคนเฝ้า (`roadmap.md` F-25)

## 6. ทุก feature ต้องมี validation.md

บอกไว้ล่วงหน้าว่า "เสร็จ" หมายถึงอะไร และตรวจอย่างไร — เขียนก่อนลงมือทำ ไม่ใช่เขียนตามหลัง

## 7. เลือกการตรวจตามผลกระทบและลดงานซ้ำ

**การปรับ workflow ที่เจ้าของสั่ง 2026-10-20:** พัฒนาให้เร็ว ถูกต้อง และปลอดภัย
ด้วยการตรวจเท่าที่จำเป็นตามผลกระทบ ไม่มีเพดานเวลาทดสอบตายตัว
เวลาใช้หาคอขวด ไม่ใช้ตัดสินว่าผ่านหรือเป็นเหตุข้าม safety checks
ด่านก่อน merge และเกณฑ์ตรวจรับที่อนุมัติแล้วยังคงใช้ตามระยะรันด้านล่าง

### เลือกหลักฐานให้เพียงพอ

- ก่อนตรวจแต่ละชุด ระบุสั้น ๆ ใน checkpoint/บันทึกเดิมว่า diff กระทบพฤติกรรมหรือความเสี่ยงใด
  หลักฐานเดิมยังขาดหรือหมดอายุตรงไหน และชุดตรวจที่เลือกจะพิสูจน์อะไร
  ไม่ต้องสร้างเอกสารใหม่หรือบันทึกแยกทุก test case
- เลือกชุดตรวจที่เล็กที่สุดซึ่งครอบคลุมผลกระทบจริง รวม callers, dependencies และ contracts
  ใช้ Tests เดิมก่อนเพิ่มใหม่; เพิ่มเมื่อมีพฤติกรรม/กรณีผิดพลาดที่ยังไม่ครอบคลุม
  แต่ละระดับ unit/integration/end-to-end ต้องมีสิ่งที่พิสูจน์เพิ่ม ไม่ทำซ้ำโดยไม่มีเหตุผล
- เอกสารหรือการแก้ที่ไม่เปลี่ยน runtime behavior ให้ตรวจเนื้อหา ความสอดคล้อง และรูปแบบที่เกี่ยวข้อง
  ไม่รัน application tests โดยอัตโนมัติ; หากเป็น config, contract หรือเอกสารที่ใช้สร้างโค้ด
  ให้ประเมินผลกระทบต่อระบบด้วย
- ใช้ระดับตรวจที่พิสูจน์ความเสี่ยงได้จริง: unit สำหรับตรรกะที่แยกได้ และ integration
  บนระบบฐานข้อมูลจริงสำหรับ transaction/locking/concurrency ที่ mock พิสูจน์ไม่ได้
  ลด fixture ได้เมื่อยังรักษาเงื่อนไขที่กระตุ้นข้อผิดพลาดและ assertions ที่จำเป็น
- เมื่อผลที่จำเป็นต่อ checkpoint ผ่านและไม่มีความเสี่ยงค้างที่ต้องพิสูจน์ ให้ทำงานต่อ
  ไม่เพิ่ม Tests, refactor, diagnostics หรือรอบรีวิวเพื่อความมั่นใจโดยไม่มีช่องว่างที่ระบุได้
  งานตรวจรับที่เลื่อนได้ให้บันทึก Pending ตามกฎด้านล่าง; failure ด้าน correctness/safety ต้องแก้
  ก่อนถือว่าส่วนที่เกี่ยวข้องพร้อม งานที่ไม่ขึ้นต่อผลนั้นทำต่อได้ภายในขอบเขตที่อนุมัติ

### ระยะรันและความหมายของผล

**รวมตรวจท้ายแต่ละชุด — Approved 2026-10-27:** เจ้าของให้รวมการตรวจที่ใช้เวลานาน
เมื่อพัฒนาครบแต่ละชุดใน roadmap เช่น ชุดที่ 4 — Paper Trading หลัง F-13–F-17
พัฒนาและรีวิวครบพร้อมด่านที่ไม่เลื่อนผ่านแล้ว ไม่ต้องรอทุก feature เป็น Completed
จึงเริ่มตรวจรับรวม ใช้กับงานปัจจุบัน งานที่กลับมาทำต่อ และงานถัดไป แทนระยะรันเดิม
ที่สั่งชุดยาวท้ายแต่ละ feature หรือเลื่อนทุกชุดไปชุดที่ 9 รวมคำสั่งเดิมที่ให้รันชุดยาวราย feature
เปลี่ยนเฉพาะเวลา ไม่เปลี่ยนเกณฑ์ผลิตภัณฑ์หรือ safety gates

- แต่ละงานยังตรวจ targeted correctness/safety/regression และ static checks
  ตามผลกระทบ พร้อม review และ required CI ก่อน merge
- เมื่อพัฒนาครบชุดและ candidate รวมของชุดนิ่ง ให้รวม full regression,
  integration ข้าม feature, end-to-end และ performance/workload/stress/endurance/resource
  ที่เกี่ยวข้องเป็นรอบตรวจรับร่วม ผูกผลกับเกณฑ์ validation ของแต่ละ feature
  ใช้ผลเดิมที่ยัง valid และใช้การรันร่วมปิดหลายเกณฑ์ได้เมื่อพิสูจน์เงื่อนไขครบจริง
  ไม่แยกรันชุดยาวเดิมซ้ำราย feature ไม่ลด duration, thresholds, modes หรือ coverage
- เกณฑ์ที่ยังต้องพึ่ง feature จากชุดถัดไปหรือ profile ที่ยังไม่อนุมัติ ให้คง
  Pending Full Validation/Pending Dependency พร้อม dependency และ checkpoint ถัดไป
  ที่พร้อมใน validation/roadmap ไม่ถือว่าทั้ง feature/ชุดผ่านครบ
  ไม่เลื่อน correctness/trading safety ที่จำเป็นต่อพฤติกรรมที่เปิดใช้งาน
- ชุดที่ 9 คงตรวจรับระบบรวมและเกณฑ์ค้างก่อน release/production activation/
  ใช้เงินจริง/เปิดให้คนนอก ใช้หลักฐานท้ายชุดที่ยัง valid ตามกฎหลักฐานด้านล่าง
  ตรวจใหม่เมื่อผลกระทบหรือเกณฑ์บังคับ ไม่รันทุกชุดยาวซ้ำโดยอัตโนมัติ
- ระหว่างรอตรวจรวม ใช้ Development Complete — Pending Full Validation
  เมื่อ implementation/review และด่านที่ไม่เลื่อนผ่านครบ; ไม่เปลี่ยนสถานะอัตโนมัติ
  เก็บผล Failed/Partial เดิม และตรวจครบทุกเกณฑ์ก่อน Completed/release
- ข้อยกเว้นให้ตรวจเร็วขึ้นเมื่อ targeted tests ไม่พอพิสูจน์ความเสี่ยง และเกณฑ์
  full regression ก่อน merge ด้านล่างยังบังคับ; แจ้งเหตุผล/ขอบเขตก่อนรันชุดยาว
  required CI checks ยังต้องผ่าน การอนุมัตินี้ไม่เปลี่ยน CI configuration

ตามลำดับที่อนุมัติ; ไม่ต้องแก้ requirements/plan ทุก feature เพื่อย้ำกฎเดียวกัน.
ปรับเฉพาะ plan/validation ที่มีคำสั่งรันซึ่งขัดกับการเลื่อนที่เจ้าของอนุมัติ
และติดตามเกณฑ์ค้างใน roadmap โดยไม่ลด scope, duration หรือ threshold ของชุดเต็ม.
ระหว่างพัฒนาใช้ targeted correctness/safety/regression ตามผลกระทบและหลักฐานเดิม
ที่ยัง valid. หากต้องรัน timed smoke หรือ workload ก่อน checkpoint ให้แจ้งความเสี่ยง
ที่ต้องพิสูจน์ เหตุที่หลักฐานเดิมหรือ tests ที่เล็กกว่าไม่พอ และขอบเขต/เวลาคาดหมาย
ก่อนรัน พร้อมบันทึกใน checkpoint เดิม; ไม่รันเพียงเพื่อความมั่นใจหรือเพราะจบงาน.
ข้อยกเว้นนี้ไม่อนุญาตเลื่อน correctness/trading safety ที่จำเป็นหรือข้าม candidate
gates ก่อน merge; จุดอนุมัติเมื่อเปลี่ยน spec ยังบังคับตาม AGENTS.md.

| ระยะ | ตรวจอะไร |
|---|---|
| ระหว่างพัฒนา | targeted Tests, lint/types และ smoke ตาม diff กับ dependencies ที่ได้รับผลกระทบ |
| Candidate ก่อน merge | regression ตามผลกระทบและเกณฑ์ full regression ด้านล่าง พร้อม lint/types/imports/build/generated contracts ที่เกี่ยวข้อง และ required CI เมื่อชุดการแก้นิ่ง |
| ท้ายแต่ละชุด | full regression, integration/end-to-end ข้าม feature และชุดยาวที่เกี่ยวข้อง บน candidate รวมที่นิ่ง พร้อมเกณฑ์ validation ของแต่ละ feature |
| Release checkpoint/ชุดที่ 9 | ตรวจรับระบบรวมและเกณฑ์ค้างก่อนใช้งานจริง ใช้หลักฐานท้ายชุดที่ยัง valid ตามกฎหลักฐาน |

### เป้าหมายเวลาตรวจชุดยาว — Approved 2026-10-27

- ตั้งเป้ารอบตรวจรับปกติท้ายแต่ละชุดประมาณ **1–2 ชั่วโมงต่อรอบ**
  รวม regression, integration และ workload ที่เกี่ยวข้อง ใช้เป็นงบวางแผน
  ไม่ใช่เวลาขั้นต่ำหรือเพดานตัดการตรวจ และไม่ใช่ timeout ของคำสั่งทดสอบ
- หากคาดว่าเกิน **2 ชั่วโมง** ให้ตรวจงานซ้ำ ใช้หลักฐานเดิมที่ยัง valid
  และพิจารณารันส่วนที่เป็นอิสระพร้อมกันเมื่อพิสูจน์ isolation ได้
  แจ้งเจ้าของก่อนเริ่มถึงเหตุผล ขอบเขต และเวลาคาดหมาย พร้อมบันทึกใน checkpoint เดิม
  การแจ้งนี้ไม่ใช่จุดขออนุมัติใหม่ เว้นแต่ต้องเปลี่ยน spec หรือเข้าเงื่อนไขหยุดถามเดิม
- การตรวจความเสถียรระยะยาวให้แยกรอบ เช่น รันข้ามคืน เฉพาะเมื่อเกณฑ์ที่อนุมัติ
  กำหนดหรือมีความเสี่ยงที่ต้องพิสูจน์ แจ้งเหตุผลและเวลาคาดหมายก่อนเริ่ม
  ไม่ใช้การแบ่งรอบตัดช่วง endurance ที่เกณฑ์กำหนดให้รันต่อเนื่อง
- หากเวลาจริงเกินเป้าหมาย ให้แจ้งความคืบหน้าและเวลาคาดหมายใหม่
  ไม่หยุดหรือถือว่าผ่านเพียงเพราะครบเวลา ไม่ลด duration, thresholds หรือ coverage เอง
  เกณฑ์ที่ยังตรวจไม่ครบคง Pending Full Validation พร้อมรักษาผล Failed/Partial เดิม

### แจ้งประมาณเวลาทดสอบก่อนเริ่ม — เจ้าของสั่ง 2026-10-29

- ก่อนเริ่มทุกชุดตรวจ รวม targeted tests, lint/types/build, regression และ
  workload/diagnostic ให้แจ้งเจ้าของว่าตรวจอะไร เพื่อพิสูจน์อะไร และใช้เวลารวม
  ประมาณเท่าไหร่ รวมคำสั่งที่เกี่ยวข้องเป็นชุดเดียวได้ ไม่ต้องแจ้งแยกทุกคำสั่ง
- แยกเวลาประมาณเป็น เตรียมระบบ/ข้อมูล, รันทดสอบ และ cleanup/วิเคราะห์ผล
  โดยเฉพาะ workload ต้องแยกระยะวัดที่ specification บังคับออกจากเวลารวม
  ระบุเวลารอทรัพยากรถ้ามี ไม่เสนอเฉพาะเวลาวัดจนทำให้เข้าใจว่าเป็นเวลาจบงาน
- ใช้ประวัติรันบน configuration ที่เทียบกันได้หรือระยะที่ spec กำหนดเป็นฐาน
  ให้เป็นช่วงเวลาและระบุความไม่แน่นอน หากยังไม่มีข้อมูลให้แจ้งว่าเป็นประมาณการ
  เบื้องต้นหรือส่วนใดยังประเมินไม่ได้ ไม่รับประกันเวลาจบและไม่รวมเวลาแก้บั๊ก
  ที่ยังไม่ทราบโดยไม่บอกเจ้าของ
- หากคาดว่าจะเกินช่วงที่แจ้ง ให้แจ้งทันทีเมื่อทราบ พร้อมสาเหตุ งานที่เหลือ
  และประมาณเวลาที่เหลือใหม่ ไม่ปล่อยให้เจ้าของรอจนต้องถามเอง
- เมื่อจบ ให้สรุปผลและเวลาจริงเทียบกับประมาณการ บันทึกสั้นใน checkpoint เดิม
  ของงานเมื่อมีอยู่แล้ว ไม่สร้างรายงานซ้ำ และไม่รันซ้ำอัตโนมัติเพียงเพื่อให้ผ่าน
- การแจ้งเวลาไม่ใช่การขออนุมัติขั้นตอนเดิมซ้ำ และไม่ให้อำนาจลด coverage,
  duration, SLA หรือ safety gates; คงข้อจำกัดการรันทีละชุดและจุดหยุดที่เจ้าของกำหนด

### เมื่อแก้หลายรอบแล้วยังไม่ผ่าน — เจ้าของสั่ง 2026-10-28

- เมื่อแก้และตรวจผลต่อเกณฑ์เดิมแล้วยังไม่ผ่าน **3 รอบ** หรือเจ้าของแจ้งว่าใช้เวลามากเกินไป
  ต้องหยุดวงจรแก้/ทดลองซ้ำเพื่อเกณฑ์นั้น และเสนอทบทวนเกณฑ์ก่อนเริ่มรอบถัดไป
  นับรอบจาก checkpoint เดิมข้าม turn/การกลับมาทำงานต่อ ไม่เริ่มนับใหม่เมื่อเปลี่ยนชื่อการทดลอง
  ใช้กับงานค้างรวม F-18 และงานถัดไป; งานอื่นที่เป็นอิสระและอนุมัติแล้วทำต่อได้
- ข้อเสนอต้องระบุที่มาของเกณฑ์และความต้องการผู้ใช้ที่รองรับ นิยามการวัด
  ผลจริงพร้อม source/configuration และข้อจำกัดของหลักฐาน สาเหตุที่ทราบ/ยังไม่ทราบ
  รวมเวลาที่ใช้ไปและประมาณการของทางเลือก หากข้อมูลไม่พอให้บอกตรง ๆ ไม่สร้างตัวเลขขึ้นเอง
- ต้องเปรียบเทียบอย่างน้อย **คงเกณฑ์แล้วแก้ implementation** กับ
  **ปรับเกณฑ์หรือขอบเขตความจุให้ตรงความต้องการใช้งานจริง** พร้อมข้อแนะนำ
  ระบุค่า/ขอบเขตที่เสนอ เหตุผล ผลต่อผู้ใช้ ความเสี่ยง ต้นทุน และการตรวจที่ต้องทำใหม่
  พิจารณาทรัพยากรหรือสถาปัตยกรรมเมื่อเกี่ยวข้อง ไม่เสนอเพิ่มเวลาเพียงให้ครอบผลที่ล้มล่าสุด
  หากยังไม่มีหลักฐานพอรองรับค่าใหม่ ให้เสนอประเด็นที่เจ้าของต้องตัดสินใจแทนการเดาค่า
- กฎนี้บังคับให้ **เสนอทบทวน** ไม่ใช่บังคับลดเกณฑ์ และไม่อนุญาตให้เปลี่ยนเกณฑ์เอง
  รอเจ้าของเลือกทางและอนุมัติการเปลี่ยนที่เป็นรูปธรรมก่อนลงมือ; หากยังคงเกณฑ์เดิม
  ให้ตกลงขอบเขต/จุดหยุดของการทดลองถัดไป ไม่วนทดลองต่อโดยไม่มีจุดตัดสินใจ
- หากอนุมัติปรับเกณฑ์ ให้แก้ requirements/plan/validation ที่เกี่ยวข้องก่อนแก้โค้ดหรือ oracle
  ระบุเหตุผลและการอนุมัติ เก็บผล Failed/Partial เดิม และสร้างหลักฐานภายใต้เกณฑ์ใหม่แยกชัดเจน
  ห้ามเปลี่ยนผลเก่าย้อนหลังเป็น Passed หรือถือว่าการอนุมัติเกณฑ์ใหม่เท่ากับผ่าน validation
- ห้ามใช้กฎนี้ยอมรับเงิน/ปริมาณ/PnL ผิด ออเดอร์ซ้ำ การข้าม authorization,
  balance/position ไม่สอดคล้อง หรือข้อมูลสูญหาย และห้ามตัด samples, unacknowledged inputs,
  เวลารอ หรือกรณีที่ล้มออกเพื่อให้ผ่าน การทบทวน SLA/โหลด/ความจุต้องแสดงผลต่อ trading safety
  แยกจากการพิสูจน์ correctness และคงข้อบังคับ safety เดิมจนมีการตัดสินใจตามขั้นตอนของโครงการ

### การเลือก full regression — Approved 2026-10-26

- ไม่บังคับ full regression ก่อน merge ทุก feature โดยอัตโนมัติ งานที่ระบุขอบเขต
  ผลกระทบได้ใช้ targeted Tests ครอบคลุม diff, callers, dependencies และ contracts
  พร้อม static checks ที่เกี่ยวข้อง; บันทึกเหตุผลและหลักฐานใน checkpoint เดิม
- บังคับ full regression เมื่อเปลี่ยนส่วนกลาง กระทบหลายระบบ ระบุขอบเขตผลกระทบไม่ได้
  หรือ targeted Tests ไม่เพียงพอพิสูจน์ความเสี่ยง และที่ checkpoint ท้ายชุด/ตรวจรับระบบรวม
- งานที่กระทบเงิน ออเดอร์ balance/position หรือ risk ต้องผ่าน safety/integration/
  concurrency/idempotency tests ที่เกี่ยวข้องเสมอ ไม่เลื่อน correctness/trading safety
  ไป release เพียงเพราะไม่ได้รัน full regression
- รวมการแก้ให้ candidate นิ่งก่อนรันชุดเต็ม เมื่อพบ failure ให้แก้สาเหตุและตรวจ
  failing Tests กับ regression ที่ได้รับผลกระทบก่อนเริ่มชุดเต็มใหม่ ใช้ผลเดิมที่ยัง valid
  ตามเงื่อนไขหลักฐานด้านล่าง ไม่เริ่มใหม่เพียงเพราะกลับมาทำงานต่อ
- กฎนี้ใช้กับงานปัจจุบันและงานถัดไป แทนข้อบังคับทั่วไปให้รัน full regression ทุก feature
  ก่อน merge รวมข้อความทั่วไปในแม่แบบ/แผนเดิม; ไม่ยกเลิกกรณีตรวจรับเฉพาะ feature
  หรือเปลี่ยนผล Failed/Partial/Not Run เป็น Passed รายการชุดเต็มที่รอ release
  ต้องติดตามใน validation/roadmap เป็น Pending Full Validation
- required CI checks บน candidate สุดท้ายยังต้องผ่าน หาก CI ปัจจุบันรันชุดเต็ม
  กฎนี้ไม่ได้ทำให้ job นั้นถูกข้ามหรือใช้ผล local แทนได้ การปรับ CI ต้องเป็นงานแยก
  ที่ประเมินผลกระทบและผ่านขั้นตอนอนุมัติที่เกี่ยวข้อง

`Pending Full Validation` คือเกณฑ์ชุดเต็มที่ยังรอ checkpoint ไม่ใช่ผล Passed
ถ้าเคย Failed/Partial ให้เก็บผลนั้นและเพิ่มระยะรัน/งานค้างแยกต่างหาก
การกำหนด checkpoint ต้องชี้กลับไปยังเกณฑ์เดิมและทะเบียน roadmap; ไม่ลบ workload,
ระยะเวลา, thresholds, modes หรือกรณีขอบเขตสูงสุดเพื่อให้รอบสั้นผ่าน

เกณฑ์หนึ่งอาจมีหลายส่วน: ตรวจ correctness/safety/transaction/concurrency/idempotency
ที่ได้รับผลกระทบระหว่างพัฒนา แม้จะอยู่ใน V เดียวกับ benchmark
หาก smoke ไม่พอพิสูจน์ความเสี่ยงด้านเงิน/ออเดอร์/ความถูกต้อง ต้องรันชุดที่จำเป็นก่อน
ไม่รอ release; smoke ที่ผ่านไม่ถือว่าผ่านเกณฑ์ชุดเต็ม

### ก่อนและระหว่างพัฒนา

**การปรับ workflow ที่เจ้าของสั่ง 2026-10-13:** ใช้รายการปิดงานและหลักฐานเดิม
เพื่อทำต่อถึง checkpoint ภายในขอบเขตที่อนุมัติ พร้อมบันทึกเวลาสำหรับหาคอขวด
โดยคงจุดอนุมัติ ด่านบังคับ และเกณฑ์ตรวจรับเดิม

- เริ่มหรือกลับมาทำ milestone ด้วยรายการงานค้างจาก plan/validation และ checkpoint เดิม:
  ข้อที่ต้องแก้ หลักฐานที่ยังขาด และสิ่งที่ต้องรอเจ้าของ; ตรวจ diff ที่เกิดหลัง checkpoint
  เพื่อยืนยันว่ารายการและหลักฐานยังใช้ได้ ไม่สร้างแผนหรือรายงานใหม่เพื่อเริ่มทำงานต่อ
- ทำงานที่ได้รับอนุมัติต่อจนถึง checkpoint โดยไม่ขออนุมัติซ้ำระหว่างเขียนโค้ด เทสต์
  รีวิว และแก้ findings; หากพบเหตุให้หยุดตาม `AGENTS.md` ให้ระบุสิ่งที่บล็อกให้ชัด
- เพิ่มงานในรายการปิด milestone เฉพาะเมื่อจำเป็นต่อเกณฑ์เดิมหรือพบความเสี่ยงจาก diff
  พร้อมระบุเกณฑ์/ความเสี่ยงนั้น ข้อเสนอปรับปรุงที่อยู่นอกขอบเขตให้รายงานแยก
  โดยไม่ลงมือเพิ่ม scope; เมื่อหลักฐานครบให้ส่ง checkpoint ตามแผน
- ใช้ milestone/แนวทางจาก plan ที่อนุมัติแล้ว ผูกกับ Tests และเกณฑ์ใน `validation.md`
  ไม่เขียนแผนใหม่หากข้อกำหนดและแนวทางไม่เปลี่ยน ไม่ลดเกณฑ์เพื่อให้ตรวจเร็วขึ้น
- อ่าน spec และโค้ดที่เกี่ยวข้องให้ครบครั้งแรก จากนั้นอ่านซ้ำเมื่อมีการเปลี่ยนแปลง
  dependency ใหม่ หรือข้อขัดแย้ง; ขยายการค้นหาเมื่อยังระบุผลกระทบไม่ได้
- ก่อนการตรวจชุดยาว ตรวจ runtime versions, lockfiles, virtualenv, services,
  DB bootstrap และ tooling ที่ต้องใช้ ให้ตรงกับ environment ที่กำหนด
  ยืนยันว่า harness, assertions และ cleanup ของรอบนั้นพร้อมด้วย smoke ที่เกี่ยวข้อง
  ใช้หลักฐาน smoke เดิมได้เมื่อยัง valid ไม่เริ่มรอบยาวระหว่างที่ยังแก้ harness ส่วนที่รอบนั้นพึ่งพา
- เลือก Tests จากผลกระทบของ diff รวม callers, dependencies, contracts, database,
  concurrency และ trading safety ไม่เลือกจากชื่อไฟล์อย่างเดียว และไม่มีรายการข้ามตายตัว
- รวมการแก้ที่เกี่ยวข้องก่อนตรวจ ไม่รันทุกคำสั่งหลังทุก patch/ทุกงาน
  ใช้ focused Tests ระหว่างพัฒนา ไม่รัน full suite อัตโนมัติหลังทุก fix
- ในชุดตรวจที่เลือกตามผลกระทบ ให้เริ่มจากคำสั่งที่พบข้อผิดพลาดได้เร็ว
  ไม่รัน format/lint/type-check/build ทุกคำสั่งเป็นพิธีหลังทุกชุดการแก้
  แล้วตรวจ integration และด่านรับงานที่เกี่ยวข้อง โดยไม่ลดความเข้มของคำสั่งตรวจ
- หลังแก้ข้อผิดพลาด ตรวจ Tests ที่ล้มและ regression ที่ได้รับผลกระทบก่อนรันชุดยาวใหม่
- แยก environment/fixture/tooling failure จาก code failure ก่อน retry
  แก้สาเหตุหรือเพิ่ม diagnostic เฉพาะจุด ไม่รอ timeout เดิมซ้ำโดยไม่มีข้อมูลใหม่
- ไม่เริ่ม benchmark ชุดเต็มโดยปริยาย ใช้ smoke เมื่อช่วยวินิจฉัยความเสี่ยงของ diff;
  รันเต็มก่อน release checkpoint เฉพาะเมื่อมีความเสี่ยงจริงที่จำเป็นต้องพิสูจน์ พร้อมบันทึกเหตุผล
- ไม่เพิ่ม parallel workers ให้ Tests ที่ใช้ shared mutable state จนพิสูจน์ isolation ได้
- ห้ามลดหรือข้ามการตรวจที่บังคับเกี่ยวกับ order execution, duplicate orders,
  balances, positions, financial precision, risk management, concurrency,
  idempotency และ exchange integration
- ห้ามส่งออเดอร์ Live ใน automated validation; ใช้ fixtures/FakeVenue/Paper
  ส่วน venue contract จริงคงเป็น bounded public requests ตามหัวข้อ 5

### หลักฐานและการตรวจรับ

- บันทึกคำสั่ง, environment, revision และการเปลี่ยนแปลงที่ยังไม่ commit,
  ผลตรวจ, เวลาที่วัดได้ และเกณฑ์ validation ที่ผลนั้นครอบคลุม
  ใช้ ledger/หลักฐานเดิมเมื่อเพียงพอ ไม่สร้าง manifest หรือรายงานใหม่หลังทุก patch
- ใน checkpoint เดิม สรุปงานที่เสร็จพร้อมหลักฐาน งานค้าง และสิ่งที่บล็อก;
  เพิ่มเวลาที่วัดได้แยกอ่าน/วางแผน เขียนโค้ด ตรวจ tests/static/build รีวิว และรออนุมัติ
  ใช้เวลาเริ่ม/จบหรือระยะเวลาจากเครื่องมือที่มี ไม่เพิ่มระบบจับเวลาเป็นงานใหม่
  ระบุช่วงที่ไม่ได้วัดหรือเป็นค่าประมาณ และไม่บวกเวลางานที่รันพร้อมกันเป็นเวลารวม
  ใช้ข้อมูลนี้เลือกแก้ขั้นที่เสียเวลาหรือทำซ้ำจริง แทนการลดด่านตรวจโดยไม่มีหลักฐาน
- ก่อนรันคำสั่งเดิมซ้ำ ระบุเหตุผล เช่น inputs เปลี่ยน, ผลเดิมไม่ครบ,
  ตรวจ flaky behavior หรือเกณฑ์กำหนดให้รันหลายรอบ
- ใช้ผลเดิมประกอบการตรวจรับได้เมื่อยืนยันว่า source, Tests, contracts, migrations,
  dependencies, configuration, environment และ test harness ที่ผลนั้นพึ่งพาไม่เปลี่ยน
  และเกณฑ์ไม่ได้กำหนดให้ตรวจใหม่; หากยืนยันไม่ได้ ให้ตรวจซ้ำหรือขยายขอบเขต
- ก่อน merge ต้องตรวจด่านบังคับครบ พร้อมหลักฐานที่ใช้ได้กับ candidate สุดท้าย
  ก่อน Completed/release ต้องตรวจครบทุกเกณฑ์ใน `validation.md` รวมชุดเต็มที่เลื่อน
  focused Tests ไม่ทดแทนด่านที่ยังไม่ครบ
- Full regression ก่อน merge บังคับตามเกณฑ์การเลือกข้างต้น ไม่บังคับทุก feature;
  required CI checks ยังบังคับบน candidate สุดท้าย
  หลังแก้ให้ตรวจเฉพาะส่วนที่ผลเดิมได้รับผลกระทบ; ขยายถึง full เมื่อเข้าเกณฑ์ข้างต้น
  ไม่ตรวจซ้ำส่วนที่ยัง valid และไม่ใช้ผล local แทน required CI บน commit สุดท้าย
- อัปเดตผล validation ตามหลักฐานจริง ไม่เปลี่ยน Partial/Failed/Not Run เป็น Passed
  จนเงื่อนไขของด่านนั้นครบ; diagnostic run สั้นไม่ทดแทน load/soak/acceptance ที่กำหนด

### ปิด checkpoint หลังโค้ดเสร็จ — Approved 2026-10-26; ปรับจุดหยุดโดยเจ้าของ 2026-10-28

- เมื่อ implementation ครบทุกขอบเขตของทั้ง feature ใน plan เช่น F-18 ให้แจ้ง
  **Ready for Code Review** ทันทีตาม AGENTS.md พร้อมส่วนที่เปลี่ยน ผล Tests,
  validation ที่ยังค้าง และความเสี่ยงที่ reviewer ควรเน้น แล้วหยุดรอเจ้าของใช้คำสั่ง
  `review code` ก่อนเริ่มรีวิว ไม่รอปิด release validation ทุกข้อก่อนแจ้ง
- ไม่ใช้ข้อความ Ready for Code Review เมื่อจบงานย่อย, milestone, การแก้ finding
  เช่น R15 หรือการตรวจเฉพาะส่วน ให้รายงานความคืบหน้าตามปกติ
- ขั้น review → แก้ findings → ตรวจครั้งสุดท้ายด้านล่างเริ่มได้เมื่อเจ้าของสั่งรีวิวแล้ว
  และต้องอยู่ในขอบเขตคำสั่งนั้นกับแผนที่อนุมัติ
- ใช้รายการปิดงานเดียวใน checkpoint/หลักฐานเดิม ผูกกับ plan/validation:
  findings ที่ต้องแก้, checks ที่จำเป็นต่อ checkpoint, หลักฐานที่ยังขาด และ blockers
  ไม่สร้างแผน รายงาน หรือรายการตรวจใหม่เพียงเพราะเข้าสู่ขั้นรีวิวหรือกลับมาทำงานต่อ
- รีวิว diff และ dependencies ที่กระทบ ใช้หลักฐานเดิมที่ยัง valid; หลังแก้ findings
  ตรวจเฉพาะ findings ที่แก้, diff ใหม่ และ regression ที่ได้รับผลกระทบ
  ไม่เริ่มรอบรีวิวหรือ validation ทั้งหมดใหม่ เว้นแต่ผลกระทบใหม่หรือเกณฑ์บังคับทำให้จำเป็น
- เพิ่ม Tests, diagnostics, refactor หรือขยายรอบตรวจได้เฉพาะเมื่อระบุความเสี่ยงหรือช่องว่าง
  ของเกณฑ์เดิมที่ยังไม่มีหลักฐานรองรับ พร้อมบันทึกสั้นในรายการปิดงานเดิม
  ไม่เพิ่มเพื่อความมั่นใจอย่างเดียว; ข้อเสนอปรับปรุงนอกขอบเขตรายงานแยกโดยไม่บล็อกงาน
- เมื่อ review และ checks ที่จำเป็นต่อ checkpoint ผ่าน หลักฐานใช้ได้กับโค้ดล่าสุด
  และไม่มี correctness/safety findings หรือ blockers ของ checkpoint ค้าง ให้ส่ง checkpoint
  ทันทีพร้อมผลตรวจและงานค้าง ไม่เพิ่มรอบตรวจหรือไล่ปิดทุกเกณฑ์ release ก่อนส่ง
- ใน checkpoint หลังรีวิวและแก้ findings ครบ ให้ถามเจ้าของว่า
  **ให้ `refactor the code` ต่อหรือไม่** แล้วรอคำตอบก่อนเริ่ม refactor ขั้นถัดไป
  คำสั่ง `review code` ไม่ถือเป็นการอนุญาตขั้น refactor นี้; หากเจ้าของให้ทำต่อ
  ยังคงใช้ขอบเขต spec/plan ที่อนุมัติและเงื่อนไขหยุดถามเดิม
- หลัง refactor ที่เจ้าของอนุญาตเสร็จ ให้เริ่มทดสอบระบบตาม `validation.md` ของ feature
  ต่อทันที ไม่ต้องรอคำสั่งทดสอบหรือขออนุมัติซ้ำ ประเมินผลกระทบของ refactor
  เพื่อเลือกการตรวจซ้ำ ใช้หลักฐานเดิมที่ยัง valid และตรวจเกณฑ์ที่ถึงกำหนดให้ครบ
  บันทึกผล Passed/Failed/Partial พร้อมหลักฐานและงานค้างใน checkpoint เดิม
  การเลื่อนเกณฑ์ การตรวจชุดยาว และเงื่อนไขหยุดถามยังใช้กฎเดิม
- งานตรวจระดับ release ที่อนุญาตให้เลื่อนคง Pending Full Validation และติดตามใน
  validation/roadmap โดยรักษาผล Failed/Partial เดิม ไม่บล็อกงานพัฒนาถัดไปที่ไม่ขึ้นต่อ
  ผลนั้น; correctness/trading safety ที่จำเป็นยังเลื่อนไม่ได้
- การส่ง checkpoint ไม่ใช่การอนุมัติ merge หรือรับรอง Completed/release:
  ด่านก่อน merge, required CI, คำสั่ง Git และเกณฑ์ตรวจรับเดิมยังใช้ตามระยะที่กำหนด

### รีวิว

- รีวิวตามขั้น SDD; การยังไม่มี implementation ในขั้น requirements/plan ไม่ใช่ defect
- เริ่มจาก changed files กับ dependencies ที่เกี่ยวข้อง เน้น Critical/High และ trading safety
  ไม่รีวิวทั้ง repo โดยปริยาย; ขยายเมื่อ shared domain/security/architecture รับผลกระทบหรือขอบเขตไม่ชัด
- หลังแก้ findings ให้ตรวจ findings เดิม, diff ใหม่ และผลกระทบต่อ regression
  ขยายรีวิวเมื่อ scope, architecture, contracts หรือ safety logic เปลี่ยน
- ไม่เริ่มรอบรีวิวใหม่หรือรายงาน finding เดิมซ้ำเมื่อไม่มีการเปลี่ยนแปลง/หลักฐานใหม่
- รายงานความคืบหน้าตาม milestone พร้อมหลักฐานและสิ่งที่ยังขาด
  ไม่เพิ่มจุดอนุมัติซ้ำสำหรับงานที่เจ้าของอนุมัติแล้ว
