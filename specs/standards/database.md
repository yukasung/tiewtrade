# Standard — Database

สถานะ: **Proposed**

---

## 1. เงิน

- เก็บด้วย `NUMERIC` ที่ระบุความละเอียดชัดเจน **ห้ามใช้ `float`/`double` เด็ดขาด**
- ใช้ความละเอียดเดียวกันทั้งระบบ ประกาศเป็น domain เพื่อไม่ให้แต่ละตารางต่างกัน

## 2. เวลา

- เก็บเป็น `TIMESTAMPTZ` และเป็นเวลา UTC เสมอ
- แปลงเป็นเวลาไทยตอนแสดงผลเท่านั้น ไม่ใช่ตอนเก็บ

## 3. การแยกข้อมูลผู้ใช้

- ทุกตารางที่เก็บข้อมูลผู้ใช้ต้องมีคอลัมน์เจ้าของ และต้องห้ามเป็นค่าว่าง
  **ข้อยกเว้น: ตารางที่หนึ่งแถวคือตัวผู้ใช้เอง ใช้รหัสของแถวเป็นคอลัมน์เจ้าของได้**
  (เจ้าของตัดสิน 2026-09-27) ไม่ต้องเพิ่มคอลัมน์ที่เก็บรหัสเดียวกันซ้ำ
  ตารางอื่นยังต้องมีคอลัมน์เจ้าของแยกตามเดิม
- **เปิด Row-Level Security** เพื่อให้ฐานข้อมูลกันข้อมูลรั่วข้ามผู้ใช้เอง
  ไม่ใช่เชื่อว่าโค้ดจะใส่เงื่อนไขครบทุกที่
- `api` ทำงานภายใต้ RLS เสมอ
- **`engine` ใช้สองบทบาท** (เจ้าของตัดสิน 2026-09-27)
  - งานของผู้ใช้รายเดียว — คิดเงิน แก้สถานะการเทรด แตะ secret — **ทำงานใต้ RLS**
  - บทบาทที่ข้าม RLS ใช้ได้เฉพาะ **งานกวาดหารายการที่ต้องประมวลผลข้ามผู้ใช้**
    และบทบาทนั้น **อ่านคอลัมน์ secret ไม่ได้ และเขียนข้อมูลของผู้ใช้ไม่ได้**
  - ค่าปริยายคือบทบาทที่อยู่ใต้ RLS ไม่ใช่บทบาทที่ข้าม
    เหตุผล: ถ้าบทบาทข้าม RLS การสั่งให้ระบุผู้ใช้ก่อนแตะข้อมูล **ไม่ใช่การบังคับ
    ที่ระดับฐานข้อมูล** — query ที่ลืมใส่เงื่อนไขยังเห็นข้อมูลของทุกคน
- `market-data` ไม่แตะข้อมูลผู้ใช้ จึงไม่เกี่ยวกับ RLS

## 4. สิ่งที่แก้ย้อนหลังไม่ได้

- รายการเดินบัญชี, ออเดอร์ที่เกิดแล้ว, audit log — **เพิ่มได้อย่างเดียว**
- บังคับด้วยสิทธิ์ของฐานข้อมูลและ trigger ไม่ใช่แค่ตกลงกันในทีม
- ยอดคงเหลือคำนวณจากผลรวมรายการ ไม่ใช่ตัวเลขที่เขียนทับไปเรื่อย ๆ

## 5. สิทธิ์แยกตาม process

- `api` — อ่านได้ภายใต้ RLS, **อ่านคอลัมน์ secret ไม่ได้เลย** แต่ **เขียนค่าที่เข้ารหัสแล้วได้**
  ตอนผู้ใช้เพิ่ม key ครั้งแรก (เจ้าของตัดสิน 2026-09-26) — สิทธิ์คือเขียนได้ อ่านกลับไม่ได้
- `engine` — แก้สถานะการเทรดได้, อ่าน secret ได้
- `market-data` — เขียนได้เฉพาะตารางราคาและแท่งเทียน รวม metadata ควบคุม ingestion
  ของข้อมูลตลาดสาธารณะตาม [ADR-001](../decisions/001-market-data-demand.md)
  ที่เจ้าของอนุมัติพร้อมแผน F-09; ห้ามแตะข้อมูลผู้ใช้/secret/audit/ออเดอร์
- **`migrator`** — **เจ้าของตารางทั้งหมด ใช้เฉพาะตอนรัน migration ห้ามใช้ในเวลาทำงานปกติ**
  (เจ้าของตัดสิน 2026-09-27) เป็นบทบาทเดียวที่แก้โครงสร้างและปิด trigger ได้
  เหตุผล: เจ้าของตารางข้าม policy ของตารางตัวเองได้ ถ้าบทบาทที่รับคำขอจากเว็บเป็นเจ้าของตาราง
  กลไก RLS และตารางที่แก้ย้อนหลังไม่ได้ก็ถูกปิดได้จากโค้ดที่รันทุกวัน
- **ไม่มีบทบาทที่ใช้ตอนทำงานปกติเป็น superuser หรือเป็นเจ้าของตาราง**

## 6. Migration

- ทุกการเปลี่ยนโครงสร้างต้องเป็น migration ที่มีหมายเลข ไม่มีการแก้มือบนเครื่องจริง
- ต้องย้อนกลับได้ หรือเขียนไว้ชัดว่าทำไมย้อนไม่ได้
- **ห้ามทำ migration ที่ทำให้ระบบเก่าใช้ไม่ได้ทันที** ให้แยกเป็นขั้น: เพิ่มของใหม่ → ย้ายข้อมูล → ลบของเก่า

## 7. ตารางที่โตเร็ว

- ตารางแท่งเทียนและ audit log ต้องแบ่งพาร์ทิชันตามเวลาตั้งแต่ต้น
- ต้องกำหนดไว้ว่าเก็บนานแค่ไหน ไม่ใช่เก็บไปเรื่อย ๆ
