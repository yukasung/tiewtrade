ทุกตัวเลือกในเอกสารนี้เลือกจากข้อกำหนดใน `mission.md` ไม่ได้เลือกเพราะเคยใช้มาก่อน

| ไทย + อังกฤษ (R-20) | ต้องวางระบบแปลตั้งแต่แรก ทั้ง UI และข้อความแจ้งเตือน |

## 2. Backend

**เสนอ: Python 3.12+ กับ FastAPI**

เหตุผล:
- ชนิด `Decimal` เป็นของมาตรฐานในภาษา และเป็นสิ่งที่ต้องใช้ทุกจุดที่แตะเงิน
- ไลบรารีเชื่อม Binance ที่ใช้งานจริงและดูแลต่อเนื่องมีให้เลือกมากกว่า
- `asyncio` เหมาะกับงานที่เป็น I/O เป็นหลัก (WebSocket + REST ไปหา Binance พร้อมกันหลายบัญชี)
- ตรวจชนิดแบบเข้มด้วย mypy ได้ ซึ่งสำคัญมากกับโค้ดที่คำนวณเงิน

ข้อเสียที่ต้องยอมรับ:
- ต้องใช้สองภาษาในโปรเจกต์ (Python หลังบ้าน, TypeScript หน้าบ้าน) — ชนิดข้อมูลของ API
  ต้องสร้างอัตโนมัติจาก OpenAPI ไม่ให้เขียนซ้ำสองที่
- Python ช้ากว่า แต่คอขวดจริงของระบบนี้คือการรอ Binance ไม่ใช่ CPU

**ทางเลือกที่พิจารณาแล้วไม่เลือก: TypeScript/Node ทั้งระบบ**
ได้ภาษาเดียวทั้งโปรเจกต์ซึ่งดีมาก แต่ JavaScript ไม่มี decimal ในภาษา ต้องพึ่งไลบรารี
ทุกจุดที่คิดเงิน และถ้าพลาดใช้ตัวเลขปกติสักที่จะไม่มีอะไรเตือน — ความเสี่ยงนี้สูงเกินไป
สำหรับระบบที่แตะเงินจริง

## 3. Frontend

**เสนอ: React + TypeScript + Vite**

| ส่วน | เลือก | เหตุผล |
|---|---|---|
| กราฟ | **TradingView Lightweight Charts** | ฟรี ออกแบบมาเพื่อกราฟราคาโดยเฉพาะ รับข้อมูล realtime ได้ ขนาดเล็ก — ต้องแสดงเครดิตตามสัญญาอนุญาต |
| ดึงข้อมูลจาก API | **TanStack Query** | จัดการ cache และสถานะการดึงข้อมูล — **การรวม snapshot กับ stream ไม่ได้มาฟรี** ระบบต้องกำหนดเองว่าจะเรียงเหตุการณ์ กันข้อมูลซ้ำ และดึงใหม่หลังต่อกลับอย่างไร ไม่เช่นนั้น snapshot เก่าจะเขียนทับข้อมูลที่ใหม่กว่าจาก stream |
| สถานะในหน้าจอ | **Zustand** | เบา พอสำหรับสถานะที่ไม่ได้มาจาก server |
| แปลภาษา | **i18next** | รองรับไทย/อังกฤษ และการจัดรูปตัวเลข/วันที่ตามภาษา (R-20) |
| ชนิดข้อมูล API | **สร้างจาก OpenAPI อัตโนมัติ** | กันหน้าบ้านกับหลังบ้านเข้าใจไม่ตรงกัน |

**หมายเหตุเรื่อง indicator:** ค่า indicator ต้องคำนวณที่ backend แล้วส่งมา ไม่ใช่คำนวณ
ที่หน้าบ้าน เพราะกลยุทธ์ของบอทใช้ค่าเดียวกัน ถ้าคำนวณสองที่ กราฟจะไม่ตรงกับสิ่งที่บอทเห็น

## 4. ฐานข้อมูล

**เสนอ: PostgreSQL 16+**

- `NUMERIC` เก็บเงินได้แม่นยำจริง ไม่ใช่ทศนิยมลอยตัว
- **Row-Level Security** บังคับการแยกข้อมูลผู้ใช้ที่ระดับฐานข้อมูล ไม่ใช่แค่เชื่อใจว่า
  โค้ดจะใส่เงื่อนไขครบ — เป็นตาข่ายกันพลาดชั้นสุดท้าย
- **Partitioning** จำเป็นสำหรับตารางแท่งเทียนซึ่งจะโตเร็วมาก
- รันบน VPS ด้วย Docker ได้ และย้ายขึ้น managed service ของ cloud ได้ทีหลัง (R-16)

**ORM: SQLAlchemy 2 (async) + Alembic**
เลือกเพราะควบคุม SQL ได้เต็มที่เมื่อจำเป็น และสั่ง `SET LOCAL` เพื่อใช้ RLS ได้

## 5. คิวงานและข้อมูลเรียลไทม์

**เสนอ: Redis 7+**

- ส่งราคาจากตัวรับ market data ไปยังบอทและหน้าจอผู้ใช้
- คิวงานแจ้งเตือน 4 ช่องทาง (R-15) ไม่ให้ไปหน่วงคำขอของผู้ใช้

**กฎ: Redis เก็บข้อมูลชั่วคราวเท่านั้น** ทุกอย่างที่หายแล้วเดือดร้อนต้องอยู่ใน PostgreSQL
ถ้า Redis ล่มแล้วข้อมูลหาย ระบบต้องสร้างกลับมาจาก PostgreSQL ได้

## 6. โครงสร้างการทำงาน (Architecture)

**เสนอ: แยกเป็น 3 process ตั้งแต่ต้น**

| Process | หน้าที่ | ห้ามทำ |
|---|---|---|
| `api` | รับคำขอจากเว็บ, ยืนยันตัวตน, ส่ง WebSocket ให้หน้าจอ, **รับ secret ตอนผู้ใช้กรอกครั้งแรกเพื่อเข้ารหัสทันที** | ห้ามอ่าน secret ที่บันทึกแล้ว, ห้ามถอดรหัส, ห้ามบันทึกหรือ log ค่าดิบ |
| `engine` | รันบอท, คิด margin/PnL, ตัดสินใจส่งออเดอร์, ส่งออเดอร์ไป Binance | ห้ามรับคำขอจากอินเทอร์เน็ตโดยตรง |
| `market-data` | ต่อ WebSocket Binance รับราคา เก็บแท่งเทียน | ห้ามแตะออเดอร์หรือเงิน |

เหตุผลที่แยก:
- บอทต้องทำงานต่อแม้เว็บล่ม หรือแม้ไม่มีใครเปิดเบราว์เซอร์ (R-01)
- API secret ถอดรหัสเฉพาะใน `engine` ทำให้จุดที่หลุดได้แคบลงมาก (R-19)
- ราคาจาก Binance มีขีดจำกัดจำนวนการเชื่อมต่อ ต้องต่อครั้งเดียวแล้วแจกต่อ

เหตุผลที่ **ไม่** แยกมากกว่านี้: เริ่มบน VPS เครื่องเดียว (R-16) ยิ่งมี process มาก
ยิ่งดูแลยาก — ชั้นที่ส่งออเดอร์ออกไปจะทำเป็นโมดูลที่มีขอบเขตชัดใน `engine` เพื่อให้
แยกออกเป็น process ของตัวเองได้ทีหลังโดยไม่ต้องรื้อ

**กฎเหล็ก:** ตรรกะการคำนวณเงินและกลยุทธ์อยู่ในชั้นที่ไม่แตะเครือข่าย ฐานข้อมูล นาฬิกา
หรือค่าสุ่มเลย — เพื่อให้ทดสอบได้ว่าผลออกมาเหมือนเดิมทุกครั้ง (รายละเอียดใน
`standards/architecture.md`)

## 7. การยืนยันตัวตน

**เสนอ: session ฝั่งเซิร์ฟเวอร์ + cookie + TOTP**

- session เก็บใน PostgreSQL ยกเลิกได้ทันที — สำคัญเพราะระบบนี้สั่งเงินได้
- cookie แบบ httpOnly + Secure + SameSite และมีโทเคนกัน CSRF
- **TOTP บังคับก่อนเปิด Live** (R-19) และต้องยืนยันซ้ำเมื่อทำสิ่งที่เพิ่มความเสี่ยง
- รหัสผ่านแฮชด้วย argon2

**ไม่เลือก JWT** เพราะเพิกถอนทันทีไม่ได้ ซึ่งเป็นสิ่งที่ต้องทำได้ในระบบที่แตะเงิน

## 8. การเก็บ API key ของผู้ใช้

**เสนอ:**
- เข้ารหัสก่อนบันทึก ถอดรหัสได้เฉพาะใน `engine` ตอนจะใช้งานจริงเท่านั้น
- ฐานข้อมูลตั้งสิทธิ์ให้ `api` อ่านคอลัมน์ที่เก็บ secret ไม่ได้เลย

**ทางรับ secret ตอนผู้ใช้กรอกครั้งแรก** (เจ้าของตัดสิน 2026-09-26)

ผู้ใช้กรอก secret ผ่านหน้าเว็บ จึงต้องผ่าน `api` ไม่มีทางอื่น
`api` **รับได้ชั่วคราวเพื่อเข้ารหัสแล้วส่งต่อทันที** ภายใต้เงื่อนไขทุกข้อนี้:

- เข้ารหัสทันทีที่รับ **ห้ามบันทึกค่าดิบลงที่ใดเลย** ไม่ว่าฐานข้อมูล ไฟล์ คิว หรือ cache
- **ห้าม log ค่าดิบ** รวมถึงใน stack trace และข้อความ error
- **ห้ามเก็บไว้ในหน่วยความจำนานกว่าที่จำเป็น** และห้ามส่งกลับไปหน้าจอ
- หลังบันทึกแล้ว `api` **อ่านกลับไม่ได้อีก** บังคับที่ระดับสิทธิ์ฐานข้อมูล
- การถอดรหัสทำได้ที่ `engine` เท่านั้น

**ข้อแลกเปลี่ยนที่ยอมรับแล้ว:** secret ผ่าน process ที่เปิดรับอินเทอร์เน็ต
ซึ่งเป็นจุดที่ถูกโจมตีมากที่สุด ทางเลือกอื่นที่พิจารณาแล้วไม่เอา — เข้ารหัสที่เบราว์เซอร์
(ย้ายปัญหาไปที่การส่งกุญแจให้เบราว์เซอร์) และเปิดทางรับแยกที่ `engine`
(เพิ่มพื้นที่ที่ถูกโจมตีได้โดยไม่ได้ลดความเสี่ยงจริง)
- แสดงได้แค่ 4 หลักท้าย ไม่มี endpoint ไหนคืนค่าเต็ม (R-19)
- ตอนเพิ่ม key ระบบตรวจสิทธิ์ที่ Binance และ **ปฏิเสธ key ที่เปิดสิทธิ์ถอนเงิน** (R-19)

> กุญแจสำหรับเข้ารหัสจะเก็บที่ไหนบนเครื่อง VPS ยังเป็นข้อที่ต้องตัดสิน (ดูข้อ 10)
