# Mission

สถานะ: **Proposed** — รอเจ้าของอนุมัติ
วันที่: 2026-09-24

เอกสารนี้คือแหล่งอ้างอิงว่าผลิตภัณฑ์นี้ **คืออะไร** และ **ไม่ใช่อะไร**
ทุกบรรทัดมาจากคำตอบของเจ้าของในการสัมภาษณ์ 2026-09-24 และอ้างอิงด้วยรหัส `R-xx`
สิ่งที่เจ้าของยังไม่ได้ตอบ ถูกทำเครื่องหมาย **Needs Clarification** ไม่ใช่เดาแทน

---

## 1. จุดประสงค์ของผลิตภัณฑ์

ระบบเทรดคริปโตแบบ **Web application** (R-01) ที่ให้ผู้ใช้เชื่อมบัญชี Binance ของตัวเอง
แล้วเทรดได้สองทาง: **สั่งเองผ่านหน้าจอ** และ **ให้บอทเทรดตามกลยุทธ์สำเร็จรูป**

จุดขายคือการมี **Paper Trading ที่เหมือนของจริงมากที่สุดเท่าที่ทำได้** (R-17)
อยู่ข้าง ๆ Live Trading บนโดเมนเดียวกัน ผู้ใช้จึงทดสอบกลยุทธ์จนมั่นใจก่อน
แล้วค่อยเปิดใช้เงินจริงโดยไม่ต้องเปลี่ยนเครื่องมือ

> **Needs Clarification NC-01** — เจ้าของยังไม่ได้ระบุว่าผลิตภัณฑ์นี้ต่างจากคู่แข่ง
> ที่มีอยู่ในตลาดอย่างไร และทำไมผู้ใช้ถึงควรเลือกใช้ ข้อนี้มีผลต่อการตัดสินใจ
> ว่าจะลงแรงกับส่วนไหนก่อน

## 2. ผู้ใช้เป้าหมาย

**Multi-user SaaS** — เปิดให้คนทั่วไปสมัครเข้ามาใช้ได้ (R-05)

| กลุ่ม | ทำอะไรได้ | ที่มา |
|---|---|---|
| **Trader** | เชื่อมบัญชี Binance ของตัวเอง, เทรดมือ, เปิด/ปิดบอท, ดูผลงาน | R-05, R-07, R-08 |
| **Platform Admin** | ดูแลระบบ, เผยแพร่กลยุทธ์ให้ผู้ใช้เลือก, สั่งหยุดทั้งระบบได้, เพิ่ม/ถอนเหรียญในรายการที่รองรับ | R-06 (โดยนัย), เจ้าของตัดสิน 2026-09-26 |
| **Platform Owner** | ทุกอย่างที่ Admin ทำได้ **และเปิดระบบกลับหลังหยุดทั้งระบบ** | เจ้าของตัดสิน 2026-09-26 |

**ภาษา:** ไทยและอังกฤษ สลับได้ทั้ง UI และการแจ้งเตือน (R-20)

**ข้อห้ามของทั้งสองบทบาท** (เจ้าของตัดสิน 2026-09-26) — ไม่มีข้อยกเว้น:

1. **ดู API secret ของผู้ใช้ไม่ได้** (สอดคล้องกับหัวข้อ 8 ข้อ 2)
2. **สั่งออเดอร์แทนผู้ใช้ไม่ได้**
3. **ปิด position ของผู้ใช้ไม่ได้**
4. **แก้ audit log ไม่ได้** (สอดคล้องกับหัวข้อ 8 ข้อ 4)

การหยุดทั้งระบบเป็นการหยุดบอท ไม่ใช่การแตะ position หรือออเดอร์มือของผู้ใช้
ดูขอบเขตใน `standards/trading-safety.md` หัวข้อ 8

> **Needs Clarification NC-02** — อำนาจอื่นของ Platform Admin นอกจากที่ระบุข้างบน
> ยังไม่ได้กำหนด เช่น การดูข้อมูลการเทรดของผู้ใช้เพื่อช่วยแก้ปัญหา
> การระงับบัญชีที่มีปัญหา และการจัดการผู้ใช้

## 4. การแยก Paper กับ Live

คำตัดสินการใช้ strategy/ตรรกะการเทรดและ component ฟอร์มร่วมกัน พร้อมแยกหน้า/URL
และขอบเขตการรับรองผลที่ตรงกัน อยู่ใน [ADR-004](decisions/004-shared-paper-live-trading.md)
เจ้าของยืนยัน 2026-10-15; ไม่เปลี่ยนกฎแยกเงินและการเปิด Live ด้านล่าง

**กฎที่ห้ามละเมิด:**

1. **Live ต้องไม่เปิดโดยปริยาย** — ผู้ใช้ต้องตั้งใจเปิดเอง และต้องผ่าน 2FA (TOTP) ก่อน (R-19)
2. **Paper ไม่แตะเงินจริงและไม่ส่งออเดอร์ออกไป Binance** — เงินและออเดอร์จำลองทั้งหมด
3. **Paper และ Live ใช้ตรรกะโดเมนชุดเดียวกัน** (การคิด margin, position, PnL, TP/SL)
   ต่างกันแค่ชั้นที่ส่งออเดอร์ออกไป — ไม่เช่นนั้นผล Paper จะเชื่อถือไม่ได้
4. **การแสดงผลต้องบอกชัดตลอดเวลา** ว่าผู้ใช้กำลังอยู่โหมดไหน

**เงินใน Paper (R-18; NC-03 ปิดแล้ว 2026-10-15):** ผู้ใช้กำหนดยอดตั้งต้น
ที่มากกว่า 1,000 USDT ได้เองโดยไม่มีเพดานธุรกิจเพิ่มเติม แต่ค่าต้องอยู่ในขอบเขตของ
`Money` ผู้ใช้เติมเงิน
กลางรอบไม่ได้ หากต้องการเปลี่ยนยอดตั้งต้นต้องรีเซ็ตกระเป๋าเพื่อเริ่มรอบใหม่ และรีเซ็ตได้
เฉพาะเมื่อไม่มี position หรือออเดอร์ค้าง เงินตั้งต้นและยอดจากการรีเซ็ตไม่ใช่กำไร;
ผลการเทรดต้องคำนวณแยกต่อรอบ ประวัติรายการเดินบัญชีและ audit log ต้องเพิ่มอย่างเดียว
และห้ามลบหรือแก้ย้อนหลัง

## 5. โครงสร้างบัญชีและกระเป๋าเงิน

**บัญชี Binance TH หนึ่งบัญชีต่อผู้ใช้หนึ่งคน** (เจ้าของเปลี่ยน R-13 และยืนยัน 2026-10-07)
ระบบยังรองรับหลายผู้ใช้ แต่ไม่ใช้บัญชีตลาดร่วมกันทั้งระบบ
ยกเลิกการรองรับ sub-account และหลายกระเป๋า รวมเพดานหลัก1+ย่อย5ของขอบเขตเดิม

ผู้ใช้เลือก **เทรดมือหรือบอททีละแบบ** บนบัญชีเดียวกัน ไม่ใช้พร้อมกัน
คงสูงสุด1บอทต่อบัญชีในงานบอทภายหลัง; ไม่มีการรับรองว่าแยกเงินจริง/margin/การล้างพอร์ต
ระหว่างวิธีเทรดภายในบัญชีเดียว ต้องใช้ single writer และกฎความเสี่ยงเดิม

**หยุดบอทไม่เปลี่ยน BOT เป็น MANUAL** จึงไม่อนุญาตเปิดไม้ใหม่ด้วยมือในประเภท BOT
การปิด/ลด position และยกเลิกออเดอร์ยังทำได้ทุกประเภทผ่าน safety gates เดิม
(เจ้าของสั่งแก้ review issue4 วันที่2026-10-07; รายละเอียดอยู่ใน trading-safety หัวข้อ8)

การเปลี่ยนประเภทต้องมีหลักฐานว่าไม่มีบอททำงาน ออเดอร์ค้าง และ position ที่ระบบดูแล
หากไม่มีหลักฐานครบต้องปฏิเสธ ไม่เดาว่าบัญชีว่าง การแยก Paper/Live และข้อห้าม
เปิด Live โดยปริยายคงเดิม รวมการห้าม endpoint ถอน/โอน/จัดการบัญชีย่อย

รายละเอียด F-08 ใหม่ที่เจ้าของสั่ง implement ผ่าน review issue3: API key หนึ่งชุดต่อผู้ใช้, ไม่เพิ่มทะเบียนหลายกระเป๋า,
เก็บความเลือก MANUAL/BOT ที่ server และใช้ auth/TOTP/audit/UI เดิม
requirements/plan/validation ฉบับใหม่อยู่ใน
`specs/features/2026-10-07-single-trading-account/` (Approved 2026-10-07)

NC-04 และส่วน NC-05 เรื่องเพดาน6กระเป๋าถูก Superseded โดยคำตัดสินนี้
NC-22เรื่อง UID/dedupหลายบัญชีเลิกเป็นขอบเขตงาน ไม่ได้พิสูจน์สำเร็จ
ความไม่ชัดเรื่องอำนาจของ key ยังติดตามก่อน Live ร่วมกับ NC-16

### Subscription ของผู้ใช้

เจ้าของยืนยัน 2026-10-07: สมาชิกแบบชำระเงินของ TiewTrade แยกต่อบัญชีผู้ใช้
ผู้ใช้แต่ละคนสมัครและจ่ายแยกกัน บัญชีที่เป็นเจ้าของ subscription คือบัญชีผู้ใช้
TiewTrade ไม่ใช่ UID หรือ API key ของ Binance TH
ราคา แพ็กเกจ รอบบิล วิธีชำระเงิน และสิทธิ์เมื่อสมาชิกหมดอายุยังไม่กำหนด
ต้องมี spec และการอนุมัติของงาน subscription ก่อน implement billing/entitlements

## 6. ขอบเขตของ Exchange

**ข้อกำหนดนี้แทน R-02 เดิม** (เจ้าของตัดสิน 2026-09-26)
เดิมระบุว่าทำ Binance.com อย่างเดียวและเพิ่ม Binance TH ทีหลัง

**ทำ Binance TH ตลาดเดียว ไม่ทำ Binance.com**

- ผู้ใช้เป้าหมายอยู่ในไทยและเทรดบน Binance TH
- **เวอร์ชันแรกทำ Spot เท่านั้น** เพราะ Binance TH ยังไม่มี Futures
- **Futures เป็นงานอนาคต** รอ Binance TH เปิดให้ (**NC-12**)
- เคยพิจารณาใช้ Binance.com เป็นตลาดสำหรับทดสอบ Futures แล้ว **ตัดออก 2026-09-26**
  เพราะเพิ่มตลาดที่ผู้ใช้จริงไม่ได้ใช้ และต้องถอดออกทีหลังอยู่ดี
- **ไม่เขียนโค้ด Futures ไว้ล่วงหน้า** เมื่อไม่มีตลาดจริงให้เทียบ จะพิสูจน์ไม่ได้ว่าคิดถูก
  ซึ่งขัดกับข้อกำหนดว่าโค้ดที่คำนวณเงินต้องทดสอบได้ (หัวข้อ 8 ข้อ 5)
- **ต้องมีชั้นแยก venue แบบบาง** ถึงจะมีตลาดเดียว เพื่อให้เพิ่ม Futures
  หรือตลาดอื่นภายหลังได้โดยไม่ต้องรื้อ
- ไม่รองรับ exchange อื่น

**ผลตรวจความสามารถของ Binance TH** (ตรวจจาก API จริง 2026-09-26)

| สิ่งที่ตรวจ | ผล |
|---|---|
| REST API | มี — `https://api.binance.th/api/v1/...` (เป็น `v1` ไม่ใช่ `v3` แบบ .com) |
| WebSocket API | มี — `ws-api.binance.th` |
| คู่เทรด Spot | 519 คู่ สถานะ TRADING ทั้งหมด รวม 11 คู่ที่จับกับ THB |
| Futures | **ไม่มี** — `fapi.binance.th` ไม่มีในระบบ DNS และ `/fapi/` ตอบ 404 |
| ขีดจำกัดการเรียก | **แก้ 2026-10-01 จากเอกสารทางการ** — น้ำหนักการเรียกนับ **ต่อ IP**: 1,000 weight/10 วินาที และ 6,000 weight/นาที · จำนวนออเดอร์นับ **ต่อบัญชี** และตัวเลขอ่านจาก `/api/v1/exchangeInfo` ไม่ใช่ค่าที่เราเขียนไว้เอง · โดน 429 เมื่อเกินเพดาน และ 418 เมื่อถูกแบน IP พร้อม `Retry-After` เป็นวินาที<br>_ของเดิมที่บันทึกไว้ 2026-09-26 เขียนว่า "6,000 weight/นาที, 6,000 ออเดอร์/นาที, 1,000 ออเดอร์/10 วินาที" ซึ่งสลับหน่วยของหน้าต่าง 10 วินาที (เป็น weight ไม่ใช่ออเดอร์) และไม่ได้แยกว่าอะไรนับต่อ IP อะไรนับต่อบัญชี_ |
| การเชื่อมบัญชี | หนึ่งบัญชี Binance TH ต่อผู้ใช้; ไม่รองรับ sub-account/หลายกระเป๋า ตามคำตัดสิน 2026-10-07 |
| เว็บเอกสาร API | **มี — แก้ 2026-10-01** `https://www.binance.th/api-docs/en/`<br>_ของเดิมบันทึกไว้ 2026-09-26 ว่าไม่พบ เพราะหาจาก `docs.binance.th` และ `developers.binance.th` ซึ่งไม่ใช่ที่อยู่จริง — ข้อสรุป "ไม่มีเอกสาร" จึงผิด และงานที่วางแผนไว้บนข้อสรุปนั้นต้องทบทวน (พบตอนรีวิว requirements ของ F-35)_ |

ผลตรวจเดิมยืนยันว่ารายการตั้งต้นทั้ง 5 คู่มีบน Binance TH; ขอบเขต runtime ปัจจุบัน
ถูกลดเหลือ 2 คู่ตาม F-38 ด้านล่าง

**เมื่อทำ Futures ในอนาคต จะรองรับ USDⓈ-M เท่านั้น ไม่ทำ COIN-M** (เจ้าของตัดสิน 2026-09-26)

ผลที่ตามมา: หลักประกันและกำไรขาดทุนของ Futures คิดเป็น USDT ทั้งหมด
ไม่ต้องรองรับการคิดเงินเป็นตัวเหรียญ

**รองรับเฉพาะเหรียญในรายการที่คัดไว้** (เจ้าของตัดสิน 2026-09-26)
ไม่เปิดให้เทรดทุกเหรียญที่ Binance มี ใช้รายการเดียวกันทั้งเทรดมือและบอท
เพื่อคุมคุณภาพสภาพคล่องและให้ทดสอบได้ครบ

**รายการคู่เทรดที่รองรับระหว่างพัฒนา 2 คู่** (เจ้าของอนุมัติ F-38 วันที่ 2026-10-15)
`BTCUSDT`, `ETHUSDT`

รายการตั้งต้นเดิม 5 คู่ (`BTCUSDT`, `ETHUSDT`, `SOLUSDT`, `XRPUSDT`, `DOGEUSDT`)
และผลวิจัยด้านล่างเก็บไว้เป็นหลักฐานย้อนหลัง; SOL/XRP/DOGE ไม่ใช่ runtime catalog
ปัจจุบัน และจะพิจารณาเพิ่มกลับผ่าน F-37 ภายหลัง

## 8. เส้นที่ห้ามข้าม

กฎเหล่านี้มีผลเหนือความสะดวกและกำหนดเวลาเสมอ:

1. **Live ไม่เปิดเอง** — ต้องมีการกระทำที่ชัดเจนของผู้ใช้ + 2FA (R-19)
2. **ไม่มีทางอ่าน API secret กลับออกมาได้** — เก็บแบบเข้ารหัส และ **แสดงได้แค่
   4 หลักท้ายของ API key ไม่ใช่ของ secret** (R-19) (เจ้าของตัดสิน 2026-10-04 พร้อม F-07)
3. **บังคับให้ key เปิดสิทธิ์เท่าที่จำเป็น เท่าที่ตลาดบอกเราได้** (R-19)
   · วิธีบังคับคือ **ยอมรับเฉพาะสิทธิ์ที่อยู่ในรายการที่อนุญาต และปฏิเสธสิทธิ์ที่ไม่รู้จัก**
   — ซึ่งทำงานได้ก็ต่อเมื่อตลาดรายงานสิทธิ์ของ key **และ Binance TH ไม่รายงาน**
   ฉะนั้น **วันนี้ระบบยังตรวจสิทธิ์ของ key ไม่ได้เลย** (เจ้าของตัดสิน 2026-10-04 พร้อม F-07
   — รายละเอียดและมาตรการที่ใช้แทนอยู่ใน `standards/trading-safety.md` หัวข้อ 2)
   · **หน้าสร้าง key ของตลาดนี้ไม่มีช่องสิทธิ์ถอนเงินให้เปิด แต่นั่นไม่ใช่ข้อพิสูจน์ว่า
   key ถอนเงินไม่ได้** — ตลาดมี endpoint ถอนเงินที่เป็นคำขอลงลายเซ็น ดู **NC-16**
   ซึ่งยังเปิดอยู่และบล็อก F-24
4. **ทุกการกระทำที่แตะเงินต้องลง audit log** และแก้ไขย้อนหลังไม่ได้ (R-19)
5. **การคำนวณเงินต้องเป็น deterministic** — ไม่ใช้ AI ไม่ใช้ค่าสุ่ม ไม่ใช้ทศนิยมลอยตัว (R-12)
6. **ตรรกะกลยุทธ์ต้องแยกจากการส่งออเดอร์** — กลยุทธ์บอกว่า "อยากทำอะไร" ไม่ใช่ยิง Binance เอง
7. **ข้อมูลผู้ใช้แต่ละคนต้องแยกขาดจากกัน** — ทั้งในระดับฐานข้อมูลและ API (R-05)
