# ADR-004 — ใช้โค้ดการเทรดร่วมกันระหว่าง Paper และ Live

สถานะ: **Approved** — เจ้าของยืนยันแนวทางวันที่ 2026-10-15
วันที่: 2026-10-15

## เหตุผล

เจ้าของต้องการใช้โค้ดร่วมกันให้มากที่สุด รวมถึง strategy เดียวกัน เพื่อให้ Paper
ทดสอบตรรกะที่จะใช้กับ Live จริง ลดโอกาสที่การตัดสินใจหรือการคำนวณสองโหมดต่างกัน
และให้ฟอร์มเทรดใช้ component ร่วมกันโดยแยกหน้าและ URL

## คำตัดสิน

| ส่วน | แนวทางที่อนุมัติ |
|---|---|
| Strategy | ใช้ implementation เดียวกัน ไม่คัดลอก strategy แยก Paper/Live; รับข้อมูลตลาด พารามิเตอร์และสถานะผ่าน contract เดียวกัน ไม่ส่งออเดอร์เอง |
| Indicator และตรรกะโดเมน | ใช้ implementation ร่วมกันสำหรับการคำนวณเงิน/ปริมาณ, position, PnL, กฎความเสี่ยง, การตัดสินใจ TP/SL และวงจรชีวิตบอท ตามขอบเขตของ feature ที่อนุมัติ |
| คำสั่งที่ตั้งใจส่ง | ใช้ contract และกระบวนการตรวจคำสั่งร่วมกันก่อนเข้าสู่ตัวดำเนินการของแต่ละโหมด; ไม่เพิ่มสูตรหรือ safety rule แยกโดยไม่มีข้อกำหนดรองรับ |
| การดำเนินการ | Paper จำลองการจับคู่และบันทึกเงินจำลอง; Live ส่งผ่าน venue และรับผลจริง แยกทางเดินและ dependency ที่ติดต่อระบบภายนอก |
| ผลการดำเนินการ | แปลงผลจำลอง/ผลจริงเข้า contract กลาง เพื่อให้ตรรกะอัปเดตสถานะและคำนวณผลใช้ร่วมกันได้ โดยคง provenance และโหมด |
| ฟอร์มและหน้าเทรด | ใช้ component ฟอร์มร่วมกัน แต่ Paper/Live แยก page และ URL พร้อมแสดงโหมดให้เห็นชัดตลอดเวลา; รูปแบบยึด admin template |
| ข้อมูลและสิทธิ์ | balance, position, orders, ledger และ cache ต้องแยกตามโหมดและผู้ใช้; server กำหนดและตรวจโหมดจากเส้นทางรับคำสั่ง ไม่เชื่อค่า mode จาก browser |
| การเปิด Live | คงด่านเปิด Live, TOTP, credential และ safety gates ตาม spec เดิม; การเข้าหน้า Live หรือใช้ component ร่วมกันไม่เปิด Live เอง |

ชื่อ URL `/paper/trade` และ `/live/trade` ที่เสนอในบทสนทนาเป็นตัวอย่าง
ให้กำหนด route จริงและ API contract ใน spec ของ feature ที่รับผิดชอบก่อน implementation
ไม่ใช้ browser toggle เป็นตัวตัดสินเส้นทางส่งคำสั่งเงินจริง

โค้ดโดเมนยังอยู่ใน `core`, strategy พึ่ง `core` เท่านั้น และ service ประกอบ dependencies
ตาม `standards/architecture.md` ไม่เพิ่ม service-to-service import หรือ network access
ให้ core/strategy เพื่อใช้โค้ดร่วมกัน และไม่เพิ่มข้อยกเว้น import-linter
การเลือกตัวดำเนินการต้องเกิดที่ composition boundary ที่ server ควบคุม
Paper path ต้องเข้าถึง Live executor หรือ credential ไม่ได้

## ความหมายของผลที่ตรงกันและการตรวจรับ

เมื่อข้อมูลตลาด พารามิเตอร์ สถานะบัญชี/position และ input อื่นที่มีผลต่อการตัดสินใจ
รวมเวลาเหมือนกัน ทั้งสองโหมดต้องให้ signal, ผลตรวจความเสี่ยง และคำสั่งที่ตั้งใจส่ง
เหมือนกัน ทดสอบด้วย fixture เดียวกันผ่านตรรกะร่วม ไม่สร้าง implementation คู่ขนาน
เพื่อให้ได้ผลเท่ากันเฉพาะใน tests

ไม่ได้รับรองว่าผลจับคู่หรือกำไรจริงจะเท่ากัน เพราะ Live อาจมี latency, slippage,
ค่าธรรมเนียม, partial fill หรือการปฏิเสธจากตลาด ทำให้สถานะและการตัดสินใจถัดไปต่างกัน
กฎจำลองและค่าที่ใช้ต้องกำหนด/อนุมัติใน F-15 ไม่เดาค่าขึ้นในบันทึกนี้
เมื่อให้ผลการจับคู่และสถานะตั้งต้นเหมือนกัน ต้องตรวจว่าการอัปเดตสถานะ/คำนวณผล
ด้วยตรรกะร่วมให้ผลเหมือนกันด้วย

spec ของงานที่เกี่ยวข้องต้องมี parity tests ตามขอบเขตข้างต้น และ isolation tests
พิสูจน์ว่า Paper ไม่เรียก venue/credential/Live execution, เปลี่ยน URL แล้วไม่ข้ามสิทธิ์
และข้อมูล/cache ไม่ปะปนกัน ห้ามส่ง Live order ใน automated validation

## ขอบเขตการนำไปใช้

- F-14/F-17/F-18: ตรรกะสถานะ การคำนวณ TP/SL และความเสี่ยงร่วม
- F-15/F-22/F-23: execution/result contracts ร่วม แต่แยก simulator, venue execution และการกระทบยอดจริง
- F-16: component ฟอร์มร่วม แยกหน้า/URL/เส้นทางส่งคำสั่งและข้อมูลตามโหมด
- F-20/F-21: strategy และวงจรชีวิตบอทร่วม พร้อม parity tests
- F-13: ออกแบบ ledger และกระเป๋าจำลองตามขอบเขตเดิม ไม่เพิ่ม order form, strategy หรือ Live executor ในงานนี้
